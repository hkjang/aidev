## 운영자(hkjang)가 되풀이해 말한 것 — 이대로 한다 (반려·중지 사유·지시 19건에서 정제, 러너가 자동으로 붙임)
- **사람이 반려했거나 롤백된 접근은 같은 방식으로 다시 제출하지 말고, 재시도한다면 반려 사유를 직접 해소한 다른 접근으로 바꿀 것** — 반려·롤백이 9건으로 가장 잦고 반복되면 자율화 단계가 강등된다
- **테스트는 프로덕션 배선을 그대로 통과시키고 진짜 런타임 객체(예: 실제 asyncio.Task)로 검증할 것** — 손으로 만들어 주입한 의존성이나 FakeTask 대역은 배선 결함과 런타임 동작 차이를 구조적으로 못 본다
- **소스 문자열 검사를 증거로 제시하지 말고 실제 실행 결과로 증명할 것** — 문자열이 존재한다는 사실은 그 경로가 동작한다는 증거가 아니다
- **감사·로그 출력에는 식별자(AgentID 등)만 넘기고 원문 값은 넣지 말 것** — 스크럽 이전 문자열을 details 로 넘기면 audit_events.details 에 원문이 저장되고 AuditTrailEach 가 다시 내보낸다
- **같은 입력을 읽는 파서·판정기가 여러 경로에 나뉘어 있으면 한쪽만 넓히지 말고 두 경로가 같은 값을 같게 읽는지 end-to-end 로 확인할 것** — 분류기만 넓히면 렌더러가 같은 값을 다르게 읽어 결과가 깨진다
- **ptium 의 docs/deck/compile 숫자 파서를 통합하려 하지 말고 분류기 쪽을 좁히는 방향으로만 고칠 것** — 각 파서가 서로 다른 계약을 지키고 있어 구분자 처리를 넓히면 라인 차트 계열이 깨진다
- **정책 판단의 행위자는 플랫폼이 이미 쓰는 값(AgentHub 은 task.OwnerID)을 따르고 자격증명 조회용 agent.OwnerID 와 분리할 것** — 기존 정책 지점과 다른 주체를 쓰면 권한 판정이 어긋난다
- **종료·중단 판정은 파생 상태가 아니라 의도를 직접 나타내는 플래그(_shutting_down)로 할 것** — 상태값으로 판정하면 정상 종료 경로마다 오탐 ERROR 가 난다
- **문서의 API 메서드·경로는 소스에서 확인해 쓰고 같은 주제의 옛 가이드는 남겨두지 말 것** — 확인 없이 쓰면 GET/POST 가 어긋나고 정본이 둘이 된다
- **스크립트가 전역 설정이나 사용자 파일을 덮어쓸 때는 반드시 백업을 남길 것** — 백업 없는 덮어쓰기는 되돌릴 수 없다
