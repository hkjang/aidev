## 운영자(hkjang)가 되풀이해 말한 것 — 이대로 한다 (반려·중지 사유·지시 19건에서 정제, 러너가 자동으로 붙임)
- **사람이 반려했거나 릴리즈를 깨뜨려 되돌린 접근은 같은 방식으로 다시 올리지 말 것.** — 같은 접근의 반복이 회귀와 자율화 단계 강등(release → low-risk)으로 이어졌다.
- **검출/스캔 대상 문자열을 감사 기록의 details 로 넘기지 말고 식별자(AgentID 등)만 넘길 것.** — details 는 원문 그대로 저장되고 감사 출력으로 다시 내보내져 보호 대상 값이 샌다.
- **같은 종류의 파서가 여러 경로(docs 분류기·deck 렌더러·compile)에 있으면 통합하려 하지 말고 좁히는 방향으로만 고칠 것.** — 각 파서가 서로 다른 계약을 지키고 있어 한쪽만 넓히면 다른 쪽이 같은 값을 다르게 읽어 출력이 망가진다.
- **변경이 최종 출력까지 실제로 바뀌는지 end-to-end 로 확인할 것.** — 중간 단계(예: pptx/blocks.go 의 math.Abs)가 변경 효과를 삼켜 고쳐도 렌더링이 그대로인 경우가 있다.
- **프로덕션 배선을 통과하는 실행 테스트로 증명할 것 — 손으로 만들어 주입한 의존성이나 소스 문자열 검사를 근거로 삼지 말 것.** — 직접 주입한 테스트는 배선 결함을 못 보고, 소스 문자열 검사는 동작의 증거가 아니다.
- **런타임 의미를 가정하는 대역 대신 진짜 객체(예: asyncio.Task)로 검증할 것.** — cancel() 이 곧 cancelled()==True 라고 가정하는 대역은 해당 결함을 구조적으로 못 본다.
- **종료/셧다운 판정은 전용 플래그(_shutting_down)로 하고 task 상태나 exception() 같은 파생 상태로 추론하지 말 것.** — CancelledError 를 삼키고 정상 반환하는 루프에서 정상 종료마다 오탐 ERROR 가 난다.
- **가이드 문서의 API 메서드는 소스에서 확인하고, 대체된 옛 통합 가이드는 그대로 남겨 두지 말 것.** — 확인 없이 쓰면 GET/POST 가 어긋나고 옛 문서가 남아 정본이 둘로 갈린다.
- **스크립트가 전역 설정 파일을 수정할 때 백업 없이 덮어쓰지 말 것.** — 사용자의 기존 환경이 복구 불가능하게 망가진다.
- **정책 규칙의 행위자는 작업 소유자(task.OwnerID)로 잡고, 자격증명 조회(SCMTokenFor)에만 agent.OwnerID 를 쓸 것 (AgentHub).** — 이 플랫폼의 정책 지점은 모두 작업 소유자를 쓰므로 두 값을 섞으면 권한 판정이 틀어진다.
