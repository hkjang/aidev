- 요약: 검증기의 두 LIMIT 규칙(상한 검사·기본 LIMIT 주입)은 `LIMIT n` 한 가지 철자만 알았다. MySQL·SQLite 의 `LIMIT 5, 100000` 은 정규식이 첫 숫자(offset)를 잡아 5행으로 측정돼 상한 1000 을 통과했고, PostgreSQL 이 받는 표준 `FETCH FIRST n ROWS ONLY`(`OFFSET m ROWS FETCH NEXT n ROWS ONLY`·`FETCH FIRST ROW ONLY`·`WITH TIES` 포함)는 전혀 매치되지 않아 상한 검사에서 빠질 뿐 아니라 그 뒤에 기본 LIMIT 이 덧붙어 — 한 문장에 둘을 같이 쓸 수 없으므로 — 유효한 쿼리가 문법 오류로 실행 실패했다(`LIMIT ALL` 도 같은 이유로 두 번째 LIMIT 이 붙었음). `limitRe` 를 `(?:(\d+)\s*,\s*)?(\d+|all)` 로 넓혀 count 쪽 숫자를 읽고, `fetchRe` 를 추가해 FETCH 절을 LIMIT 과 같은 중첩 규칙(최상위면 기본 LIMIT 억제, 모든 깊이에서 상한 검사)으로 다루며, `ALL` 은 파싱 불가(overflow)로 취급해 상한 아래임을 보일 수 없으니 거부한다. 거부 사유는 이제 절을 쓴 그대로(`LIMIT 5, 100000 exceeds max 1000`, `FETCH FIRST 100000 ROWS ONLY exceeds max 1000`) 인용하고, `admin_text2sql.go` 의 조언 분류는 `exceeds max` 부분 문자열을 보므로 그대로 동작한다. 실행 단계의 `rowLimit` 행 cap 은 별개로 남아 있어 반환 행수는 애초에 잡혀 있었지만, DB 쪽 materialize·정렬 범위와 "유효한 PG 쿼리가 깨짐" 은 이 수정으로만 해결된다. 새 테스트 파일 `validator_limit_dialect_test.go` 에 5개(offset,count 3 철자·큰 offset 은 통과, FETCH 5 형태 통과 + 3 형태 거부, 서브쿼리 FETCH 는 기본 LIMIT 추가, LIMIT ALL 거부/미추가, 기존 `LIMIT n OFFSET m` 회귀 가드)를 넣어 수정 전 코드에서 3개가 실패함을 확인했고, gofmt·go vet·go build·`go test ./... -count=1`(12 패키지)·`go test -race ./internal/text2sql`·`cmd/api-surface-audit`(FAIL 0) 모두 통과.
