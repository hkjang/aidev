moyro v0.2.47

The custom profile value PATCH handlers refuse a body they could not read
instead of reporting a save that never happened. This is a server behavior fix.
There is no schema change, no migration, no new route and no web change. One
error id is added and two decode calls change.

`patchCustomProfileValuesGlobal` and `patchUserCustomProfileValues` in
`compat_wave_handlers_final.go` read their map-shaped body with
`_ = decodeCappedBody(w, r, &values)`, discarding the decode error. A body over
`collectionBodyMaxBytes` — one mebibyte — or one truncated mid-object left
`values` nil, and `customprofile.Service.PatchUserValues` returns on
`len(values) == 0` before it opens a transaction, so not a single row was
written. Both handlers then re-read the stored map with `GetUserValues` and
answered 200 carrying it.

That last step is what made this the worst-shaped member of its class. The
response to a refused write was byte-identical to the response to a successful
one: a 200 with a fully populated profile map. The caller has nothing to
inspect — no empty collection, no zero count, no error field. v0.2.45 fixed the
same `_ = decodeCappedBody` pattern on bulk user delete, where the giveaway was
at least an honest `{"status":"OK","count":0}`; here there was no giveaway at
all.

The false success also reached the ledger. Each handler writes an
`audit.ActionCustomValuesPatch` row, and `patchUserCustomProfileValues` is the
support path an administrator uses to backfill another user's profile, so an
operation that never happened was recorded in the audit trail under the
operator's name.

Both call sites now use `decodeOptionalCollectionBody`, the helper v0.2.45 added
for exactly this shape of endpoint, under the single new error id
`api.custom_profile.values.patch.invalid_body` that both handlers share. An
oversized body is refused with 413 and a malformed one with 400, and the
refusal is written before `h.audit.LogAsync` runs, so a refused request leaves
no audit row. Because the `Optional` variant lets `io.EOF` through, a bodyless
PATCH still answers 200 with the current map, a literal `null` or `{}` body is
still a 200 no-op, and the contract that clears a field by sending a `null`
value is unchanged. `request_body.go` is byte-identical to v0.2.46, so
`decodeCappedBody`, `decodeCollectionBody`, `drainCappedBody` and
`tooManyBatchItems` keep their behavior and the other callers that deliberately
tolerate a malformed body continue to do so. The scope was not widened to the
remaining `_ = decodeCappedBody` call sites.

Operators integrating against these two routes should note the narrow contract
change. A caller that sent an oversized or truncated body and read the false 200
as a save now receives 413 or 400 and should retry with a body under the cap. A
caller sending a well-formed body, an empty body, or no body at all sees a
byte-identical response. The webapp's two callers in `compat.ts` always send a
small well-formed map and are unaffected, and neither OpenAPI document
describes the refused-body case, so integrations outside the repository are the
only ones affected.

The defect was observed before it was fixed rather than argued from the code. A
new `custom_profile_values_body_cap_postgres_test.go` runs sixteen subtests
against a real PostgreSQL instance on an isolated schema with `store.Migrate`,
driving a chi router and the real `customprofile` and `audit` services — the
audit service real rather than nil, because the existing sibling tests leave
`h.audit` nil and a nil service never calls `LogAsync`, which would let an
"audit row absent" assertion pass for the wrong reason. Seven subtests failed
before the change, including the one that states the defect exactly:
`status = 200, want 413 (body {"field-dept":"Support"})` — the refused body's
response carrying the previous save's bytes. Sixteen of sixteen pass after it
under `-race`. Causation was checked in three directions: reverting either
decode line fails only that handler's subtests plus the shared audit subtest,
reverting both leaves every preservation assertion passing, and substituting
`decodeCollectionBody` for the `Optional` variant fails only the two bodyless
PATCH cases.
