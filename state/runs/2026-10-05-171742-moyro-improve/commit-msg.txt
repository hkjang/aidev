release: carry release markers to v0.2.47

v0.2.47 ships one server fix already merged to main. The two custom profile
value PATCH handlers now refuse a body they could not read instead of answering
200 with a response a client cannot tell apart from a real save. There is no
schema change, no migration, no new route and no web change. One error id is
added and two decode calls change.

`patchCustomProfileValuesGlobal` and `patchUserCustomProfileValues` in
`compat_wave_handlers_final.go` read their map-shaped body with
`_ = decodeCappedBody(w, r, &values)`, discarding the decode error. A body over
`collectionBodyMaxBytes` — or one truncated mid-object — left `values` nil, and
`customprofile.Service.PatchUserValues` returns on `len(values) == 0` before it
opens a transaction, so not a single row was written. Both handlers then re-read
the stored map with `GetUserValues` and answered 200 carrying it, so a refused
write produced a 200 and a populated profile map that is byte-identical to the
response of a successful save. That is a worse shape than the empty
`{"status":"OK","count":0}` envelope v0.2.45 fixed on bulk user delete, because
nothing in the response hints that the write was dropped.

The false success also reached the ledger. Each handler writes an
`audit.ActionCustomValuesPatch` row, and `patchUserCustomProfileValues` is the
support path an administrator uses to backfill another user's profile, so an
operation that never happened was recorded under the operator's name.

Both call sites now use `decodeOptionalCollectionBody`, the helper v0.2.45 added
for exactly this shape of endpoint, under the single new error id
`api.custom_profile.values.patch.invalid_body` that both handlers share. An
oversized body is refused with 413 and a malformed one with 400, and the refusal
is written before `h.audit.LogAsync` runs. Because the `Optional` variant lets
`io.EOF` through, a bodyless PATCH still answers 200 with the current map, a
literal `null` or `{}` body is still a 200 no-op, and the contract that clears a
field by sending a `null` value is unchanged. `request_body.go` is untouched, so
`decodeCappedBody`, `decodeCollectionBody`, `drainCappedBody` and
`tooManyBatchItems` keep their behavior and the other callers that deliberately
tolerate a malformed body continue to do so.

Operators integrating against these two routes should note the narrow contract
change. A caller that sent an oversized or truncated body and read the false 200
as a save now receives 413 or 400 and should retry with a body under the cap. A
caller sending a well-formed body, an empty body, or no body at all sees a
byte-identical response. The webapp's two callers always send a small
well-formed map and are unaffected, and neither OpenAPI document describes the
refused-body case, so integrations outside the repository are the only ones
affected.
