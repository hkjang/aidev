# 시스템 운영 현황 카드

`/app/system-status`에서 문서를 선택해 기대하는 시스템 버전·배포 식별자·운영 환경·담당자를 등록하고 실제로 수신한 관측과 비교합니다. 카드와 보고는 Markdown 원문, 문서 저장본 번호, 게시 승인 상태, 실제 시스템을 자동 변경하지 않습니다.

**운영 카드의 관측은 보고 주체의 주장입니다. madi가 대상 서버에 접속해 배포나 정상 동작을 독립 검증한 결과가 아닙니다.** 등록된 기대값, 사용자의 수동 보고, API/서비스 계정 보고, Runbook 실행 결과, 커넥터 수집 사실을 구분해서 읽으세요.

## 관리자 설정

`/admin/system-status`에서 보고 수신을 활성화합니다. 기본은 꺼짐이며 네 필수 환경변수 외 추가 환경변수는 필요 없습니다.

| 정책 | 범위·기본 |
| --- | --- |
| 최대 관측 TTL | 60~604800초, 기본 86400초 |
| 허용할 최대 과거 관측 | 60~604800초, 기본 86400초 |
| 관측 보고 보존 | 8~3650일, 기본 90일 |

정책 저장은 현재 revision과 명시 확인을 요구하고 변경 이력을 남깁니다. 동시 변경은 409로 거절합니다. 보존 기간이 지난 보고는 읽기에서 제외하며 유지관리 배치가 한 번에 최대 5000개를 삭제합니다. 보존 축소로 삭제된 보고는 백업이 없다면 복구할 수 없습니다.

정책을 켜도 보고 권한이 자동 생기지는 않습니다. 서비스 관리자가 다른 사용자의 private 문서를 열람하거나 운영 보고를 대신 만들 수 없습니다. 카드 설정과 원문 접근은 기존 워크스페이스·공간·상위 문서·문서 ACL의 교집합을 계속 적용합니다.

## 기대값과 보고 주체

1. 현재 문서를 선택하고 **운영 카드 등록**을 엽니다. 기대 시스템 버전 또는 배포 식별자 중 하나 이상을 입력합니다.
2. 현재 작성 권한이 있는 일반 사용자를 담당자로 지정합니다. 보고 주체는 해당 문서의 현재 작성 권한을 가진 일반 사용자 또는 서비스 계정 중 명시적으로 선택합니다. 빈 목록이면 누구도 보고하지 못합니다.
3. 문서별 TTL을 관리자 최대값 이하로 설정합니다. 설명에는 문서의 모든 열람자에게 공유해도 되는 정보만 넣습니다.
4. 원문 저장본 번호와 카드 revision을 확인하고 저장합니다. 기대값만 등록하면 **아직 관측 보고 없음**입니다.

기준 변경은 카드 revision과 검증 epoch를 바꾸고 이전 보고를 새 기준의 관측으로 사용하지 않습니다. 원문이 수정되면 **원문 변경 · 기준 재검토**가 됩니다. 담당자가 현재 원문을 확인하고 기준을 다시 저장한 뒤 새 관측을 보고해야 합니다. 문서 CAS 번호를 과거 번호로 낮추거나 원문을 자동 덮어쓰지 않습니다.

## 실제 관측과 신선도

**실제 관측 보고**에서 직접 관측한 버전·배포 식별자·상태·관측 시각을 입력합니다. 정상/저하/중단 값은 각각 “정상이라고 보고됨”처럼 보고 주체의 주장으로 표시됩니다. 상태 기본값은 확인 안 됨입니다.

서버는 별도의 수신 시각을 기록합니다. 관측 시각은 서버보다 60초 넘게 미래일 수 없고, 현재 정책의 최대 과거 범위 안이어야 합니다. 더 오래된 관측으로 최신 보고를 교체하지 않습니다. 만료는 다음 중 이른 시각입니다.

```text
min(관측 시각 + 유효 TTL, 서버 수신 시각 + 유효 TTL)
```

따라서 미래 오차나 오래된 보고의 재전송으로 신선도가 늘어나지 않습니다. TTL은 카드와 현재 관리자 최대값 중 작은 값입니다. 카드·문서 기준이 일치하고 TTL이 지나지 않은 보고만 기대값과 비교해 불일치 항목을 표시합니다. 기대 버전 일치가 서비스 정상 동작 인증을 의미하지는 않습니다.

| 화면 상태 | 의미 |
| --- | --- |
| 카드 미등록 / 아직 관측 보고 없음 | 등록·관측의 부재, 성공으로 추정하지 않음 |
| 보고 정책 비활성 | 과거 이력만 제공, 현재 관측으로 확인하지 않음 |
| 원문 변경 / 기준 변경 | 새 기준 검토와 관측 필요 |
| 유효 시간 지난 관측 | 과거 관측이며 현재 상태는 알 수 없음 |
| 신선한 보고 · 기대값 일치 | 해당 주체의 현재 유효한 보고 문자열이 기대값과 일치 |
| 신선한 보고 · 기대값 불일치 | 해당 주체의 현재 유효한 보고와 기대 버전/배포가 다름 |

조회 화면은 보이는 동안 3초 간격으로 현재 권한·문서·카드·정책을 다시 읽습니다. 권한 조회 실패 시 기존 카드 내용을 화면에서 제거합니다. 이 주기는 네트워크/DB 대기와 브라우저 중단까지 포함한 회수 SLA 보증은 아니며 이미 읽거나 내려받은 정보는 회수할 수 없습니다.

## API와 MCP

API/서비스 계정 보고에는 같은 워크스페이스의 `document:read`와 `document:write`, 실제 문서 작성 권한, 카드의 `reporter_ids` 포함 조건이 모두 필요합니다. 서비스 계정 키는 관리자가 발급하며 서비스 계정은 로그인할 수 없습니다. 카드 기대값·담당·보고 주체 변경과 삭제는 일반 사용자 로그인에서만 허용합니다. 플러그인 제한 principal에는 보고 권한을 추가로 부여하지 않습니다.

| API | 용도 |
| --- | --- |
| GET `/api/v1/documents/{id}/system-status` | 현재 카드·정책·보고·신선도·실행/수집 맥락 |
| PUT `/api/v1/documents/{id}/system-status` | 원문/카드 CAS를 동반한 기대값 저장 |
| POST `/api/v1/documents/{id}/system-status/reports` | 실제 관측 보고 |
| DELETE `/api/v1/documents/{id}/system-status` | 카드·보고 이력 삭제, 원문 유지 |
| GET/PUT `/api/v1/admin/system-status/policy` | 관리자 정책·변경 이력 |

먼저 GET으로 최신 `current_document_version`과 카드의 `revision`, `report_revision`, `verification_epoch`를 확인합니다. POST 예시는 다음과 같습니다. 실제 값은 현재 GET 응답과 직접 관측한 자료를 사용하세요.

```json
{
  "request_id": "a466fa37-38d1-4696-a4a6-38a4a7308ff1",
  "card_revision": 1,
  "report_revision": 0,
  "verification_epoch": 123456789,
  "document_version": 1,
  "observed_at": "2026-09-08T09:00:00Z",
  "observation": {
    "version": "v1.0.0",
    "deployment": "release-blue",
    "health": "unknown",
    "note": "보고 주체가 확인한 근거만 기록"
  },
  "confirm": true
}
```

새 보고는 201이며 같은 계정·키·동일 UUID·동일 본문을 재전송하면 기존 확정 영수증을 200으로 반환합니다. 원문·기준 epoch·계정·키·정책 권한을 먼저 다시 확인하므로 과거 영수증은 권한 증표가 아닙니다. 새 보고끼리 경쟁하면 현재 `report_revision`의 한 요청만 성공하고 다른 요청은 409입니다. 다시 읽고 관측 순서를 확인하세요. 같은 UUID에 내용을 바꾸어 보내면 409입니다.

MCP의 `get_system_status`와 `report_system_status`는 동일한 REST 핸들러와 모든 현재 권한·CAS 검사를 거칩니다. 보고 도구에는 위 필드와 `document_id`를 제공하며 `confirm:true`가 필수입니다. 대상 시스템 접속·셸 실행·Runbook 실행·외부 URL 가져오기 도구로 확대하지 않습니다.

## 실행·수집 근거와 보안

Runbook 맥락은 같은 문서의 현재 열람 가능한 실행 ID·단계·상태·시각만 제공합니다. `succeeded`는 실행 어댑터의 결과이며 기대 버전의 배포 확인 보고를 자동 생성하지 않습니다. 로그·Runner 인증정보·실행 입력 스냅샷을 카드에 복제하지 않습니다.

커넥터 맥락은 기존 연결 관리 권한이 있는 사용자에게 같은 문서의 수집 시각·문서 버전·내용 해시·종류만 표시합니다. 현재 연결 주체·서비스 계정·공간 권한을 다시 확인하며 URL·원격 원문·인증정보는 노출하지 않습니다. `last_seen_at`은 원격 자료 수집 시각이지 시스템 관측 시각이 아닙니다.

기대값과 보고 본문은 현재 정보보호 정책 검사를 통과해야 하며 DB에 암호화해 저장합니다. 마스킹이 필요한 입력을 조용히 다른 주장으로 바꾸지 않고 수정 후 재확인을 요구합니다. 보고/변경 감사에는 ID·revision·유형/개수만 남기고 원문 메모를 넣지 않습니다.

논리/네이티브 백업 복원은 보고 정책을 비활성화하고 모든 카드 revision·검증 epoch를 바꿉니다. 이전 관측은 과거 이력으로 남아도 새 환경의 신선한 관측이 되지 않습니다. 삭제 후 새로 만든 카드도 새로운 epoch로 구분하여 과거 오프라인 보고가 revision 1에 재적용되지 않게 합니다.

## 검증

```sh
MADI_TEST_POSTGRES_DSN='postgres://tester@127.0.0.1:5432/madi_test?sslmode=disable' \
  go test -race ./internal/server -run 'TestPostgresSystemStatus|TestSystemStatus' -count=1 -v

# web 빌드와 Playwright Chromium 설치 후
MADI_TEST_POSTGRES_DSN='postgres://tester@127.0.0.1:5432/madi_test?sslmode=disable' \
MADI_BROWSER_SYSTEM_STATUS=1 \
  go test ./internal/server -run '^TestBrowserSystemStatus$' -count=1 -v
```

시험은 매번 별도 임의 스키마를 생성·정리합니다. 대상 시스템의 실제 운영 상태를 인증하는 시험이 아니라 합성 관측·실제 HTTP 프로토콜 fixture·현재 ACL·CAS·재전송·보존/복원 경계를 검증합니다.

2026-09-08 Go 1.26.8/PostgreSQL 18.6에서 E7와 기존 승인 교차 PG race 24.025초 PASS: 보고 스코프·서비스 계정·MCP·자기 범위/private 보존·실제 row-lock 대기 후 세션 만료·CAS·TTL·암호화/PII·감사 원문 제외·카드 재생성·복원 epoch·보존을 확인했습니다. 실제 AWX/HTTP connector fixture 11.613초 PASS로 실행 성공과 자료 수집이 관측 보고를 자동 만들지 않음을 확인했습니다. 실제 브라우저의 기본 off·정책·기대값·보고·drift·두 탭 기준 변경·원문 변경·권한 회수·390px는 23.32초에 통과했습니다. 자동 시험이며 실제 사용자를 관찰한 사용성 측정은 아닙니다.

2026-09-09 최신 `main-C6aNRXQA.js`에서 모바일 머리글 배치와 관측 카드까지 재검증했습니다. 운영 현황 실제 브라우저 회귀 17.23초 통과, 예외 승인 화면을 포함한 합계 35.364초 통과입니다.
