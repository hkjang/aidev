# 변경 영향 예외 승인

변경 영향 검토의 `예외 요청`은 승인 완료가 아닙니다. 별도 승인 정책과 실제 검토자의 결정이 있어야 하며, 이 결정도 문서 본문·게시 상태·Runbook 실행 권한을 바꾸지 않습니다.

## 관리자 설정

1. 서비스 설정에서 검토·승인 기능을 켭니다. 설정이 꺼져 있으면 예외 요청·결정 화면을 제공하지 않습니다.
2. **승인 정책 관리 → 변경 영향 예외**에서 워크스페이스 또는 공간의 정책을 등록합니다.
3. 지정 사용자·역할·팀에 따른 단계와 병렬 검토 대상을 선택합니다. 변경 원문과 대상 문서를 모두 읽을 수 있는 현재 사용자가 실제 검토 대상입니다.

이 리소스에는 문서 게시용 기본 `reviewer_role`을 자동 적용하지 않습니다. 명시된 예외 정책이 없으면 신청을 차단합니다. 신청자와 대상 담당자는 자신을 승인할 수 없습니다.

## 요청자와 검토자

1. **변경 영향**에서 연결 문서의 검토 결과를 `예외 요청`으로 저장합니다.
2. 해당 검토의 **예외 승인·이력**을 열고 현재 검토 revision, 변경 원문·대상 버전을 확인합니다.
3. 대체 절차·적용 이유를 적고 1~90일의 유효기간을 선택합니다. 명시 확인 후 **예외 승인 요청**을 누릅니다.
4. 독립 검토자는 **검토 처리함**에서 고정된 버전·기한·실제 예외 근거를 읽고 단계별 승인 또는 반려를 처리합니다.
5. 반려 후에는 근거를 보강해 새 요청을 보낼 수 있습니다. 이전 요청과 결정 이력은 그대로 남습니다. 처리 중 요청은 신청자·담당자가 취소할 수 있습니다.

선택 상자의 값이나 문서·검토·요청 상태가 바뀌면 확인 선택을 해제합니다. 화면에 `승인 완료` 이력이 남아도 `현재 무효`라면 적용 가능한 예외가 아닙니다.

## 현재 유효 여부

현재 유효한 예외는 다음 조건을 모두 만족해야 합니다.

- 변경 원문과 대상 문서의 현재 접근 권한
- 승인 당시 원문·대상 버전, 검토 revision·상태·담당자 일치
- 원문·대상 제목/본문/태그/별칭의 SHA-256 무결성 해시 일치
- 직접 의존 관계 및 관계 생성 기록 일치
- 승인 당시의 명시 정책·전역 승인 설정 revision 일치
- 독립 검토자의 실제 승인 완료와 만료 전 유효기간

원문 수정, 검토 수정, 관계 삭제·재연결, 정책 변경, 만료 후에는 과거 승인을 재사용하지 않습니다. 복원 시 진행 중·승인 완료 예외를 취소 이력으로 보존해 다른 설치 환경에서 부활시키지 않습니다. 문서가 비공개로 바뀌어 현재 권한을 잃으면 근거와 이력을 더 이상 표시하지 않습니다.

이 기능은 대체 절차의 적절성을 자동 검증하지 않으며, 외부 시스템이나 조직의 별도 법적·운영적 승인을 대체하지 않습니다.

## API와 MCP

| 경로 | 용도 |
| --- | --- |
| `GET /api/v1/knowledge/impact-reviews/{id}/exceptions` | 현재 권한으로 최근 20개 요청, 요청 가능 여부 |
| `POST /api/v1/knowledge/impact-reviews/{id}/exceptions` | 버전 CAS와 명시 확인에 따른 새 신청 |
| `GET /api/v1/knowledge/impact-exceptions/{id}` | 실제 근거·과거 결과·현재 `effective` |
| `GET /api/v1/approvals/requests/{id}` | 고정 snapshot과 현재 ACL의 `review_context` |
| `POST /api/v1/approvals/requests/{id}/decisions` | 기존 승인 엔진의 승인·반려·취소 |

신청에는 `review_revision`, `source_version`, `target_version`, `reason`, `valid_until`(RFC3339), `confirm:true`가 필요합니다. 동일 현재 검토의 동시 신청은 한 건만 확정되고 나머지는 409입니다. 응답을 잃으면 먼저 GET으로 기존 요청을 확인합니다. 자동 재신청하지 않습니다.

조회는 `document:read` 키와 양쪽 문서의 현재 ACL 교집합으로 제한합니다. 신청·결정은 실제 사용자의 로그인 세션에서만 가능합니다. 서비스 계정·개인 API 키·플러그인으로 사람의 확인을 대신할 수 없습니다. MCP `get_impact_exception`은 동일 REST 경계의 읽기 전용 도구이며, 예외 신청·승인 도구는 제공하지 않습니다.

사유는 암호화 저장하고, 일반 승인 snapshot과 감사 로그에는 원문 사유를 넣지 않습니다. 현재 정보보호 정책이 사유·결정 의견의 표시나 저장을 금지하면 차단합니다. 잠금 대기 뒤에도 세션·키 만료와 현재 권한을 재확인합니다.

## 검증

2026-09-09, 작업용 PostgreSQL 18.6의 격리 스키마에서 다음 회귀를 실행했습니다. 운영 데이터베이스나 인증 정책은 변경하지 않았습니다.

```bash
MADI_TEST_POSTGRES_DSN='postgres://…/madi_test?sslmode=disable' \
  go test -race ./internal/server \
  -run 'TestPostgresImpactException|TestPostgresApprovalSessionExpiresBehindResourceLock'
```

초기 예외/기존 고급 승인/Runbook 교차 시험 37.678초 통과. 실제 HTTP의 문서 submit·리소스 조회·요청 조회·승인 결정이 행 잠금에서 기다리는 동안 세션을 만료시킨 부정 시험과 예외 회귀는 26.698초 통과했습니다. 이 수치는 단일 개발 환경의 회귀 실행 시간이며 운영 지연 SLA가 아닙니다.

추가 키/MCP·시간 만료·정보보호·동시 신청·기존 Text2SQL/전체 배포 승인 교차 회귀도 38.167초 통과했습니다. 실제 Chromium의 작성자/검토자 별도 세션, 확인 선택·셀렉트, 자기 승인 차단, 독립 승인, 원문 불변, 현재 무효 표시, 접근 회수 후 화면 제거와 390px 화면을 검사했습니다. 운영 현황 화면을 포함한 브라우저 회귀 합계 35.364초 통과(`main-C6aNRXQA.js` 기준).

승인 근거 단락의 전용 배치를 보강한 최종 `main-B0QpEkx9.js`에서도 19.262초 통과했습니다. 실제 단락 너비·16px 글자 크기를 검사했으며 정상 화면으로 캡처를 갱신했습니다. 무결성 해시와 generic 승인 조회의 만료 상태를 포함한 후속 PG-race는 31.709초 통과했습니다.
