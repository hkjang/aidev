# 외부 알림 · 이메일 및 Webhook 수집 가이드

두 기능은 기본적으로 꺼져 있으며 추가 환경변수나 수신 포트를 요구하지 않습니다. 서비스 관리자가 목적지·호스트와 사용 여부를 정하고 개인이 받을 채널 또는 내 수집함 연결을 선택합니다.

## 외부 알림

관리자 화면 `/admin/notification-channels`에서 외부 전송을 켜고 정확한 목적지 호스트를 등록합니다. SMTP 이메일, Slack, Teams, Mattermost, 일반 서명 Webhook 채널을 추가할 수 있습니다. 채널은 서비스 공용 또는 워크스페이스 전용입니다. 전용 채널에는 해당 워크스페이스 문서의 알림만 보내며, 특정 문서에 연결되지 않은 알림은 공용 채널에서만 처리합니다.

SMTP는 TLS 또는 STARTTLS와 사내 CA를 지원합니다. 비밀 인증은 TLS에서만 보내며, 명시적인 테스트 평문 모드에서는 비밀번호 인증을 사용할 수 없습니다. 수신 주소를 임의 지정하지 않고 사용자의 현재 계정 이메일로 전송합니다. Webhook의 전체 URL에도 인증 비밀이 포함될 수 있으므로 URL·비밀번호·서명 키는 암호화 저장하고 조회 시 원문을 반환하지 않습니다. 편집 화면의 빈 비밀은 기존 값을 유지합니다.

Teams에는 Adaptive Card를 받는 Workflow 또는 호환 Webhook을 구성합니다. Microsoft 365의 기존 Connector 정책과 Workflow 소유자 유지 조건은 운영 테넌트에서 확인하세요. [Microsoft의 Teams Webhook 안내](https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook)를 참고할 수 있습니다. Slack은 조직에 설치한 앱의 Incoming Webhook을 사용합니다. [Slack 공식 Webhook 안내](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/)를 참고하세요.

개인은 `/app/notification-settings`에서 받을 채널을 선택합니다. 선택은 서버에 저장하며 이후 발생하는 알림부터 적용합니다. 이전 알림을 일괄 발송하지 않습니다. 관리자나 사용자가 전송을 중지하거나, 원본 문서·계정·채널 설정이 바뀌면 대기 전송을 제외할 수 있습니다.

외부 메시지는 새 알림 안내와 로그인 후 개인 알림함 링크만 담습니다. 문서 제목·본문·댓글·사용자 ID는 보내지 않습니다. 기존 인앱 알림은 원본 트랜잭션의 outbox에 기록되고 PostgreSQL 작업 큐가 전송합니다. 일시 오류는 제한된 재시도로 처리하며 개인 페이지에서 이력·시도 수·결과를 확인합니다.

외부 시스템과 데이터베이스 사이에는 분산 트랜잭션이 없으므로 응답 유실 때 같은 메시지가 중복 도착할 수 있습니다. SMTP Message-ID와 일반 Webhook 전송 ID는 재시도 중 유지합니다. 일반 Webhook 수신자는 아래 HMAC을 검증한 뒤 전송 ID를 저장하여 중복 효과를 막으세요.

## 개인 이메일 수집

관리자는 `/admin/inbound-capture`에서 IMAP TLS를 켜고 사내 메일 호스트를 허용합니다. 개인은 `/app/capture-channels`에서 워크스페이스, IMAP 서버·포트, 폴더, 계정·비밀번호 또는 앱 암호, 주기를 입력합니다. 메일 서버 인증서 검증이 기본이며 사내 CA를 지정할 수 있습니다. OAuth 전용 메일 서비스라면 조직에서 허용하는 앱 암호나 호환 게이트웨이가 필요합니다. IMAP OAuth/XOAUTH2는 이 연결 방식에 포함하지 않습니다.

처음 연결한 이후의 메일부터 수집하는 것이 기본입니다. 기존 메일도 가져오려면 생성 시 해당 선택을 해제합니다. 폴더는 EXAMINE으로 읽기 전용 선택하고 본문은 BODY.PEEK로 읽습니다. 읽음 표시, 원격 메일 이동·삭제는 하지 않습니다. 원격 서버·계정·폴더는 생성 후 변경하지 않으며 새로운 수집 경계가 필요하면 새 채널을 만듭니다.

UIDVALIDITY와 UID로 검사 위치를 보존하고 Message-ID가 반복되면 중복 문서를 만들지 않습니다. Message-ID가 없는 메일은 원문 해시를 보조 식별자로 사용합니다. 같은 ID의 내용이 바뀌면 정상 중복으로 간주하지 않습니다. 한 검사에서는 최대 100 UID 범위를 살펴보고 최대 20개 메시지와 제한된 바이트 수를 처리합니다. 빈 구간과 대규모 기존 메일함은 여러 예약 주기에 걸쳐 진행할 수 있습니다.

메일 제목·본문·첨부는 내 워크스페이스의 **비공개 수집함 문서**가 됩니다. HTML 본문은 안전한 Markdown으로 변환하며 plain text 대체 본문이 있으면 우선 사용합니다. MIME 첨부는 실행하거나 압축을 풀지 않고 일반 첨부로 보존합니다. 수집 후 공개 또는 공간 이동은 사용자가 직접 결정합니다.

## HMAC Webhook 수집

관리자가 개인 Webhook 수집을 허용한 뒤 개인 수집 채널에서 서명 Webhook을 생성합니다. 화면에 한 번만 표시하는 비밀을 발신 시스템에 보관하세요. 서명 비밀 회전은 이전 비밀을 즉시 폐기하고 채널 버전 변경으로 대기 자료도 취소할 수 있습니다.

엔드포인트는 `POST /api/v1/capture-hooks/{채널 UUID}`입니다. 세션 쿠키 또는 API 키 대신 채널 서명을 요구합니다. 비밀을 가진 발신자도 해당 채널의 소유자·워크스페이스에 고정된 비공개 수집함에만 쓸 수 있습니다.

| 헤더 | 값 |
| --- | --- |
| `Content-Type` | `application/json` |
| `X-Madi-ID` | 발신자가 생성한 UUID, 재시도 때 유지 |
| `X-Madi-Timestamp` | 현재 Unix 초, 서버 시간과 ±5분 |
| `X-Madi-Signature` | `sha256=` + HMAC-SHA256의 소문자 16진수 |

HMAC의 입력 바이트는 `timestamp + "." + ID + "." + HTTP 본문 원본 바이트`입니다. 이 서명 규칙은 일반 외부 알림 Webhook도 동일하게 사용합니다. 발신자와 수신자는 시간 동기화가 필요합니다.

```json
{
  "title": "빠르게 수집한 운영 메모",
  "text": "확인할 내용을 개인 수집함에 저장합니다.",
  "url": "https://intranet.example.internal/runbook",
  "attachments": [{"name":"note.txt","type":"text/plain","data":"aGVsbG8="}]
}
```

`url`과 `attachments`는 선택 항목이고 첨부 `data`는 base64입니다. URL은 출처로 보관할 뿐 서버가 해당 페이지를 자동 다운로드하지 않습니다. 허용하지 않은 JSON 필드는 거부합니다. 수락하면 HTTP 202와 `{id, duplicate, status}`를 반환합니다. 같은 채널·ID의 동일 내용은 재사용하고, 다른 내용이면 409입니다. 원래 자료가 완료되거나 취소된 경우 중복 응답의 상태도 함께 확인하세요. 202는 문서 저장 완료가 아니라 영속 큐 수락을 뜻합니다.

## 실패와 운영 한도

| 항목 | 제한 |
| --- | --- |
| Webhook 요청 / MIME 원문 | 10MB |
| 해제 본문·첨부 합계 | 10MB |
| Markdown 본문 | 4MB |
| 첨부 | 20개 |
| MIME 구조 | 10단계, 100파트 |
| 개인 대기 원본 | 100MB 또는 100건 |
| Webhook 수락 빈도 | 채널당 분당 60건 |

자료는 암호화한 임시 원본과 작업 ID로 보관하고, 문서·버전·첨부·공통 수집 영수증·문서 이벤트를 같은 DB 트랜잭션에서 반영합니다. 첨부 저장이나 DB 검증에 실패하면 반쪽짜리 문서를 남기지 않습니다. 소유자의 작성 권한이나 수집 정책이 회수되면 처리하지 않습니다. 개인 이력에서 작업 상태를 확인하고 대기 자료를 취소할 수 있습니다.

완료·거부·취소된 임시 암호화 원본은 7일 뒤 정리하고 생성된 문서 및 멱등 이력은 유지합니다. 복원 시 외부 알림·수집 정책과 채널을 끄고 대기 작업을 중단합니다. 목적지와 소유자 권한을 재검증한 뒤 다시 켜세요.

## 검증 범위

실제 PostgreSQL 및 race 검사에서 트랜잭션 outbox, HMAC 검증·재시도, 최소 본문, 개인 채널 선택 회수, SMTP TLS MIME 전송을 시험했습니다. 실제 TLS IMAP 서버를 사용해 EXAMINE/BODY.PEEK, 메시지 중복 방지, MIME 처리와 첨부 실패 시 전체 문서 롤백도 검증했습니다. 운영할 메일·메시징 제품의 인증·Workflow·테넌트 정책은 별도 수용 시험해야 합니다.
