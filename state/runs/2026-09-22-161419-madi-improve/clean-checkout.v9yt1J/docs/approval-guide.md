# 검토·승인 운영 가이드

madi의 검토·승인은 선택 기능입니다. 관리자가 활성화하지 않은 서비스에는 검토 요청·승인·반려 메뉴와 API가 노출되지 않습니다. 사용자 화면은 `/app/approvals`, 관리자 정책 설정은 `/admin/approvals`입니다.

## 관리자 설정

1. **서비스 관리 → 검토·승인 정책**에서 사용 여부를 설정합니다.
2. 기본 검토 역할을 워크스페이스 관리자 또는 편집자 이상으로 선택합니다. 기능을 활성화했지만 상세 정책이 없으면 다른 해당 역할 담당자 한 명의 승인을 사용합니다.
3. 상세 정책은 워크스페이스, 선택 공간, 대상 유형에 연결합니다. 가장 가까운 상위 공간의 활성 정책을 우선 사용하고, 없으면 워크스페이스 정책을 사용합니다.
4. 각 승인 단계를 순서대로 추가합니다. 단계 안의 검토 대상은 지정 사용자, 팀·부서, 역할, 문서 운영 속성의 검토자 중에서 선택합니다.
5. 단계의 **모든 검토 대상 승인**은 병렬 승인입니다. 예를 들어 운영 부서와 보안 부서를 지정하면 각 부서의 후보 중 한 명씩 승인해야 다음 단계로 진행합니다. **검토 대상 중 한 곳 승인**은 어느 한 대상의 승인으로 다음 단계로 진행합니다.

요청당 최대 20단계, 단계당 20개 검토 대상, 대상당 200명, 전체 후보 2,000명을 허용합니다. 대규모 역할 전체를 선택하기보다 실제 담당 팀이나 사용자를 지정하세요. 서비스 계정과 비활성 사용자는 검토자가 될 수 없습니다.

정책이 비활성화되면 상위 또는 기본 정책을 사용합니다. 전체 승인 절차를 제외하려면 서비스의 검토·승인 사용을 끄세요. 실행형 리소스에는 기본 문서 정책을 대신 적용하지 않으며 명시적인 실행 승인 정책이 필요합니다.

## 작성자

문서의 **검토 및 승인 → 현재 버전 검토 요청**을 선택합니다. 저장되지 않은 변경이 있으면 먼저 저장합니다. 서버는 원본 버전, Markdown, 문서 속성, 정책, 후보 담당자를 고정합니다. 소유자와 요청자는 해당 요청을 스스로 승인할 수 없습니다.

검토 중 원본이나 정책이 바뀌면 이전 요청은 승인할 수 없습니다. 작성자는 새 버전을 다시 제출합니다. 이전 원본과 결정은 이력에 보존됩니다. 반려된 요청에는 사유가 표시되며 보완 후 새 요청을 만들 수 있습니다. 요청자 또는 소유자는 진행 중인 요청을 취소할 수 있습니다.

## 검토자

**검토함**은 현재 단계의 담당자이면서 현재 대상 조회 권한이 있는 요청만 표시합니다. 문서 편집 권한이 없어도 정책에서 지정한 조회 가능 담당자는 검토할 수 있습니다.

1. 검토 원본을 열고 요청에 고정된 Markdown 또는 JSON을 확인합니다.
2. 순차·병렬 단계, 다른 담당자의 결정과 의견을 확인합니다.
3. 여러 검토 대상을 맡았다면 처리할 대상을 선택합니다.
4. 원본 확인 체크 후 승인하거나 사유와 함께 반려합니다.

동적 임베드·플러그인은 검토 원본에서 실행하지 않습니다. 현재 다른 문서의 내용으로 바뀌어 보이는 대신 요청 시점의 참조 원문을 표시합니다. 참조 대상 내용 자체를 검토 범위에 넣으려면 고정된 내용을 문서에 포함하세요.

화면은 5초 간격으로 원본 변경과 접근 권한을 재확인합니다. 권한이 회수되면 열린 원본을 숨깁니다. 모든 결정은 서버에서 최신 권한과 원본·정책 버전을 다시 검증하므로 화면 갱신 전의 오래된 버튼으로도 승인할 수 없습니다.

## API와 원자성

- `GET /api/v1/documents/{id}/approval`: 문서 정책·현재 요청·단계·검토자·최근 20개 요청.
- `POST /api/v1/documents/{id}/approval`: `action=submit` 또는 `approve/reject/cancel`.
- `GET /api/v1/approvals/resources/{kind}/{id}`: 문서·SQL 계획·실행 리소스 공용 현황.
- `GET /api/v1/approvals/requests/{id}`: 현재 권한으로 접근 가능한 고정 원본과 이력.
- `POST /api/v1/approvals/requests/{id}/decisions`: `action`, `request_version`, 필요 시 `gate_index`, `comment`.
- `GET /api/v1/approvals/inbox?workspace_id=...`: 현재 담당 검토함.

문서 승인 API로 결정할 때는 `request_id`와 `request_version`을 모두 전달합니다. 반려에는 의견이 필수입니다. 동시 요청 중 이미 처리된 버전은 HTTP 409로 거절합니다. API 키와 플러그인은 권한에 맞는 조회 또는 문서 제출을 할 수 있지만 승인·반려·취소는 실제 사용자의 로그인 세션에서만 가능합니다.

최종 문서 게시, 버전 이력, 결정, 알림, 이벤트는 하나의 PostgreSQL 트랜잭션에서 반영됩니다. 연결된 SQL 계획도 같은 트랜잭션에서 확인된 계획의 읽기 전용 쿼리만 생성합니다. 콜백 실패 시 결정과 효과가 함께 롤백됩니다.

## 실행형 리소스와 복원

문서 게시 승인은 코드 실행 승인이 아닙니다. 실행 모듈은 별도의 `runbook` 대상에 정확한 실행 payload를 고정하고 `ConsumeApprovalTx`로 승인된 요청을 한 번만 소비합니다. 실행 작업 등록과 소비는 같은 트랜잭션에서 처리하고 실제 격리 실행은 커밋 후 수행해야 합니다. 원본·정책 변경 또는 재사용은 거절됩니다.

백업 복원 시 기존 대기 요청과 비문서 대상의 미소비 승인을 무효화합니다. 과거 백업의 승인으로 외부 작업을 다시 실행하지 않습니다. 이미 게시된 문서의 승인 이력은 보존됩니다.

## 검증 범위

실제 PostgreSQL 및 race 검사로 다단계·팀 병렬 승인, 읽기 전용 담당자, 자기승인·API 키 결정 차단, 반려·재요청, 정책·원본 변경, 팀 권한 회수, 동일 버전 동시 결정, 콜백 롤백, 실행 승인 한 번 소비를 검증합니다. 브라우저 검증은 한국어 정책 선택 UI, 복수 계정의 검토, 새로고침 경로 유지, 열린 원본 권한 회수와 모바일 레이아웃을 별도로 확인합니다.
