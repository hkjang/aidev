# v0.317.0 — 옮긴 첨부가 목적지의 끝에 서고, 첨부 정리가 저장 중인 업로드를 지우지 않습니다

이 릴리즈는 첨부 이미지의 결함 둘을 담습니다. 하나는 사용자가 **고칠 수 없는 순서**를 만들고, 하나는 **방금 올린 이미지를 지웁니다.** 둘 다 `internal/app/attachments.go` 한 파일이고, 프런트엔드와 `migrations/` 는 한 줄도 바뀌지 않았습니다.

## 1. 두 이미지가 같은 순서 번호를 갖고, 위/아래 이동이 통하지 않았습니다

첨부의 삽입 위치(`placement`)를 바꾸는 PATCH 에서 `updateAttachment` 는 `sort_order` 를 **그대로 뒀습니다.** 그런데 업로드 경로는 새 이미지의 번호를 그 `placement` **안에서만** `max(sort_order)+1` 로 셉니다.

그래서 한 그룹을 빠져나간 번호가 그 안에서 다시 쓰이고, 그 번호를 들고 돌아온 이미지가 목적지에 이미 있는 행과 **같은 `sort_order`** 를 갖습니다. 프런트가 실제로 내는 요청 네 번이면 됩니다 — 2장 업로드, 한 장을 다른 위치로 이동, 1장 업로드, 그 장을 처음 위치로 이동.

결과는 두 겹입니다.

- 목록과 내보낸 덱의 순서가 사용자가 고른 값이 아니라 **`id` 로** 정해집니다.
- `AttachmentPanel` 의 위/아래 이동은 두 행의 `sort_order` 를 맞바꾸므로, **같은 값끼리 맞바꾸면 아무 일도 일어나지 않습니다.** 어긋난 순서를 사용자가 고칠 방법이 없습니다.

### 목적지 그룹의 끝 번호를 받습니다

- 같은 `UPDATE` 안에 `CASE` 를 넣어, 보낸 `sortOrder` 가 있으면 그것을 쓰고, 없고 `placement` 가 **현재 값과 다르면** 목적지 그룹의 `coalesce(max(sort_order),-1)+1` 을, 그 밖에는 지금 값을 그대로 씁니다.
- 그 식은 **업로드 경로와 같은 식**입니다. 두 입구가 한 그룹의 끝을 같은 값으로 읽어야 번호가 겹치지 않습니다.
- `SET` 의 하위질의는 변경 전 스냅숏을 읽으므로 **옮기는 행이 자기 자신을 세지 않습니다.** 추가 왕복도, 두 요청 사이의 경합도 없습니다.
- 보낸 `sortOrder` 는 그대로 이깁니다 — 맞바꾸기 PATCH 의 동작은 변하지 않습니다. 같은 `placement` 를 다시 보내는 것은 이동이 아니므로 순서를 건드리지 않습니다.
- 응답 본문·OpenAPI·소유권 검사·`caption` 과 `placement` 의 `coalesce` 동작·`RowsAffected()==0` 분기는 그대로입니다.

## 2. 첨부 정리가 첫 업로드의 저장 중인 이미지를 지웠습니다

`cleanupAttachmentFiles` 는 디렉터리가 고아인지를 **`report_attachments` 의 행 수**로 판단했습니다 — 행이 0 이면 보고서가 지워진 것으로 보고 디렉터리를 통째로 제거했습니다.

그런데 업로드는 **모든 파일의 검사를 끝낸 뒤** 한 트랜잭션에서 행을 넣습니다(v0.314.0 이 그렇게 만들었습니다). 그래서 **첫 업로드가 디스크에 쓰이는 동안 그 보고서의 첨부 행 수는 0 입니다.** 기동 직후와 30분 유지보수 주기에 도는 정리가 그 틈에 겹치면, 살아 있는 보고서의 **방금 올라온 이미지를 지웠습니다.**

행 수가 0 인 경우는 그 하나가 아닙니다. 마지막 첨부를 지워 디렉터리만 남은 보고서도 0 이고, 실패한 업로드의 잔여 파일만 있는 보고서도 0 입니다.

### 삭제된 보고서의 디렉터리만 제거합니다

- 정리는 이제 `weekly_reports` 에 그 보고서가 **있는지**를 묻습니다. 애초에 정리의 대상은 삭제된 보고서의 디렉터리였고, 첨부 행 수는 그것을 묻는 잘못된 방법이었습니다.
- 보고서가 살아 있으면 **첨부 행이 없거나 디렉터리가 비어 있어도** 보존합니다.
- 조회가 실패하면(취소·시간 초과) 보존합니다. 질의가 답하지 못한 것은 보고서가 없다는 증거가 아닙니다.
- 실패한 업로드의 잔여 파일은 사라지지 않고, 그 보고서가 삭제된 뒤 정리됩니다.
- 이 동작을 `docs/OPERATIONS.md` 의 보존 절에 적었습니다.

## 검증

구현 단계에서 새 시험 7개를 실제 PostgreSQL 위에서 돌렸습니다. 첨부는 모두 프로덕션 `Handler()` 를 지나는 실제 HTTP 업로드로 만듭니다.

- `internal/app/attachmentorder_test.go` — `TestMovingACaptureAcrossGivesItTheEndOfTheGroupItArrivesIn` 이 위의 네 단계를 그대로 거칩니다(업로드는 항상 `AFTER`, 이동 PATCH 는 `placement` 만). 고치기 전 `BEFORE holds b.png and c.png on the same sortOrder 1, so the deck orders them by id and the panel cannot swap them apart` 로 실패하고, 고친 뒤 통과합니다. `CASE` 를 잠시 원래 식으로 되돌려 **같은 실패가 다시 나는 것**까지 확인했습니다. 회귀 시험 2개(`TestASentSortOrderIsStoredAsSent`, `TestResendingTheSamePlacementLeavesTheOrderAlone`)는 의도대로 고치기 전에도 통과합니다 — 바꾸지 말아야 할 동작을 지키는 자리입니다.
- `internal/app/attachmentcleanup_test.go` — 행이 아직 보이지 않는 틈은 `LOCK TABLE report_attachments IN SHARE MODE` 로, 조회 실패는 취소된 컨텍스트로 만듭니다. 네 시험이 각각 저장 중인 첫 업로드의 보존, 삭제된 보고서만 제거, 조회 실패 시 보존, 살아 있는 보고서의 빈 디렉터리 보존을 봅니다.
- 재사용 매개변수는 `PREPARE` 로 `{character varying, text, integer, bigint, bigint}` 를 확인해 `sqlparams_test.go` 의 허용 목록에 사유와 함께 적었습니다.

릴리즈 단계에서도 실제 PostgreSQL 위에서 `go test ./... -count=1` 전체를 통과했습니다. `gofmt`·`go build ./...`·`go vet ./...`, 버전·OpenAPI·쪽넘김·모달 검사, 프런트엔드 시험과 타입 검사·프로덕션 빌드, `scripts/build.sh` 를 통과했습니다. 로드맵 HTML·PDF 와 두 안내서 HTML 을 기존 스크립트로 다시 만들었습니다.

검증하지 않은 것을 밝힙니다. **운영 DB 에 이미 들어간 중복 `sort_order` 는 이 릴리즈가 고치지 않습니다** — 새로 생기는 중복을 막을 뿐입니다. `migrations/` 에 `UNIQUE` 제약을 새로 걸지 않은 것은 출하된 마이그레이션의 체크섬을 바꿀 수 없고 기존 중복이 그 제약을 막을 수 있기 때문입니다. 프런트엔드는 소스를 읽어 확인한 것까지이며 `AttachmentPanel` 의 렌더 시험으로 밟지는 않았습니다. 정리 쪽은 유지보수 주기를 실제로 30분 기다려 본 것이 아니라 같은 함수를 직접 불러 확인했습니다. 제자리에서 소스를 고치는 `mutation-check`·`authz-check` 는 과거 회차가 시간을 넘겨 돌리지 않았습니다. `gh` 를 사용할 수 없는 세션이므로 원격 이력을 보는 advisory `release-check.sh` 와 docker 빌드가 필요한 `install-check.sh` 는 실행하지 않았습니다.

## 업그레이드

마이그레이션·새 환경변수·설정 변경은 없습니다. 기존과 같이 PostgreSQL 과 상태 볼륨을 백업한 뒤 v0.317.0 이미지를 올립니다.

**정리 쪽은 올리는 즉시 값이 있습니다.** 기동 직후의 정리가 그때 올라오는 중인 첨부를 더는 지우지 않습니다. 이전 버전에서 "올렸는데 사라졌다" 는 문의를 받고 있었다면 그 문의가 사라집니다. 반대로, 살아 있는 보고서의 **잔여 파일은 이제 더 오래 남습니다** — 실패한 업로드의 파일은 그 보고서가 삭제될 때까지 디스크를 차지합니다. 첨부 볼륨의 사용량을 보는 운영자는 이 변화를 알고 보십시오.

**순서 쪽은 새로 만드는 첨부에만 적용됩니다.** 배포 후 삽입 위치를 옮긴 첨부가 목적지 그룹의 **끝**에 서는지, 그 뒤 위/아래 이동이 실제로 순서를 바꾸는지를 보고서 한 건으로 확인합니다. 이미 같은 `sort_order` 를 가진 쌍이 있는 보고서는 그대로 `id` 순으로 보입니다. 그런 보고서가 신고되면 첨부 하나의 `sortOrder` 를 명시해 PATCH 하면 풀립니다 — 보낸 값은 그대로 저장되므로, 겹친 쌍 중 하나에 비어 있는 번호를 주면 됩니다.

되돌려야 하면 v0.316.0 이미지로 내립니다. 스키마가 바뀌지 않았으므로 데이터 되돌림은 필요하지 않고, 되돌리면 두 결함도 함께 돌아옵니다.
