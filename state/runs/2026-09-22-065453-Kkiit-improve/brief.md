- 과제: 승인 정책 배열 조건의 잘못된 타입을 저장 단계에서 거부하기 (가치 3 / 위험 2 / 작업량 M)
- 왜: `approvals.go:validateApprovalPolicy`는 숫자 조건만 검사하므로 `service_types: "AI"` 같은 값도 저장되고, `talents.go:approvalConditionsMatch`는 배열이 아니면 조건을 무시한다. 생성·수정 API에서 잘못된 배열을 거부하면 운영자가 의도한 적용 범위가 조용히 넓어지는 것을 막는다.
- 수용 기준: 1) POST `/api/v1/admin/approvals/policies`와 PUT `/api/v1/admin/approvals/policies/{id}` 모두 `service_types`·`seller_levels`가 존재할 때 문자열 배열만 허용한다. null·문자열·숫자·객체·문자열 아닌 원소·빈 문자열·공백뿐인 원소는 400 `invalid_policy`; 실패한 생성은 행을 남기지 않고 실패한 수정은 기존 조건을 유지한다. 2) 필드 생략과 빈 배열은 기존처럼 제한 없음이며 정상 문자열 배열은 GET에 그대로 보존된다. 기존 대소문자 무시 매칭, 숫자 조건, 알 수 없는 조건 키 허용은 유지한다. enum 화이트리스트나 문자열 자동 trim/대문자화는 이번 범위가 아니다. 3) 실제 Handler→HTTP JSON→DB 저장/조회→상품 공개 경로 테스트로 두 필드의 일치/불일치가 `review_pending`/`published`를 구분함을 증명한다. 공개 상품 중요 수정(`PUT /api/v1/talents/{id}`→`requeueForReview`)에서도 동일 조건을 읽어 일치 시 재검토, 불일치 시 공개 유지함을 확인한다. 순수 검증기 테스트만으로 완료 처리하지 않는다.
- 건드릴 파일: `internal/httpapi/approvals.go:validateApprovalPolicy` — 두 배열 필드의 공통 검증을 추가; 같은 파일 `createApprovalPolicy`·`updateApprovalPolicy`가 이미 이 함수를 호출하므로 핸들러 배선은 유지. `internal/httpapi/auth_test.go:TestValidateApprovalPolicyRejectsInvalidConditions` — JSON 디코딩 형태([]any)를 포함한 정상/오류 표 테스트 확장. `internal/httpapi/integration_test.go` — 새 `TestIntegrationApprovalPolicyArrayConditions` 추가, 기존 `integrationServer`·`newClient`·`grantRole`·`talentPayload` 및 `TestIntegrationApprovalShowsWhatIsBeingApproved`의 로그인·정책 생성 방식을 재사용. 별도 테스트 파일로 분리해도 된다.
- 검증 명령: `go test ./cmd/... ./internal/...`; `go vet ./cmd/... ./internal/...`; `go test ./internal/httpapi -run TestValidateApprovalPolicyRejectsInvalidConditions -count=1`; 버릴 PostgreSQL의 DSN을 KKIIT_TEST_DSN에 지정한 뒤 `go test ./internal/httpapi -run TestIntegrationApprovalPolicyArrayConditions -count=1 -v -timeout 300s`, 이어 `make test-integration KKIIT_TEST_DSN="$KKIIT_TEST_DSN"`. 마지막 두 명령은 DSN 없으면 SKIP하므로 PASS로 간주하지 말 것. 새 테스트명은 제안이며 아직 존재하지 않는다.
- 위험과 피할 것: 기존 잘못된 정책 행은 자동 보정하지 않는다(수정/활성 전환 시 400이 될 수 있어 조건을 먼저 바로잡아야 함). 기존 `approvalConditionsMatch`·`matchingApprovalPolicy`의 해석 변경, DB 마이그레이션, auth/session·원장·.github/workflows, 프런트·dist·PDF·의존성은 건드리지 않는다. 알 수 없는 키 삭제나 판매자 등급 목록 고정은 별도 문제다. 테스트는 전용 DB에서 직렬 실행하고 만든 정책은 cleanup에서 비활성화해 다른 테스트를 오염시키지 않는다. API 응답과 저장된 행을 검증하며 소스 문자열 검사·가짜 DB로 대체하지 않는다.
- 차선 후보: README 환경변수 계약을 필수 네 개 + 선택 종료 설정으로 정리 — 배열 검증이 이미 해결됐거나 전용 DB 검증 환경을 확보하지 못할 때만 선택. README 실행 계약과 `internal/config/config.go:Config` 주석을 `Load`의 실제 다섯 변수와 일치시키고 기본5·0~120·잘못된 값은 기본값이라는 종료 설정을 명시한다. 런타임 동작은 바꾸지 않으며 `go test ./internal/config`로 기존 동작을 확인한다.
