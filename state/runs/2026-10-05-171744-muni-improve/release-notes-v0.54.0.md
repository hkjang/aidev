워크스페이스를 ZIP으로 내보낼 때 **같은 부모 아래 이름이 같은 폴더 둘이 압축을 풀면 한 디렉터리로 합쳐지던 것**을 고쳤습니다. 화면은 바뀌지 않았고, 마이그레이션도 설정 변경도 없습니다.

## 고친 것

### 이름이 같은 폴더 둘이 ZIP에서 한 디렉터리가 되던 것

폴더 이름 검사는 **비어 있지 않고 120룬 이하인지만** 봅니다 — 형제 폴더의 이름은 보지 않습니다. 그래서 같은 부모 아래 `기획` 폴더 둘을 편집기에서 그대로 만들 수 있고, 사용자는 사이드바에서 폴더 둘을 봅니다.

내보내기가 폴더를 디렉터리 경로로 바꾸는 `folderPaths`는 `path.Join`으로 만든 경로의 중복을 전혀 보지 않았습니다. 그래서 그 둘이 똑같은 디렉터리 문자열 `기획/`을 받았고, ZIP에는 '같은 이름의 디렉터리 둘'을 적을 방법이 없으므로 **사용자가 보던 폴더 둘이 압축을 풀면 하나가 됐습니다.**

문서 자체는 사라지지 않았습니다 — 이름이 겹치는 항목을 `(2)`로 옮기는 `uniqueEntryName`이 파일 쪽은 막아 주기 때문입니다. 그래서 잃는 것은 문서가 아니라 **사용자가 내려받던 폴더 구조**였고, 증상이 디렉터리 쪽에만 남아 눈에 덜 띄었습니다.

| 워크스페이스 (같은 부모 아래) | ZIP 항목 (이전) | ZIP 항목 (지금) |
| --- | --- | --- |
| `기획` 폴더의 `첫째 문서` | `기획/첫째 문서.md` | `기획/첫째 문서.md` |
| 또 다른 `기획` 폴더의 `둘째 문서` | `기획/둘째 문서.md` — **같은 디렉터리** | `기획 (2)/둘째 문서.md` |

이제 `folderPaths`는 **경로를 만든 직후 그 경로를 장부에 올리고**, 다른 폴더가 이미 가져간 이름에 도달한 폴더를 `기획 (2)`로 옮깁니다. 파일 이름에서 하던 것과 같은 수단을 한 단계 위에 둔 것입니다.

장부의 키는 항목 이름과 같은 규칙인 `entryKey`를 지납니다. 압축을 푸는 것은 내려받은 기계이고 배포 대상인 **Windows에서 `Report`와 `report`는 한 디렉터리**이므로, 대소문자만 다른 형제 폴더 둘도 함께 갈라집니다. 접는 것은 **비교 키뿐**이고, 돌려주는 경로와 ZIP에 실제로 쓰는 디렉터리 이름은 폴더에 적힌 대소문자를 글자 그대로 둡니다.

이것은 [v0.53.0](https://github.com/hkjang/muni/blob/v0.54.0/docs/releases/v0.53.0.md)이 항목 이름에서 막은 것의 **남은 절반**입니다. 그 릴리스는 "대소문자로만 다른 폴더 둘은 Windows에서 여전히 한 디렉터리로 합쳐지므로 폴더 구조 보존은 약속하지 않는다"고 적어 두었고, 이번 릴리스가 그 자리를 채웁니다.

### 접미사가 요청마다 다른 폴더에 붙지 않게 순회 순서를 고정했습니다

접미사를 붙이는 순간 **누가 원래 이름을 갖고 누가 `(2)`를 받는지가 생깁니다.** 그 순서가 요청마다 달라지면 같은 워크스페이스를 두 번 내려받은 사용자가 서로 다르게 배치된 ZIP 둘을 받습니다.

SQL에 `ORDER BY name, id`를 더하는 것만으로는 **부족합니다.** 읽은 행이 맵으로 들어가고 `for id := range all`이 그 순서를 다시 버리기 때문입니다. 그래서 읽은 순서를 슬라이스로 남겨 그것을 순회합니다. 맵은 `resolve`가 하는 부모 조회에만 씁니다.

같은 워크스페이스를 **열두 번 내려받아 항목 이름이 모두 같은 것**을 확인했고, 슬라이스만 되돌리면 요청마다 달라지는 것도 확인했습니다 — 둘 가운데 하나만으로는 효과가 없습니다.

### 바뀌지 않은 것

`depth>32` 순환 방어, '부모가 없는 폴더의 자식은 루트에 놓인다'는 동작, 휴지통 접두사, `safeFolderSegment`·`uniqueEntryName`·`entryKey`는 **건드리지 않았습니다.** 이름이 겹치지 않는 평범한 폴더는 적힌 글자를 그대로 유지하고, 자식은 부모 아래에, 지운 문서는 `휴지통` 아래에 그대로 있습니다. 같은 ZIP 한 번에서 이 셋을 함께 확인하는 검증을 넣었습니다.

| 워크스페이스 | ZIP 항목 이름 |
| --- | --- |
| `README` 폴더의 `그대로 문서` | `README/그대로 문서.md` |
| `README/하위` 폴더의 `중첩 문서` | `README/하위/중첩 문서.md` |
| `README/하위` 폴더에서 지운 `버린 문서` | `휴지통/README/하위/버린 문서.md` |

### 남아 있는 것

- **둘 가운데 어느 쪽이 `(2)`를 받는지는 고정하지 않았습니다.** `resolve`는 형제보다 부모를 먼저 따라가므로, 자식을 가진 폴더가 목록에서 앞선 형제보다 먼저 자기 이름을 가져갈 수 있습니다. 실제로 세 번째 `기획` 폴더가 `기획 (2)`를 받고 두 번째가 원래 이름을 받는 배치를 확인했습니다. 고정된 것은 **같은 워크스페이스가 매번 같게 나온다**는 것까지이며, 테스트도 "한쪽만 접미사를 받는다"까지만 확인합니다.
- **폴더 이름 중복 자체는 그대로 둡니다.** `createFolder`에는 형제 이름 중복 검사가 없고, 이번 변경은 내보내기 쪽만 손댔습니다. 사용자는 여전히 사이드바에서 구분되지 않는 폴더 둘을 만들 수 있습니다 — 그 둘이 **내려받은 ZIP에서는 더 이상 합쳐지지 않는다**는 것이 이번 릴리스가 지키는 것입니다.
- **실제 Windows·macOS에서 디렉터리 둘이 합쳐지는 것은 이번 릴리스 준비에서 재현하지 않았습니다.** 리눅스 파일 시스템은 대소문자를 구분합니다. 검증이 증명한 것은 "ZIP 안의 어떤 두 디렉터리 경로도 소문자로 접었을 때 같지 않다"까지이며, 합쳐짐이 사라진다는 것은 그 성질에서 따라오는 결론입니다.
- **문서 쪽 정렬 동률은 그대로입니다.** 문서 조회의 `ORDER BY d.folder_id NULLS FIRST, d.title`에는 문서 ID 동률 처리가 없어, **한 폴더 안에 제목이 똑같은 문서 둘**이 있으면 어느 쪽이 `(2)`를 받는지는 요청마다 달라질 수 있습니다. 문서가 사라지지는 않습니다(두 항목 모두 ZIP에 있습니다). 이번 변경은 폴더 쪽 순회만 고정했습니다.
- **안내 파일 `목록.md`는 그대로입니다.** 각 줄이 ZIP 항목 이름을 적힌 그대로 적으므로, `기획 (2)/`로 옮겨진 디렉터리도 목록과 항목이 정확히 일치합니다.
- 저장되는 값은 바뀌지 않습니다. **폴더 이름도 문서 제목도 DB에서 손대지 않았으므로** 이미 만들어 둔 폴더와 문서에 다시 손댈 필요가 없습니다. 접미사는 내보내는 ZIP 안에서만 보입니다.

## 검증

- 전용 PostgreSQL 16에서 `go test -count=1 -json ./...`: 하위 테스트 포함 **722 PASS**, 외부 코퍼스·수동 출력 4 SKIP, 실패 0. HTTP API 테스트는 SKIP 없이 통과했습니다.
- 실제 라우트로 검증을 추가했습니다: 이름이 같은 `기획` 폴더 둘을 인증 API로 만들고 각각에 문서를 둔 뒤, ZIP 응답의 항목 이름을 모두 읽어 **두 문서의 디렉터리가 서로 다른지**와 **ZIP 안의 어떤 두 디렉터리도 소문자로 접었을 때 겹치지 않는지**를 확인합니다. 같은 ZIP에서 평범한 폴더·중첩 폴더·휴지통 경로 셋이 그대로인 것도 함께 확인합니다. 고치기 전에 이 검증이 ``both 기획 folders became the one directory "기획/"``로 실패하는 것을 먼저 확인했습니다.
- v0.53.0이 넣은 대소문자 검증도 디렉터리까지 함께 보도록 넓혔습니다: `Report`·`report` 폴더 둘이 **접미사로 갈려 서로 다른 디렉터리가 되는지**와 각자 적힌 대소문자를 유지하는지 확인합니다.
- 순회 순서는 프로브로 분리해 확인했습니다: 같은 워크스페이스를 **열두 번** 내려받아 항목 이름이 모두 같은 것과, 읽은 순서를 담는 슬라이스만 되돌리면 요청마다 달라지는 것을 각각 확인했습니다.
- 프런트 `npm run lint`(`tsc -b`), `npm test` 42파일·297건, `npm run build` 통과.
- `go vet ./...`, Go 포맷 검사, placeholder 검사, `git diff --check` 통과.
- `CGO_ENABLED=0 go build -trimpath`, Docker 이미지 빌드 통과.
- 브라우저 E2E, 실제 Windows·macOS 압축 풀기, 실제 운영 배포는 이번 릴리즈 준비에서 실행하지 않았습니다. 배포용 archive는 태그 푸시 워크플로가 생성합니다.

## 업그레이드

기존 DB와 환경변수를 그대로 사용합니다. 이미지를 불러온 뒤 사용하는 Compose 파일의 `image`를 `muni:v0.54.0`으로 지정하세요. 저장소의 예제는 `muni:v0.1.0`을 가리키므로 운영 버전에 맞춰 변경해야 합니다.

```bash
gzip -dc muni-v0.54.0.tar.gz | docker load
# compose.example.yaml의 image를 muni:v0.54.0으로 지정합니다.
docker compose -f compose.example.yaml --env-file .env up -d
```

배포 담당자는 먼저 검증 환경에서 `/healthz`·`/readyz`와 워크스페이스 ZIP 내보내기를 확인한 뒤 운영에 적용하세요. 이름이 겹치는 폴더가 없는 평범한 워크스페이스를 내보내 **디렉터리 이름이 이전과 한 글자도 다르지 않은지**, 그리고 같은 워크스페이스를 두 번 내려받아 **두 ZIP의 항목 이름이 같은지** 함께 확인합니다. 두 상태 점검이 실패하거나 평범한 워크스페이스의 디렉터리 이름이 이전과 다르면 배포를 중단하고, 보관한 이전 이미지 태그로 되돌려 같은 Compose 명령을 실행합니다. 이번 변경에 따른 DB 되돌리기는 필요하지 않습니다.

배포 후 첫 주에는 워크스페이스 내보내기 관련 문의를 확인합니다. 확인 기준은 이름이 겹치지 않는 워크스페이스의 디렉터리 이름이 0건 바뀌고, ZIP을 풀었더니 폴더가 합쳐져 있다는 문의가 더 오지 않는 것입니다. 실제 운영 적용과 사후 관찰은 배포 담당자가 수행합니다.

## 운영 정보

- 서비스 포트: `8080`
- Liveness: `/healthz`
- Readiness: `/readyz`
- REST API: `/api/v1`
- 공개 링크: `/s/{token}` — 인증 없이 열리는 유일한 화면입니다
- 문서 넘기기: `/handoff?source&claim` (받는 쪽, 세션 필요, 허용 목록의 오리진만) · `/api/v1/handoff/claims/{claim}` (내주는 쪽, 인증 없이 5분짜리 단일 사용 표로만 열립니다)
- 메일 알림: 사내 SMTP 릴레이로 1분마다 배경 발송, 기본 꺼짐 · 발송 기록 `/api/v1/admin/mail/deliveries` (관리자 인증 필요)
- OpenAPI: `/api/openapi.yaml` — 실제 라우트와 일치하며, 테스트가 그것을 지킵니다
- Prometheus: `/metrics` — 관리자 인증 필요
- MCP: `/mcp`
- Momento 프록시: `/momento/*` — 방문 추적을 Momento 로 켜 둔 동안에만 답합니다
- 지원 DB: PostgreSQL 15 이상
- 이미지에는 PDF Export용 Chromium과 Noto CJK 글꼴이 포함되어 있습니다.
