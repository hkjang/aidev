
사용자 목록 검색어에 다른 조회 경로와 같은 200자 상한을 적용한 패치 릴리스입니다.

- `GET /api/v1/users?q=`만 검색어 길이 상한이 없어 `TrimSpace`만 거친 값이 `username`·`email`·`display_name` 세 컬럼의 `ILIKE '%…%'` count·목록 두 조회에 그대로 들어가던 문제 해결. 감사 이벤트·레거시·MCP 검색은 모두 200자를 넘는 검색어를 거부하고 있었습니다
- `listUsers`가 `TrimSpace` 직후, count 조회 전에 같은 문자 수(rune) 기준 검사를 수행해 200자를 넘으면 DB 조회 없이 400 `query_too_long`(`검색어는 200자 이하여야 합니다.`, 레거시 조회와 같은 문구)으로 거부합니다. 공백으로 감싼 200자는 trim 뒤 허용되고, 바이트가 아니라 문자 수 기준이므로 한글 200자도 통과합니다
- 실제 핸들러와 PostgreSQL을 지나는 통합 테스트(190자 검색 → 해당 사용자 1건, 200자 → 조회 실행·빈 페이지, 201자 → 400 `query_too_long`, 공백 포함 200자 → 허용, 빈 `q` → 전체)로 검증
- `docs/api.md` 사용자 목록 절에 `q` 길이 상한 계약을 명시
