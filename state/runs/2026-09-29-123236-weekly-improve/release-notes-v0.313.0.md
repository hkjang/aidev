# v0.313.0 — Confluence 상태를 읽지 못하면 수동 동기화를 접수하지 않습니다

## 실패한 조회가 접수 성공으로 바뀌었습니다

관리자가 수동 동기화를 요청하면 `POST /api/v1/admin/confluence/sync` 는 먼저 현재 상태를 읽습니다. 이때 `Scan` 오류를 무시해, 상태 테이블을 읽지 못하거나 상태 행이 없어도 `202` 와 `queued=true` 를 반환하고 요청 감사 기록을 남겼습니다. 관리자는 상태 확인에 실패한 요청을 정상 접수로 받아들일 수 있었습니다.

## 상태 확인에 실패하면 그 자리에서 멈춥니다

- 상태 조회 오류와 행 없음에 `500 QUERY_FAILED` 를 반환합니다. 안전한 한국어 오류 메시지를 보내며 DB 오류 원문은 응답에 넣지 않습니다.
- 오류 반환은 worker 깨우기와 요청 감사 기록보다 먼저입니다. 실패한 조회를 접수로 기록하지 않습니다.
- 정상 조회의 RUNNING·IDLE 처리와 기존 성공 응답은 유지합니다. POST OpenAPI 응답 계약에 `500` 을 추가했습니다.

## 검증

구현 단계에서 실제 PostgreSQL·애플리케이션·HTTP Confluence 서버를 사용해 테이블 이름 변경/복원, 상태 행 없음, RUNNING, IDLE 과 요청 감사 증감을 검증했습니다. 구 코드에서는 기대한 500 대신 `202 queued=true` 와 감사 기록 증가 1건이 발생했고, 수정 후 통과한 뒤 구 코드 재복원으로 같은 실패를 다시 확인했습니다. worker fixture 는 실제 검색 응답과 production advisory lock 으로 동기화했습니다.

프런트 렌더링과 worker 깨우기 호출 부재 자체의 동적 계측은 하지 않았습니다. 오류 반환 위치는 코드 검토로, HTTP 응답과 감사 기록은 실제 행동 시험으로 확인했습니다.

릴리즈 단계에서도 실제 PostgreSQL 위에서 `go test ./... -count=1` 을 통과했습니다(`internal/app` 147.821초). `go vet ./...`·`go build ./...`, 전체 가드 341개, 버전·OpenAPI·쪽넘김·모달 검사, 두 시간대의 프런트엔드 시험 각각 173개, 타입 검사·프로덕션 빌드와 `scripts/build.sh` 를 통과했습니다. 로드맵 HTML·PDF 와 두 안내서 HTML 을 기존 스크립트로 다시 만들었습니다. `gh` 를 사용할 수 없는 세션이므로 원격 이력의 advisory `release-check.sh` 는 실행하지 않았습니다.

## 업그레이드

Confluence 수동 동기화를 쓰는 관리자와 이 POST API 를 호출하는 클라이언트에 해당하는 수정입니다. 마이그레이션·새 환경변수·설정 변경은 없습니다. 기존과 같이 PostgreSQL 을 백업한 뒤 v0.313.0 이미지를 올립니다. 외부 클라이언트는 상태 조회 실패를 접수 성공으로 처리하지 않고 `500 QUERY_FAILED` 를 오류로 처리해야 합니다.

배포 담당자는 배포 후 정상 상태의 수동 요청이 기존 응답을 유지하는지 확인하고, 정상 DB 상태에서도 수동 요청이 500 으로 실패하면 확대를 중단하고 v0.312.0 이미지로 되돌립니다. 되돌리면 이번의 잘못된 접수 문제도 다시 발생합니다. 배포 다음 날까지 관련 문의와 수동 요청 오류를 확인하며, 상태 조회 실패가 접수 성공으로 기록된 사례 0건을 확인 기준으로 삼습니다.
