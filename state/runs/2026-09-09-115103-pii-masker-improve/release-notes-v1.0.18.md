Let running async jobs finish before shutting down. `App.Serve` drained in-flight HTTP requests with `http.Server.Shutdown` but simply abandoned the `go s.runJob` goroutines behind them, so a job that had already fetched its upstream response and finished masking the document was thrown away by every deploy or restart, and the next start could only mark it `job_interrupted` failed. `Service` now carries a `draining` channel, a `drainMu` read-write mutex and a `runners` wait group: `CreateJob` registers a runner through the new `startJobRunner` before it launches the goroutine, and the new `Service.Shutdown(ctx)` closes `draining` to refuse new runners and then waits for the ones already running until the context deadline.

A runner that has not taken a concurrency slot yet gives up immediately instead of holding shutdown open — `acquireJobSlot` checks `draining` before the slot and the new `markJobInterrupted` records a retryable `job_interrupted` failure, so a polling client gets an answer right away rather than waiting out the drain. `App.Serve` calls `svc.Shutdown` with the same `PII_MASKER_SHUTDOWN_TIMEOUT_SECONDS` budget it gives `server.Shutdown`, and treats an overrun as a log line rather than a server error: the job files stay on disk and the next start marks them interrupted, exactly as before.

Verified with two `internal/app` integration tests (a job holding an upstream response keeps `Serve` from returning after cancellation, and the job.json on disk ends up `completed` once the gate opens; with one slot, a second job is written as `job_interrupted` failed right after cancellation while the running first job still completes) and five `internal/service` unit tests (immediate return with no runners, `DeadlineExceeded` with a running runner, `startJobRunner` refused after draining, a slot waiter giving up on drain, and `CreateJob` storing `job_interrupted` while draining). `gofmt -l` is silent and `go vet ./...`, `go build ./...`, `go test -count=1 ./...` and `go test -race -count=3 ./...` all pass; removing the `svc.Shutdown` call makes both new integration tests fail as expected. The README shutdown section now documents the async drain rule.
