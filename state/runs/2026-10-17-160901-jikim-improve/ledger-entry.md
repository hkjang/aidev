- 결과: 성공
- 요약: `openbao.go:241` 의 게이트가 `r.ContentLength > 0 && !decodeBaoJSON(...)` 라서 `Transfer-Encoding: chunked` 요청(Go 가 `ContentLength = -1` 로 채움)은 본문을 **한 바이트도 읽지 않고** 기본값으로 진행했다. 그래서 `{"ttl":"1h"}` 를 chunked 로 보낸 호출자가 **12시간** 토큰을 200 으로 받고(수명 12배), `{"ttl":"99999h"}`·`{"ttl":"0s"}`·`{"ttl":"soon"}` 같은 거절 대상도 400 이 아니라 기본 TTL 로 성공했으며, 깨진 JSON(`{"ttl":`)과 두 개의 JSON 값(`{} {}`)도 400 없이 통과했다. 같은 저장소의 다른 세 호출부(`resource_handlers.go:521`·`oidc.go:68`·`ai.go:228`)는 모두 `r.ContentLength != 0` 이라 이 한 줄만 다른 판정을 하고 있었다. 게이트를 `if !decodeOptionalBaoJSON(w, r, &input)` 로 바꾸고, `decodeBaoJSON` 을 공용 코어 `decodeBaoJSONBody(…, allowEmpty bool)` 로 뽑아 빈 본문(`io.EOF`)만 기본값으로 통과시키는 변형을 추가했다 — `r.ContentLength != 0` 로만 바꾸면 **빈 chunked 본문이 400** 이 되므로 본문 없는 요청이 기본 12시간으로 성공하는 현행 계약(수용 기준 3)이 깨진다. 기존 두 메시지·`maxJSONBody`·`UseNumber`·단일 JSON 검사는 손대지 않았고 `DisallowUnknownFields` 도 넣지 않았다. 과제서 권고대로 `sessionCreator` seam(`server.go`, 기존 `resolveSession`/`revokeSessionToken` 과 같은 모양)을 **먼저** 넣어 거절 케이스가 nil store panic 대신 "200 + 생성 카운터 1회" 로 관찰되게 했다. 프로덕션 2파일(`openbao.go` +20/-2, `server.go` +8) + 테스트 1파일(신규, 서브테스트 18개) + 문서 1줄(compatibility.md 인증 계약 bullet). 검증은 `quietServer` + `sessionResolver`/`sessionCreator` 주입 + `http.NewServeMux()` + `openBaoRoutes` 로 **실제 라우트와 `withBaoAuth`** 를 통과시켜 했고, 거절 케이스마다 생성기 **0회 호출**, 수락 케이스에서 `lease_duration == 3600` 과 생성기가 받은 `name == "ci"`·`ttl == 1h` 를 단정했다. `go test ./internal/httpapi/ -run 'TokenCreate|BaoToken' -count=1 -v`(18/18 PASS)·`-run 'TokenCreate|Bao|Transit|Session' -race -count=5`(ok 2.136s)·`go test ./... -count=1`(전부 ok)·`go vet ./...`(출력 없음)·`gofmt -l`(출력 없음)·`bash scripts/verify.sh`(exit 0, 프런트 59/59, `검증 완료: jikim v0.2.39`) 모두 통과. 커밋 `ebd6c59`.
