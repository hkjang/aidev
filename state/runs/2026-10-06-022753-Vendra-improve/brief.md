- 과제: 업무 목록이 **적용하지 못한 정렬**을 적용한 척 답하는 것 고치기 — `order=amount_desc` 가 `<type>.amount.read` 없이 조용히 최신순으로 떨어지고, 응답 어디에도 그 말이 없다 (가치 4 / 위험 1 / 작업량 S)
- 왜: `objectOrderBy`(internal/httpapi/objects.go:119-131)는 `amount_desc` 를 받고 `amountVisible` 이 false 면 **아무 말 없이** `"o.updated_at DESC"` 로 떨어진다. 그런데 `listObjects`(:76-114)의 응답은 `{items,count,limit,truncated}` 뿐 — 적용된 정렬을 돌려주지 않는다. 그래서 `contract.amount.read` 가 없는 역할이 웹의 「금액 높은순」(web/src/pages/Objects.tsx:329)을 고르면 드롭다운과 URL 은 계속 `amount_desc` 를 보여 주는데 행은 최신순으로 오고, 금액 칸은 `redactObject` 가 떨어뜨려 비어 있다 — 사용자는 **그 목록의 맨 위를 「가장 큰 계약」으로 읽는다**. 이 저장소는 이미 같은 거짓을 목록 절단에서 고쳤다(`truncate` 주석: "A list that silently stops at its limit reads as 'this is everything'" → `truncated` 를 응답에 넣음). 정렬도 똑같이 응답이 말해 주면 되는 자리이고, 같은 조용한 낙하가 알 수 없는 값(`order=banana`)에도 걸려 있다.
- 수용 기준:
  1) `GET /api/v1/contracts?order=amount_desc` 응답에 **적용된** 정렬 키가 담긴다(예: `"order":"updated_desc"`). `contract.amount.read` 를 가진 역할에게는 같은 요청이 `"order":"amount_desc"` 를 답한다 — **같은 세션/같은 쿼리스트링에서 응답이 갈라지는 것**이 이 과제의 관찰 가능한 결과다.
  2) 알 수 없는 정렬 값(`order=banana`, `order=` 없음)도 실제로 적용된 `"updated_desc"` 를 답한다. 요청을 거절하지 않는다(400 으로 바꾸지 말 것 — 기존 클라이언트가 깨진다).
  3) SQL 은 한 글자도 바뀌지 않는다: 기존 `TestObjectOrderByProtectsRedactedAmounts`(productivity_test.go:63-74, 세 갈래를 SQL 리터럴로 고정)가 **고치지 않은 채로** 계속 통과해야 한다. 이번 회차에 실제로 돌려 PASS 를 확인했다(`go test ./internal/httpapi/ -run TestObjectOrderBy -count=1` → 0.054s PASS, DB 불필요). 낙하 자체는 의도된 보호이고(테스트 이름이 그렇게 말한다) 고칠 것은 **응답이 그 사실을 말하지 않는 것**뿐이다.
  4) 새 통합 테스트가 실제 세션 쿠키로 `GET /api/v1/contracts?order=amount_desc` 를 두 역할(금액 권한 있음/없음)로 치고 **응답 본문의 `order` 필드와 `items` 의 실제 순서를 함께** 읽어, 권한 없는 쪽이 최신순이면서 그 사실을 응답이 말한다는 것을 고정한다. 고치기 전에 먼저 돌려 `order` 필드 없음으로 실패하는 것을 확인할 것.
- 건드릴 파일 (프로덕션 1개):
  - `internal/httpapi/objects.go` — ① 새 `objectOrderApplied(order string, amountVisible bool) string` 를 `objectOrderBy` 바로 위에 추가: `due_asc`/`title_asc` 는 그대로, `amount_desc` 는 `amountVisible` 일 때만 `"amount_desc"`, 그 밖은 전부 `"updated_desc"`. ② `objectOrderBy` 의 **시그니처와 반환 SQL 을 바꾸지 말고** 그 `switch order` 를 `switch objectOrderApplied(order, amountVisible)` 로 바꿔 「무엇이 적용됐나」의 출처를 한 곳으로 만든다(두 함수가 어긋날 자리를 없애는 것이 요점). ③ `listObjects`(:91)에서 `applied := objectOrderApplied(order, hasPermission(p, objectType+".amount.read"))` 를 한 번 계산해 `orderBy` 와 응답에 같이 쓰고, `writeJSON`(:113)의 맵에 `"order": applied` 를 더한다.
  - 신규 테스트 1개 — `internal/httpapi/object_order_integration_test.go`(새 파일). 기존 테스트 파일은 **한 글자도 고치지 말 것**(추가만).
  - 주석은 이 저장소 문체로: 「왜 거절하지 않고 적용된 값을 돌려주나」(기존 클라이언트·웹 드롭다운이 요청한 값을 그대로 들고 있고, 거절은 목록을 통째로 잃게 한다), 「왜 `truncated` 와 같은 모양인가」를 서술할 것.
