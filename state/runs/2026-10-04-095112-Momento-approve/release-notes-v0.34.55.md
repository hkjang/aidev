# Momento v0.34.55 — 사이트를 추가하거나 설정을 저장하다 실패하면 한국어로 무엇을 고칠지 말해 줍니다

콘솔의 **「새 분석 사이트」·「사이트 분석 설정」** 다이얼로그가 거절당했을 때 띄우는 문장이 달라집니다. 지난 릴리스가 사용자 다이얼로그에 한 것을 사이트 다이얼로그에 합니다. 서버·API·데이터베이스는 그대로입니다.

## 자유 입력 칸의 실수가 영문으로 돌아왔습니다

두 다이얼로그의 Alert 은 `{create.error.message}`·`{update.error.message}` 로 **서버가 보낸 문장을 그대로** 띄웠습니다.

「IANA 시간대」 는 고를 목록이 없는 자유 입력 칸입니다. 그래서 `Asia/Seoul` 대신 `Seoul` 이라고 적는 가장 흔한 실수가 이렇게 돌아왔습니다.

```
timezone must be a valid IANA timezone
```

무엇이 틀렸다는 말은 있지만, **올바른 이름이 어떤 모양인지는 말하지 않습니다.**

500 으로 떨어지면 더 나빴습니다. `internal/httpapi/admin.go` 의 `createSite`·`updateSite` 가 실패를 `err.Error()` 로 그대로 실어 보내므로(`:269`·`:352`·`:376`), pgx 의 원문이 **데이터베이스에서 브라우저까지 그대로** 흘렀습니다.

## 이제 무엇을 고칠지 말합니다

| 서버가 거절한 이유 | 화면에 뜨던 것 | 이제 뜨는 것 |
|---|---|---|
| 시간대 이름 | `timezone must be a valid IANA timezone` | 시간대 이름이 올바르지 않습니다. 「IANA 시간대」 칸에 `Asia/Seoul` 처럼 **지역/도시** 형태로 적으세요. |
| 이름이 공백뿐 | `site name is required` | 사이트 이름을 입력하세요. **공백만 적으면** 이름이 비어 있는 것으로 처리됩니다. |
| 참여 기준 시간 범위 | 영문 한 문장 | 「참여 기준 시간(초)」 은 1초에서 300초 사이로 적으세요. |
| 세션 만료 범위 | 영문 한 문장 | 「세션 만료(분)」 은 1분에서 1440분 사이로 적으세요. |
| 삭제된 사이트 | `site not found` | 이 사이트가 이미 삭제되었습니다. 목록을 새로 고친 뒤 확인하세요. |
| 생성·저장 500 | pgx 원문 | 사이트를 만들지(설정을 저장하지) 못했습니다 + 작은 글씨로 **서버 원문** |

「이름이 비어 있다」 는 한 줄로 끝내지 않았습니다. 「생성」 버튼은 칸이 빈 동안 눌리지 않으므로(`AdminPage.tsx`), 이 거절은 칸에 **공백만** 들어 있고 서버의 `TrimSpace` 가 그것을 떼어낼 때 옵니다. "이름을 입력하세요" 라고만 말하면 비어 있지 않은 칸을 보고 있는 사람에게 거짓말로 읽힙니다.

## 500 은 원인을 말하지 않습니다

`SITE_CREATE_FAILED` 의 문구는 일부러 중립으로 두었습니다. 이 500 은 **workspaces 표가 비어 있는 경우**(`admin.go:264` 의 `QueryRow` 가 `no rows in result set` 을 돌려줍니다)와 **데이터베이스 장애**가 함께 쓰고 있고, 둘을 확실하게 갈라 줄 표지가 없습니다.

특히 **'이미 있는 사이트 이름' 이라고 설명하지 않습니다.** `sites` 에는 `site_key` 에만 UNIQUE 가 있고 `name` 에는 없습니다(`internal/database/migrations/001_initial.sql:34-49`). 이름 중복이라고 말했다면 그것은 그냥 거짓입니다. 그래서 "사이트를 만들지 못했습니다" 라고만 말하고, **서버 원문은 지우지 않고** `UserErrorAlert` 과 같은 모양의 작은 글씨로 함께 둡니다 — 관리자에게 전달할 유일한 단서입니다.

## 사용자 쪽 함수와 합치지 않았습니다

`web/src/pages/adminErrors.ts` 에 `describeSiteError` 를 **따로** 두었습니다. 두 핸들러는 `INVALID_PAYLOAD` 말고는 코드 이름 몇 개만 겹치고, 같은 이름이어도 뜻과 고쳐야 할 것이 서로 다릅니다. 하나의 `switch` 가 두 계약을 대신 답하게 만들지 않았습니다.

대신 **에러에서 코드와 메시지를 읽어내는 `refusal` 하나만** 공유합니다. 두 경로가 같은 입력을 같은 값으로 읽는다는 것은 이제 구조로 보장됩니다 — 둘이 서로 다르게 읽게 될 여지가 없습니다. 화면 쪽도 같은 모양입니다: `AdminNoticeAlert` 이 배치를 맡고, `UserErrorAlert`·`SiteErrorAlert` 은 어느 `describe*` 에 물을지만 정합니다. 모르는 코드는 **서버 메시지로 되돌아갑니다** — 나중에 서버에 거절 하나가 늘어도 삼켜지지 않고 그대로 보입니다.

## 확인

`web/test/adminErrors.test.mjs` 가 이 성질을 고정합니다(184 → **191**건).

사이트 핸들러가 실제로 내는 코드를 전부 적어 두고, 아는 코드의 안내에 **서버의 영문이 섞여 있지 않은 것**과 pgx 표지(`duplicate key`·`SQLSTATE`·`relation`·`pgx` 등)가 **Alert 본문에는 없고 detail 에는 남아 있는 것**을 함께 단언합니다. 둘을 함께 보는 것이 중요합니다 — 원문을 지우는 것은 고치는 것이 아니라 단서를 버리는 것이기 때문입니다. 500 을 이름 중복으로 설명하지 않는 것, 코드도 메시지도 없는 실패에 빈 Alert 을 남기지 않는 것도 고정했습니다.

릴리스 검증은 이전과 같습니다 — `go test`·`go vet`, sdk typecheck 와 테스트 27건, 콘솔 `eslint`·테스트 191건·`npm run build` 모두 통과합니다.

## 함께 들어간 것

- **콘솔 의존성에서 `braces` 취약 경로를 끊었습니다.** `typescript-eslint` 를 8.42.0 에서 8.48.0 으로 올렸습니다. `npm audit` 가 이제 `found 0 vulnerabilities` 입니다. 개발 의존성만 바뀌므로 배포되는 산출물에는 영향이 없습니다.

## 범위

바꾼 것은 프로덕션 2파일(`web/src/pages/adminErrors.ts`, `AdminPage.tsx` 의 Alert 두 곳)과 테스트 1파일, 그리고 `web` 의 개발 의존성 하나입니다. **서버는 손대지 않았습니다** — `admin.go` 가 검증의 정본으로 남습니다. 사용자 쪽 안내 문구, 성공 토스트, 다른 섹션의 Alert 들은 각각 다른 핸들러의 코드 집합이라 이번에 포함하지 않았습니다. Go·API 변경과 데이터베이스 마이그레이션은 없습니다.
