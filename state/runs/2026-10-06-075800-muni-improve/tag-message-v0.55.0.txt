v0.55.0 — 제목이 같은 문서가 ZIP 의 어느 파일에 담길지 고정됩니다

문서를 읽는 쿼리의 정렬이 d.folder_id 와 d.title 뿐이라 폴더와 제목이 같은
문서들은 동률로 남았다. 편집기의 새 문서 버튼으로 만든 문서는 제목이 없고
createDocument 가 그런 문서 전부에 똑같은 '제목 없는 문서' 를 주므로, 이
동률은 엣지케이스가 아니라 상례다 — 아무도 이름을 바꾸지 않은 워크스페이스에서
모든 문서가 서로 동률이다. PostgreSQL 은 동률 행의 순서를 약속하지 않는다:
EXPLAIN (ANALYZE) 가 내놓은 정렬 키는 둘뿐이고 방식은 quicksort 로 안정 정렬이
아니며, 입력 순서는 행이 힙에서 읽힌 순서를 따라가고 그 순서는 행이 다시 써질
때마다 움직인다. 그 순서에 매달려 있던 것이 셋이다 — uniqueEntryName 에 누가
먼저 도착해 '제목 없는 문서.md' 를 갖고 누가 '제목 없는 문서 (2).md' 로
밀리는지, 목록.md 가 그 이름에 적어 주는 작성자와 수정일, 그리고 문서 2000건
경계 밖으로 어느 문서가 빠지는지다. 그래서 아무것도 편집하지 않은 워크스페이스를
두 번 내려받으면 같은 이름의 파일이 다른 문서를 담고 목록.md 의 작성자도 함께
바뀔 수 있었다. 이제 ORDER BY 가 d.id 로 끝난다 — ID 는 유일하므로 어떤 동률도
남지 않는다. 바뀐 것은 SQL 한 토큰이고, d.title 이 여전히 앞에 오므로 제목이
서로 다른 평범한 워크스페이스의 파일 이름과 순서는 한 글자도 바뀌지 않는다.
uniqueEntryName·entryKey·safeFilename, 휴지통 접두사, 2000건 경계, 목록.md 의
형식, v0.54.0 이 고정한 폴더 순회는 건드리지 않았고 md·html·txt 셋이 모두 같은
쿼리를 지난다. 제목을 주지 않고 문서 넷을 인증 API 로 만들어 이름 → 본문 대응을
기록하고 그 가운데 한 행만 title=title 로 다시 쓴 뒤 열두 번 더 내려받아 대응이
그대로인지 보는 검증을 넣었다 — 항목 이름의 집합은 어느 순서에서도 같아서 이름만
비교하면 고치기 전에도 통과하고, 동률 넷을 순서대로 전부 다시 쓰면 상대 순서가
보존되어 역시 통과한다. 고치기 전 실패는 d.id 한 토큰만 되돌려 직접 재현했다:
다섯 번 중 네 번 실패하고 한 번은 힙 순서가 우연히 유지되어 통과했으며, 토큰을
되돌려 놓고는 여덟 번 연속 통과했다. 전용 PostgreSQL 16 의 전체 Go 테스트
(723 PASS / 4 SKIP / 0 FAIL, HTTP API 는 SKIP 없음), 프런트 lint·테스트
(42파일 297건)·빌드, vet·포맷·placeholder·git diff --check, Go·Docker 빌드를
통과했다. 어느 쪽이 원래 이름을 갖는지는 문서 ID 순서로 정해지며 ID 는
gen_random_uuid() 이므로 만든 순서가 아니다 — 고정된 것은 같은 워크스페이스가
매번 같은 배치로 나온다는 것까지다. 제목이 똑같은 문서 둘 자체와 폴더 이름 중복
검사, 2000건 경계는 그대로 둔다. 2000건을 넘는 워크스페이스의 경계 동작과 브라우저
E2E 는 이번 준비에서 실행하지 않았다. 저장되는 값은 바뀌지 않으며, 마이그레이션과
설정 변경은 없다.
