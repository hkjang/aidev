# Postra v0.25.9 — IMAP 서버인지 확인한 뒤에 세션을 시작합니다

IMAP `Dial` 은 서버의 첫 줄에서 **`* PREAUTH` 와 `* BYE` 만 가려냈고, 그 밖의 모든 첫 줄은 그냥 세션을 시작했습니다.** 그래서 IMAP 을 말하지 않는 peer — 수신 포트를 POP3·SMTP 기본값으로 둔 계정, 엉뚱한 백엔드 앞에 놓인 프록시 — 가 `LOGIN` 이나 `SELECT` 까지 끌려가고, 운영자에게는 **비밀번호나 메일함이 잘못됐다고** 보고됐습니다. 더 나쁜 경우는 그 peer 가 명령에 그럴듯하게 대답할 때입니다: 동기화가 **빈 메일함으로 "성공"** 하고 끝났습니다 — 아무도 들여다보지 않는 결말입니다. 이번 릴리즈는 RFC 3501 §7.1.1 이 허용하는 세 가지 환영 메시지만 세션을 열게 합니다.

함께 Go 툴체인을 **1.26.9**, `golang.org/x/net` 을 **v0.60.0** 으로 올려 `net/http`·`html/template`·`crypto/tls`·`mime/multipart` 권고(GO-2026-6599 등)를 정리했습니다. **새 설정 키, 새 환경변수, DB 마이그레이션, 화면 변경은 없습니다.**

**정상적인 IMAP 서버에 붙는 설치는 아무 변화가 없습니다.** 달라지는 것은 수신 설정이 IMAP 서버를 가리키지 않는 계정이 **조용히 넘어가지 않는다**는 점입니다.

## 무엇이 어긋나 있었나

- `internal/adapters/imap/client.go` 의 `Dial` 은 환영 메시지를 읽은 뒤 `* PREAUTH`(로그인 생략)와 `* BYE`(거부) 두 분기만 두고, **나머지는 전부 통과**시켰습니다. `+OK POP3 ready`, `220 ... ESMTP Postfix`, `* CAPABILITY IMAP4rev1`, 태그 붙은 완료 응답이 모두 "환영 메시지" 취급을 받았습니다.
- 그래서 실패 지점이 뒤로 밀렸습니다. 침묵하는 peer 라면 **연결 예산이 아니라 명령 예산**을 다 쓴 뒤에, 그것도 `로그인`·`메일함 선택` 단계로 실패했습니다 — 운영자를 비밀번호와 메일함 권한 쪽으로 보내는, 사실과 어긋난 안내입니다.
- 명령에 형식만 맞게 대답하는 peer 라면 **동기화가 성공으로 끝났습니다.** 메일 0통은 "새 메일이 없다" 와 구별되지 않으므로, 잘못된 포트 설정이 몇 달이고 드러나지 않을 수 있었습니다.
- 발신·POP3 쪽에는 없던 구멍입니다. POP3 어댑터는 처음부터 `readGreeting` 에서 자기 `+OK` 를 요구해 왔습니다. **수신 어댑터 둘 사이의 비대칭**이었습니다.

## 무엇이 바뀌었나

`Dial` 이 환영 메시지를 `isGreeting` 으로 가늠한 뒤에만 세션을 엽니다:

- **허용되는 것은 RFC 3501 §7.1.1 의 세 가지뿐입니다** — 태그 없는 `OK`, `PREAUTH`, `BYE`. 조건어는 ABNF 의 리터럴과 같게 **대소문자를 구분하지 않고** 맞춥니다. 소문자로 인사하는 서버는 이상하지만 적법하므로 거부하지 않습니다.
- **`PREAUTH` 와 `BYE` 분기는 지금도 대소문자를 구분합니다.** 그 두 곳을 함께 넓히면 *어떤 세션이 `LOGIN` 을 생략하고 어떤 세션이 거부로 집계되는지*가 달라지기 때문입니다. 이번 변경은 "세션을 열어도 되는가" 라는 문턱만 세웁니다.
- 환영 문구는 없어도 됩니다 — `* OK` 한 줄도 통과합니다. 이 검사가 막는 것은 **다른 프로토콜을 말하는 peer** 이지, 말이 짧은 서버가 아닙니다.
- 거부는 `Stage: domain.StageGreeting` 으로 기록되어 진단에 **`서버 환영 메시지 수신`** 단계로 적힙니다(이미 등록된 레이블입니다). `Class` 는 `domain.ClassifyInbound` 의 판정(`other`)이라 `retryableInbound` 는 전과 같이 재시도 대상으로 보고, 동기화는 기존 3회 시도를 모두 쓴 뒤 **실패**로 끝납니다.
- **오류에는 줄의 길이만 들어갑니다.** 진단은 저장되고 화면에 보이므로 서버가 보낸 바이트는 한 글자도 싣지 않습니다(`imap greeting: N bytes that are not an IMAP greeting (no untagged OK, PREAUTH or BYE)`). 어댑터·애플리케이션 양쪽 테스트가 `POP3`·`ESMTP`·`CAPABILITY`·응답 문구가 새지 않는지 단언합니다.

새 단계·분류 레이블이 없으므로(`greeting`·`other` 둘 다 기등록) 생성되는 API 계약, 브라우저 화면, `internal/transport/spa/assets` 는 손대지 않았습니다.

**일부러 묶지 않은 것 하나를 밝혀 둡니다.** `isGreeting` 의 **낱말 경계 판정**(`* OKAY` 는 `* OK` 가 아니다 — 조건어가 줄 끝이거나 뒤에 공백이 와야 한다)은 테스트가 보증하지 않습니다. 그 줄을 `if true` 로 바꿔도 현재 사례들은 전부 통과하므로, 깨진다고 적는 것은 거짓 주장이 됩니다.

## 의존성

- Go 툴체인 **1.26.6 → 1.26.9** (`go.mod` 의 `toolchain`, `Dockerfile`, `ci.yml`·`contracts.yml`·`release.yml` 의 `GO_VERSION` 을 함께), `go.mod` 의 언어 버전 `1.25.0 → 1.26.0`.
- `golang.org/x/net` **v0.57.0 → v0.60.0**, `golang.org/x/crypto` v0.54.0 → v0.57.0, `golang.org/x/term` v0.45.0 → v0.46.0, 간접 의존성 `golang.org/x/sync`·`sys`·`text` 동반 갱신.
- 애플리케이션 코드는 이 갱신으로 한 줄도 바뀌지 않았습니다.

## 검증

- **변이 검증으로 인과를 고정했습니다.** 세 번 모두 예상한 테스트만 반응했습니다:
  - 환영 메시지 가드를 끄면 → 어댑터 테스트의 `pop3 greeting`·`smtp greeting`·`untagged capability`·`tagged response` 네 하위 테스트가 `Dial accepted "+OK POP3 ready" as a greeting and asked for ["LOGIN" "SELECT"]` 로 실패하고, 애플리케이션 테스트는 `sync status = succeeded, want failed — a server that never greeted as IMAP was synced as if empty` 로 실패합니다. **이 릴리즈가 막는 결말이 바로 그 문장입니다.**
  - 조건어 비교를 대소문자 구분으로 되돌리면 → `ok lower case` **하나만** 실패합니다(적법한 소문자 인사를 거부).
  - 낱말 경계 판정을 `if true` 로 바꾸면 → 아무 테스트도 실패하지 않습니다. 위에 그대로 적어 두었습니다.
  - 전부 원복하고 잔재 0건을 확인했습니다(`strings.EqualFold` 1건, 변이 흔적 0건).
- 테스트는 손으로 만든 대역 없이 루프백 `net.Listen` 스크립트 서버와 실제 `Dialer{}.Dial`·실제 `DialOptions` 로 돕니다. 애플리케이션 쪽 픽스처(`inFrameServer`)는 **어떤 첫 줄로 인사했든 태그 명령에 정상 응답하고 빈 INBOX 를 보고**하므로, 두 하위 테스트의 유일한 차이는 환영 메시지 한 줄입니다 — 결과 차이를 설명할 다른 변수가 없습니다.
- `go test -race -count=1 -timeout=900s ./...` 25개 패키지 실패 0건
- **플레이크 확인**: `go test -race -count=3` 로 `./internal/adapters/imap/`·`./internal/application/` 통과, 플레이크 0건
- `go build ./...`, `go vet ./...`, `make lint-format` 무지적, `go mod tidy` 무변경, canonical API 계약 검사(`postra-contracts -check`) 종료 코드 0
- `make lint-security` — 141개 파일 지적 0건
- `govulncheck ./...`(CI 와 같은 v1.6.0, Go 1.26.9) — 호출되는 취약점 0건
- `make frontend-check` 통과 후 `internal/transport/spa/assets` 변화 없음 — 태그에 담긴 `/app` 번들이 최신입니다(릴리즈 워크플로가 같은 검사를 다시 합니다)
- 외부 PostgreSQL(`POSTRA_TEST_PG`)과 브라우저 e2e 는 돌리지 않았습니다 — 프런트엔드가 바뀌지 않은 Go 전용 변경이라 범위 밖입니다.

## 업그레이드 및 호환성 주의사항

DB 마이그레이션, 새 설정 키, 새 필수 환경변수가 없습니다. 실행 파일 또는 컨테이너 이미지를 교체한 뒤 재시작하면 끝이고, 되돌릴 때도 v0.25.8 로 그대로 내려갈 수 있습니다.

- **지금까지 조용히 "성공" 하던 IMAP 계정이 있다면 이번 업그레이드 후 실패로 바뀝니다.** 그것이 이 릴리즈의 의도입니다: 그 계정은 메일을 가져오고 있던 것이 아니라 IMAP 이 아닌 포트에 붙어 빈 메일함을 보고하고 있었습니다. `서버 환영 메시지 수신` 단계로 멈춘 계정이 보이면 **수신 호스트·포트·프로토콜(IMAP 143/993)을 먼저 확인**하세요 — POP3 포트(110/995)나 SMTP 포트(25/465/587)가 IMAP 계정에 들어가 있는 경우가 대표적입니다.
- 993·995 포트에 보안 모드가 TLS 가 아닌 채로 들어간 계정에는 기존 안내(`이 포트는 접속 직후 TLS를 요구합니다`)가 그대로 먼저 나옵니다.
- **적법한 IMAP 서버가 거부되는 일은 없습니다.** 태그 없는 `OK`/`PREAUTH`/`BYE` 는 모두 통과하고, 대소문자도 가리지 않으며, 환영 문구가 비어 있어도 통과합니다. 그런데도 거부된다면 그 peer 는 RFC 3501 의 환영 메시지를 보내지 않는 것이므로 서버·중간 장비(투명 프록시, 메일 검사 장비) 쪽을 보세요.
- 이 거부를 **대시보드나 알림에서 단계 문자열로 잡아 두었다면** `서버 환영 메시지 수신` 이 새로 등장할 수 있습니다. `domain.SyncDiagnostic` 에 필드가 추가되지 않아 API 응답의 모양은 그대로입니다.
- v0.25.8 의 기본값 implicit TLS 인증서 검증 보증, v0.25.7 의 `STARTTLS 전환` 단계 진단, v0.25.5 의 거부된 `LIST` 크기 선별 경고, v0.25.4 의 크기 제한 없는 계정 본문 잘림 수정, v0.25.3 의 POP3 `fetch` 진단 교정, v0.25.2 의 OpenTelemetry v1.45.0, v0.25.1 의 "계정당 인바운드 연결 하나"와 `mail.idle_enabled`, v0.25.0 의 동기화 실패 진단은 바뀌지 않았습니다.
