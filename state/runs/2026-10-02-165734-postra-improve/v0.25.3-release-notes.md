# Postra v0.25.3 — POP3 본문 수신 진단 교정

POP3 메일 본문 수신(`fetch`)이 멈출 때, 진단이 **"제한 60초" 한 마디만** 남기고 실제로 얼마를 기다렸는지는 적지 않았습니다. v0.25.0 진단의 핵심인 "서버가 느린 것인가, 연결이 밖에서 끊긴 것인가" 구분이 **본문 정지가 가장 잘 나는 그 단계에서만** 사라져 있었습니다. 덤으로 `TOP` 으로 멈춘 실패가 `RETR` 로 보고됐습니다. 이번 릴리즈는 그 두 가지를 고칩니다. 설정 키, 환경변수, DB 마이그레이션, 화면 변경은 **없습니다**.

## 무엇이 비어 있었나

- 인바운드 어댑터는 실패를 `WrapInbound(단계, 명령, 오류, 경과, 제한)` 으로 감쌉니다. 저장소의 8개 호출 지점 중 POP3 의 `Retrieve`(RETR)와 `Top`(TOP) **둘만** 경과 시간을 `0` 으로 하드코딩하고 있었습니다.
- 진단 문장을 만드는 `syncTiming` 은 경과가 `0` 이면 **측정값이 없다**는 뜻으로 보고 `제한 60.0초` 만 출력합니다. 그래서 POP3 본문 수신 실패에는 다음 두 문장이 **둘 다 나올 수 없었습니다**:
  - `제한 60.0초 중 60.0초 경과` — 그 단계가 자기 제한 시간을 다 썼다. 서버가 실제로 응답하지 않은 것이다.
  - `제한 60.0초 중 0.9초에 중단(이 단계의 제한 시간에는 이르지 않았습니다)` — 제한 시간은 남아 있었는데 중단됐다. 시간 예산이 **다른 곳**에서 왔다(작업 취소, 짧은 연결 제한 시간, 프록시의 유휴 종료).
- 영향은 조사 방향입니다. 큰 첨부로 서버가 느린 경우와 중간 장비가 연결을 끊은 경우가 화면에서 똑같이 보였고, [동기화 실패 진단 문서](../SYNC_DIAGNOSTICS.md)가 `fetch` + `timeout` 을 "그 단계 제한 시간 소진" 으로 읽으라고 안내하는데 정작 그 판단에 필요한 숫자가 없었습니다.
- 두 번째 결함: `Top` 은 실패에 명령 이름을 `"RETR"` 로 적었습니다. 미리보기 경로(TOP)에서 멈춘 동기화가 본문 받기(RETR)에서 멈춘 것으로 보고되어, 메일 최대 크기나 첨부를 엉뚱하게 의심하게 만들었습니다.

## 고친 내용

- 명령 제한 시간을 설정하는 주체가 `retrBody` 이므로 **그 호출 직전에 측정을 시작**해(`bodyStart := time.Now()`) 실패 시 `time.Since(bodyStart)` 를 넘깁니다. 이제 `fetch` 단계도 다른 7개 지점과 같은 정보를 남깁니다.
- `Top` 의 실패는 `TOP` 으로 보고합니다.
- 프로덕션 변경은 `internal/adapters/pop3/client.go` **한 파일, 5줄**(주석 3줄 포함)입니다. 재시도 정책, 제한 시간 기본값, 저장 스키마, API 응답 형태는 건드리지 않았습니다.

## 검증

- 되돌려 실패를 먼저 확인했습니다: 수정 전 `Elapsed = 0s`(RETR·TOP 모두)와 `Command = "RETR"`(TOP). 각 절반만 되돌리면 **자기 하위 테스트만, 자기 단언에서만** 실패합니다.
- 테스트는 손으로 만든 대역을 쓰지 않습니다. `net.Listen` 루프백 TCP 서버가 `RETR`/`TOP` 에 `+OK` 만 답하고 본문과 종결 `.` 을 보내지 않으며, 실제 `Dialer` 와 실제 `CommandTimeoutSec: 1` 로 구동합니다. 서버가 받은 와이어 문자열(`RETR 7`, `TOP 7 4`)까지 단언합니다.
- `go test -race -count=3 ./internal/adapters/pop3/` 통과, 전체 `go test -race ./...` 25개 패키지 실패 0건
- `go build ./...`, `go vet ./...`, `gofmt` 무지적, `go mod tidy` 무변경, canonical API 계약 검사(`postra-contracts -check`)
- `govulncheck ./...` — 호출 경로 기준 취약점 0건, `gosec -severity medium` — 141개 파일 지적 0건
- 브라우저: `npm run typecheck`, `npm test` 50개 파일 426개 테스트 통과, `npm audit --omit=dev --audit-level=high` 0건
- `npm run build` 후 `internal/transport/spa/assets` 변화 없음 — 태그에 담긴 `/app` 번들이 최신입니다(릴리즈 워크플로가 같은 검사를 다시 합니다)

## 업그레이드 및 호환성 주의사항

DB 마이그레이션, 새 설정 키, 새 필수 환경변수가 없습니다. 실행 파일 또는 컨테이너 이미지를 교체한 뒤 재시작하면 끝입니다. 되돌릴 때도 v0.25.2 로 그대로 내려갈 수 있습니다.

- 바뀌는 것은 **실패한 동기화 작업에 남는 진단 문장**뿐입니다. 성공 경로, 수집 결과, 저장된 메일은 영향이 없습니다.
- 이미 저장된 과거 작업의 진단은 그대로입니다. 새 문장은 이 버전 이후에 실패한 작업부터 나타납니다.
- POP3 본문 수신 실패를 로그·알림 문구로 자동 분류하고 있다면, `fetch` 단계 문장이 `제한 60.0초` 에서 `제한 60.0초 중 ...` 형태로 바뀌고 명령 이름에 `TOP` 이 새로 나타날 수 있습니다.
- v0.25.2 의 OpenTelemetry v1.45.0, v0.25.1 의 "계정당 인바운드 연결 하나"와 `mail.idle_enabled`, v0.25.0 의 동기화 실패 진단은 바뀌지 않았습니다.
