# Ptium 1.69.58

## 바뀐 동작은 없습니다 — 웹을 짓는 도구 두 개를 올렸습니다

마크다운 리더도, 덱도, 서버도 이번 판에서는 한 줄도 바뀌지 않았습니다. 바뀐 것은
`web/package.json` 과 `web/package-lock.json` 두 파일이고, 그 안에서 바뀐 것은 웹 화면을
**짓고 시험하는 동안에만** 쓰는 꾸러미 두 개의 버전입니다.

그래도 판을 새로 내는 이유는 CI 의 검사 한 단계에 있습니다. `npm audit --audit-level=high`
는 npm 이 들고 있는 **보안 권고 목록을 그 자리에서 조회**합니다. 그 목록은 이 저장소가 한
글자도 바뀌지 않은 날에도 늘어납니다. 그래서 문서 한 파일만 고친 변경이 코드와 아무 상관
없이 두 번 떨어졌습니다 — 검사가 가리킨 것은 그 변경이 아니라, 꾸러미 두 개에 그날 새로
붙은 권고였습니다.

~~~
막고 있던 권고:
  source-map-js  1.2.1 → 1.2.2   high      GHSA-68fv-2mgg-jv7q
  tinypool       1.1.1 → 2.2.0   critical  GHSA-5gmw-xhrv-c9v3 · GHSA-85c8-ppgw-ccpr

이전:  npm audit --audit-level=high   → 종료 코드 1  (1 moderate, 1 high, 2 critical)
지금:  npm audit --audit-level=high   → 종료 코드 0  (2 moderate)
~~~

두 꾸러미가 하는 일은 이렇습니다. `source-map-js` 는 **소스맵** — 줄여 쓴 자바스크립트를
원래 쓴 줄로 되짚는 지도 — 을 읽고 쓰는 꾸러미이고, 빌드 도구(`vite` → `postcss`)가
데려옵니다. `tinypool` 은 시험 러너(`vitest`)가 시험 파일들을 여러 **작업자**에게 나눠
돌릴 때 쓰는 풀입니다. 둘 다 짓고 시험하는 쪽에만 있고, **나가는 이미지 안에서 도는 코드가
아닙니다** — 웹 화면은 미리 지어 정적 파일로 담고, 그 파일을 Go 서버가 내보냅니다. 그래서
이 판으로 올려도 쓰는 사람이 보는 화면과 동작은 이전 판과 같습니다.

앞의 하나는 락파일만 다시 쓰면 끝났습니다. `postcss` 가 `^1.2.1` 로 선언해 두었고 고쳐진
1.2.2 가 그 범위 안이라, `npm audit fix` 가 선언을 건드리지 않고 락파일만 고쳤습니다.

뒤의 하나는 **고쳐진 1.x 가 없었습니다**. 권고가 `2.1.1` 이하 전부를 덮고, `vitest` 3.2.7
은 `^1.1.1` 로 선언합니다 — 선언을 지키면서 안전한 버전이 하나도 없다는 뜻입니다. 그래서
`package.json` 에 `overrides` 한 블록을 넣어 2.2.0 으로 넘겼습니다. 선언 범위 밖의 버전을
강제하는 것은 **보통은 쓸 도구가 아닙니다**: 꾸러미가 "나는 이 범위에서만 돈다"고 적어 둔
말을 거짓으로 만드는 일이기 때문입니다. 여기서만 받아들인 이유는 2.x 메이저가 API 변경이
아니라 **Node 하한을 올린 것**이라는 데 있습니다 — 1.1.1 이 `^18 || >=20` 을 요구한 자리에
2.2.0 이 `^20 || >=22` 를 요구하고, CI 의 node 22 와 Dockerfile 의 `node:22-alpine` 이
둘 다 그 하한을 넘습니다.

그 판단은 혼자 둘 말이 아니라 시험으로 확인할 수 있는 말입니다. `tinypool` 은 **시험 파일
전부가 지나가는 작업자 풀**이므로, API 가 바뀌었다면 시험이 돌다 말았을 것입니다. 48개
파일·271개 시험이 1.1.1 때와 **같은 수로** 통과했고, `node` 환경 36개와 `jsdom` 환경 12개
양쪽이 실제로 돌았습니다.

## 그대로인 것

`.github/workflows/ci.yml` 은 **한 글자도 바뀌지 않았습니다**. 검사를 느슨하게 해서 녹색을
만드는 길 — `--omit=dev`, `--audit-level=critical`, `|| true`, `continue-on-error` — 은
어느 것도 쓰지 않았습니다. 막던 권고는 꾸러미를 올려서 치웠습니다.

`@vitest/mocker` 의 권고 하나는 **남겨 두었습니다**. moderate 라서 이 검사의 문턱(high)
아래에 있고, 치우려면 `vitest` 를 5 로 올려야 하는데 그것은 시험 설정을 다시 쓰는 일입니다.
문턱 아래라서 조용히 넘어간 것이 아니라, 따로 결정할 문제로 두었습니다.

더 깔끔한 길도 실제로 시도했습니다. `vitest` 를 4.1.11 로 올리면 `tinypool` 의존이 아예
없어지고 중첩된 `vite` 사본까지 접힙니다. 막힌 것은 이 저장소가 아니라 도구였습니다: node
22 가 싣는 npm 10.9.8 — CI 가 돌리는 바로 그 npm — 이 vitest 4.x 의 선택적 peer 그래프를
풀다 크래시해서, CI 가 읽어야 할 락파일을 만들 수가 없었습니다. 그래서 이 판은 막던 둘만
치우고, 도구 쪽 문제는 다음 회차로 넘깁니다.

Go 서버, API 스키마, 데이터베이스 스키마, 덱 문법, 마크다운 리더는 모두 그대로입니다.
`=` 로 밑줄 그은 제목(1.69.51), `#` 뒤에 공백을 요구하는 규칙(1.69.53), 닫아 쓴 제목의
뒤쪽 `#` 을 떼는 동작(1.69.54), 구분선(1.69.55), YAML 머리말(1.69.56), 인용 마커
(1.69.57)는 모두 1.69.57 과 같이 동작합니다. 목록 안의 인용(`- > 인용`)이 아직
`- \> 인용` 인 것도 1.69.57 과 같습니다 — 이번 판에서 다루지 않았습니다.

## 지키는 장치

이번 판은 새 동작이 없어서 **새 단위 시험도 없습니다**. 그 자리의 증거는 검사의 **종료
코드**이고, 세 단계로 고정해 두었습니다. 고치기 전 `npm ci` 뒤의 검사는 `source-map-js`
1.2.1 과 `tinypool` 1.1.1 을 들어 `종료 코드 1` 이었습니다. `npm audit fix` 만 돌린 중간
단계는 `tinypool` 때문에 여전히 `종료 코드 1` 이었습니다. `overrides` 를 넣은 뒤 같은
명령이 `2 moderate` 만 남기고 `종료 코드 0` 으로 뒤집혔습니다 — 어느 한 걸음이 무엇을
치웠는지가 종료 코드로 갈립니다.

릴리즈 준비에서 `go test -race ./...`(26개 패키지 전부 통과, `golden`·`korean` 포함),
`go vet ./...`, `internal/docs` 의 `gofmt`, 웹의 `npm ci`·`npm run typecheck`·`npm run
build`·`npm test`(48개 파일, 271개 시험), `npm audit --audit-level=high`(종료 코드 0),
버전 일치 검사를 통과했습니다. 오프라인 이미지의 최초 실행과 업그레이드는 빌드 스크립트
검사 대상이고, 컨테이너 안의 `npm ci` 가 이 락파일로 도는 것도 그 빌드에서 함께 확인됩니다.
DB 단위 시험은 `PTIUM_TEST_DSN` 이 없는 환경에서 건너뜁니다.

## 설치와 되돌리기

기존 오프라인 설치 절차를 따라 1.69.58 이미지와 함께 제공되는 매니페스트를 사용합니다.
이번 변경에 새 설정이나 데이터베이스 스키마 변경은 없습니다.

이번 판은 쓰는 사람에게 보이는 변화가 없으므로, 시험 환경에서 확인할 것은 **이전 판과
같은지**입니다 — 로그인, 덱 하나 열기, `.md` 하나 올려 각 장의 요점 보기, 내보내기 한 번을
해 보고 이전과 같은 결과가 나오는지 봅니다. 다른 것이 한 건이라도 보이면 확대를 멈추고
이전 1.69.57 이미지와 해당 버전의 배포 설정으로 되돌립니다. 저장된 데이터는 이 판이
건드리지 않으므로 되돌림에 추가 절차가 없습니다.
