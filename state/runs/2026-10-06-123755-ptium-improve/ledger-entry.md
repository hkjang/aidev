- 선택: CI 의 `npm audit --audit-level=high` 가 막는 권고를 락파일/overrides 범위에서 해소해 PR #44 를 녹색으로 돌리기 (가치 4 / 위험 2 / 작업량 S)
- 결과: 성공
- 요약: 이 샌드박스는 `npm` 이 돌아가서 정찰이 못 한 0단계를 실제로 했고, 걸린 권고는 정찰의 추측(중첩 vite 7.3.6)과 **달랐다** — vite 권고는 하나도 없었다. 막던 둘은 `source-map-js` 1.2.1(high, GHSA-68fv-2mgg-jv7q)과 `tinypool` 1.1.1(critical, GHSA-5gmw-xhrv-c9v3·GHSA-85c8-ppgw-ccpr)이다. 앞은 `vite 8.2.0 → postcss 8.5.25` 가 `^1.2.1` 로 선언하고 패치 1.2.2 가 그 범위 안이라 `npm audit fix`(--force 없이)가 락파일만 고쳐 끝났다. 뒤는 패치된 1.x 가 없어(권고가 `<=2.1.1` 전부) vitest 3.2.7 의 선언 `^1.1.1` 안에 안전한 버전이 없으므로 `package.json` 에 `overrides: { "tinypool": "^2.1.2" }` 한 블록을 넣어 2.2.0 으로 넘겼다 — 2.x 메이저가 Node 하한만 올린 것(`^18||>=20` → `^20||>=22`, CI 의 node 22·Dockerfile 의 node:22-alpine 모두 충족)이고 API 변경이 아니라는 증거로, **tinypool 은 vitest 가 모든 테스트 파일을 돌리는 워커 풀**인데 48파일·271테스트가 1.1.1 때와 같은 수로 통과했다(node 36 + jsdom 12 양쪽 실제 실행). `vitest.config.ts` 는 건드릴 필요가 없었다 — 프로덕션 2파일. 검증: `npm ci` 뒤 `npm audit --audit-level=high` **exit 0**, `npm run typecheck`·`npm run build`·`npm test`(48/271) 통과, `go test -race ./...`·`go vet ./...`·`go test -count=1 ./internal/docs` 통과, `docker build --build-arg VERSION=ci` 통과(web 스테이지를 `--no-cache-filter web-build` 로 강제 재빌드해 컨테이너 안 `npm ci` 가 이 락파일로 돌아 "2 moderate" 만 보고하는 것을 확인). `git diff --stat` 으로 `.github/` 와 `server/` 변경 0 확인 — ci.yml 은 한 글자도 안 바꿨고 `--omit=dev`·`--audit-level=critical`·`|| true`·`continue-on-error` 는 어느 것도 넣지 않았다. 커밋 0f06b6d.
- 실패 재현: 이 회차는 의존성 과제라 새 단위 테스트가 아니라 **게이트의 exit 코드**가 증거다(과제서가 지정한 증거 형태). 고치기 전 `npm ci` 뒤 `npm audit --audit-level=high` → `source-map-js 1.0.0 - 1.2.1 Severity: high` + `tinypool <=2.1.1 Severity: critical` / `4 vulnerabilities (1 moderate, 1 high, 2 critical)` / `EXIT CODE: 1`. `npm audit fix` 만 돌린 중간 단계도 `tinypool` 때문에 여전히 `EXIT CODE: 1` 이었고, overrides 를 넣은 뒤 같은 명령이 `2 moderate severity vulnerabilities` / `EXIT CODE: 0` 으로 뒤집혔다 — 세 단계 exit 코드로 인과를 고정했다.
- 보류 아이디어: vitest 를 4.1.11 로 올려 tinypool 의존을 아예 없애고 중첩 vite 사본까지 접기 — 시도했고 **npm 10.9.8(CI 의 node 22 가 싣는 바로 그 npm)이 vitest 4.x 의 선택적 peer 그래프에서 크래시**해 락파일 생성 자체가 불가능했다, 다음 회차는 이 npm 버그부터 (3/3/M) · CI 의 web 단계에 vitest 실행을 추가하기 — CI 가 녹색으로 돌아온 뒤 별도 회차로 (3/3/S) · 목록 안 인용(`- > 인용`)의 `>` 도 떼기 — 차선 후보였으나 1순위가 실제로 걸려 있어 손대지 않았다 (2/2/S) · 외곽 파이프 없는 GFM 표가 요점으로 쏟아지는 것 — 앞보기 계약 선행 (3/3/M) · 마크다운 setext h2(`---`)도 제목으로 읽기 — case 순서 설계 필요 (2/3/S)
- 과제서: 채택 — 절차(0단계로 사실 확보 → 1단계 `npm audit fix` → 2단계 경로별 분기)와 "패치된 버전이 선언 범위 밖이면 overrides 로 거짓 선언을 만들지 말고 도구를 올려라" 는 원칙을 그대로 따랐다. 다만 과제서의 **진단은 틀렸다**: 걸린 것은 vite 가 아니라 source-map-js·tinypool 이었고(vite 권고 0건), 그래서 "중첩 vite 7.3.6" 분기는 타지 않았다. 또 과제서가 권한 "선언 범위 밖이면 vitest 를 올린다" 는 길은 실제로 시도했으나 npm 자체 버그로 막혀, 같은 원칙의 예외 조건(2.x 메이저가 Node 하한 변경뿐이고 워커 풀 전체가 테스트로 실증됨)을 근거로 overrides 를 택했고 그 이유를 커밋 메시지에 남겼다.
