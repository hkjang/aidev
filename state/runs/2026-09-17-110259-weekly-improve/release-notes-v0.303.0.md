# v0.303.0 — 마이그레이션 시험이 데이터베이스의 과거가 아니라 이 빌드를 봅니다

제품의 코드는 v0.302.0 과 같습니다. 이번 판이 고치는 것은 **릴리즈를 두 번 멈춘 시험** 하나입니다.

`TestDatabaseMigrationsAndSecretRotation` 은 설정된 데이터베이스의 `schema_migrations` 에서 `max(version)` 을 읽어 내장 마이그레이션 파일 수(30)와 견줬습니다. 그 표는 **그 데이터베이스에 지금까지 적용된 모든 것의 역사**라, 여러 브랜치가 한 시험 DB 를 나눠 쓰는 기계에서는 이 트리에 없는 다른 브랜치의 031~033 이 남아 `got=33 want=30` 으로 실패했습니다 — 이 빌드의 서른 개는 모두 적용돼 있었고 맞았는데도. 로컬의 `go test ./...` 가 같은 이유로 두 번 멈췄고, 검증이 멈추면 릴리즈도 멈춥니다.

## 자기 데이터베이스에서 묻습니다

- 시험이 묻는 것은 "**이 빌드의** 마이그레이션이 **빈** 데이터베이스에 모두 적용되고 기록되는가" 입니다. 그래서 하네스가 이미 만들어 주는 자기만의 스크래치 DB(`createScratchDatabase`, 템플릿 복사 0.4초)에서 묻습니다. 다른 브랜치·다른 회차가 그 데이터베이스에 무엇을 남겼든 이 시험의 답은 달라지지 않습니다.
- 가장 큰 번호 하나가 아니라 **기록된 번호의 집합 전체**를 내장 파일의 번호와 맞춥니다(`migrationVersions` 와 `slices.Equal`). 마지막 파일만 기록되고 가운데 하나가 빠져도 최댓값은 같기 때문이고, 번호에 빈 자리가 생겨도 견딥니다.
- 같은 DB 를 되풀이해 쓰던 때의 `clone-test` 정리 DELETE 두 줄은 더는 할 일이 없어 지웠습니다.
- 워크플로와 검증 명령은 **느슨하게 하지 않았습니다.** GitHub 의 release.yaml 은 DB 가 없어 이 시험을 건너뛰므로 손댈 것이 없었고 손대지 않았습니다.

## 검증

고치기 전 파일을 되돌려 공유 DB 에서 `got=33 want=30` 실패를 먼저 확인했고, 고친 뒤 그 시험이 통과합니다(0.67s). 실제 PostgreSQL 위에서 전체 Go 테스트와 `go vet`·`gofmt`, release.yaml 과 같은 DB 없는 조건(`env -u WEEKLY_TEST_POSTGRES_DSN`, TZ=UTC)의 전체 Go 테스트, 가드·OpenAPI·모달·버전 검사를 통과했습니다.

## 업그레이드

마이그레이션도, 새 환경변수도, 응답 모양의 변경도 없습니다. 바뀐 파일은 시험 하나(`internal/app/db_integration_test.go`)뿐이라 제품의 동작은 v0.302.0 과 같습니다. 기존과 같이 PostgreSQL 을 백업한 뒤 v0.303.0 이미지를 올리면 됩니다.
