release: v0.77.17

MCP 도구 호출의 캐시 키를 만드는 과정이 호출자의 ACL 주체 목록을 제자리 정렬하던 것을
고칩니다. internal/mcp/cache.go:32 이 principals := principalACLs(p) 로 받은 슬라이스를
그대로 sort.Strings 했고, principalACLs(args.go:170) 는 p.ACLPrincipals 가 비어 있지
않으면 그 슬라이스를 그대로 넘기며 search.WithUnrestricted(service.go:230-233) 도 제한
있는 역할에서는 받은 슬라이스를 그대로 돌려줍니다. 그래서 키 하나를 계산하는 동작이
호출자의 auth.Principal.ACLPrincipals 를 재배열했고, 같은 요청에서 그 뒤에 주체 목록을
읽는 구간은 바뀐 순서를 봤습니다. 같은 함수의 바로 다음 줄이 AllowedRepositories 를
복사한 뒤 정렬하는 비대칭이 근거였으므로 같은 관용구로 복사한 뒤 정렬하게 한 줄
고쳤고, sort.Strings 는 그대로 뒀습니다 — 순서 무관 키가 본래 목적입니다. 잘못된
응답이 나가던 사례는 확인되지 않았습니다. ACL 판정과 캐시 키는 모두 순서에 무관한
집합 연산이므로 이 릴리스는 "키를 계산하는 함수가 입력을 변경하지 않는다"는 계약을
되돌리는 수정이며, 접근 판정과 캐시 키 값 자체는 바뀌지 않습니다. 실제 sqlite
fixture 의 실제 mcp.Server 와 실제 auth.Principal 로 s.cacheKey 를 호출하는 회귀
시험을 제한·무제한 두 분기 표로 두었고, 수정 전 코드에서 제한 분기만 실패함을 먼저
확인했습니다. search.WithUnrestricted 가 입력 슬라이스를 그대로 돌려주는 성질 자체는
호출자 세 곳을 함께 검토해야 하는 변경이라 건드리지 않았습니다. 마이그레이션과
재색인은 필요하지 않습니다.
