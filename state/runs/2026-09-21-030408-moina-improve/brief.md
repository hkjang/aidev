- 과제: 미디어 multipart 본문 한도 초과를 400 대신 413 media_too_large로 분류 (가치 3 / 위험 1 / 작업량 S)
- 왜: `backend/internal/httpapi/social.go:uploadMedia`는 파일 한도 초과에는 413을 내지만 `MaxUploadBytes + 1 MiB` 본문 제한을 넘으면 `ParseMultipartForm`의 모든 오류를 400 invalid_media로 처리하므로 더 큰 파일에서 오히려 잘못된 형식 안내가 나온다. 크기 초과만 구분하면 클라이언트가 크기를 줄여 재시도할 원인을 정확하게 알 수 있고 기존 요청 크기 제한은 그대로 유지된다.
- 수용 기준: 1) 유효한 multipart의 file 바이트가 본문 상한(`MaxUploadBytes + (1<<20)`)보다 큰 요청은 413과 error.code=`media_too_large`, 기존 메시지 `파일이 비어 있거나 업로드 한도를 넘었습니다`를 반환한다(ContentLength=-1인 요청도 포함). 2) 파일 한도만 조금 초과한 요청과 빈 파일은 기존 413을 유지하고, 상한 아래의 깨진 multipart는 기존 400 invalid_media, file 필드가 없는 정상 multipart는 400 file_required를 유지한다. 3) 실제 `multipart.Writer`와 `httptest`로 `uploadMedia`를 실행하는 회귀 테스트가 수정 전 큰 본문 케이스에서 400/413 불일치로 실패하고 수정 후 통과해야 한다. 테스트는 DB DSN 없이 실행되어야 하며 에러 문자열 비교나 Content-Length만 검사하는 구현에 의존하지 않아야 한다.
- 건드릴 파일: `backend/internal/httpapi/social.go:uploadMedia` — ParseMultipartForm 오류 분기에 `var maxBytes *http.MaxBytesError`와 `errors.As(err, &maxBytes)`로 크기 초과만 413으로 분리한다(같은 저장소 `analytics.go`의 Momento 프록시 오류 처리에 선례 있음). `backend/internal/httpapi/httpapi_test.go` — 기존 미디어 테스트 옆에 `TestUploadMediaRejectsOversizedMultipart`와 오류 분류 회귀 케이스 추가(필요하면 새 `media_upload_test.go`로 분리 가능). `api/openapi.yaml:/api/v1/media.post` — 설명에 파일/본문 크기 초과가 413임을 짧게 명시; 기존 response를 삭제하지 않는다.
- 검증 명령: 저장소 루트에서 `cd backend && go test -race ./internal/httpapi -run 'TestUploadMediaRejectsOversizedMultipart|TestDetectMediaType|TestSafeFilename|TestUnsupportedMediaMessage' -count=1`; `cd backend && go test -race ./... && go vet ./...`; 루트에서 `make fmt && make check`. 첫 명령의 새 테스트 이름은 위 이름으로 구현한다. 정찰에서는 `cd backend && go test -race ./...`, `make check`, `make fmt` exit 0을 확인했다. MOINA_TEST_POSTGRES_DSN이 unset이므로 PostgreSQL integration은 skip이며 DB 포함 성공으로 보고하지 말 것.
- 위험과 피할 것: 본문 허용량 +1 MiB와 ParseMultipartForm(64<<10), 파일 크기 한도, MIME·safeFilename·저장·인증 정책을 바꾸지 않는다. `multipart.ErrMessageTooLarge` 등 다른 파싱 오류를 무조건 413으로 바꾸거나 문자열 비교를 쓰지 않는다. auth·migrations·.github/workflows·버전·compose·PDF·시각 베이스라인은 범위 밖이다. 직전 파일 이름 수정은 완료됐으니 다시 손대지 않는다. OpenAPI의 기존 인증/미들웨어 응답을 지우지 않는다(최근 git log의 PATCH 403 복구 교훈). multipart 파서는 filename=""를 파일로 취급하지 않으므로 빈 파일 케이스에는 비어 있지 않은 filename과 0바이트 payload를 쓴다.
- 차선 후보: Makefile test의 Go 검사를 CI와 같은 `go test -race ./...`로 맞추기 — 1순위가 재현되지 않거나 이미 수정된 경우에만 실행; Makefile:test 한 줄과 필요 시 README 개발·검증 설명만 수정, CI/workflows 및 Dockerfile의 CGO_ENABLED=0 빌드는 변경하지 않는다. 검증은 `make -n test`로 -race 전달 확인 후 `make test`(frontend npm ci 포함), race 사용 가능한 Go/CGO 환경 확인.

구현 순서·예산(총 40분 + 예비 5분): 회귀 테스트 작성·수정 전 실패 확인 12분 → 오류 분리·API 설명 8분 → 전체 Go·fmt·check 15분 → diff와 결과 정리 5분. 본문 초과가 재현되지 않으면 12분 지점에 ContentLength와 실제 form 크기부터 확인하고, 전제가 틀린 경우에만 차선으로 전환한다.
