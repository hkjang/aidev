# v0.314.0 — 거절된 첨부 업로드가 앞선 이미지를 남기지 않습니다

## 실패했다고 답한 업로드가 파일 일부를 이미 저장했습니다

보고서에 첨부를 올리면 `uploadAttachments` 는 한 요청의 파일을 하나씩 "읽고 → 디스크에 쓰고 → 행을 넣고 → 다음" 순서로 처리했습니다. 그래서 두 번째 파일이 이미지가 아니면 `400 UNSUPPORTED_IMAGE` 를 반환하면서도 **첫 번째 이미지는 이미 디스크와 `report_attachments` 에 남겼습니다**.

화면은 업로드가 실패했다고 말하므로 작성자는 성한 파일만 다시 골라 보냅니다. 그러면 보고서가 **같은 캡처를 두 벌** 갖습니다. 이 저장소는 `writeAttachmentFile` 한 장 단위로 "통째로 쓰이거나 전혀 안 쓰인다" 를 이미 시험으로 못박아 두었는데(`attachmentwrite_test.go`), 요청 단위에서는 그 약속이 깨져 있었습니다.

## 검사를 전부 끝낸 뒤에만 저장합니다

- 저장을 두 단계로 나눴습니다. ① `readUploadedImage` 로 **모든** 파일의 크기·디코딩·형식을 먼저 검사하고 `checkedAttachment` 에 sha256·크기·상대경로만 모아 둡니다. ② 그제서야 `os.MkdirAll` → `a.db.Begin` → 파일 쓰기 + INSERT → `tx.Commit` 으로 저장합니다.
- 검사 단계는 파일 본문을 일부러 들고 있지 않고 저장 단계에서 다시 읽습니다. 기본 상한이 10MB×20장이라 전부 쥐고 있으면 동시 요청마다 200MB 가 힙에 올라가고, 그것은 이번에 고치는 결함보다 나쁜 회귀입니다. 이유는 코드 주석에 남겼습니다.
- 행 삽입을 한 트랜잭션으로 묶어, 세 번째 INSERT 가 실패해도 앞의 두 행이 남지 않습니다. 롤백 뒤 디스크에 남는 바이트는 내용 주소(sha256)라 재시도가 같은 이름에 덮어씁니다.
- 응답 코드·문구·필드와 OpenAPI 는 하나도 바꾸지 않았습니다. 프런트엔드는 고칠 것이 없어 한 줄도 건드리지 않았습니다.

## 검증

구현 단계에서 실제 PostgreSQL(pgvector/pgvector:pg16) 위에 새 시험 `TestARefusedAttachmentUploadStoresNoneOfTheImages` 를 두고, 고치기 전 코드에서 `a refused upload stored 1 image(s); the writer was told none of it was kept: UNSUPPORTED_IMAGE` 로 실패하는 것을 먼저 확인했습니다. 디스크에도 파일 한 개가 남는 것과, 재업로드 뒤 행이 2가 아니라 **3** 이 되는 실제 피해(`two readable images stored 3 rows`)를 같은 시험이 함께 보여 줍니다. 비평 단계에서 main 을 별도 트리로 꺼내 새 시험만 얹어 같은 실패를 독립적으로 재현했고, 수정 후에는 통과합니다.

릴리즈 단계에서도 실제 PostgreSQL 위에서 `go test ./... -count=1` 전체를 통과했습니다. `go vet ./...`·`go build ./...`·`gofmt`, 전체 가드 검사, 버전·OpenAPI·쪽넘김·모달 검사, 프런트엔드 시험과 타입 검사·프로덕션 빌드, `scripts/build.sh` 를 통과했습니다. 로드맵 HTML·PDF 와 두 안내서 HTML 을 기존 스크립트로 다시 만들었습니다.

검증하지 않은 것을 밝힙니다. 새 시험이 증명하는 것은 **검사 실패** 경로뿐입니다 — `tx.Commit` 실패 경로와 `STORAGE_FULL`(ENOSPC) 경로는 시험으로 밟지 않았고 코드 검토로만 확인했습니다. `guard-check` 는 새 시험의 `uploadAttachments` 도달률을 56% 로 잽니다. `gh` 를 사용할 수 없는 세션이므로 원격 이력을 보는 advisory `release-check.sh` 는 실행하지 않았습니다.

## 업그레이드

보고서에 첨부를 올리는 모든 사용자에게 해당하는 수정입니다. 마이그레이션·새 환경변수·설정 변경은 없고, 성공하는 업로드의 응답은 이전과 같습니다. 달라지는 것은 요청 안에 거절될 파일이 섞였을 때뿐입니다 — 그때 앞선 이미지가 더 이상 저장되지 않습니다. 기존과 같이 PostgreSQL 을 백업한 뒤 v0.314.0 이미지를 올립니다.

이미 생긴 중복 첨부는 이 릴리즈가 지우지 않습니다. 작성자가 보고서 화면에서 지우거나, 관리자가 필요하면 손으로 정리합니다.

배포 담당자는 배포 후 ① 이미지 여러 장의 정상 업로드가 전부 저장되는지, ② 이미지가 아닌 파일을 섞은 업로드가 `400 UNSUPPORTED_IMAGE` 를 받고 **아무 행도 남기지 않는지** 를 확인합니다. 정상 업로드가 실패하거나 저장된 장수가 보낸 장수와 다르면 확대를 중단하고 v0.313.0 이미지로 되돌립니다. 되돌리면 이번의 부분 저장 문제도 다시 발생합니다. 배포 다음 날까지 첨부 관련 문의를 확인하며, 거절된 업로드가 남긴 첨부 행 0건을 확인 기준으로 삼습니다.
