근거와 구현 순서
1. 확인한 서버 계약: `internal/api/catalog.go:258~259`는 전체 GET과 키별 PUT만 등록한다. `internal/api/routes.go:adminSettings`는 Settings 맵을 그대로 반환하고 `putAdminSetting`은 input.Value로 전체 값을 교체한다. 동일 파일 validateSetting의 sessionGateway 분기는 enabled가 false/없으면 빈 객체도 막지 않는다.
2. 5분: 새 테스트에서 비어 있지 않은 게이트웨이 설정을 준비하고 잘못된 GET이 정상 백업이 아님을 실제 라우터로 확인한다. `internal/api/dlpreport_live_test.go:gatewayDeployment`의 store.Open/Migrate/New(...).Handler() 조립 패턴과 `internal/api/mcpoauth_live_test.go`의 db.CreateAPIKey를 참고하되 관리자 계정·REST 관리자 scope를 사용한다. 기존 helper가 반환하는 일반 사용자를 관리자라고 가정하지 말 것.
3. 15분: 작은 모듈에 백업/복원 제어 흐름을 추출하고 기존 Playwright call 어댑터를 통해 실제 e2e 분기에서 호출한다. 전체 스크립트의 import가 브라우저를 시작하므로 테스트에서 전체 스크립트를 import하지 않는다. 스크립트의 12초 settle 및 launch 검사 의미는 유지한다.
4. 15분: 실제 서버/DB 테스트에서 Node가 공통 모듈로 임시 PUT을 한 뒤 정상/throw 경로를 지나 원본을 GET으로 재확인한다. 실제 API를 대역으로 재구현하거나 소스 문자열 검사를 증거로 삼지 않는다. 키 부재/읽기 거절 등은 실제 API 응답으로 가능한 경우 검증하고, 복원 500 같은 장애 주입은 보조 테스트에 한정한다.
5. 10분 예비: Node 실행 경로·관리자 scope·격리 DB 연결 문제 해결 및 관련 테스트. 총 35분 + 예비 10분, 45분 안에 완결할 M. DB 검증이 불가능하면 이유와 SKIP을 적고 차선으로 전환한다.
