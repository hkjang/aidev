# 수리 요약 (시도 3)

- 지적이 맞았다. probe 로 재현: 허용 목록 64개×64룬 + 스니펫 32개×32룬을 한국어(U+AC00)로 채우면 `Validate()` 가 통과하고 `pagePolicy()` 가 **33513 바이트**, 네 바이트 글자(U+1F600)로는 **42309 바이트**를 쓴다. ASCII 는 15921. 세 경우 모두 **룬 수는 15921 로 동일** — 즉 두 상한이 묶는 단위는 룬이고 바이트는 최대 네 배다.
- 비평가가 준 세 길 중 **①예산을 룬으로 말하기 + ②테스트가 멀티바이트 최악을 측정·단언하기**를 함께 했다(③합계를 바이트로 두기는 main 에 이미 나간 허용 목록 상한의 단위까지 바꿔야 해 범위 밖).
- `tracking.go` 주석은 이제 "이 두 상한이 묶는 것은 15921 **룬**이고, 바이트는 ASCII 15921 / 한국어 33513 / 네 바이트 42309 로 글자에 따라 최대 네 배" 를 말한다. 바로 옆 `MaxAllowedHostsTotalRunes` 의 같은 거짓("12.5 킬로바이트")도 룬으로 바로잡았다(같은 결함, 비평 노트의 남는 우려).
- 결합 테스트는 ASCII·한국어·네 바이트 세 경우를 모두 세워 `Validate()` 통과를 확인하고, 룬 증가량 `== 3*(4096+64)+3*(1024+32)` 를 정확히 단언하고, ASCII 만 바이트 예산 안쪽임을 단언한다. 멀티바이트가 예산 **밖**인 것도 단언한다 — 나중에 바이트로 묶으면 이 줄이 깨져 주석을 다시 쓰게 만든다.
- 검증: `go test -race ./cmd/... ./internal/...` 30 ok / 2 no-test-files, gofmt·vet 깨끗. 상한 값·`Validate()` 동작은 한 줄도 바꾸지 않았다.
