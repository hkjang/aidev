- 요약: `ai_admin.app_user.display_name` 은 `varchar(190)`, `email` 은 `varchar(320)`(`001_ai_admin.sql:9-12`)이고 PostgreSQL 의 varchar 는 길이와 무관하게 NUL 을 담을 수 없는데, 이 컬럼에 쓰는 두 핸들러가 모두 `strings.TrimSpace` + `utf8.RuneCountInString` 만 보고 NUL 을 통과시켰다 — `updateProfile`(`users.go:413-446`)의 `displayName`·`email`, `updateUser`(`users.go:88-113`)의 `displayName`. `encoding/json` 은 `"\u0000"` 을 실제 0x00 바이트가 든 Go 문자열로 디코딩하고 `TrimSpace` 는 그것을 지우지 않으며 rune 수는 1 이라, 호출자 입력 오류가 400 이 아니라 `UPDATE` 에서 터져 500(`profile_update_failed`/`user_update_failed`)으로 나갔다. 같은 핸들러들이 길이·빈값·이메일 형식을 이미 "쓰기 전에 400" 으로 못박아 둔 세 자리에 `storableInVarchar`(`strings.ContainsRune(value, 0)` 한 줄, 상한 리터럴 옆 주석과 같은 스타일로 근거 주석) 하나를 더해 같은 규칙으로 거부하게 했다(프로덕션 파일 1개 — `users.go`). 오류 코드는 통일하지 않고 각 핸들러의 기존 코드(`profile_invalid`/`email_invalid`/`name_invalid`)를 그대로 쓰고, 판정은 디코딩된 값의 rune 을 보므로 여섯 글자 문자열 `\u0000` 자체는 계속 저장된다. `updatePreferences`/`loadPreferences`/`objectValue` 와 미머지 브랜치 `auto/2026-10-04-1142` 가 쓴 이름(`jsonObjectHasNUL`·`storablePreferenceObject`)은 건드리지도 재사용하지도 않았다. 검증: 신규 `internal/server/profile_nul_integration_test.go` 가 전용 폐기 `postgres:16-alpine`(포트 55531) → `database.Open` → `DROP SCHEMA` → `db.Migrate` → `db.Seed` → `New(db,cipher,logger).Handler()` → `signIn` → 실제 `PATCH /api/v1/profile`·`PATCH /api/v1/users/{adminID}` 전 경로로 거부 7건(프로필 표시명 trailing/leading/only NUL, 프로필 이메일 NUL, 사용자 표시명 trailing/embedded/only NUL)마다 400 과 함께 `display_name`·`email`·`updated_at` 세 값이 **모두 불변**임을 매번 SELECT 로 확인하고, 회귀 4묶음(리터럴 `\u0000` 여섯 글자 200 저장·조회 일치, 한글 190자 200 + 저장값 일치·191자·공백만 400 `profile_invalid`, `updateUser` 의 빈 문자열·공백만·191자 400 `name_invalid` + 190자 200, `@` 없는 이메일 400 `email_invalid` + 정상 이메일 200 저장)을 고정한다. `go test -race -count=1 ./...` 전체 통과(internal/server 148.3s), `make lint`(gofmt·go vet·verify-version 1.2.33)·`go build ./...` 통과, `docs/api.md` 의 프로필 절·사용자 절에 각각 한 문장으로 적었다. 웹 변경이 없어 `npm test`·`make build`(`internal/ui/dist` 재빌드)는 하지 않았고 VERSION·CHANGELOG 는 건드리지 않았다(커밋 addbbf7, 변경 3개 중 프로덕션 1개).
