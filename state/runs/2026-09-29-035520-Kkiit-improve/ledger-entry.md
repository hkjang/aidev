- 선택: 포트폴리오 수정·삭제의 DB 저장 실패를 404 "포트폴리오를 찾을 수 없습니다." 가 아니라 500 으로 알리기 (가치 2 / 위험 1 / 작업량 S)
- 결과: 성공
- 요약: `updateMyPortfolio`(discovery.go:196)와 `deleteMyPortfolio`(:211)가 `err != nil || tag.RowsAffected() == 0` 로 DB 오류와 "행 없음" 을 묶어 둘 다 404 `portfolio_not_found` 로 돌려주었다 — 바로 위 `createMyPortfolio` 는 같은 표의 INSERT 실패를 이미 500 `create_failed` 로 보고하므로, 목록에서 자기 포트폴리오를 보고 있는 소유자가 수정만 하면 "없다" 는 안내를 받는 비대칭이었다. 저장 실패를 500 `portfolio_save_failed` "포트폴리오를 저장하지 못했습니다."(createMyPortfolio 문구와 동일)로 가르고 `RowsAffected()==0` 만 404 로 남겼으며, DELETE 도 같은 형태로 500 `portfolio_delete_failed` 로 갈랐다. 검증: 실제 라우터 + 버릴 PostgreSQL 16(docker 29.7.2)으로 HTTP→DB 왕복 통합 테스트를 먼저 실패시킨 뒤 수정해 통과시켰고, 임시 프로브로 실패 경로의 오류가 `*pgconn.PgError{Code:"22021", Message:"invalid byte sequence for encoding \"UTF8\": 0x00", Where:"unnamed portal parameter $3"}` 이면서 그 행이 실제로 존재한다(`row_exists: true`, `rows: 0` = 문장이 아예 실행되지 않음)는 것을 눈으로 확인한 뒤 프로브를 제거했다. 분기를 두 방향으로 변이시켜(항상 500 → `status=500 want=404`, 항상 404 = 원본 → `status=404 want=500`) 각각 다시 실패하는 것을 확인했다. 깨끗한 DB(DROP/CREATE)로 `go test ./cmd/... ./internal/...` 전체 통과(httpapi 92.0초, 통합 실제 실행), 새 테스트 단독 `-v` 로 `--- PASS`(SKIP 아님) 확인, `go vet ./cmd/... ./internal/...` 무결, `gofmt -l cmd internal` 무출력, `npm --prefix web test` 10건 통과. 프런트는 `error.message` 를 그대로 띄우므로 `web/`·`internal/ui/dist` 를 건드리지 않았고 `docs/openapi.yaml` 의 `/me/portfolios/{id}` put 에 `'400'`(핸들러가 실제로 내는 `invalid_portfolio`)·`'500'`, delete 에 `'404'`·`'500'` 을 더했다. 프로덕션 파일 1개(discovery.go) + 문서 1개.
