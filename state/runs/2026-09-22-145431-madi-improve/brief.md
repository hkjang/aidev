- 과제: 고정 runtime APK 잠금 파일을 전체 빌드 전에 검사하는 사전 점검 스크립트 (가치 3 / 위험 1 / 작업량 M)

- 수용 기준: 1) 저장소 밖에서 절대 경로로 실행해도 기본 Dockerfile의 runtime-base 이미지와 기본 lock을 정확히 찾아 linux/amd64 임시 컨테이너에서 apk add --no-cache --simulate를 실행한다. 이미지 태그/digest를 스크립트에 중복 하드코딩하지 않는다. 2) 성공은 exit 0, Docker·pull·네트워크·APK 실패는 비영(원래 번호 일치까지는 요구하지 않음)이며 stderr를 숨기거나 성공으로 바꾸지 않는다. 현재 기본 lock의 실패는 정상 탐지이며 lock 자동 갱신은 하지 않는다. 3) --lock FILE로 읽기 전용 시험 입력을 지정할 수 있고, 빈 파일·주석만 있는 파일·잘못된 인수/잠금 행은 실행 전 명확히 거부한다. 주석/빈 줄은 제외하고 package=version 형식의 실제 인수를 전달하며 eval을 쓰지 않는다. 4) 실제 Docker/APK로 유효 busybox 고정 버전은 성공, 존재하지 않는 버전은 실패함을 새 실행 테스트가 증명한다. 기본 lock 및 fixture 해시와 git diff가 실행 전후 같고 다른 작업 디렉터리·공백 포함 fixture 경로에서도 동작한다. 가짜 docker 실행 파일이나 소스 문자열 검사는 증거로 삼지 않는다. 5) deploy/README.md에 연결망·Docker 필요, 실행 명령, 실패 진단, 버전/대응 소스/이미지 검증을 함께 검토해야 한다는 안내와 이 점검이 전체 이미지 검증을 대신하지 않는다는 범위를 적는다.

범위와 대안 비교: 대상은 이미지 제작자에게 수동 사전 점검 진입점을 주는 것뿐이다. (A) 독립 시뮬레이션 스크립트는 작은 비용으로 실제 APK resolver를 쓰므로 선택.
