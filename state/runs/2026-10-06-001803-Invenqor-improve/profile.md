# Invenqor 프로필 (2026-10-06)
- 목적: Rust Agent 가 호스트·프로세스·소프트웨어를 수집해 Go Server 로 보내고 React 콘솔·REST·MCP 로 IT 자산을 관리하는 시스템.
- 스택: Rust 1.85(Agent, Linux/Windows), Go 1.25.14(chi·go-oidc·pgx·modernc sqlite), PostgreSQL 기본/명시적 SQLite 폴백, React 19·TypeScript·Vite 7·Vitest.
- 구조:
  - `src/`, `tests/`, `Cargo.toml`: Agent 수집·전송·업데이트와 Rust 테스트.
  - `server/cmd/invenqor-server`: 진입점. `server/internal/httpapi`: REST·MCP·콘솔 핸들러와 실제 라우터 테스트.
  - `httpapi/assets.go` 함수 위치(**main@a1c9474 기준**, 전 프로필의 12ada2f 번호에서 밀림): listAssets:190, getAsset:261, createAsset:328, updateAsset:375, setAssetDeleted:498, assetHistory:536, assetRelations:574, createAssetRelation:622, deleteAssetRelation:665, canonicalUUID:702, assetIDParam:723, missingAssetID:739, mergeAssets:757, splitAsset:877, recordAdminAudit:973.
  - `server/internal/{querydsl,storage,storagetest,auth,apikeys,ingest,softwarecatalog,mail,tracking,updates,agents,audit}`: DSL·DB·인증·수집과 운영 서비스.
  - `server/migrations/{postgres,sqlite}`: 같은 순번의 두 SQL 방언 유지. PostgreSQL assets/asset_relations ID 는 UUID, SQLite 는 TEXT.
  - `web/src`: 콘솔. `web/scripts/sync-embedded.mjs` 가 React 빌드를 체크인 대상 `server/internal/webui/dist` 로 복사.
  - `openapi.yaml`: 공개 API. `docs/`: 역할별 Markdown/PDF·릴리즈 노트. `scripts/`: PostgreSQL 테스트·패키징·e2e·문서 생성.
- 빌드·테스트:
  - `cd server && go test ./... && go vet ./...`; 포맷은 `gofmt -l .` 빈 출력. 빌드는 `go build ./cmd/invenqor-server`.
  - 좁은 검증: `cd server && go test ./internal/httpapi/ -run 'Relation' -count=1` — 10/06 실측 통과 2.072초. 넓게는 `-run 'AssetRoutes|AssetCollections|Merge|Split|Relation'`(10/05 실측 6.683초).
  - 루트: `POSTGRES_CONTAINER=<회차고유이름> POSTGRES_PORT=<빈포트> ./scripts/test-postgres.sh -run '…' -count=1` — 10/05 포트 55505/55516 사용 가능, 기본 55432 는 점유 중이었다. httpapi 전체 68초.
  - `cd web && npm ci && npm test && npm run build`; 빌드 후 루트 `git diff --exit-code -- server/internal/webui/dist` 가 CI 검증. `npx --yes @redocly/cli@2.47.0 lint openapi.yaml`.
  - Rust: `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`; 크로스 빌드와 e2e 는 CI 장기 작업. 크로스 빌드는 실제 HOME 을 넘겨야 한다.
- 관례: 커밋은 한국어 fix/build/chore 및 별도 버전 릴리즈. 설정은 DB settings 와 관리 API. migrations 두 방언 동시 유지. 버전 범프·릴리즈 노트·PDF 재생성은 일반 구현 과제에 섞지 않는다.
- 위험 구역: auth/session/OIDC/API key 권한(`httpapi/auth.go`, `auth/`), migrations, merge/split 트랜잭션·감사, `.github/workflows`, 임베드 UI 산출물. 정찰에서는 코드·커밋을 변경하지 않는다.
- 자주 깨지는 곳:
  - PostgreSQL JSONB LIKE·공유 파라미터 타입 추론·LIKE 대소문자·UUID 입력과 SQLite 의 차이. **기본 `go test` 통과만으로 PostgreSQL 동작을 보장하지 못한다** — 네 회차 연속 실측으로 확인됨.
  - `canonicalUUID`(:702) 는 하이픈 있는 36자만 허용하고 대문자를 소문자로 돌린다. 중괄호·32자·urn 은 거절. **merge·split·상세/수정/삭제/복원/history/relations 조회·관계 생성·관계 삭제에 적용 완료**(79f1889, v0.2.43). 남은 미점검 경로: `classification.go:425 reviewProposedRelation` 의 relationID 원문 UPDATE, `mcp.go`·`users.go`·`api_keys.go`·`agents.go`.
  - 입력 **값 범위** 검증은 UUID 형식 검증과 달리 아직 비어 있다. `asset_relations.confidence` 는 두 방언 모두 CHECK 없는 DOUBLE PRECISION/REAL(`001_initial.sql:252`)이고 `createAssetRelation` 에 `[0,1]` 검사가 없다 — 10/06 회차 과제.
  - SQLite 단일 커넥션에서 열린 tx 가 있는 동안 `internalError` 가 진단 DB 쓰기를 하면 교착할 수 있다. merge 의 missingAssetID 오류 경로만 rollback 선행; 다른 tx 오류 경로는 여전. 가짜 Runtime 으로 검증하지 않는다.
  - `assetHistory:536`·`assetRelations:574` 는 `rows.Err()` 검사와 `LIMIT` 이 둘 다 없다.
  - 시간 값은 DB 별 string/time.Time 차이를 `apiTime` 으로 통일. 자산 변경 JSON 의 식별자는 MCP 조회와 같은 정규형이어야 한다.
  - 같은 패키지 테스트 헬퍼 중복 선언 금지. 재사용할 것: `newRuntime/testServer`, `authenticateInitialAdmin/performAuthenticatedJSON`, `insertSoftwareTestAsset`(software_inventory_test.go:133), `assetIDSpellings/assetIDResponse`, `countRows`(asset_merge_validation_test.go:41), `errorCode`(external_api_test.go:226), `relationValidationClient/relationValidationAssets/relationValidationBody/assertRelationResponse`(asset_relation_validation_test.go:16,41,50,56).

  - 외부 API 는 `external_api_test.go:createAPIKeySecret/performWithAPIKey` 로 실제 키를 발급해 검증. 콘솔(`server.go:380-428`)과 외부(`:211-232`)는 같은 핸들러를 공유하나 **둘 다** 테스트할 것 — 그래서 `server.go` 와 `web/` 을 건드리지 않고 두 경로가 함께 고쳐진다.
