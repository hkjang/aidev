v0.42.0 — 자동화가 같은 결정을 두 번 내리지 않는다

v0.39.0 과 같은 자리를 다시 봤다. 그때는 자동 시도를 정산하는 쪽이 없어 가드가
한 번도 발동하지 않았고, 이번에는 가드가 볼 것이 아예 없었다 — 발급을 멈출
조건이 자기 행동으로 닫히지 않는 루프다.

무인 스윕이 같은 병합을 15분마다 다시 승인했다 (#67)
  `AutoApproveMerges` 는 작업이 DONE 이고 게이트가 그 커밋에서 통과했다는
  조건만 보고 승인을 발급했다. 이 조건은 승인을 발급해도 변하지 않는다. 병합은
  사람이 `goalforge merge` 를 돌릴 때 일어나고, 병합해도 작업 항목은 DONE 에
  그대로 남는다. 그래서 `goalforge worker` 의 스윕이 돌 때마다 완전히 같은
  (작업·커밋·대상) 범위의 승인이 하나씩 쌓였다.

  실행 승인 경로에는 이 문제가 없다. `AutoApprove` 는 `item.Status != "BACKLOG"`
  를 건너뛰고 승인이 상태를 APPROVED 로 옮기므로 루프 조건이 자기 행동으로
  닫힌다. 병합 경로에는 그렇게 닫을 상태가 없었다.

  쌓인 승인은 기록상의 군더더기가 아니라 리뷰 없는 병합 권한이다.
  `ConsumeScopedApproval` 은 한 건씩(LIMIT 1) 소비하므로 첫 병합이 하나를 쓰고
  남은 것들은 같은 커밋을 그대로 다시 병합할 수 있는 승인으로 남는다. 그 승인을
  내준 리뷰는 어디에도 없다.

  `Store.ScopedApprovalExists` 로 발급 전에 "이 릴리즈가 이미 결정됐는가" 를
  묻는다. 상태로 걸러내지 않는다 — PENDING 은 리뷰를 기다리는 요청, APPROVED 는
  쓰이기를 기다리는 승인, CONSUMED 는 이미 나간 릴리즈, REJECTED 는 사람이 이
  커밋에 아니라고 말한 것이다. 넷 모두 "또 발급할 것인가" 의 답은 아니오이며,
  뒤의 둘에서 발급하면 같은 커밋을 두 번 내보내거나 리뷰어의 거절을 15분 뒤에
  자동화가 뒤집는다.

  봉투 규칙의 복제가 아니다. 무엇을 허용하는지는 `admits()`/`AutoApprove` 한
  곳의 판단이고 여기서 되풀이하지 않는다. 새 가드는 "이 결정이 이미 내려졌는가"
  만 묻는다 — 실행 승인에서 `item.Status` 가 답하던 것과 같은 종류의, 규칙이
  아닌 멱등성 가드다.

조용한 스윕이 `Merged` 축에서 다시 깨져 있었다 (#67)
  `TickResult.Acted()` 는 `len(Merged)>0` 을 활동으로 센다. 승인이 매 순회마다
  새로 발급되는 동안 스윕은 영원히 "조용하지 않은" 상태였고, 2026-10-01 이
  복구한 침묵 설계가 이 축에서 무력화돼 있었다. 중복 발급이 멈추면서 함께
  닫혔다.

범위 일치 조건을 한 곳에 뒀다
  발급 쪽과 소비 쪽이 상수 `scopedApprovalRelease` 하나를 읽는다. 두 벌로 적어
  두면 어긋나고, 어긋남은 어느 방향이든 결함이다. 발급 쪽이 좁으면 중복이 다시
  쌓이고, 넓으면 소비 쪽이 찾을 수 없는 릴리즈의 발급을 건너뛰어 병합이
  교착된다.

  건너뛴 항목은 버리지 않고 `Detail` 에 담는다. "승인할 것이 없다" 와 "쓰이기를
  기다리는 승인이 있다" 는 명령을 다시 돌린 운영자에게 같아 보이지만 같은 것이
  아니다.

검증: 테스트 셋을 고치기 전에 돌려 빨강을 눈으로 확인했고, 가드만 꺼서 셋이
다시 실패하는 것으로 인과를 확정했다. 실제 `*store.Store`(SQLite)와 프로덕션
함수를 그대로 쓰고 대역은 없다. 릴리즈를 끊기 전에 이 기계에서 `gofmt -l`,
`go vet ./...`, `go build ./...`, `go test ./... -count=1` 전 패키지 통과와
go.mod 정돈을 확인했고, 여섯 플랫폼 크로스컴파일 뒤 산출물을 풀어 `goalforge
version` 을 돌리고 SHA256SUMS 까지 검증했다.
