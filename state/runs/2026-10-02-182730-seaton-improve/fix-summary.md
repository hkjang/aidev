# 수리 요약 (시도 1 거절 → 수리)

- 세 지적 모두 맞았다. 뿌리는 하나였다: `saveEmployee` 가 조직명이 있으면 external_id 를 `import:<조직명>` 으로 지어 `ON CONFLICT(external_id) DO UPDATE SET name` 으로 넣어, 오타 난 조직코드는 새 조직을 만들고(양식은 두 열을 모두 채우므로 새 검증을 지나쳤다), 오타 난 조직명 한 줄은 기존 조직을 개명하고, 조직코드 열이 없는 내보낸 직원목록은 중복 조직을 만들었다.
- 고친 방법: 직원 저장 경로는 조직을 만들지도 고치지도 않는다. 새 `findOrganization`(employees.go:103) 이 조직코드가 있으면 그것만으로 기존 조직을 찾고(같은 행의 조직명은 쓰지 않아 개명 불가), 조직코드가 없으면 조직명으로 기존 조직을 찾는다. 없으면/같은 이름이 여럿이면 그 행을 사유와 함께 되돌린다. 조직 생성은 조직 API·인사 동기화만 한다. USER_GUIDE 3.4 의 가져오기·내보내기 문구를 이 동작과 일치시켰다(html 재생성, pdf 미변경).
- 재현·검증(실서버 E2E, 격리 postgres+도커 이미지): 새 4개 케이스를 **변경 전(HEAD) 이미지에서 4개 모두 실패**시킨 뒤 수정본에서 7/7 통과. 전체 스위트 83 passed / 1 failed — 실패는 tracking.spec.ts:110 하나이고 변경 전 이미지에서도 같은 자리 실패(브리지 네트워크에서 컨테이너→호스트 수집기 접근 불가, 이 변경과 무관).
- 그 밖: `go test ./...` `go vet ./...` `gofmt -l .` 통과, web `npm test` 159 통과, `npm run lint`(tsc -b) 통과. 테스트를 지우거나 느슨하게 한 곳은 없다.
- 남은 판단거리: 이제 가져오기가 조직을 만들지 않으므로, 조직이 비어 있는 설치에서 조직명만 적은 파일로 조직을 만드는 길이 사라졌다(조직 생성 UI 는 원래 없고 API·인사 동기화뿐). 안전을 택한 의도적 선택이며 안내문에 적었다.
