저장 결과가 200건을 넘는 설치에서 201번째부터 화면에 아예 존재하지 않던 문제를 고쳤습니다. 목록을 페이지로 나눠 부르고, 건수를 서버가 세어 준 총계로 보여 줍니다.

**목록에 보이는 것이 전부가 아니었습니다.**

`/saved` 는 저장 결과를 `limit=200` 으로 한 번만 불렀습니다. 201번째부터는 다음 페이지가 없는 것이 아니라 화면에 존재하지 않았고, 목록 위의 건수도 총계가 아니라 "불러온 200건 중 검색으로 걸러진 수"였습니다. 오래 쓴 설치일수록 예전에 저장해 둔 결과에 닿을 방법이 없었고, 건수가 그럴듯해 보여 없어진 줄도 몰랐습니다.

이제 서버가 이미 주고 있던 `limit`/`offset`/`total` 로 한 페이지에 100건씩 나눠 부르고, 목록 아래에 이동 바를 답니다. 관리 화면의 이력 목록에서 쓰던 표기(`← 이전`/`다음 →`, `페이지 n / m`)를 그대로 따릅니다.

| 상황 | 이후 동작 |
| --- | --- |
| 저장 결과 105건 | `1-100 / 총 105건`, 이동 바로 2쪽 이동 |
| 한 페이지에 다 들어감 | 이동 바를 숨김 |
| 검색어 입력 | 건수에 `· 이 페이지에서 N건` 을 덧붙여 범위를 밝힘 |
| 검색 결과가 이 페이지에 없음 | `이 페이지에는 없습니다.` (전체에 없다고 하지 않음) |
| 마지막 페이지의 마지막 항목 삭제 | 한 페이지 물러나 다시 부름(빈 화면에 갇히지 않음) |

검색은 지금 보고 있는 페이지 안에서만 돕니다. 그렇게 보이도록 문구를 고쳤을 뿐, 전체를 뒤지지는 않습니다. 서버 쪽 검색은 다음으로 미뤘습니다.

**스프레드시트로 붙여 넣은 TSV 의 수식 보호가 한쪽에만 걸려 있었습니다.**

결과를 TSV 로 복사할 때 `=`, `+`, `-`, `@` 로 시작하는 값은 스프레드시트가 수식으로 읽지 않도록 문자로 고정합니다. 그런데 이 보호가 값에만 걸리고 열 이름에는 걸리지 않았고, 저장 결과 화면과 워크스페이스가 서로 다른 변환을 쓰고 있었습니다. 보호 여부를 문자열로 바꾼 뒤에 판정해 숫자 `-1` 같은 값의 처리가 화면마다 어긋나기도 했습니다.

이제 두 화면이 같은 변환(`tsvCell`)을 씁니다. 헤더와 값에 같은 규칙이 걸리고, 보호 여부는 문자열로 바꾸기 전 원래 타입으로 판정하며, 탭과 개행은 공백으로 바꿔 셀이 다른 행이나 열로 갈라지지 않습니다.

서버와 SQL 은 바뀌지 않았습니다. 화면(JS)만 바뀝니다.
