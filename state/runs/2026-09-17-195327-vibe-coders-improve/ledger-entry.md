- 요약: 이 저장소는 사용자별 계정(`AUTH_ENABLED`, `users`)과 Keycloak OIDC 웹 로그인(`auth_identities` 에 issuer+subject 로 연결)이 이미 있고 `/.well-known/oauth-protected-resource` 는 없었으므로 MCP-OAUTH-STANDARD 를 그대로 구현했다. `go-oidc` 가 없는 hand-rolled Keycloak 저장소라 기존 `keycloakDiscover`(discovery 캐시)·`keycloakJWKSKey`(JWKS 캐시, kid 미스 시 재요청)·`keycloakVerifyJWT`(RS256 서명·iss·exp) 를 재사용하고 그 위에 `nbf`·`typ=ID` 거부(헤더·클레임 모두)·`cnf` 거부·`sub` 필수·대상 검사를 얹었다(`internal/proxy/mcp_oauth.go`, 한 파일). **고른 것과 이유**: (1) 설정 자리 — 런타임 설정 레지스트리의 `mcp` 범주에 표준 이름 그대로 `mcp.oauth.enabled|resource|audience|scopes` 를 두었다(방문 추적과 같은 `settingDef` 패턴이라 감사·버전·전 파드 재적재·두 콘솔 자동 노출을 공짜로 얻고, `mcp.oauth.scopes` 는 `allScopes` 어휘만 받도록 검증). 발급자·클라이언트 ID 는 SSO 탭/`SSO_KEYCLOAK_*` 를 재사용해 새로 적지 않는다. (2) 리소스 식별자 출처 — `mcp.oauth.resource` → 비면 **Keycloak Redirect URI 의 출처**(이 배포가 이미 적어 둔 유일한 공개 주소) + `/mcp` → 그것도 없으면 요청 origin(마지막 수단). `/mcp/gateway` 는 같은 출처 + 그 경로로, 메타데이터는 `…/oauth-protected-resource`(= `/mcp`)·`…/mcp`·`…/mcp/gateway` 세 경로에서 맨 JSON·CORS `*`·꺼지면 404. (3) 대상 — `aud` 에 (호출 경로의) 리소스 식별자, 또는 `aud`/`azp` 가 `mcp.oauth.audience` 나 웹 로그인 Client ID 에 있으면 통과(weekly 와 같은 규칙; Keycloak 26 은 `aud=[account]`, 클라이언트는 `azp`). 거부 메시지에 본 `aud`/`azp` 와 고칠 값(`mcp.oauth.audience 에 "claude-mcp" 를 더하거나 … Audience 매퍼로 https://…/mcp`) 을 넣고 `WWW-Authenticate` 의 `error_description` 에도 같은 문장을 실었다. (4) 계정 — `AuthIdentityBySubject("keycloak", issuer, sub)` 로 이미 연결된 계정만 찾고(같은 realm 은 클라이언트가 달라도 같은 `sub` 를 주므로 웹 로그인 한 번이면 됨), 없으면 "웹 콘솔에 SSO 로 한 번 로그인" 거부, 비활성이면 거부, username/email 폴백은 이 저장소가 identity 별칭화를 엄격히 막고 있어 넣지 않았다. 역할은 저장된 계정 역할, 범위는 `mcp.oauth.scopes` ∩ 역할 범위(∩ 토큰이 우리 어휘를 실었을 때 그것)이며 `/mcp` 는 키와 같은 `apiScopeForRequest`(`mcp:use`) 문을 지난다. (5) 헤더 가르기 — 두 MCP 핸들러만 새 `authenticateMCP` 를 쓴다: JWT 모양(점 둘, 세 조각)이고 SSO 문이 열려 있고 키 표에 없으면 OAuth, 그 외는 전부 기존 `authenticateProxyContextWithOutcome` 그대로(키는 prefix+base64url 이라 점이 없어 절대 JWT 모양이 아님). 꺼져 있으면 토큰을 내밀어도 예전과 같은 `invalid proxy API key` 이고 도전 헤더도 없다. REST(`/v1/*`)·관리 API 는 손대지 않았다.
