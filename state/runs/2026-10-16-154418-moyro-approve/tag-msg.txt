moyro v0.2.50

Channel bookmark reorder rewrites a channel's positions densely instead of
writing only the row it was asked to move, and the Go toolchain and
`golang.org/x/net` are raised to versions `govulncheck` accepts. The first is a
server behavior fix; the second changes no product behavior and exists to clear
a release gate. There is no schema change, no migration, no new route, no new
error id and no web source change. One production file changes, and the
`bookmarks` package gains its first tests.

`Reorder` in `bookmarks/service.go` carried a doc comment promising a dense,
conflict-free re-shuffle of the channel's bookmarks and a body that was a single
`UPDATE` of the target row's `sort_order`. The comment described a "simple
two-shot update"; the second shot was never written. Two or more bookmarks in
one channel were therefore left sharing a `sort_order`, and `List` orders by
`sort_order ASC, create_at ASC`, so the tie fell to the older row: a drag landed
one slot away from its target, or produced no visible movement at all. Nothing
read a corrupted value — the rows simply never stopped colliding, and the old
comment's own excuse for the shortcut, that a race only means two clients "see
slightly different orders for ~100ms", described a transient disagreement this
code could not actually produce. The duplicates persisted until something else
rewrote them.

`Reorder` now opens a transaction, reads the channel's active rows in `List`'s
own order, moves the target inside that slice, and rewrites `0..n-1` in a single
`unnest` `UPDATE` scoped to the channel's non-deleted rows, which is the idiom
`sidebar.UpdateOrder` already uses. The read that decides the sequence and the
write that applies it share the transaction, so two concurrent reorders cannot
interleave back into the duplicate positions the change exists to remove.
Positions are 0-based to match Mattermost's endpoint, while `Create` still
appends with `COALESCE(MAX(sort_order),0)+1`; a channel that has never been
reordered therefore starts at 1 and a reordered one starts at 0. `List` exposes
only relative order, so that asymmetry is invisible to clients, and it is
recorded in the doc comment rather than smoothed over. An out-of-range position
still clamps to either end instead of erroring, keeping the response contract
callers already have. The handler, `Create`, `List` and `Patch` are untouched,
and the channel and `delete_at` filters on the rewrite keep another channel's
rows and soft-deleted rows out of it.

What an operator should expect is a correction, not a contract change. A channel
whose bookmarks already share positions keeps that order until something
reorders it; the first reorder after this upgrade rewrites the whole channel
densely and may therefore move more rows than the one the client dragged. That
is the backlog of duplicates being cleared, not a new fault.

The toolchain half raises `Dockerfile`'s `server-build` stage to
`golang:1.27.2-alpine` at its matching digest, `server/go.mod`'s `go` directive
to 1.27.2, and the module graph to `x/crypto` v0.57.0, `x/net` v0.60.0 and the
indirect `x/mod` v0.41.0, `x/sync` v0.23.0, `x/sys` v0.48.0 and `x/text`
v0.42.0. `govulncheck` had begun reporting reachable advisories against the
previous Go 1.27.0 and `x/net` v0.58.0 pins, which fails the release job's own
scan step. All of these are patch and minor bumps within one module family; no
direct dependency is added, removed or re-ranged. `GOTOOLCHAIN=local` in that
stage means the published image is built by the pinned toolchain rather than one
downloaded at build time, so the `Dockerfile` and `go.mod` pins have to move
together, and they do.

Two machine-specific adjustments, neither of them a change to the tree. The
Playwright browser install still needs the one the previous two tags recorded:
`npx playwright install --with-deps chromium` fails here because `--with-deps`
escalates to `sudo` with no terminal available, while `npx playwright install
chromium` without that flag succeeds and the browser gate then runs clean. New
this time, `HOME` on this machine points inside the release run directory rather
than at the user's home, so both that install and `verify-product-ui.sh` were
run with `HOME` set back to the user's home to reach the existing
`~/.cache/ms-playwright` store; nothing in the repository reads `HOME`. The
checksum-pinned `postgres:16-alpine` digest the two verify scripts default to
was pulled before they ran, because the copy already on this machine was a
different digest of the same tag.
