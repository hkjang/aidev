- 요약: `people.id`·`person_links.id` 는 uuid 컬럼인데 `getPerson`·`updatePerson`·`deletePerson`·`listPersonLinks`·`createPersonLink`·`deletePersonLink` 가 `chi.URLParam` 값과 본문 `person_id` 를 검사 없이 질의 파라미터로 넘겨, 모양이 어긋난 문자열이 오면 postgres 가 `22P02` 를 내고 핸들러가 `internalError` 로 감싸 500 을 냈다. 파일 수준 순수 함수 `looksLikeUUID`(표준 라이브러리만, `8-4-4-4-12` 16진수·대소문자 무시) 하나를 더해 여섯 곳 맨 위에서 가드하고, 경로 파라미터는 기존 404 메시지 그대로·본문 `person_id` 는 다른 본문 검증과 같은 400 으로 갈랐다. 새 오류 코드·메시지는 만들지 않았고 프로덕션 파일은 `data.go` 하나다. 검증: `gofmt -l internal/server`(출력 없음)·`go vet ./...`·`go test -race -count=1 -v ./internal/server -run 'Person|Link|UUID'`(신규 20 하위 시험 전부 PASS)·`go test -race -count=1 ./...` 전부 초록. 추가로 정찰이 "미확인" 으로 남긴 추론을 실제 postgres(docker `postgres:16-alpine`, 포트 55521)로 확인했다 — `looksLikeUUID` 를 `return true` 로 한 줄만 되돌린 빌드에서 실제 핸들러가 `getPerson`/`createPersonLink` 본문/`deletePersonLink` 모두 **500 internal_error**, 가드를 되살리면 404/400 이고, 같은 실행에서 정상 uuid 경로(없는 uuid 404 / listPersonLinks 200 / createPersonLink 201 / deletePerson 204)는 양쪽에서 동일했다. `psql` 로 `ERROR: 22P02: invalid input syntax for type uuid` 까지 직접 확인했다. 이 DB 탐침은 일회용이라 커밋하지 않았고, 커밋된 테스트는 `&Server{store: nil}` 로 DB 없이 CI 에서 실제로 돈다.
