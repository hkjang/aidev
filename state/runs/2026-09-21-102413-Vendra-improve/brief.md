- 과제: MCP search_suppliers가 공급업체 번호로도 검색되게 하기 (가치 3 / 위험 1 / 작업량 S)
- 왜: `internal/httpapi/integrations.go:runMCPTool`의 search_suppliers SQL은 이름·사업자번호만 검색하지만 같은 파일의 mcpTools 설명과 USER_GUIDE.md 4.6은 공급업체 번호 검색도 약속한다. 이미 번호를 검색하는 listSuppliers·globalSearch와 MCP를 맞추면 사용자가 알고 있는 업체 번호를 AI에 주었을 때 존재하는 업체를 없다고 답하는 일을 막는다.
- 수용 기준: 1) 공급업체 번호만 일치하고 이름·사업자번호에는 검색어가 없는 업체를 MCP tools/call(search_suppliers)이 반환한다; 전체 번호와 2자 이상 부분 번호, 대소문자 차이에도 기존 ILIKE 방식대로 일치한다. 2) 동일 사용자·동일 검색어로 GET /api/v1/suppliers?q=…, GET /api/v1/search?q=…, POST /mcp 세 경로가 같은 대상 업체 ID를 반환하며, 다른 부서·own 범위 밖·소프트 삭제 업체 번호 검색은 결과에서 제외한다(전체 응답 형식·정렬·상한을 같게 만들라는 뜻은 아니다). 3) PostgreSQL과 실제 App.Handler, 로그인 세션을 거치는 회귀 테스트가 수정 전 MCP 번호 검색 실패와 수정 후 성공을 증명하고 이름·사업자번호 검색 및 기존 MCP 상한·포털 거부 테스트도 통과한다.
- 건드릴 파일: `internal/httpapi/integrations.go:runMCPTool` — search_suppliers의 기존 검색 괄호 안에 `OR supplier_number ILIKE '%'||$1||'%'` 추가; deleted_at, orgInScope/own 조건, 바인딩 인자, 금액 마스킹, ORDER BY name LIMIT 100은 유지. `internal/httpapi/mcptools_test.go:callMCPTool, toolRows` — 기존 helper를 이용한 TestMCPSupplierNumberSearchMatchesREST 신설(제안 이름); 필요하면 테스트 파일만 분리. 읽고 재사용할 곳: `internal/httpapi/datascope_test.go:newScopeWorld, scopeWorld.call, wipe`, `internal/httpapi/login_integration_test.go:newTestApp`, `internal/httpapi/suppliers.go:listSuppliers`, `internal/httpapi/analytics.go:globalSearch`, `internal/httpapi/app.go:Handler` 라우팅. REST 프로덕션 코드는 이미 번호 조건이 있어 수정 불필요.
- 검증 명령: 저장소 루트에서 `go test ./internal/... ./cmd/... -count=1` (정찰 실행 통과, httpapi 1.436s; 세 DSN unset으로 DB 테스트는 skip). 구현 검증은 전용 PostgreSQL DB의 VENDRA_TEST_DSN을 설정하고 `go test ./internal/httpapi -run 'TestMCPSupplierNumberSearchMatchesREST|TestMCPToolAnswersAreBounded|TestMCPRefusesSupplierPortalAccounts|TestDepartmentScopeRefusesAnotherDepartmentsRecords|TestOwnScopeRefusesAColleaguesRecords' -count=1 -v`; 신규 테스트 이름은 구현 후 실제 이름에 맞출 것, SKIP이면 검증 완료 아님. 전체 DB 검증에는 VENDRA_TEST_DSN / VENDRA_TEST_MIGRATE_DSN / VENDRA_TEST_UPGRADE_DSN을 서로 다른 테스트 DB로 설정한 뒤 위 전체 명령 실행(뒤 둘은 빈 DB). 마무리 `go vet ./internal/... ./cmd/...`, `gofmt -l internal cmd`, `git diff --check`. 웹 변경은 범위 밖.
- 위험과 피할 것: newScopeWorld는 supplier_number/business_number/name을 모두 SC-MINE 같은 값으로 만든다; 그대로 쓰면 기존 코드도 통과하므로 두 업체의 이름·사업자번호를 번호와 겹치지 않는 별개 값으로 바꾸고 번호는 SC- 접두사를 유지해 wipe가 청소하도록 한다. 실제 Handler/API 응답의 ID를 검사하고 SQL 문자열 검사·가짜 DB·Principal 직접 주입을 회귀 증거로 쓰지 않는다. 다른 부서 번호가 OR 괄호 밖으로 빠져 데이터 범위를 우회하지 않게 한다. 소프트 삭제는 소유 업체에 적용한 뒤 세 경로에서 누락되는지 확인한다. 테스트는 t.Parallel 없이 기존 fixture 규칙을 따르고 cleanup은 context.Background 사용; 새 비밀번호 리터럴을 추가하지 않는다. auth·workflows·migrations·.github/workflows, 통화 정책, 검색 공통화, wildcard 의미 변경, limit 인자 지원을 함께 바꾸지 않는다. 신규 재현은 정찰에서 미실행이며 SQL 누락과 REST 차이로 판단했다.
- 차선 후보: 사용자 가이드 MCP 도구표를 실제 tools/list 응답과 양방향 대조하는 가드 (가치 2 / 위험 1 / 작업량 S) — 1순위가 이미 해결된 경우만 선택. 실제 로그인과 Handler를 통해 목록을 받고 guide_docs_test.go의 repoFile 방식으로 USER_GUIDE.md 4.6 표를 읽어 누락·유령·중복 도구를 검출; mcpTools 변수나 Go 소스 긁기만으로 응답을 대체하지 않는다.
