# Hunter v1.17.0

저장한 **목록 보기**가 다음 방문에 조용히 사라지는 대신, 읽기 검사가 버릴 조건을 저장하는 순간 거절하도록 고친 릴리즈입니다. 서버 API·권한·감사 기록과 저장한 보기의 보관 규칙은 달라지지 않으며 일반 PostgreSQL·네 환경변수·서비스 Docker 이미지 하나의 기본 배포를 유지합니다.

## 사용자가 달라지는 점

- **"저장했습니다"가 다음 방문에도 남아 있습니다.** 저장한 보기를 읽는 `readListPreferences`(`web/src/saved-list-views.ts`)는 조건 문자열이 8192자를 넘는 항목을 버립니다. 그런데 저장은 검색어와 각 필터 값이 500자 이하인지만 확인했습니다. 한글은 URL 인코딩에서 한 글자가 `%XX%XX%XX` 9자로 늘어나므로, 검색어 500자와 필터 500자는 값 한도를 모두 통과하고도 조건 문자열이 8192자를 넘습니다. 그래서 저장 성공 안내를 본 사용자가 다음 방문에 그 보기를 찾지 못했습니다. 이제 저장이 읽기와 **같은 한도·같은 값**(`savedListQueryLimit`)을 검사하고, 통과하지 못하면 "검색어와 필터가 너무 길어 이 보기를 저장할 수 없습니다. 조건을 줄여 주세요."로 거절합니다.
- **저장 조건은 폼 순서대로 한 가지씩 알려줍니다.** 다섯 조건을 순수 함수 `savedViewSaveError` 로 모으고 `ListTools.save()`(`web/src/list-tools.tsx`)는 그 함수만 호출합니다. 이름 없음 → 보기 8개 상한 → 같은 이름 → 값 500자 초과 → 조건 문자열 한도 초과의 순서이며, 이름 칸이 고칠 수 있는 오류(이름 없음·같은 이름)에만 초점을 이름 입력으로 되돌립니다. 여러 조건이 한꺼번에 어긋나도 사용자가 먼저 고칠 수 있는 항목을 안내합니다.
- **보관 규칙과 화면 동작은 그대로입니다.** 사용자·메뉴별 최대 8개, 값 500자 한도와 자르기, 허용된 목록 조건만 보관하고 상세 ID·임의 URL 매개변수·폼 초안·비밀값을 저장하지 않는 규칙, 저장과 복원이 같은 조건 문자열을 비교하는 동작은 달라지지 않습니다. 이미 저장된 보기도 다시 해석하지 않습니다.

## 운영 조건과 한계

8192는 저장한 보기 하나를 읽을 때 검사하는 한도이며 브라우저 저장소 용량 한도가 아닙니다. 저장소 용량은 원점 단위로 저장한 전체 자료에 대해 측정되고 값 하나마다 정해지지 않습니다. 이 구분을 코드 주석에 바로잡았고, 읽기와 저장이 같은 상수를 함께 씁니다. 실제 저장소 용량이 가득 찬 경우는 이 검사와 별개이며 이번 릴리즈가 다루지 않습니다. 서버 API·권한·감사 기록은 바꾸지 않았고 관리자 설정 항목도 추가하지 않았습니다.

## 검증과 배포

`web/tests/saved-list-views.test.mjs` 에 저장 조건 검사 8개를 넣었습니다. 검색어와 필터가 각각 한글 500자인 조건 문자열이 실제로 8192자를 넘고 `readListPreferences` 가 그 보기를 버리는 것을 먼저 확인한 뒤 같은 입력의 저장이 거절되는 것을, 읽기가 보존하는 짧은 조건은 저장이 통과하고 다음 방문에 복원되는 것을 확인합니다. 이름 없음·아홉 번째 보기·같은 이름·500자 초과 값은 각각 거절되고 초점 복귀 여부가 고정되며, 모든 조건이 동시에 어긋날 때 메시지가 폼 순서를 따르는 것도 검사합니다. 어느 조건 하나를 지우면 검사가 실패합니다. 릴리즈 커밋에서 실행한 검사와 건너뛴 검사는 [검증 기록](validation.md)에 적었습니다.

화면 캡처는 v1.9.0의 검증 장면을 보존했습니다. 가이드·README·llms.txt·openapi.json 의 버전 표기를 갱신하고 가이드 HTML·PDF 를 재생성했습니다.
