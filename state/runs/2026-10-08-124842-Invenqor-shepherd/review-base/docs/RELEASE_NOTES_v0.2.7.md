# Invenqor Server·Agent v0.2.7 릴리즈 노트

릴리즈 일자: 2026-07-29
호환 Agent: v0.2.7

이번 릴리즈는 네 가지 영역을 다룹니다. Keycloak·사용자 관리 결함 수정, 자산
시각화 체계, 수집 결과의 자동 분류·관계 추론, 그리고 Agent 자동 업데이트의
결함 수정과 운영 단순화입니다.

## 1. Keycloak 연동과 사용자 관리 결함 수정

### 사용자 관리

- **사용자 목록에서 역할이 사라지던 문제.** 조회 결과를 담는 slice가 커지는 동안
  포인터를 보관해, `append`가 재할당되면 역할 지정이 버려진 배열에 기록되었습니다.
  10개 계정 중 9개가 역할 없음으로 표시되어, 실제 권한이 있는 계정이 콘솔에서
  권한 없는 것처럼 보였습니다.
- **마지막 역할까지 회수할 수 있던 문제.** 권한은 역할에서만 나오므로 로그인은
  되지만 아무것도 할 수 없는 계정이 만들어졌습니다. 생성 시에는 이미 거부하던
  조건을 수정 시에도 적용하고, 콘솔은 요청 전에 안내합니다.
- **삭제한 사용자 ID를 재사용할 수 없던 문제.** `normalized_username`에 UNIQUE
  제약이 있는데 논리 삭제가 이름을 계속 점유했고, 막고 있는 행은 콘솔에 보이지
  않았습니다. 이제 삭제 시 이름을 해제하고 원래 이름은 `원래이름#deleted-<id>`로
  보존해 감사 추적을 유지합니다.

### Keycloak

- **SSO 직후 로그아웃 상태로 보이던 문제.** Session Cookie가 `SameSite=Strict`라
  Keycloak Callback이 되돌아오는 외부 사이트 이동에서 전송되지 않았습니다. `Lax`로
  변경했고, 상태를 바꾸는 요청은 여전히 CSRF 헤더와 Cookie 이중 확인을 요구합니다.
- **평문 HTTP 설치에서 로그인이 조용히 실패하던 문제.** Cookie에 항상 `Secure`가
  붙어 브라우저가 저장하지 않았습니다. 문서가 지원한다고 명시한 폐쇄망 HTTP 구성이
  로그인 성공처럼 보이고 실패했습니다. 이제 요청이 HTTPS일 때만(직접 TLS 또는
  `X-Forwarded-Proto: https`) `Secure`를 부여합니다.
- **재사용된 Callback이 미아 Session을 남기던 문제.** 일회용 flow를 Session 생성
  **뒤에** 소비했습니다. 이제 먼저 청구합니다.
- **브라우저 이동에 JSON 오류를 반환하던 문제.** 사용자에게는 JSON만 있는 빈
  화면이었습니다. 이제 원인 코드와 request ID를 붙여 로그인 화면으로 돌려보내고,
  조치 문구와 함께 진단 로그(`keycloak` 구성요소)에 기록합니다. Keycloak 자체
  오류 응답도 처리합니다.
- 도달 불가한 issuer와 미설정 client secret이 HTTP 500이던 것을 각각의 코드로
  구분합니다. client secret이 없으면 로그인 화면이 Keycloak 버튼을 노출하지 않습니다.
- 활성화 전 연결 테스트가 아무 검증도 하지 않아 빈 양식이 discovery 실패로 보이던
  문제, 그리고 기존 로컬 계정과 이름이 겹치는 Keycloak 사용자가 불투명하게
  실패하던 문제(`KEYCLOAK_USERNAME_CONFLICT`로 명시, 자동 연결하지 않음)를
  수정했습니다.
- 버려진 `oidc_flows` 행이 무한히 누적되던 문제를 수정했습니다.

## 2. 자산 시각화

하나의 집계 API 위에 여섯 개 화면을 제공합니다. 같은 필터를 공유하므로 화면 간
수치가 어긋나지 않습니다.

- **구성**: 환경 → 자산 유형 treemap
- **위험 매트릭스**: 중요도 × 환경 히트맵, 정지 자산 렌즈 전환
- **신선도**: 마지막 확인 시점 구간
- **증감**: 신규·폐기 발산 막대
- **성장 추이**: 누적 규모, crosshair
- **관계**: 자산 관계 토폴로지

타일·칸을 선택하면 모든 화면이 좁혀지고, 각 화면은 표와 CSV를 함께 제공합니다.
`GET /api/v1/assets/visualization`이 데이터베이스에서 집계하므로 브라우저가 전체
인벤토리를 내려받지 않습니다.

색은 취향이 아니라 검증으로 결정했습니다. 범주형 8색은 고정 순서이며 콘솔의 실제
light/dark 표면에서 색각 이상 분리도를 통과합니다. 히트맵·신선도는 단일 색상 단조
단계이고, 증감은 중립 기준선을 가진 발산 색 한 쌍입니다. 칸 안 글자색은 측정된
명암비로 선택합니다(노란 칸 위 흰 글자 2.2:1 → 검정 7.4:1). 토폴로지는 노드를
유형별 색으로 칠하지 않습니다. 노드 그래프는 임의의 두 색을 나란히 놓는 형태여서
여덟 색이 색각 검증을 통과할 수 없기 때문에, 연결 수를 단일 순차 색으로 표현하고
유형은 필터로 옮겼습니다. 색 없이도 읽을 수 있도록 질감 전환과 `forced-colors`를
지원합니다.

기존 콘솔 차트 팔레트는 검증에 실패했습니다(2개 색상이 채도 하한 미달, 파랑과
청록이 정상 시야에서 ΔE 14.5).

**함께 수정한 결함**: SQLite는 시각을 Go 드라이버 형식으로 저장하는데 SQLite의
`DATE()`가 이를 파싱하지 못해 NULL을 반환했습니다. 그 결과 기동 대체 모드에서 모든
일별 시리즈가 조용히 비어 있었고, 대시보드의 7일 추이도 포함됩니다.

## 3. 자산 자동 분류와 관계 추론

수집 결과에는 업무 맥락이 없었습니다. 환경은 전부 `other`, 중요도는 전부 `normal`,
관계는 모든 레코드에 대해 일반 `belongs_to_host` 하나씩 — 리눅스 호스트 한 대의
설치 패키지만으로 수천 개의 간선이 만들어졌습니다.

- **규칙 기반 분류**: 우선순위 순으로 실행되고, 뒤의 규칙은 앞의 규칙이 정한 값을
  조건으로 쓸 수 있습니다. “운영 환경의 데이터베이스는 치명”이 별도 엔진 없이
  표현됩니다. 모든 자산에 적용 규칙·확신도·시각이 기록되고, 확신도는 값을 정한
  규칙 중 가장 낮은 값을 씁니다.
- **운영자 지정 우선**: 사람이 수정한 필드는 어떤 자동 실행에서도 되돌리지 않습니다.
- **재분류**: 규칙 변경을 이미 저장된 인벤토리에 다시 적용합니다.
- **환경 규칙은 이름 토큰을 비교**합니다. 부분 문자열 `*stg*`는 `postgresql`에도
  걸려 Postgres 서비스가 staging으로 분류되었습니다. 구성요소는 자신이 읽힌 장비의
  환경을 물려받습니다.
- **관계는 데이터가 뒷받침하는 것만** 만듭니다. 한 수집 이벤트의 동일 장비 사실로
  인터페이스·볼륨·하드웨어·컨테이너 런타임·큐레이션된 미들웨어에 유형이 있는 간선을
  만들고 근거를 기록합니다. 실측: 자산 1,434건에서 관계 196건(이전에는 1,434건).
- **추론하지 않는 것**: 서비스 간 의존 관계는 Agent가 상대편을 보고하지 않으므로
  만들어낸 값이 됩니다. 변경관리가 그것을 근거로 판단하므로, 없는 것이 잘못된 것보다
  낫습니다. 동일 machine identifier는 이미지 복제이므로 `duplicate_of` **제안**으로만
  남기고 병합은 사람이 결정합니다.
- 콘솔 **설정 → 자산 분류**에서 규칙의 조건·결과·적용 건수를 확인하고, 재분류를
  실행하고, 제안을 승인·거부합니다.

## 4. Agent 자동 업데이트

### 수정한 결함

- **잘못된 서명으로도 게시가 성공했습니다.** Server에 공개키가 없어 서명 형식만
  확인했기 때문입니다. 게시는 성공하고 그 뒤 fleet의 모든 Agent가 검증에 실패하며,
  증상은 각 호스트 로그 한 줄뿐이었습니다. `INVENQOR_UPDATE_PUBLIC_KEY`를 설정하면
  게시 시점에 `UPDATE_SIGNATURE_REJECTED`로 거부합니다. 콘솔은 현재 검증 가능
  여부를 표시하므로 검증하지 않은 것을 검증한 것처럼 보이지 않습니다.
- **실행되지 않는 바이너리가 활성화될 수 있었습니다.** 서명과 해시가 맞아도 실행이
  불가능한 빌드를 설치하면 그 릴리즈를 받은 모든 호스트에서 수집이 멈추고 장비마다
  손으로 복구해야 합니다. 이제 설치 직전에 스테이징된 바이너리를 실행해
  `--version`을 확인하고, 실패하면 설치를 중단하고 기존 바이너리를 유지합니다.
- **OpenRC·SysV에서는 업데이트가 영구히 적용되지 않았습니다.** systemd만 감시
  경로를 설치했습니다. 두 init 스크립트가 서비스 시작 시 적용합니다.
- **스테이징 파일이 삭제되지 않아** 업데이트마다 수 MB가 상태 디렉터리에 남았습니다.
- **fleet 전체가 동시에 확인**했습니다. 첫 확인 지연과 주기를 Agent 식별자로
  결정적으로 분산해, 같은 호스트가 항상 같은 순번을 유지하면서 서버가 몰리지
  않게 했습니다.
- 문서에 있으나 파서가 거부하던 플래그가 있었습니다. 두 목록을 한 곳에서 관리하고
  테스트로 고정했습니다.

### 운영 단순화

- **재업로드 없는 rollout 조절**: `PATCH /api/v1/admin/agent-updates/{release}`.
  콘솔에서 10/25/50/100% 버튼과 **중단**(rollout 0) 버튼을 제공합니다.
- **적용 현황 가시화**: `GET /api/v1/admin/agent-updates`가 릴리즈별 적용 대수와
  대상 대수, fleet 버전 분포를 반환합니다.
- **서명 파일 그대로 업로드**: `openssl pkeyutl -sign`이 만든 64 byte 원본을 그대로
  올릴 수 있고, base64 문자열(줄바꿈 포함)도 받습니다.
- **한 번의 명령으로 갱신**: `invenqor-agent --update-now`가 확인·검증·자기 점검·
  설치를 수행합니다. 권한이 없으면 스테이징까지만 진행하고 종료 코드 3과 함께 필요한
  명령을 알려 줍니다.
- **서명된 롤백**: `allow_downgrade` 릴리즈만 Agent가 하위 버전으로 받아들입니다.
  잘못된 릴리즈에 갇힌 fleet을 꺼낼 수 있습니다.
- `--status`와 `--diagnose`가 업데이트 상태(실행 버전, 대기 버전, 마지막 오류,
  적용 경로)를 보고합니다.

## 호환성

- 마이그레이션 `005_asset_classification`이 추가됩니다(PostgreSQL·SQLite 양쪽).
  기존 데이터는 변환하지 않고 열만 추가하며, 최초 실행 시 표준 분류 규칙을 넣습니다.
  이미 수집된 자산에 적용하려면 **설정 → 자산 분류 → 저장된 자산 재분류**를 실행하십시오.
- Agent가 만드는 관계 유형이 일반 `belongs_to_host`에서 유형이 있는 관계로
  바뀝니다. 기존 행은 그대로 남습니다.
- Session Cookie가 `SameSite=Lax`가 되고, 평문 HTTP에서는 `Secure`가 붙지
  않습니다. TLS를 상위 Proxy에서 종료하면 `X-Forwarded-Proto: https`를 전달하십시오.
- 자동 업데이트를 사용하는 배포는 `INVENQOR_UPDATE_PUBLIC_KEY` 설정을 권장합니다.
  설정하지 않으면 이전과 동일하게 동작하지만 게시 시점 검증이 없습니다.
- 게시 API는 같은 버전·아키텍처의 재게시를 거부합니다. rollout 변경은 PATCH를
  사용하십시오.
