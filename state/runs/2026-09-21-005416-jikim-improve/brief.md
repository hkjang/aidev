- 과제: AI 채팅의 HTTP 오류 처리와 세션 만료 처리를 일반 API 클라이언트와 일치시키기 (가치 3 / 위험 1 / 작업량 S)
- 왜: `web/src/lib/api.ts:streamChat()`은 401에서도 `jikim:unauthorized`를 보내지 않아 `AuthProvider`의 사용자 초기화가 실행되지 않고, `AiPage`에는 서버의 JSON 오류 봉투가 그대로 표시된다. 일반 `api()`와 오류 처리를 공유하면 채팅에서도 기존 재로그인 흐름이 작동하고 400·429·503 등의 한국어 메시지를 읽을 수 있다.
- 수용 기준: 1) `/api/v1/ai/chat`이 401을 반환하면 일반 `api()`와 동일하게 요청당 세션 만료 이벤트를 정확히 한 번 보내고 실제 `AuthProvider`의 user가 null이 된다. 2) 두 경로 모두 JSON 오류의 message/status/details를 같은 `ApiError` 계약으로 전달하고, text 오류도 기존처럼 읽을 수 있으며 400·403·429·500·503은 세션을 지우지 않는다. 3) 실제 HTTP 응답과 실제 `Response`/`ReadableStream`을 통과하는 회귀 테스트가 위 동작 및 정상 SSE 한국어 청크 수신·AbortSignal 취소 유지를 증명한다. `api`, `streamChat`, `AuthProvider` 자체를 mock하거나 이벤트를 테스트가 직접 발송해서 배선을 우회하지 않는다.
- 건드릴 파일: `web/src/lib/api.ts:api, streamChat, ApiError` — 비성공 응답의 본문 해석·메시지 선택·401 알림을 작은 내부 공통 함수로 모으고 두 호출자가 사용. `web/src/lib/api.test.ts` — 일반/스트리밍 HTTP 오류의 동일 계약과 정상 SSE·취소 회귀 검증. `web/src/lib/api.auth.test.tsx`(신규 제안) — 실제 AuthProvider/useAuth를 렌더링하고 로그인된 `/session` 응답 이후 streamChat 401로 user가 사라지는 통합 검사. `docs/USER_GUIDE.md:3.7 AI 보안 도우미` — 필요하면 일반 API와 같은 세션 만료 처리·읽기 쉬운 오류 안내를 한 문장으로 반영.
- 검증 명령: 저장소 루트에서 `go test ./...` (정찰에서 exit 0 확인; PostgreSQL opt-in 테스트는 DSN 없으면 skip). 프런트 의존성 준비 후 `npm --prefix web ci --no-audit --no-fund`, `npm --prefix web test -- --maxWorkers=1`, `npm --prefix web run lint`, `VITE_APP_VERSION="$(./scripts/version.sh)" npm --prefix web run build`. 최종 `./scripts/verify.sh`는 Go·프런트·문서·Compose를 모두 검사한다. 정찰 환경은 Node v22.23.1/npm 10.9.8이고 web/node_modules가 없어 프런트 명령과 전체 verify는 미실행; 저장소/CI 기준 Node 24를 사용한다.
- 위험과 피할 것: `internal/httpapi/auth*`, `server.go:withAuth`, `web/src/contexts/AuthContext.tsx`, `web/src/App.tsx:ProtectedRoute`, OIDC/silentSso, migrations, .github/workflows는 읽기 참조로만 두고 기존 인증·재로그인 정책을 변경하지 않는다. 500을 세션 만료로 취급하지 않는다. 성공 SSE body를 JSON/text 공통 파서로 먼저 소비하지 않는다. AbortError를 ApiError로 바꾸거나 SSE 파서 규약·[DONE]·재시도·대화 보존까지 확대하지 않는다. 기존 JSON ApiError.details와 unwrap/token 봉투 보존 계약을 유지한다. 미머지 메일·출력 축소 PR, 버전·CHANGELOG·PNG·PDF 재생성은 범위 밖이다.
- 차선 후보: `streamChat()`이 onChunk 콜백 예외를 JSON 파싱 오류로 오인해 원문 JSON을 다시 전달하는 문제 — 현재 try 블록이 JSON.parse와 onChunk를 함께 감싸 catch에서 onChunk(raw)를 다시 호출한다. 1순위가 다른 브랜치에서 이미 해결됐을 때만, 파싱 try 범위를 좁혀 소비자 예외는 그대로 한 번 전파하고 실제 스트림+던지는 콜백으로 중복 호출 부재를 검증한다(가치 2 / 위험 1 / 작업량 S).

근거와 구현 순서:
1. 기준 HEAD는 `9ea43d0`(v0.2.16). `internal/httpapi/server.go`의 POST /api/v1/ai/chat 등록은 withAuth를 통과하며 withAuth는 세션 부재/만료에 401, 조회 장애에는 별도 서버 오류를 반환한다. `internal/httpapi/ai.go:aiChat`은 스트림 시작 전 검증·설정·제한·공급자 오류를 JSON으로 반환한다.
2. `web/src/contexts/AuthContext.tsx:AuthProvider`는 `jikim:unauthorized`를 구독해 setUser(null)를 실행한다. `web/src/App.tsx:ProtectedRoute`가 그 결과로 기존 로그인/조용한 SSO를 선택한다. `web/src/pages/AiPage.tsx:submit`은 caught.message를 그대로 화면에 보여 준다.
3. 정찰 재현: Node의 실제 loopback HTTP 서버에서 `{error:{code:"unauthorized",message:"로그인이 필요합니다"},request_id:"scout"}`를 401 JSON으로 반환하고, 소스 api.ts를 Node --experimental-strip-types로 직접 import해 native fetch로 호출했다. 일반 api 결과는 message="로그인이 필요합니다", 이벤트 1회; streamChat은 JSON 원문 message, 이벤트 0회였다. 브라우저 화면 이동 자체는 미실행이며 위 배선에 근거한 판단이다.
4. 테스트는 node:http 임시 서버 + 원래 native fetch를 쓰고, 상대 URL만 localhost origin으로 해석하는 얇은 adapter를 둘 수 있다. `/session`은 실제 AuthProvider 초기 로딩을 통과시키고 chat 응답을 401/500 등으로 바꾼다. 응답 객체와 reader를 손으로 만든 가짜로 대체하지 않는다. 서버·리스너·fetch 교체는 종료 시 복원한다. 기존 App.silentSso.test.tsx는 AuthProvider와 api를 mock하므로 이번 통합 증거로 재사용하지 않는다.
5. 예상 작업 35분(재현/회귀 15, 공통 오류 처리 10, 검증·문서 10) + 예비 10분. Node/의존성 환경 문제가 생기면 그 사실을 남기고 범위 확장 없이 동일 과제를 마친다. 위 테스트 구성은 제안이며 실제 Vitest 환경 실행 가능 여부는 구현자가 확인해야 한다.
