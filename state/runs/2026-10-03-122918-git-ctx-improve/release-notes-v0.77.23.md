# git-ctx v0.77.23

이번 릴리스는 **백그라운드 워커가 다음 색인 작업을 찾기까지의 유휴 대기 간격에 이름과 주입 지점을 줍니다.** 그 값은 `New()` 의 구조체 리터럴에 2초로 적혀 있어 바깥에서 바꿀 방법이 없었고, 그래서 시험 픽스처는 자기가 방금 큐에 넣은 작업을 기다리며 틱을 통째로 흘렸습니다. **운영 동작은 바뀌지 않습니다** — 기본값은 같은 2초이고, 이 간격을 조정하는 환경변수나 관리 설정은 **없습니다.** 새 필드는 `FromEnv` 가 채우지 않으며 프로세스 안에서만 지정됩니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

> **재색인도 마이그레이션도 필요하지 않습니다.** 저장되는 내용과 검색 결과는 바뀌지 않으며, 설정을 따로 넣지 않은 설치본의 동작은 전과 한 틱도 다르지 않습니다.

## 수정

### 유휴 폴링 간격이 `New()` 안에 적혀 있어 아무것도 바꿀 수 없었습니다

- `internal/worker/worker.go` 의 `New` 는 `poll: 2 * time.Second` 를 구조체 리터럴에 직접 넣었고, 루프는 `time.NewTicker(w.poll)` 로 그 값을 씁니다. 이름도 주입 지점도 없었으므로 이 간격은 소스를 고치지 않고는 손댈 수 없었습니다.
- 그 값을 `DefaultPollInterval` 상수로 끌어내고 `Worker.SetPollInterval` 을 더했습니다. **비양수 값은 무시**하므로 아무것도 지정하지 않은 설치본은 기본값을 그대로 쓰고, 호출자가 루프를 바쁜 대기로 바꿀 수도 없습니다.
- 주입 경로는 `config.Config.WorkerPollInterval` → `App.startBackground` → `Worker.SetPollInterval` 한 줄씩입니다. 이 필드는 이미 있던 `WorkerIdentity` 와 같은 관례를 따릅니다 — 운영에서는 0 이고 `FromEnv` 가 채우지 않으며, 두 복제본을 구분해야 하는 시험처럼 특정 값이 필요한 쪽만 지정합니다. **운영자가 돌릴 손잡이가 생긴 것이 아닙니다.**
- **재시도 일정은 건드리지 않았습니다.** `claim` 은 여전히 `next_run_at` 으로 거르므로, 이 간격이 정하는 것은 "기한이 된 작업을 언제 알아차리는가" 뿐입니다.
- 기본값을 더 짧게 바꾸지 않은 것은 의도입니다. 큐를 더 자주 읽으면 이 플랫폼이 사내 GitLab·Bitbucket 서버에 보내는 호출이 그만큼 늘고, 매 틱은 모든 복제본에서 공유 작업 큐에 두 번씩 질의합니다.

### 시험 픽스처가 자기가 방금 넣은 작업을 기다리느라 틱을 통째로 흘렸습니다

- 작업 등록은 즉시 일어납니다 — 저장소를 등록하면 그 요청 안에서 `index_jobs` 에 `pending` 행이 들어갑니다. 루프는 시작할 때 한 번 훑고 그 다음은 틱까지 기다리므로, 등록 직후의 작업은 남은 틱을 그냥 흘렸고 `RunOnce` 는 틱당 한 건만 집으므로 저장소 N 개는 틱 N 번을 썼습니다.
- 그래서 `internal/app` 수트의 벽시계는 2초 단위로 양자화되어 있었습니다 — 저장소 한 개 2.3~2.5초, 두 개 4.2초, 다섯 개 10.3초. 단정이 아니라 대기였습니다.
- 픽스처가 짧은 간격을 넘기도록 바꾸자 그 수트는 **개발 기계에서 약 40% 짧아졌습니다**(평문 약 117초 → 약 73초). 수트의 벽시계는 기계와 실행마다 흔들리므로 이 수치는 한 기계의 측정값입니다. 릴리스 빌드 잡은 이 수트를 평문과 `-race` 로 두 번 돌리고, 그 뒤에도 통합 시험·`govulncheck`·Docker 빌드·패키징을 하나의 타임아웃 안에서 끝내야 합니다.
- **단정은 하나도 지우지 않았고 건너뛴 시험도 없습니다.** 하위 통과와 건너뜀 수가 그대로이고, 최상위 통과는 새 시험 하나만큼 늘었습니다.

## 영향 범위

- 지정하지 않은 설치본의 동작은 전과 완전히 동일합니다. `WorkerPollInterval` 은 0 이고, 0 은 무시되며, 기본값은 종전과 같은 2초입니다.
- 작업이 처리되는 순서·횟수·재시도 간격은 바뀌지 않습니다. 이 값은 큐를 들여다보는 주기일 뿐 작업 자체의 일정이 아닙니다.
- 환경변수와 API 스키마는 바뀌지 않습니다. `FromEnv` 는 이 필드를 채우지 않으므로 운영 배포가 새로 넣을 설정값은 없습니다.
- `internal/worker` 패키지를 직접 쓰는 코드에는 `DefaultPollInterval` 상수와 `SetPollInterval` 메서드가 추가됩니다. 기존 시그니처는 그대로입니다.

## 검증

- 대역 타입을 쓰지 않고 실제 배선으로 회귀 시험했습니다. `internal/app/worker_poll_test.go` 는 실제 `New(ctx, config.Config{…})` 로 앱을 띄우고 실제 `Handler().ServeHTTP` 의 `POST /api/v1/admin/repositories` 로 저장소를 등록한 뒤, 실제 `index_jobs` 행이 집히기까지의 지연만으로 단정합니다 — 손으로 조립한 워커가 아니라 지정한 값이 실제로 루프에 닿는지를 봅니다. 색인 완료 시각이 아니라 집기 지연에 걸려 있으므로 색인이 느려져도 흔들리지 않습니다.
- 배선을 들어내면 그 시험이 실패함을 되돌림 프로브로 확인했습니다 — `App.startBackground` 의 주입 한 줄을 지우면 `worker_poll_test.go` 가 `timed out after 1s waiting for the worker to claim the queued job` 으로 실패하고, 픽스처의 간격만 2초로 되돌리면 수트의 벽시계도 함께 되돌아옵니다.
- `internal/worker/poll_interval_test.go` 는 반대 방향의 대조군입니다. 비양수 값이 기본값을 남기고 양수 값만 간격을 바꿈을 단정합니다.
- 일반·FTS5 빌드와 전체 테스트, 전체 race, `vet`·`gofmt` 통과
- 짧은 간격이 새 경쟁을 만들지 않음을 `internal/app`·`internal/worker` 의 `-race -count=2` 로 확인했습니다(경쟁 보고 0).
- 버전 정합성·회귀 시험, Kubernetes Kustomize 렌더링과 콘솔 구문·계약 시험 통과
- 로컬 검증 결과는 `docs/completion-audit.md`에 기록했습니다.
- PostgreSQL·pgvector·Vault 통합, `govulncheck`, Docker 이미지 빌드·오프라인 아카이브 검증 및 GitHub 공개는 태그 푸시 후 릴리스 워크플로에서 수행합니다. PostgreSQL 경로에서 짧은 간격이 `claim` 의 잠금 경쟁에 닿는 것은 그 잡에서 처음 돕니다.

## 업그레이드 참고

- 마이그레이션과 재색인은 필요하지 않습니다.
- 설정·환경변수·API 스키마 변경은 없습니다. 새 필드는 운영에서 비어 있습니다.
- 복제본을 여러 개 띄운 배포도 그대로입니다. 기본 간격이 같으므로 공유 큐에 가는 질의 수는 전과 같습니다.
