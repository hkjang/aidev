release: v0.77.23

백그라운드 워커가 다음 색인 작업을 찾기까지의 유휴 대기 간격에 이름과 주입 지점을 줍니다.
그 값은 internal/worker/worker.go 의 New 안에 poll: 2 * time.Second 로 적혀 있어 바깥에서
바꿀 방법이 없었습니다. 작업 등록은 즉시 일어나므로 — 저장소를 등록하면 그 요청 안에서
index_jobs 에 pending 행이 들어갑니다 — 루프가 시작된 뒤 큐에 들어간 작업은 누가
들여다보기까지 남은 틱을 그대로 흘렸고, RunOnce 는 틱당 한 건만 집으므로 저장소 N 개는 틱
N 번을 썼습니다. 그것이 internal/app 수트 벽시계의 대부분이었고 — 저장소 한 개 2.3~2.5초,
두 개 4.2초, 다섯 개 10.3초로 양자화되어 있었습니다 — 릴리스 빌드 잡은 이 수트를 평문과
-race 로 두 번 돌린 뒤에도 통합 시험과 govulncheck, Docker 빌드와 패키징을 하나의 타임아웃
안에서 끝내야 합니다. 기본값을 줄이는 대신 주입 경로만 더했습니다 —
config.Config.WorkerPollInterval 이 간격을 나르고(운영에서 0, FromEnv 가 채우지 않으며 이미
있던 WorkerIdentity 와 같은 모양), App.startBackground 가 그것을 넘기며,
Worker.SetPollInterval 은 비양수 값을 무시하므로 아무것도 지정하지 않은 설치본은
DefaultPollInterval 을 그대로 쓰고 호출자가 루프를 바쁜 대기로 바꿀 수도 없습니다. FromEnv 가
이 필드를 채우지 않으므로 운영자가 돌릴 손잡이가 생긴 것은 아닙니다. 운영 기본값은 이름을
얻었을 뿐 2초 그대로입니다 — 큐를 더 자주 읽으면 이 플랫폼이 사내 GitLab·Bitbucket 서버에
보내는 호출이 그만큼 늘고, 매 틱은 모든 복제본에서 공유 작업 큐에 두 번씩 질의합니다. 재시도
일정은 건드리지 않았습니다 — claim 은 여전히 next_run_at 으로 거르므로 이 간격이 정하는 것은
기한이 된 작업을 언제 알아차리는가 뿐입니다. 대역 타입 없이 실제 배선으로 회귀 시험했습니다 —
worker_poll_test.go 는 실제 New(ctx, config.Config{…}) 로 앱을 띄우고 실제
Handler().ServeHTTP 의 POST /api/v1/admin/repositories 로 저장소를 등록한 뒤 실제 index_jobs
행이 집히기까지의 지연만으로 단언하며, 색인 완료 시각이 아니라 집기 지연에 걸려 있어 색인이
느려져도 흔들리지 않습니다. 배선을 들어내면 그 시험이 실패하고 픽스처의 간격만 2초로 되돌리면
수트의 벽시계도 함께 되돌아옴을 되돌림 프로브로 확인했습니다. poll_interval_test.go 는 비양수
값이 기본값을 남기고 양수 값만 간격을 바꿈을 단언하는 반대 방향의 대조군입니다. 개발 기계에서
internal/app 수트의 벽시계는 약 40% 짧아졌고(수치는 기계와 실행마다 흔들립니다), 단정은 하나도
지우지 않았으며 건너뛴 시험도 없습니다. 지정하지 않은 설치본의 동작은 전과 완전히 같고,
환경변수와 API 스키마 변경은 없으며 마이그레이션과 재색인은 필요하지 않습니다.
