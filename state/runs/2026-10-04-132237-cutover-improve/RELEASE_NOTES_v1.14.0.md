## KCB Cutover Dashboard v1.14.0

### 버그 수정
- **활동 데이터 읽기가 실패해도 상황판이 "0% 완료 (0/0)" 빈 화면을 조용히 보여주는 것 수정**: 상황판(`/`)·전광판(`/pc`)·관리 화면(`/admin`) 세 화면은 모두 `GET /api/activities` 를 폴링해 작업 트리를 그립니다. 그런데 이 읽기가 **서버에서 실패했을 때**(`activity.json` 파일 읽기 오류, 권한 오류 등) 서버는 `500` 과 함께 **`activities` 가 빈 배열인 정상 모양의 JSON** 을 돌려주고, 세 화면의 데이터 읽기 코드는 **HTTP 상태를 전혀 검사하지 않았습니다.**
  - 그래서 응답이 **정상 데이터로 파싱되어** 오류가 사라졌습니다. 화면에는 오류가 한 글자도 뜨지 않고, 대신 **"등록된 작업 없음"** 과 **"0% 완료 (0/0)"** 이 보였습니다.
  - 이것은 **작업이 아직 등록되지 않은 정상 상태와 똑같은 화면** 입니다. 즉 **데이터를 읽지 못하고 있다는 사실을 화면에서 구분할 방법이 전혀 없었습니다.** 컷오버 당일 전광판이 조용히 "0% 완료" 를 띄우고 있어도, 그것이 아직 시작하지 않은 것인지 서버가 데이터를 잃은 것인지 알 수 없었습니다.
  - 각 화면에 있던 "오류" 분기(`if (error)`)는 이 때문에 **한 번도 실행되지 않는 죽은 코드** 였습니다.
  - 이제 **HTTP 실패를 실제 오류로 취급합니다.** 세 화면이 공용 읽기 코드(`lib/fetchJson.ts`)를 함께 쓰며, 응답이 실패 상태면 서버가 보낸 오류 문구를 담아 오류로 처리합니다.
  - **상황판·전광판**: 첫 로드부터 실패하면 빈 트리 대신 **읽기 실패 화면** 을 보여 줍니다. 한 번 성공한 뒤 폴링이 실패하면 **직전에 성공한 트리를 그대로 유지한 채 상단에 경고만** 띄웁니다 — 일시적인 읽기 실패로 전광판이 갑자기 비지 않습니다.
  - **관리 화면**: 읽기 실패를 **저장 실패 배너와 구분되는 별도 배너** 로 보여 줍니다. 저장이 실패한 것인지 읽기가 실패한 것인지 섞이지 않습니다.

### 알려진 동작
- **`200` 과 함께 온 빈 작업 목록은 여전히 정상** 입니다. 작업이 등록되지 않은 새 서버는 v1.10.0 이 넣은 빈 상태 안내와 **최상위 작업 추가** 버튼을 그대로 보여 줍니다. 이번 수정은 **HTTP 가 실패했을 때만** 새 표시를 냅니다.
- `GET /api/activities` 의 **응답 모양(상태 코드·본문)은 바꾸지 않았습니다.** 이번 변경은 전부 화면 쪽이며, 이 API 를 직접 호출하는 외부 연동이 있다면 영향이 없습니다.
- 관리 화면의 저장 실패 배너·`401` 재로그인 처리(v1.9.0)와 인식할 수 없는 PUT 거부(v1.12.0)는 손대지 않았습니다.

### 검증
- 새 e2e 4건이 가짜 대역 없이 **실제 fetch 경로에 `GET` 만 `500`(실제 본문 모양 그대로)을 주입** 해 ① 상황판 첫 로드 실패 ② 성공 후 폴링 실패 시 직전 트리 유지 + 경고 ③ 전광판의 같은 두 경우 ④ 관리 화면의 읽기 실패 배너를 확인합니다(`e2e/dashboard-load-failure.spec.ts`). `PUT` 은 그대로 통과시키므로 기존 저장 실패 테스트와 섞이지 않습니다.
- 전체 검사 통과: 타입 검사, 린트, 단위 테스트 95건, 프로덕션 빌드, e2e 29건.
