로그인이 막혔을 때 언제 다시 눌러야 하는지 알려 주고, 서버가 HTML 오류 페이지를 돌려줘도 자바스크립트 파서 오류 문구가 화면에 새지 않게 고쳤습니다.

**잠긴 줄 모르고 계속 눌렀고, 오류 자리에는 파서 문구가 떴습니다.**

로그인 실패가 쌓이면 서버는 429 와 함께 `Retry-After` 로 얼마나 기다려야 하는지 정확히 알려 주고 있었지만, 로그인 화면은 그 값을 쓰지 않았습니다. 단추는 곧바로 다시 눌리는 상태로 돌아왔고, 누르면 또 429 였습니다. 대기 시간은 실패가 누적될수록 길어지는데 화면에는 남은 시간이 어디에도 없어서, 쓰는 사람은 계정이 잠긴 것인지 비밀번호가 틀린 것인지도 구분할 수 없었습니다.

같은 몇 줄 안에 두 번째 결함이 있었습니다. 실패 응답 본문을 항상 JSON 으로 읽었기 때문에, 앞단 프록시가 HTML 오류 페이지를 내려 주는 502·503 같은 상황에서는 파서가 던진 `Unexpected token '<' in JSON at position 0` 이 그대로 로그인 오류 자리에 찍혔습니다.

이제 429 면 `Retry-After` 헤더가 준 초만큼 단추를 비활성으로 두고 라벨에 남은 시간을 세다가 0 에서 `로그인` 으로 되돌립니다(헤더가 없으면 30초). 서버가 보낸 문구에서 숫자를 뽑아 쓰지 않으므로 문구가 바뀌어도 어긋나지 않습니다. 오류 본문 읽기는 감싸 두어, 읽지 못하면 `로그인하지 못했습니다. (HTTP nnn)` 으로 상태코드만 알립니다.

| 상황 | 이후 동작 |
| --- | --- |
| 429, `Retry-After: 12` | 단추 비활성 + `12초 후 다시 시도` → `11초…` → 0 에서 `로그인` 복구 |
| 카운트다운 도중 단추 클릭 | 요청을 보내지 않음 |
| 429 인데 `Retry-After` 없음 | 30초로 같은 카운트다운 |
| 502 등 비-JSON 오류 본문 | `로그인하지 못했습니다. (HTTP 502)` — 파서 문구 노출 없음 |
| 401 | 서버가 준 문구를 그대로 표시(변화 없음) |
| 카운트다운 중 새 제출 시작 | 이전 타이머를 끊고 새 결과만 반영 |

서버는 손대지 않았습니다. 로그인 화면 스크립트만 바뀌므로 잠금 정책과 응답은 그대로입니다.

**검증.** 새 `test/js/login.test.mjs` 6개(가짜 타이머로 실시간 대기 없이 수행, 구현 전 4개 실패 확인 후 통과)를 포함해 `go test -race ./...` 38개 패키지, `go vet ./...`, `gofmt -l .`, `go build ./cmd/dartfly` 가 모두 통과했습니다. 여기에 실제 바이너리와 MariaDB 를 띄워 진짜 429(`Retry-After: 12`)를 만들고 Chromium 으로 확인했습니다 — 임베드된 `/js/login.js` 에 새 코드가 들어 있고, 라벨이 `12초 후 다시 시도`에서 `9초…`를 거쳐 `로그인` 으로 돌아오며, 카운트다운 중 강제 클릭 3회에도 `auth/login` 요청은 0건, HTML 502 응답에서 파서 문구 없이 `(HTTP 502)`, 401 은 서버 문구 그대로, 성공하면 실제로 `/saved` 로 이동했고 CSP 위반 콘솔 기록은 없었습니다. 릴리스 이미지는 `deploy/build-release.sh` 가 `test/smoke/artifact.sh` 로 기동 점검(healthz/readyz, 임베드 정적 자산, 로그인, 내장 마스터 키 질의, TZ)까지 마친 것입니다.
