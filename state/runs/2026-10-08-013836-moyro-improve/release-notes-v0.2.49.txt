moyro v0.2.49

File search reports a database fault raised while it walks its result rows
instead of answering "no file matches", and the daily digest mail cuts mention
excerpts on character boundaries instead of byte offsets. Both are server
behavior fixes. There is no schema change, no migration, no new route, no new
error id and no web source change. Two production files change.

This tag follows v0.2.47 rather than v0.2.48 because no v0.2.48 was ever
published. A v0.2.48 annotated tag exists in a local worktree, pointing at a
marker commit built on the merge of pull request #36, but neither that commit
nor that tag is present on `origin`: `git ls-remote --tags origin` stops at
v0.2.47 and the GitHub release list stops there too, so the release job never
ran for it and no v0.2.48 image or archive exists anywhere. That local tag is
left exactly where it is — moving it would destroy the only record of the
attempt, and its commit is not an ancestor of this one, so `release.yml`'s
"release tag must point to a commit on origin/main" check could not pass for it
in any case. v0.2.48 is retired as a version number and the digest fix it
described ships here. An operator upgrading from the last published image,
v0.2.47, receives both fixes at once.

`searchFiles` and `searchTeamFiles` in `compat_wave_handlers_final.go` ran
`for rows.Next()` and never checked `rows.Err()`. pgx streams this query, so the
pool hands back a `Rows` carrying no error and a failure arriving mid-iteration
only ends the loop: `Next()` answers `false` and parks the error on the `Rows`
for a caller who asks. Neither handler asked. Both fell through to their normal
success path and emitted 200 with `{"order":[],"file_infos":{}}` — byte for byte
the body a search with no hits produces, which a client and a user can only read
as "that file is not here". A database outage was indistinguishable from an
empty result set. The two 500s these functions already own,
`api.file.search.app_error` and `api.file.search.team.app_error`, were reachable
only when the query failed to *start*.

The fix adds a `rows.Err()` check after each loop reporting through those same
two existing ids, and replaces the `continue` on a `rows.Scan` error with the
same 500 return. Both refusals end before `h.audit.LogAsync`, so a refused
search is not written to the ledger as a search that happened. This repository
had already made `rows.Err()` its own convention in 43 other files;
`compat_wave_handlers_final.go` was the only production file using `rows.Next()`
that omitted it, and it omitted it in both of its loops.

No error id and no status code is introduced. The SQL, the `LIMIT 50`, the
`store.LikeContains` term handling and the visibility conditions — the
`channel_members` subquery, the `c.team_id` predicate and `delete_at = 0` — are
untouched, so nothing about who may see which file moves. A genuinely empty
search still answers 200 with an empty result and an empty `terms` still returns
200 early. The `_ = decodeCappedBody` calls in the same two functions and the
`terms` value in their audit details were held out of scope.

Operators should expect one consequence rather than read it as a contract
change: monitoring that treated file search as an endpoint which does not fail
will begin to see 500s from these two routes during a database incident where it
previously saw 200s. That is the existing fault becoming visible, not a new one.

The digest half is the fix v0.2.48's notes described. `loadMentions` in
`digest/worker.go` shortened each excerpt with `excerpt[:160]`, where both `len`
and the slice count bytes, while the templates this product renders are Korean —
`email/template.go` emits `<html lang="ko">` — and a Hangul syllable is three
UTF-8 bytes. A Korean mention over 160 bytes was cut inside a character, which
left the rendered mail body itself invalid UTF-8 and the recipient's mail client
drawing U+FFFD at the cut, and it capped a Korean excerpt at roughly 53
characters against an English one's 160. A package-local `truncateRunes` now
counts runes, following the `knowledge.truncateRunes` precedent. ASCII excerpts
are byte-for-byte unchanged and an excerpt at or under the limit is returned
untouched, so the only behavior that moves is a multi-byte excerpt over the
limit. A Korean excerpt now carries up to 160 characters — about 480 bytes where
it carried 160 — so digest mail containing long Korean mentions grows
accordingly; a deployment that sized digest mail against the old byte ceiling
will see larger messages. No API path, response shape or stored value is
affected.

One change in this tag is not a version marker. `npm audit --audit-level=high`,
which `release.yml` runs as a release gate, began failing on GHSA-68fv-2mgg-jv7q,
a high-severity event-loop denial of service in `source-map-js` at 1.0.0 through
1.2.1. It reaches this tree only as a development transitive dependency, under
`vite`'s `postcss` and under `jsdom`'s `css-tree`, so it is absent from the
shipped bundle and from the server image, and the `--omit=dev` audit was already
clean. The remedy is lockfile-only: `webapp/package-lock.json` moves
`source-map-js` from 1.2.1 to 1.2.2, a semver patch inside both consumers'
existing ranges, so no manifest dependency changes and no direct dependency is
added, removed or re-ranged. Both audits then report 0 vulnerabilities.
