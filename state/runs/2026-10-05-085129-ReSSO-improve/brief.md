- 과제: Revocation Endpoint 가 판정하지 못한 Client 인증에 401 대신 503 `temporarily_unavailable` 로 답하게 하기 (가치 3 / 위험 2 / 작업량 M)
- 왜: `revoke`(internal/httpserver/oidc.go:1302)가 `authenticateOIDCClient` 의 모든 실패를 `writeClientAuthError` 로 넘겨 401 `invalid_client` "client authentication failed" 로 답한다 — `clients` 테이블이 답하지 못했거나 저장된 digest 가 깨져 Secret 에 대해 **아무것도 판정하지 않은** 경우까지 "네 Secret 이 틀렸다" 로 답한다. 토큰이 유출돼 폐기를 부른 호출자에게 401 은 자격증명을 폐기하고 사람을 부르라는 신호이고, 정작 **유출된 토큰은 살아 있는데** 그 사실은 전해지지 않는다. RFC 7009 §2.2.1 의 503 은 "토큰이 아직 존재한다고 가정하고 잠시 뒤 재시도하라" 를 뜻해 정확히 이 상태를 가리키며, 이 핸들러는 이미 같은 503 + 같은 본문 문안을 네 자리에서 쓴다.
- 수용 기준:
  1) `clients` 테이블을 읽을 수 없는 동안 `POST /realms/{realm}/protocol/openid-connect/revoke` 가 **503 `temporarily_unavailable`** + 본문 `the token could not be revoked and is still valid; retry after a short delay` 로 답하고, 본문에 `invalid_client` 가 없으며 `WWW-Authenticate` 헤더가 없다.
  2) 같은 실패에 `TOKEN_REVOKED`/`FAILURE` 감사 항목이 1건 남고 `revoked=none` 이다 — 지금은 한 줄도 남지 않는다(같은 함수의 Realm 조회 실패 분기 oidc.go:1286-1299 가 "감사 항목이 아예 없는 것" 을 스스로 결함으로 적어 둔 선례). 감사의 주체는 **Realm**(`realm.Name`/`&realm.ID`)으로 키를 잡고 `client_id` 는 넣지 않는다 — 이 시점의 `client_id` 는 인증 없이 보낼 수 있는 미검증 입력이다.
  3) 틀린 Secret·등록되지 않은 `client_id` 는 **여전히 401 `invalid_client`** 이고, Rate limit 초과는 여전히 429 + `Retry-After` 다(이쪽 장애만 갈라진다). `resso_client_auth_errors_total{stage="client"}` 는 v0.9.97 배선대로 장애 1건당 1 오르고 `resso_client_auth_failures_total` 은 그 동안 오르지 않는다.
  4) 장애가 끝난 뒤 **같은 Client·같은 Secret 이 429 가 아니라 200 으로 폐기에 성공**한다(Limiter 예산이 깎이지 않았다는 증거 — v0.9.97 이 고친 부분의 회귀 방지).
  5) 호출자가 중간에 끊은 요청(`r.Context().Err() != nil`)은 503 통에 들어가지 않는다 — `clientAuthUndecided` 의 `ours == false` 경로는 `errClientAuthUndecided` 로 감싸지 않으므로 기존 401 그대로다. 인증 없는 호출자가 `resso_http_requests_total{route,status="503"}` 를 마음대로 올릴 수 없어야 한다(8f2c73c 가 닫은 구멍).

- 위험과 피할 것:
  - **introspection(oidc.go:1171-1173)은 건드리지 말 것.** 그쪽 계약은 200 `active=false` + 새 `introspection_errors{stage="client_auth"}` 라벨이고, RFC 7662 는 "properly authorized" 가 아닌 호출자에게 200 을 주라고 하지 않는다 — 규범 해석이 미확인이라 별도 회차다. 세 Endpoint 를 `writeClientAuthError` 안에서 **합치지 말 것**(계약이 셋이라는 것이 이 저장소의 명시적 설계다).
  - `writeClientAuthError` 자체를 고치면 세 Endpoint 가 함께 움직인다 — 반드시 **revoke 호출부에만** 분기를 둘 것.
  - `clientAuthUndecided`(965행)의 `ErrNotFound`/context/Limiter 판정은 한 줄도 바꾸지 말 것. 등록되지 않은 `client_id` 가 세는 경로에 남아 있는 것은 Limiter 의 존재 이유다.
  - 응답·로그·감사·지표 라벨 어디에도 Secret 원문과 `client_id` 를 넣지 말 것. 감사 detail 의 `err.Error()` 는 Realm 분기(1292행)가 이미 쓰는 형태여서 허용되지만, 여기에 폼 값을 덧붙이지 말 것.
  - `revoke` 는 성공 시 200·빈 본문이라는 RFC 7009 계약을 유지해야 한다 — 없는 토큰·다른 Client 의 토큰이 200 으로 나가는 기존 동작을 바꾸지 말 것.
