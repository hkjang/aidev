- 선택: RBAC Diff(SEC-08)가 문자열 집합 차이로 비교해 `resourceNames` 를 푼 확대를 놓치고 wildcard 축소를 위험 확대로 보고하던 결함 4종 (가치 4 / 위험 1 / 작업량 S)
- 결과: 성공
- 요약: `RBACDiffExpansions` 는 Role/ClusterRole 의 최근 두 리비전을 `apiGroup|resource|verb` 문자열로 펼쳐 집합 차이를 냈는데, 그 표현이 볼 수 없는 것이 셋이었다 — ① `resourceNames` 가 문자열에 없어 **`tls-cert` 하나만 get 하던 규칙이 네임스페이스의 모든 Secret get 으로 넓어져도** 양쪽이 같은 `|secrets|get` 이라 항목이 생기지 않았다(이 화면이 잡으라고 있는 바로 그 확대) ② wildcard 를 문자 그대로 비교해 `resources: ["*"]` → `["secrets"]`, `verbs: ["*"]` → `["get","list"]`, `apiGroups: ["*"]` → `["apps"]`, `*/scale` → `deployments/scale` 같은 **축소(하드닝)가 위험 확대로** 보고됐다 — 하드닝을 권한 상승이라 말하는 화면은 무시하도록 학습시킨다 ③ `nonResourceURLs` 규칙은 아예 읽지 않아 `*` 를 얻은 ClusterRole 이 변경 없음이었다. 이제 이전 리비전이 각 grant 를 이미 **덮고 있는지** 를 API 서버의 매칭 규칙(모든 슬롯의 `*`, `*/subresource`, 끝 `*` URL prefix, resourceNames 는 객체 단위 제한)으로 판정하고, 이름으로 한정된 확대는 네 번째 `|name` 세그먼트로 표시한다. `IsRiskyPermission` 은 그 형식을 받고 포스처 검사(rbac-wildcard high)와 맞춰 apiGroups `*` 도 risky 로 본다. ④ UI 의 YAML 딥링크가 `e.cluster_id` 를 읽는데 응답에 그 필드가 없어 전 클러스터 보기에서 모든 행이 페이지가 선택한 클러스터로 연결됐다 — `cluster_id` 를 omitempty 로 추가. 두 번째 커밋으로 핸들러가 4000행을 kind 구분 없이 updated_at 순으로 받아 메모리에서 Role 만 남기던 것을 `Kinds: [Role, ClusterRole]` 로 좁혔다(바쁜 클러스터에서 안정적인 Role 이 창 밖으로 밀리면 표시 없이 건너뛰었음 — 포스처 핸들러의 `SecurityRelevantKinds` 와 같은 방식). 검증: 신규 테스트 6개(analyzer 5 + proxy 1)를 고치기 전 코드에 되돌려 붙여 4개가 각 결함을 지목하며 실패함을 확인했고(5번째는 `*/scale`·다른 리소스의 group wildcard 가 과잉 적용되지 않는지 지키는 오탐 회귀, 6번째는 핸들러 종단 + cluster_id), `go build ./...`·`go vet ./...`·`go test ./...` 전부 통과(20 패키지). 이번 세션 규칙에 따라 버전·changelog·docs 마커는 건드리지 않았다.
