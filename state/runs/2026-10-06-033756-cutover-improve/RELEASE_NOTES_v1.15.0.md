## KCB Cutover Dashboard v1.15.0

이번 판은 **관리 화면의 저장이 실제로는 아무 효과가 없었는데도 "저장 성공" 으로 보이던 두 경우** 를 각각 `409`·`404` 로 막습니다. v1.12.0(인식할 수 없는 요청 → `400`)·v1.14.0(읽기 실패 → 오류 화면)과 같은 방향의 수정으로, **조용한 성공** 을 남겨 두지 않는 것이 목표입니다.

### 버그 수정
- **관리 화면이 오래된 작업 목록을 통째로 덮어써 다른 관리자의 변경을 조용히 되돌리는 것 수정**: 관리 화면(`/admin`)의 상태 드롭다운과 행 편집(💾)은 바뀐 행 하나만 보내지 않고, 콘솔이 들고 있는 **작업 목록 전체** 를 `PUT /api/activities` 로 보냅니다. 서버는 받은 목록을 **아무 검사 없이 그대로 저장** 했습니다.
  - 그래서 콘솔이 최신 목록을 받지 못한 상태에서 저장하면 **그 사이 다른 관리자가 넣은 변경이 전부 옛 값으로 되돌아갔습니다.** 내가 건드리지 않은 작업까지 함께 되돌아갑니다.
  - 저장은 `200` 으로 **성공** 하므로 **되돌렸다는 사실이 양쪽 화면에 전혀 드러나지 않았습니다.** 상대방 콘솔에서는 방금 넣은 변경이 다음 폴링에 조용히 사라진 것만 남았습니다.
  - 평시에는 1초 폴링이 목록을 금방 따라잡아 창이 좁았지만, **v1.14.0 이 추가한 노란 읽기 실패 배너가 떠 있는 동안**(`GET /api/activities` 실패) 폴링이 멈추는데도 저장은 그대로 동작해, **목록이 임의로 오래되어도 저장이 되는 상태** 였습니다. 이때 되돌림 범위에는 제한이 없습니다.
  - 이제 두 저장 요청이 **자기 목록의 시점(`expectedLastUpdated`)을 함께 보내고**, 서버는 그 값이 저장된 `lastUpdated` 와 다르면 **아무것도 쓰지 않고 `409`** 를 돌려줍니다(`{ error, code: 'STALE_SNAPSHOT' }`). 빨간 저장 실패 배너(v1.9.0)에 `다른 곳에서 상황판이 먼저 바뀌어 저장하지 않았습니다. …` 가 떠, 덮어쓰지 못했다는 사실이 화면에 남습니다. 거절은 **다른 곳(다른 관리자 콘솔, 다른 탭, `activity.json` 업로드)에서 실제로 저장이 일어났을 때만** 나옵니다.
- **읽기가 실패하는 동안 혼자 하는 연속 저장이 `409` 로 막히는 것 수정**: 위 검사만 넣었을 때는 `GET` 이 실패하는 동안 폴링이 목록을 전진시키지 못하므로 **다른 관리자가 없어도 두 번째 저장부터 전부 `409`** 가 되었습니다(실측으로 재현). 성공한 `PUT` 응답에는 새 `lastUpdated` 가 담긴 전체 목록이 들어 있으므로, **그 응답을 그대로 콘솔에 반영해** 내 쓰기만큼 목록이 전진하게 했습니다(업로드 직후에 쓰던 것과 같은 방식). 읽기 실패 중에도 혼자서는 연속으로 저장할 수 있습니다.
- **이미 지워진 작업을 🗑/▲▼/상태 버튼으로 건드렸을 때 조용한 "저장 성공" 이 나오는 것 수정**: `PUT /api/activities` 의 세 요청 형태(`action: 'delete'`, `action: 'move'`, `targetId` + `newStatus`)는 **대상 작업 id 가 저장된 목록에 없어도 오류를 내지 않았습니다.** 삭제는 걸러낼 것이 없어 같은 목록을, 이동은 대상을 찾지 못해 복사본을 그대로 돌려주고, 상태 변경은 어떤 항목에도 맞지 않습니다 — 그래서 서버는 **아무것도 바뀌지 않은 목록을 다시 저장하고 새 `lastUpdated` 와 `200`** 을 돌려주었습니다.
  - 관리 화면의 저장 처리는 `res.ok` 만 검사하므로(v1.9.0 의 배너), 이 응답은 **성공과 구분되지 않았습니다.** 다른 관리자가 **이미 지운 행** 을 내 화면에서 🗑 / ▲▼ / 상태 드롭다운으로 건드리면, **오류 배너가 한 글자도 뜨지 않은 채 "저장됐다" 로 보였습니다.** 실제로는 아무 변경도 적용되지 않았습니다.
  - 게다가 그 요청이 **`lastUpdated` 만 앞으로 밀어** 서, 바로 위 `409` 검사를 쓰는 **다른 관리자의 정상적인 저장을 쓸데없이 `409`** 로 만들었습니다.
  - 이제 세 형태 모두 **대상 id 가 저장된 목록에 없으면 아무것도 쓰지 않고 `404`** 를 돌려줍니다(`{ error, code: 'TARGET_NOT_FOUND' }`). 검증·저장·메일 알림까지 내려가지 않으므로 **`lastUpdated` 도 전진하지 않습니다.** 빨간 저장 실패 배너에 `대상 작업(...)이 상황판에 없어 변경하지 않았습니다. 다른 곳에서 이미 지웠을 수 있습니다. …` 가 뜨고, 1초 폴링이 곧 그 행을 화면에서 치웁니다.

### 알려진 동작 / 한계
- **`409` 검사는 동시 쓰기를 전부 막지는 못합니다.** 서버가 읽고 검사하고 쓰는 사이에 다른 저장이 끼어들면 두 요청 모두 `200` 이 되고 한쪽 변경이 조용히 사라집니다. 실측으로 확인했으며, **두 관리자가 거의 동시에 저장한 경우뿐 아니라 한 사람이 앞 저장의 응답이 닿기 전에 두 행을 연달아 바꾼 경우도 같습니다.** 이번 변경은 **목록이 실제로 뒤처진 저장** 을 막는 것이고, 겹치는 순간의 경합은 이전과 같습니다(이번 변경이 악화시킨 것은 아니며, 이전에는 이것이 유일한 동작이었습니다). 같은 작업은 한 사람이 맡는 것이 안전합니다.
- **`409` 검사는 opt-in 입니다.** `expectedLastUpdated` 필드가 없는 기존 `{ activities }` 형태의 `PUT` 은 **그대로 `200`** 입니다. 이 API 를 직접 호출하는 외부 연동·스크립트가 있다면 동작이 바뀌지 않습니다.
- **`404` 는 대상 하나만 지정하는 세 형태에만 걸립니다.** `action: 'delete'`·`action: 'move'`·`targetId` + `newStatus` 뿐이며, **`activities` 배열을 통째로 보내는 저장은 `targetId` 를 함께 보내더라도 영향이 없습니다**(관리 화면의 상태 변경·행 편집이 그 형태입니다). `action: 'add'` 와 대시보드 제목 변경도 그대로입니다. 분기 자체가 성립하지 않는 요청은 v1.12.0 대로 `400`(`UNSUPPORTED_ACTION`) 입니다.
- **읽기 실패 배너가 1초 가량 깜빡일 수 있습니다.** 읽기가 실패하는 중에 저장이 성공하면 노란 배너가 한 번 사라졌다가 다음 폴링 실패에 다시 나타납니다(실측). 스스로 복구되며 저장 동작에는 영향이 없습니다.
- **`409`·`404` 는 실제로 어긋났을 때만 납니다.** 폴링이 정상으로 도는 평시에는 입력란을 열어 둔 뒤 들어온 변경을 💾 로 덮어쓰는 기존 동작(관리자 가이드 4.4 절)이 그대로입니다. v1.13.0 의 편집 입력란 갱신과 함께 봐 주세요.
- 상태 변경의 하위 작업 전파 규칙(v1.7.0, 가이드 4.3 절)과 `activity.json` 업로드 라우트는 손대지 않았습니다. 데이터 형식·마이그레이션 변경이 없어 이전 버전으로 되돌리면 완전히 복구됩니다.
- 관리자 가이드(`docs/ADMIN_GUIDE.md`)에 **4.5 절(동시 편집 충돌 — 대응 절차와 위 한계 포함)** 과 **5.6 절 API 표의 `409`·`404` 설명** 을 더했습니다.

### 검증
- 새 e2e `e2e/admin-stale-overwrite.spec.ts` 4건: `GET` 만 고정해 콘솔의 목록을 묶어 둔 뒤 같은 컨텍스트에서 실제 "다른 관리자" 변경을 넣고, ① UI 상태 변경이 `409` 와 배너를 내는지 ② API 계약으로도 `409` 가 나고 상대방 값·`lastUpdated` 가 **그대로 남는지** ③ 필드가 맞거나 없는 `{ activities }` `PUT` 이 여전히 `200` 인지 ④ **읽기가 죽어 있어도 혼자 하는 연속 저장이 `409` 가 되지 않는지** 확인합니다.
- 새 e2e `e2e/admin-missing-target.spec.ts` 5건: 없는 `targetId` 로 보낸 delete / move / 상태 변경이 각각 `404` `TARGET_NOT_FOUND` 이고 **`activities` 와 `lastUpdated` 가 둘 다 그대로인지**, 그리고 **있는 대상에 대한 기존 `200` 계약 2건** 이 그대로인지 확인합니다.
- 세 수정 모두 **수정 전 실패 / 수정 후 통과** 를 확인했습니다(`409` 쪽은 `409` 대신 `200`·④는 `200` 대신 `409`, `404` 쪽은 3건이 `404` 대신 `200` 이면서 응답 본문에 바뀌지 않은 목록과 새 `lastUpdated` 가 그대로 보였습니다).
- 릴리즈 시점 전체 검사 통과: 타입 검사(`tsc --noEmit`), 린트, 단위 테스트 **95건**, 프로덕션 빌드, e2e **38건**. 아래 배포 이미지도 같은 소스에서 빌드했습니다.

### 배포
- 폐쇄망 배포용 Docker 이미지: `cutover-v1.15.0.tar.gz`
  ```bash
  docker load -i cutover-v1.15.0.tar.gz
  docker run -d -p 3000:3000 \
    -e USER_PASSWORD=1234 \
    -e ADMIN_PASSWORD=admin1234 \
    -e AUTH_SECRET=운영환경용-충분히-긴-임의문자열 \
    -v cutover-data:/app/data \
    --name cutover-app \
    --restart always \
    cutover:v1.15.0
  ```
- 올린 뒤 확인할 것: 관리자 두 명이 같은 시간대에 콘솔을 쓰는 중 **빨간 저장 실패 배너에 위 `409`·`404` 문구가 나오는지**, 그리고 **혼자 쓰는 동안에는 이 배너가 나오지 않는지**. 후자가 나오면 목록 갱신이 아니라 이번 검사가 과하게 걸린 것이므로 보고해 주십시오.
