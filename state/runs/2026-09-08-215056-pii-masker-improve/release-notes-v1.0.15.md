Cap the number of jobs the history endpoint returns. `handleHistory` only checked that the `?limit=` query parameter parsed to a value greater than zero and then passed it straight to `ListJobs`, so a single `GET /v1/history?limit=100000` request made the server copy, sort and JSON-encode every job record still inside the retention window (24 hours by default) — the one request path left without a ceiling, while synchronous masking (`PII_MASKER_MAX_CONCURRENT_SYNC`), asynchronous jobs (`PII_MASKER_MAX_CONCURRENT_JOBS`) and upload bodies were already bounded. A new `historyLimit` helper clamps the parameter to a default of 20 and a maximum of 100, falling back to the default when the value is missing, unparseable, zero, negative or outside `int` range; the `?limit=8` the playground UI sends is unaffected.

This also adds the first unit test inside `internal/httpapi` (a 10-case table over `historyLimit`) plus an integration test that seeds 150 job records on disk and checks the returned count and newest-first ordering for five queries (default, `5`, `100000`, `-1`, `all`). `gofmt -l`, `go vet ./...`, `go build ./...`, `go test -count=1 ./...` and `go test -race -count=1 ./...` all pass, `-race -count=5` showed no flakiness, and temporarily removing the clamp confirmed both new tests fail without it. The endpoint list in the README now documents the default and the maximum.
