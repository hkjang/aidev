- 과제: 프로파일 카탈로그 GET API 5개의 인증·프로파일 권한 배선 수정 (가치 5 / 위험 2 / 작업량 M)
- 왜: 메타 DB 모드에서 상세·스키마·데이터셋 GET은 인증 없이 `userFrom(ctx)==nil`을 `canUseProfileID`에 넘겨 로컬 신뢰 분기로 통과하며, 목록 GET은 사용자 컨텍스트가 없어 로그인해도 사용할 수 있는 프로파일을 누락한다. 같은 화면의 조회 API 5개에 기존 인증·권한 경로를 연결하면 미인증 조회를 막고 일반 사용자가 소유하거나 공유받은 카탈로그를 정상 조회할 수 있다.
- 수용 기준:
  1) 메타 DB 모드에서 아래 5개 GET은 쿠키/키/마스터 토큰이 없거나 무효이면 JSON 401이며 카탈로그 본문·운영 경로를 반환하지 않는다: `/api/profile-catalogs`, `/api/profile-catalogs/active`, `/api/profile-catalogs/{profile}`, `/api/profile-catalogs/{profile}/schemas`, `/api/profile-catalogs/{profile}/dataset/{name}`. 마지막 3개는 인증된 타인의 비공개 프로파일에 기존 API 관례인 403을 반환한다. 소유자·shared·use grant·admin은 기존 접근 규칙을 유지하며 DBA 역할을 새로 요구하지 않는다.
  2) 목록은 인증된 사용자의 소유·공유·grant 프로파일만 포함하고 count도 일치한다. 같은 프로파일은 목록과 상세·데이터셋에서 같은 권한 판정을 받는다. `/active`는 인증만 요구하고 기존 응답 형태를 유지한다(전역 활성 정보이며 임의의 profile ACL을 만들지 않는다). 단독 모드(Meta=nil)는 AdminToken 설정 유무와 무관하게 기존 읽기 동작을 유지한다. POST/PUT 및 stdio/MCP 공통 권한 함수의 계약은 변경하지 않는다.
  3) `newAuthServer` → 실제 `/auth/login` 쿠키 → `Server.Register` mux → `doReq`로 회귀를 증명한다. 5개 경로의 익명/무효 인증 거절, 상세 3개의 타인 403, 소유자·use grant·shared 및 관리자 허용, 목록-상세 일치, 단독 모드 호환을 검증한다. 상세·dataset 허용 검증은 임시 워크스페이스에 식별 가능한 실제 JSON을 넣고 summary/content를 확인하여 단순 200 오류 봉투를 성공으로 오인하지 않는다. schema 허용 경로는 외부 DB 없이 실제 드라이버의 제한된 연결 실패 응답까지 도달한 것을 검증해도 되지만, 실제 스키마 조회 성공을 입증했다고 쓰지 않는다. 적어도 목록과 상세 조회에는 실제 발급 MCP 키 및 메타 모드 마스터 토큰 경로도 확인한다. 사용자 컨텍스트 직접 주입·가짜 인증 함수·소스 문자열 검사로 HTTP 검증을 대신하지 않는다.
- 건드릴 파일:
  - `internal/mcp/admin.go:registerAdmin` — 위 5개 GET 핸들러 맨 앞에 `actor, ok := s.requireActor(w, r)`를 호출하고 실패 시 return. 상세 3개는 `canUseProfileID(r.Context(), actor, profile)`로 검사. 목록은 `s.listProfileCatalogs(withUser(r.Context(), actor))`로 실제 사용자를 넘긴다. active는 인증 성공 후 기존 함수를 호출한다. 공통 인증 함수 수정은 필요 없다.
  - `internal/mcp/authhttp_test.go:newAuthServer, withCookie, TestPerUserProfilePermissions` — 기존 로그인·프로파일·grant HTTP 패턴을 재사용하여 새 `TestProfileCatalogReadAuthorization` 및 `TestProfileCatalogReadStandaloneCompatibility` 등을 추가한다. 테스트를 새 `profilecatalog_auth_test.go`로 분리해도 된다.
  - `CHANGELOG.md:Unreleased` — 인증 누락 및 목록 사용자 컨텍스트 수정 한 항목만 추가, 기존 줄바꿈 유지.
- 검증 명령: `go test ./internal/mcp -run 'TestProfileCatalogRead|TestPerUserProfilePermissions|TestStandaloneUnaffected' -count=1`; `go vet ./...`; `go test ./... -count=1`; `git diff --check`. 정찰에서 뒤의 vet와 전체 test는 실제 실행하여 모두 통과했다(internal/mcp 3.577초). 신규 TestProfileCatalogRead 이름은 구현자가 추가할 이름이다.
- 위험과 피할 것: `auth.go`, `authapi.go`는 읽기 참고만 하고 `canUseProfileID`의 nil-user 신뢰를 전역 제거하지 않는다(stdio 계약). `requireActor`는 사용자 객체를 반환할 뿐 요청 컨텍스트를 바꾸지 않으므로 목록에 반드시 별도로 전달한다. requireAdmin/requireDBA 감사 개편, auth/session, migrations, .github/workflows, 전체 gofmt/줄바꿈 정리, UI 및 PDF 변경은 제외한다. 이전 성공 기록의 b14b245/f727973 등은 현 HEAD 57f99b7에 없으며 이번 회차에 재구현하거나 cherry-pick하지 않는다. 라이브 schema 검증을 위해 실제 운영 DB에 접속하지 않는다. 테스트 데이터·워크스페이스는 t.TempDir에만 둔다.
- 차선 후보: 비어 있는 docs/README.md를 실제 존재하는 관리자·사용자 가이드의 문서 색인으로 채우기 — 1순위가 구현 시작 시 이미 해결되어 회귀 테스트까지 있는 경우에만 선택한다. 비어 있는 문서들로 링크를 확장하거나 소스 미확인 API 메서드를 쓰지 않는다.

구현 순서·견적: 재현 HTTP 테스트 12분 → 5개 핸들러 수정 8분 → 권한 행렬·단독 모드 회귀 10분 → 전체 검증·변경 이력 5분, 연결 실패/fixture 조정 여유 10분으로 총 45분(M). 실제 스키마 성공 fixture를 만드는 데 시간이 들면 위 허용된 드라이버 실패 경로 검증으로 제한하되 익명·타인 거절 및 실제 dataset 본문 검증은 생략하지 않는다.
대안 판단: requireDBA/requireAdmin으로 전부 막는 방식은 일반 사용자의 카탈로그 화면(`guardPage`, nav.js show=always)을 깨므로 제외. 글로벌 middleware나 nil 신뢰 제거는 범위를 넓히므로 제외. 기존 requireActor를 각 HTTP 경계에서 재사용하는 안을 선택한다.
