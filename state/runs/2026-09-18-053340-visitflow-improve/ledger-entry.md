- 결과: 성공
- 요약: 이 저장소에는 사용자별 계정(`users`, `oidc_issuer`/`oidc_subject` 바인딩)·go-oidc 기반 Keycloak 웹 로그인·`vf_` 접두사 개인 키가 이미 있어 MCP-OAUTH-STANDARD.md의 대상이다. weekly 참조 구현을 이 저장소의 구조(설정은 `settings` 표, 인증은 `auth.go`의 `authenticated` 미들웨어, chi 라우터)로 옮겨 `internal/app/mcpoauth.go` 한 파일에 메타데이터·401 도전·토큰 검증·계정 매핑을 두었다. **고른 것과 이유**: (1) 설정 자리는 표준 이름 그대로 `settings` 표(마이그레이션 `0016_mcp_oauth.sql`, 미머지 메일 브랜치의 0015와 충돌하지 않도록 번호를 건너뜀 — 로더가 빈 번호를 허용함을 확인)이고 관리 화면 Keycloak SSO 탭 아래 카드 하나로 두었다(스위치·리소스 식별자·허용 대상·범위·복사 가능한 MCP URL/메타데이터 주소). (2) 리소스 식별자는 `mcp.oauth.resource` → 기존 `general.base_url` + `/mcp` → 요청 Host(마지막 수단) 순서이며, 채울 때는 `/mcp`로 끝나는 http(s) URL만 받는다. (3) 대상 검사는 `aud`에 리소스 식별자 또는 `aud`/`azp`가 `mcp.oauth.audience`·웹 클라이언트(`oidc.client_id`)에 있으면 통과, 아니면 본 aud/azp와 고칠 값을 메시지에 넣어 거부한다. (4) 계정은 웹 로그인과 같은 조회(issuer+subject 바인딩, 또는 아직 바인딩 안 된 `source='oidc'` 계정을 `preferred_username`으로)로 활성 계정만 찾고 아무것도 쓰지 않는다 — 로컬 계정은 이름이 같아도 열리지 않고 토큰의 role/groups는 무시된다. (5) 범위는 `mcp.oauth.scopes`(기본 `read mcp`)를 키 정책 `security.api_key_allowed_scopes`로 자르고, 토큰 `scope`에 read/write/mcp가 실려 오면 교집합만 준다. 캠페인 규칙대로 기존 `/mcp` 핸들러의 `writeAllowed`가 `len(scopes)==0`을 무제한으로 읽는 것을 소스에서 확인했고, 그래서 교집합에 `mcp`가 없으면 빈 슬라이스를 넘기지 않고 403 `insufficient_scope`로 명시적으로 거부한다. (6) 거부 분기는 `s.logger.Warn("mcp oauth token refused", code, cause)`가 실제로 호출되어 서명·발급자(go-oidc 문구 "different provider")·만료·nbf·대상·계정 중 무엇이 실패했는지 남는다 — 테스트가 로거를 버퍼로 바꿔 각 원인 문자열을 확인한다. OAuth 토큰은 `/mcp`에서만 받고(JWT 모양이어도 REST는 종전대로 401 `authentication_required`), 꺼져 있으면 메타데이터 404·토큰도 종전과 똑같이 거부되어 새 설치에서 달라지는 것이 없다. 켜기는 Issuer가 비면 저장 시 거부(`mcp_oauth_incomplete`)하고, 가져온 설정으로 그 상태가 되면 조용히 꺼진 채 로그에 이유를 남긴다. Discovery는 issuer별로 캐시(요청 컨텍스트와 분리, 10초 제한 클라이언트)하고 실패는 5초 기억한다. 검증: `gofmt`·`go vet ./...`, docker postgres:16-alpine의 `VISITFLOW_TEST_DSN` 전체 Go 테스트 통과(internal/app 53.5초), `npm ci && npm run lint && npm test(8) && npm run build`, `docker build` 통과. 새 테스트는 통합 5개(기본 꺼짐·메타데이터 두 경로의 맨 JSON+CORS·MCP 401 헤더와 REST 401 무헤더·설정 리소스 우선·키 페이지 정보 / 정식 aud·웹 클라이언트 azp·타 앱 azp 거부 메시지·허용 대상 등록 후 통과·미등록/비활성 거부와 계정 미생성·미바인딩 SSO 계정·로컬 동명 거부·role claim 무시·REST 거부 / 범위 천장·교집합·mcp 없는 토큰 403·키 정책 상한·mcp 없는 천장 저장 거부 / 만료·nbf·타 발급자·타 키 서명·typ=ID·cnf·sub 없음·HS256·none 각각 거부와 로그 원인, 뒤이어 정상 토큰과 키 모두 동작 / Keycloak 불통 시 거부와 실패 기억·메타데이터 계속 제공)와 단위 1개(JWT 모양·메타데이터 URL·교집합 7경우·설정 검증)이며, 가짜 IdP는 `crypto/rsa`로 직접 RS256 서명하고 discovery·JWKS를 서빙해 go.mod를 건드리지 않았다. 변이 3건(대상 검사 제거·거부 로그 제거·빈 교집합 통과+핸들러 검사 제거)에서 각각 해당 테스트가 실제로 실패하는 것을 확인했다. 실제 확인: 릴리즈 Dockerfile로 만든 이미지를 postgres와 가짜 IdP 컨테이너에 붙여 띄우고 curl로 꺼짐 404/401 무헤더 → 켜기 → 메타데이터 200+CORS → 401에 `resource_metadata` → 미등록 subject `account_not_registered` → 등록 후 `tools/list` 200 → azp=claude-mcp 거부 메시지(aud=[account], azp="claude-mcp", 고칠 값) → 허용 대상에 적은 뒤 200 → 기본 천장에서 create_visit "write 범위가 필요합니다" → REST에 토큰 401 → 서버 로그에 원인까지 봤다. 실제 Keycloak/Claude 클라이언트는 이 환경에 없어 하지 못했고, 가이드에 Keycloak 클라이언트·Audience 매퍼·(선택) `read`/`mcp` client scope·짧은 토큰 수명과 introspection 없음의 한계·curl 확인·거부 메시지별 조치 표를 적고 공용 md2pdf로 ADMIN_GUIDE.pdf를 다시 구웠다(27쪽, 16쪽에 새 소절).
