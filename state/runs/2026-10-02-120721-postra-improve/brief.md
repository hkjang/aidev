- 과제: POP3 가져오기(fetch) 단계 진단이 실제 경과 시간을 기록하고 TOP 실패를 TOP 으로 보고하게 (가치 3 / 위험 1 / 작업량 S)
- 왜: v0.25.0(d97577a)이 "동기화가 어디서 멈췄는지"를 보여주는 진단을 넣었지만, POP3 본문 읽기 실패만 `internal/adapters/pop3/client.go:347`(Retrieve)·`:358`(Top)에서 `domain.WrapInbound(..., 0, s.commandTO)` 로 경과 시간을 **하드코딩 0** 으로 넘긴다 — 이 저장소에서 `WrapInbound`/`InboundError` 를 만드는 다른 7개 지점은 모두 `time.Since(start)` 를 넘긴다(확인: internal/domain/inbound_error.go:152, imap/client.go:790, pop3/client.go:95,123,172,240,244,283,303). 그래서 느린/멈춘 본문 읽기가 `syncTiming`(internal/application/sync_diagnostics.go:293)의 `ElapsedMS==0` 분기로 떨어져 "제한 60초" 만 출력하고, 이 기능의 핵심인 "자기 제한 시간을 다 썼는가(느린 서버) / 밖에서 끊겼는가(:295 분기)" 구분이 fetch 단계에서만 사라진다. 같은 두 줄에서 `Top` 이 동사를 `"RETR"` 로 적어 TOP 실패가 RETR 로 보고된다.
- 배선 확인(코드로 확인함): `ingestOne`(sync.go:539) → `sess.Retrieve` 오류 → `syncDiagnosticStage(&diag, domain.StageFetch, ingestErr)`(sync.go:344) → `d.ElapsedMS, d.TimeoutMS = durationMS(inbound.Elapsed), durationMS(inbound.Timeout)`(sync_diagnostics.go:173) → `job.Diagnostic`(sync.go:153) → `/api/jobs`·`/app/jobs`·MCP job_status·인시던트 상세. 즉 0 은 UI 까지 간다.
- 수용 기준: 1) RETR 에 `+OK` 만 답하고 본문·종결 `.` 을 보내지 않는 실제 루프백 서버에 대해 `Retrieve` 가 반환한 오류를 `errors.As(err, &*domain.InboundError)` 로 꺼냈을 때 `Stage=="fetch"`(`domain.StageFetch`), `Elapsed > 0` 이고 명령 제한 시간에 근접한다(예: `CommandTimeoutSec:1` 에서 `Elapsed >= 900ms`). 2) 같은 서버 모양에서 `Top` 실패의 `Command == "TOP"` 이다. 3) 테스트가 수정 전 실패를 증명한다(현재 코드에서 `Elapsed==0`, `Command=="RETR"` 로 FAIL) — 손으로 만든 대역 없이 `net.Listen("tcp","127.0.0.1:0")` 스크립트 서버 + 실제 `pop3.Dialer{}.Dial` + 실제 `domain.POP3DialOptions`. 4) 기존 POP3 테스트(현재 `go test -race -count=1 ./internal/adapters/pop3/` → ok 3.206s, 이번 정찰에서 실행)가 무수정 통과한다.
- 건드릴 파일 (프로덕션 1개):
  - `internal/adapters/pop3/client.go:321 retrBody` — 함수 진입에서 `start := time.Now()` 를 잡고 실패 시 경과를 호출자에 알리거나(반환 시그니처 변경), 더 간단히 `Retrieve`/`Top` 에서 `start := time.Now()` 를 `retrBody()` 호출 직전에 잡는다. 둘 중 호출자 쪽이 변경이 작다.
  - `internal/adapters/pop3/client.go:341 Retrieve` / `:352 Top` — `0` 대신 `time.Since(start)`, `Top` 은 `"RETR"` → `"TOP"`.
  - `internal/adapters/pop3/client_test.go` — 새 테스트 1~2개. 기존 스크립트 서버 헬퍼(`client_test.go` 에 이미 있음)와 `CommandTimeoutSec` 를 작게 준 DialOptions 를 재사용해 테스트가 60초를 기다리지 않게 한다.

- 위험과 피할 것:
  - `retrBody` 의 **누적 상한(MaxMessageBytes)** 은 이번 범위가 아니다. 미병합 브랜치 04b15be / PR #22 영역이고 사람 반려 여부가 아직 미확인이다(이번 회차에 `gh` 호출이 승인되지 않아 확인 못 함). 상한 코드를 추가하지 말 것.
  - `maxListBytes`/`listLineOverhead`/`readList`·`s.deadline()` 의 루프 안 위치·STLS 사전 평문 검사·`loginFailure` 의 AuthError 분류·`sync.go`·설정 카탈로그·`docs/SYNC_DIAGNOSTICS.md`·`.github/workflows`·`internal/transport/spa/assets` 는 건드리지 말 것.
  - `Top` 은 프로덕션 호출자가 없다(grep `\.Top(` → `client_test.go:620` 1건). 동사 수정은 진단 정확성 정리이고 사용자 가시 효과를 Top 으로 주장하지 말 것 — 가시 효과는 `Retrieve` 의 경과 시간이다.
  - 진단 문자열은 한국어이고 서버 원문을 절대 담지 않는 규약이다(sync_diagnostics.go). 새 텍스트를 만들지 말고 숫자 필드만 바르게 채울 것.
- 차선 후보: POP3 `retrBody` 에 **프레이밍 상한** — RETR 응답에 `.` 을 보내지 않고 짧은 줄만 흘리는 서버가 수집 워커를 영원히 붙잡는다(`retrBody` 루프 안의 `s.deadline()` 이 줄마다 명령 데드라인을 밀어낸다 — v0.23.8 이 `readList` 에서 닫은 것과 같은 모양이 fetch 단계에 남아 있고, `sync.go:512` 의 "bounded by MaxMessageBytes" 주석과 달리 `io.LimitReader` 는 `retrBody` 가 전부 `bytes.Buffer` 에 담은 **뒤** 에 걸린다). 단 PR #22 와 같은 함수이므로 착수 전 반려 여부 확인 필요.
