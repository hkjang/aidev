# Postra v0.25.4 — 크기 제한을 끈 계정의 본문 잘림 수정

`sync.max_message_bytes` 를 **0 이하로 두면 메일 한 건의 크기 제한이 없어진다** — 이 저장소가 다른 모든 곳에서 지켜 온 규약이고, v0.23.5·v0.23.7·v0.23.8 릴리즈 노트가 운영자에게 "0 이하로 끈 계정은 크기 제한 없이 본문을 계속 받습니다" 라고 약속해 온 동작입니다. 그런데 본문을 실제로 읽는 두 지점에서는 그 규약이 지켜지지 않았습니다. 상한을 끈 계정의 **모든 메일이 1바이트(음수면 0바이트)만 읽혀 그것이 메일인 것처럼 저장**됐고, 수집 작업은 끝까지 `succeeded` 로 보고됐습니다. **조용한 데이터 유실**입니다. 이번 릴리즈는 그 한 가지를 고칩니다. 설정 키, 환경변수, DB 마이그레이션, 화면 변경은 **없습니다**.

**기본값(50 MiB)을 쓰는 설치는 영향이 없습니다.** `sync.max_message_bytes` 를 0 또는 음수로 **명시적으로 바꾼 계정만** 해당됩니다.

## 무엇이 잘못됐나

- 본문을 읽는 두 지점 — `ingestOne`(수집 본경로)과 `fetchRaw`(본문 복구 경로) — 이 읽기 상한을 `io.LimitReader(rc, maxBytes+1)` 로 계산했습니다. `+1` 은 **상한에 딱 맞는 메일과 상한을 넘은 메일을 구분하기 위한** 한 바이트입니다.
- 그런데 `maxBytes` 가 `0` 이면 그 값은 **1**, 음수면 0 이하가 됩니다. 상한을 끈 계정에서 메일 한 건은 **1바이트** 또는 **0바이트**만 읽혔고, 그 조각이 본문으로 파싱되어 저장됐습니다.
- 이 사고를 잡을 장치가 하나도 작동하지 않았습니다:
  - **크기 초과(oversize) 검사가 못 잡습니다.** `maxBytes > 0 && len(raw) > maxBytes` 이므로 상한이 꺼진 계정에서는 아예 비교하지 않습니다.
  - **중복 제거가 유실을 가립니다.** 1바이트 조각은 전부 같은 내용이라 content-hash 가 같습니다. 두 번째 메일부터는 `duplicate` 로 집계되어, 화면에는 "이미 받은 메일" 처럼 보입니다.
  - **작업은 성공으로 끝납니다.** 실패도 경고도 남지 않습니다.
- 수집 경로가 `ingestOne` 을 공유하므로 **POP3 와 IMAP 두 프로토콜 모두** 같은 결함을 가집니다(`InboundSession` = `POP3Session`).
- 새로 생긴 결함이 아닙니다. `fetchRaw` 의 계산은 v0.2.0 부터, `ingestOne` 의 계산은 v0.20.0 부터 그대로였습니다. 즉 **"상한 없음" 은 한 번도 제대로 동작한 적이 없고**, 그 사이 릴리즈 노트는 동작한다고 적어 왔습니다.

## 고친 내용

- 작은 순수 함수 `rawReadLimit(maxBytes int64) int64` 하나를 두고 두 호출 지점이 공유합니다. 비양수 상한을 `math.MaxInt64` 로 바꿉니다 — `io.LimitReader` 에는 "무제한" 을 뜻하는 값이 없으므로 가장 큰 유한값이 그 자리를 대신합니다. 상한이 이미 `MaxInt64` 인 경계에서 `+1` 이 음수로 넘치는 것도 같은 분기가 흡수합니다.
- 프로덕션 변경은 `internal/application/sync.go` **한 파일**, 기존 두 줄 교체 + 근거 주석이 붙은 헬퍼입니다. 양수 상한의 동작(`+1` 바이트를 더 읽어 초과를 판정하고 `oversize` 로 집계)은 **그대로**입니다. 설정 파싱, 재시도 정책, 저장 스키마, API 응답 형태는 건드리지 않았습니다.
- `docs/SYNC_DIAGNOSTICS.md` 에 규약 한 줄을 적었습니다: 0 이하는 크기 제한 없음이고, 그때는 크기 때문에 건너뛰는 `oversize` 집계도 일어나지 않습니다.

## 검증

- **실패를 먼저 재현했습니다.** 수정 전: `new=1 duplicate=1 oversize=0 failed=0, want new=2 (status=succeeded err=)`. 두 번째 메일이 1바이트 조각의 동일 해시로 중복 처리되고 작업은 그대로 성공으로 끝나는 것까지 그 한 줄에 드러납니다. `max_message_bytes=0` 과 `=-1` 두 하위 테스트 모두.
- 테스트는 손으로 만든 대역을 쓰지 않습니다. `net.Listen("tcp","127.0.0.1:0")` 루프백 POP3 메일드롭에 **프로덕션 `pop3.Dialer`** 를 꽂고 실제 `CreateAccount` → `StartSync` → `Search` 로 끝까지 돌려, 저장된 본문이 메일 전체 크기임을 확인합니다.
- 동반 테스트가 **양수 상한은 여전히 초과 본문을 거부함**을 고정합니다. `LIST` 를 거부하는 픽스처를 써서 `runSync` 의 사전 크기 선별을 무력화해, 판정을 내리는 주체가 실제로 읽기 상한이 되게 만들었습니다.
- 경계 표(`0` / `-1` / `MinInt64` / `1` / `50 MiB` / `MaxInt64-1` / `MaxInt64`)로 메일드롭 픽스처가 닿을 수 없는 상한 최대치까지 고정했습니다.
- 변이 검증: 비양수 분기를 죽이면 무제한 테스트 2개만 재실패하고 양수-상한 테스트는 통과합니다.
- 태그 직전 재확인: `go build ./...`, `go vet ./...`, `gofmt` 무지적, `go mod tidy` 무변경, `go test -race` **25개 패키지 실패 0건**, canonical API 계약 검사(`postra-contracts -check`), `gosec -severity medium` 지적 0건, `govulncheck` 호출 경로 기준 취약점 0건.
- 프런트엔드 변경이 없습니다(`web/`·`internal/transport/spa` 변경 0건). 브라우저 테스트와 `/app` 번들은 v0.25.3 에서 검증한 상태 그대로이고, 릴리즈 워크플로가 태그에서 자산 최신 여부를 다시 검사합니다.
- 외부 PostgreSQL 과 브라우저 e2e 는 이번 범위에서 돌리지 않았습니다. 재현은 **POP3 경로로만** 했습니다 — IMAP 도 같은 `ingestOne` 을 지나므로 코드상 동일하게 영향받지만, IMAP 어댑터로 끝까지 돌린 재현은 없습니다. 본문 복구 경로(`fetchRaw`)는 공유 헬퍼와 경계 표로만 묶었습니다.

## 업그레이드 및 호환성 주의사항

DB 마이그레이션, 새 설정 키, 새 필수 환경변수가 없습니다. 실행 파일 또는 컨테이너 이미지를 교체한 뒤 재시작하면 됩니다. 되돌릴 때도 v0.25.3 으로 그대로 내려갈 수 있습니다.

**이미 저장된 잘린 메일은 업그레이드만으로 복구되지 않습니다.** 영향 범위를 먼저 확인하십시오.

- **해당 여부 확인**: `sync.max_message_bytes` 가 0 이하인 계정이 있는지 봅니다. 그 계정의 저장된 메일은 **제목과 보낸 사람이 비어 있고 본문이 한 글자**(또는 완전히 빈 본문)인 모습으로 남아 있습니다.
- **상한이 음수였던 계정**(본문 0바이트): 본문이 비어 있으므로 본문 복구 경로의 후보로 잡힙니다. `postra sync --account <ID> --repair-bodies` 가 서버에 **아직 남아 있는** 메일의 본문을 다시 받아 덮어씁니다.
- **상한이 정확히 0 이었던 계정**(본문 1바이트): `--repair-bodies` 가 **잡지 못합니다.** 그 한 바이트가 본문으로 남아 있어 "본문이 비었다" 는 후보 조건에 걸리지 않습니다. 메일 식별자(UIDL)도 이미 저장되어 있어 재동기화가 건너뜁니다. 이번 릴리즈는 그 복구 도구를 추가하지 않습니다 — 원본이 서버에 남아 있다면 해당 계정의 저장 데이터를 비우고 처음부터 다시 수집하는 방법뿐이며, 그때 레이블·협업·분석 결과는 함께 사라집니다. 서버에 원본이 남아 있는지 **먼저** 확인하십시오.
- **상한을 끈 계정은 메일 한 건이 메모리에 전부 올라옵니다.** 고쳐진 동작이 곧 설정의 의미이지만, 이 상한은 POP3 의 메모리 가드가 아닙니다(본문은 `RETR` 경로에서 먼저 모입니다). 매우 큰 첨부를 받는 계정이라면 상한을 끄는 대신 넉넉한 양수 값을 두는 편이 안전합니다.
- v0.25.3 의 POP3 `fetch` 진단 교정, v0.25.2 의 OpenTelemetry v1.45.0, v0.25.1 의 "계정당 인바운드 연결 하나"와 `mail.idle_enabled`, v0.25.0 의 동기화 실패 진단은 바뀌지 않았습니다.
