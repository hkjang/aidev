# v0.265.0

## 자동화 일정이 `*/+2` 처럼 부호가 붙은 간격도 거절합니다

cron 식의 간격 자리는 빗금 뒤에 적습니다 — `*/2 0 * * *` 는 "2분마다",
`0-30/5` 는 "0분부터 30분까지 5분마다" 입니다. 값 자리와 마찬가지로 cron
문법에서 간격 자리는 **십진 숫자만**이고, 부호를 붙이는 자리가 아닙니다.

v0.263.0 에서 값 자리(`+5 0 * * *`)의 부호를 막았는데, 간격 자리는 그때
손대지 않아 같은 결함이 남아 있었습니다. 간격을 읽는 자리가 Go 의
`strconv.Atoi` 로 곧장 갔고, 이 함수는 `+2` 를 2 로 읽어 주므로 cron 에는
없는 식이 범위 검사까지 지나갔습니다. 그래서 다음 일정들이 거절 대신
**저장**됐습니다.

| 적으신 식 | 전 | 이제 |
| --- | --- | --- |
| `*/+2 0 * * *` | 매일 00:00 부터 2분마다(하루 30번) 로 저장 | 거절 |
| `*/+3 0 * * *` | 매일 00:00 부터 3분마다(하루 20번) 로 저장 | 거절 |
| `0-30/+2 0 * * *` | 매일 00:00~00:30 을 2분마다(하루 16번) 로 저장 | 거절 |
| `0 0 * * */+2` | 일·화·목·토 00:00 으로 저장 | 거절 |

범위를 적은 뒤에 부호 붙은 간격을 쓴 식(`0-30/+2`)도 같이 통했습니다. 범위와
간격을 나눈 뒤 간격 쪽을 이 자리가 읽기 때문입니다. 간격 자리는 다섯 필드
모두에 쓸 수 있으므로 분·시·일·월·요일 어디서나 같았습니다.

저장된 일정이 적으신 분의 뜻과 우연히 같았을 수는 있습니다. 값 자리 때와
마찬가지로 문제는 남는 기록입니다. `Schedule.Expression` 에는 `*/+2 0 * * *`
가 그대로 영구히 적혔고, 이 식은 **다른 cron 구현도, 뒤에 그 일정을 읽는
사람도** 읽지 못합니다.

이제 간격 자리는 십진 숫자만 받고, 아니면 전부터 간격이 범위를 벗어났을 때
쓰던 문구와 **같은 문구**로 거절합니다. API 는 전과 같은 길로 400 과
`invalid_automation` 을 돌려줍니다.

```
invalid automation: invalid schedule minute: step must be between 1 and 60
invalid automation: invalid schedule weekday: step must be between 1 and 8
```

## 이미 저장된 일정이 있다면 올리기 전에 보십시오

**이 변경은 이미 저장된 일정을 거슬러 고치지 않습니다.** 그리고 저장된
일정을 그대로 두면 그 자동화는 **다음 시각으로 넘어가지 못합니다.** 값
자리를 막은 v0.263.0 과 똑같은 모양입니다 — 미리 계산해 둔 다음 실행
시각(`next_run_at`)으로 한 번은 그대로 실행되지만, 실행한 뒤 다음 시각을
구하려고 저장된 식을 다시 읽는 자리에서 이제 거절되고 `next_run_at` 이
넘어가지 않습니다. 같은 시각은 멱등 키로 막히므로 되풀이 실행되지는 않지만,
그 자동화는 더 돌지 않고 스케줄러 로그에 `advance schedule <id>` 오류가
남습니다.

**v0.263.0 의 릴리즈 노트에서 "간격 자리에만 부호가 든 식은 아직
받아들여지므로 멈추지는 않는다" 고 적었던 부분은 이번 릴리즈로 더 이상
맞지 않습니다.** 그때 급하지 않다고 적어 둔 식이 이번에는 멈춥니다.

올리기 전에 부호가 든 일정이 있는지 보십시오. 조회는 v0.263.0 때와 같습니다.

```sql
SELECT id, workbook_id, name, trigger_definition->>'cron' AS cron
FROM automations
WHERE deleted_at IS NULL
  AND trigger_definition->>'type' = 'schedule'
  AND trigger_definition->>'cron' LIKE '%+%';
```

올바른 cron 식에는 `+` 가 쓰이는 자리가 없으므로 걸리는 식은 모두 손볼
식입니다. 이번에 새로 멈추는 것은 그 가운데 빗금 뒤에 부호가 든
식(`%/+%`)이고, 값 자리에 부호가 든 식은 v0.263.0 부터 이미 멈춰 있습니다.
범위에 쓰는 `-`(`1-3 0 * * *`)는 올바른 식이라 조회에서 찾지 않습니다.

나온 일정은 부호를 뗀 식(`*/+2 0 * * *` → `*/2 0 * * *`)으로 다시
저장하시면 됩니다. 뜻이 달라지지 않습니다 — 전에도 `+2` 는 2 로 읽혔기
때문에 돌던 시각이 그대로입니다. 올린 뒤에도 고칠 수 있지만, **그 자동화를
편집해 저장하는 길도 일정을 고치기 전까지는 같은 400 으로 막힙니다** —
저장할 때 일정을 다시 읽기 때문입니다. 이름만 바꾸려는 경우에도 일정을
함께 고쳐 주셔야 합니다.

## 그 밖에 바뀌는 것은 없습니다

- **마이그레이션도, 새 설정도 없습니다.** 자동화 활성화 여부, 스케줄러
  폴링 간격, 실행 한도, 멱등 키 규칙은 모두 그대로입니다.
- **새 오류 문구도, 새 오류 종류도 없습니다.** 간격이 1 보다 작거나 범위를
  넘을 때 전부터 쓰던 `step must be between 1 and N` 을 그대로 씁니다.
- `*/-2`·`*/+0`·`*/0` 처럼 빼기 부호가 붙거나 0 인 간격은 **전부터
  거절**됐습니다. 이번에 달라지지 않았고, 그대로 거절되는지 검사로 못
  박았습니다.
- **부호 없이 적은 간격은 한 치도 달라지지 않습니다.** `*/2`·`0-30/5`·
  요일 `*/8`·일 `*/2` 와 별칭 `@daily` 가 돌려주는 **다음 실행 시각**까지
  그대로인지 검사로 고정했습니다.
- 일정 별칭 일곱 개(`@hourly`, `@daily`, `@midnight`, `@weekly`,
  `@monthly`, `@yearly`, `@annually`)는 그대로입니다.
- 요일 0 과 7 을 모두 일요일로 보는 규칙, 일·요일을 함께 적었을 때의 판정,
  다음 실행 시각 계산과 시간대·서머타임 처리는 한 줄도 손대지 않았습니다.
- 올바르게 적힌 일정은 전과 똑같이 저장되고 똑같은 시각에 돕니다.

## 확인

- 손으로 만든 대역 없이 **프로덕션 `ParseSchedule` 만** 불러, 부호가 간격
  자리에 올 때를 표로 못 박았습니다. 받아들여진 경우에만 다음 실행 시각을
  구해 무엇으로 저장됐는지 함께 남깁니다.
- 고치기 전에는 이 검사가 다음과 같이 실패했습니다.

  ```
  ParseSchedule("*/+2 0 * * *") 가 받아들였다: expression="*/+2 0 * * *"
    다음 실행=2026-10-16 00:02:00 +0000 UTC (<nil>)
  ParseSchedule("0 0 * * */+2") 가 받아들였다:
    다음 실행=2026-10-17 00:00:00 +0000 UTC (<nil>)
  ```

  고친 뒤 통과하고, 더한 검사 블록만 지우면 **정확히 새로 거절되는 네
  가지만** 같은 출력으로 다시 실패합니다. 새 검사가 바뀐 경로를 실제로
  지난다는 뜻입니다.
- 일정을 보던 기존 검사 여덟 개는 모두 그대로 통과합니다.
- 릴리즈 준비에서 `go build ./...`, `go vet ./...`,
  `go vet -tags=integration ./internal/...`,
  `gofmt -l ./cmd ./internal ./pkg`, `go test ./...`(테스트가 있는 19개
  패키지 전부 통과, 실패 없음), `go test ./internal/automation -race
  -count=1`, `scripts/check-release-docs.sh`,
  `scripts/check-commit-identities.sh` 를 실행했습니다.
- 웹 단위 테스트·DB 통합 테스트·브라우저 E2E 는 이번 릴리즈 준비에서 다시
  돌리지 않았습니다. 변경은 Go 패키지 한 파일에서 간격 토큰이 십진 숫자인지
  보는 한 블록이고, SQL·스키마·화면 코드는 손대지 않았습니다. 이 셋은 태그를
  올린 뒤 CI 에서 돌아갑니다.
- **실제 데이터베이스에 부호가 든 일정이 남아 있는지는 확인하지
  못했습니다.** 릴리즈 준비에 Postgres 가 없었습니다. 위의 조회는 운영
  담당자가 직접 돌려 보셔야 합니다.

## 올리실 때

v0.264.0 에서 올라오시는 분은 이미지를 바꿔 다시 띄우시면 됩니다.
마이그레이션이나 새 설정은 없고, 필수 환경 변수는 계속 `POSTGRES_DSN`
입니다.

올리기 전에 위의 조회로 부호가 든 일정을 먼저 보십시오. 한 건도 없으면
이번 변경으로 달라지는 것은 앞으로 적는 일정이 거절된다는 점뿐입니다.

운영 적용은 먼저 한 인스턴스에서 확인한 뒤 확대하십시오. 올린 뒤 기존
일정 자동화가 다음 시각으로 정상히 넘어가는지(`next_run_at` 이 앞으로
움직이는지), 스케줄러 로그에 `advance schedule` 오류가 새로 쌓이지 않는지
보십시오. 쌓이기 시작하면 부호가 든 일정이 남아 있다는 뜻입니다 — 운영
담당자가 확대를 중단하고 v0.264.0 이미지로 되돌릴 수 있습니다. 스키마도
설정도 바뀌지 않으므로 되돌린 뒤의 동작은 전과 같습니다.

## 오프라인 설치

이 릴리즈는 웹 자산과 서버 바이너리를 포함한 Docker 이미지 아카이브로 제공됩니다.

```bash
sha256sum -c kanpic-v0.265.0.tar.gz.sha256
gzip -dc kanpic-v0.265.0.tar.gz | docker load
docker run --rm -p 8080:8080 \
  -e POSTGRES_DSN='postgres://kanpic:password@postgres.internal:5432/kanpic?sslmode=require' \
  kanpic:v0.265.0
```

- 필수 런타임 환경 변수: `POSTGRES_DSN`
- Redis 및 외부 인터넷 연결: 불필요
- 관리자 초기 로그인을 보호하려면 `BOOTSTRAP_ADMIN_ID`와 `BOOTSTRAP_ADMIN_PASSWORD`를 함께 지정합니다.
- 무결성 검증 파일: `kanpic-v0.265.0.tar.gz.sha256`
