# Postra v0.23.4 — 과대 IMAP 리터럴 거부 후 메일이 섞이던 문제 수정

크기 제한을 넘는 메일 본문을 거부한 뒤 같은 IMAP 세션의 응답 경계가 어긋나, 이후 메일이 엉뚱한 내용으로 수집될 수 있던 문제를 고친 패치 릴리즈입니다. 새 설정 키, DB 마이그레이션, 새 필수 환경변수는 없습니다.

## 거부한 본문이 프로토콜로 해석되던 문제

- IMAP 어댑터는 `Sync.MaxMessageBytes`(기본 50MiB)를 넘는 서버 리터럴(`{n}`)을 **할당 전에** 거부해 과대 메일 하나가 메모리를 삼키지 못하게 막습니다. 그런데 거부가 곧바로 `return` 이었기 때문에, 서버가 이미 보내겠다고 선언한 `n` 바이트가 소켓에 그대로 남았습니다.
- 동기화 루프(`internal/application/sync.go`)는 이 실패를 해당 메일 한 건의 `Failed` 로 집계하고 **같은 세션으로 다음 메일을 계속 받습니다.** 그래서 남아 있던 본문 바이트가 다음 명령의 응답으로 읽혀 프로토콜로 해석됐습니다.

  실제 TCP 서버로 재현한 결과, 거부된 3MiB 본문 안에 우연히 `{40}` 로 끝나는 줄이 있으면 그 다음 Retrieve 가 본문에 있던 40바이트를 **메일 본문으로 돌려줬습니다.** 메일 경계가 어긋나면 이후 수집 결과는 조용히 틀린 값이 되며, 오류로 드러나지 않습니다.

- 거부된 리터럴은 이제 **버려서 스트림을 다시 맞춥니다.** `io.CopyN(io.Discard, …)` 로 1MiB 청크마다 명령 데드라인을 갱신하며(느린 회선에서 드레인 중간에 끊기지 않도록) 버리고, 태그된 완료 응답까지 읽은 뒤에 거부 사유를 반환합니다. 실패는 그 메일 한 건에 머물고, 같은 세션으로 나머지 메일함을 계속 수집합니다.
- 드레인에는 **상한**이 있습니다. 거부 임계값(`MaxMessageBytes` + 1MiB 여유)의 4배까지만 버립니다(기본값에서 약 204MiB). 그보다 큰 길이는 서버가 실제로 보내는 중인 본문이라고 보기 어렵고, 오지 않을 바이트를 기다리며 명령 데드라인까지 매달리기만 합니다. 이 경우와 드레인이 중간에 깨진 경우는 스트림 위치를 알 수 없으므로 **연결을 닫고** 이후 모든 명령(`exec`·`Idle`)을 즉시 실패시킵니다 — 계속 읽는 것이 아니라 포기하는 것이 유일하게 안전한 답입니다.
- 드레인 예산을 거부 임계값에서 파생시키므로, 예산이 임계값보다 작아 드레인 경로에 도달하지 못하는 설정이 없습니다. 기본 50MiB 에서도 정상적으로 드레인합니다.

## 검증

- 프레임 유지(거부 후 다음 Retrieve 가 올바른 본문을 돌려주는지)와 세션 폐기(예산 초과 시 이후 명령이 모두 실패하는지)를 각각 단언하는 테스트 2건을 스크립트된 루프백 IMAP 서버로 추가했습니다.
- 변이 4종으로 각 테스트가 실제로 결함을 잡는지 확인했습니다: 드레인 제거 → 프레임 테스트 실패, 예산 제거 → 행(hang)·타임아웃, 거부 오류 삼킴 → 거부 단언 실패, 스트림 손상 검사 제거 → 두 번째 명령이 raw 소켓 오류. 모두 해당 테스트만 실패함을 확인한 뒤 원복했습니다.
- `go test -race -count=3 ./internal/adapters/imap/`, 전체 `go test -race`, `go build ./...`, `go vet ./...`
- `make lint`: `gofmt` 빈 출력 + CI 와 같은 플래그의 `gosec v2.28.0` Issues 0
- 계약 검사(`postra-contracts -check`), `git diff --check`
- 프런트엔드 소스 변경이 없어 포함된 `/app` 번들은 v0.23.3 과 동일합니다.

테스트는 로컬 루프백 서버만 사용하며 운영 메일 서버나 운영 데이터에 접근하지 않습니다. 실제 IMAP 서버에서의 과대 메일 거부와 외부 PostgreSQL 은 이번에 검증하지 않았습니다.

## 업그레이드 및 호환성 주의사항

DB 마이그레이션, 새 설정 키, 새 필수 환경변수는 없습니다. DB·SecretStore·ObjectStore·KEK를 백업하고 유지한 상태에서 실행 파일 또는 컨테이너 이미지를 교체한 뒤 재시작하세요.

- **IMAP 계정에 `MaxMessageBytes` 를 넘는 메일이 있었다면 수집 결과를 확인하세요.** 이전 버전에서는 그 메일 이후의 수집분이 조용히 어긋났을 수 있습니다. 해당 계정을 재동기화하면 올바른 본문으로 다시 받습니다.
- 과대 메일을 거부할 때 그 본문을 버리는 만큼의 네트워크 전송이 발생합니다(최대 거부 임계값의 4배). 거부 자체는 예전처럼 메모리를 할당하지 않습니다.
- 드레인 상한을 넘는 리터럴을 선언하는 서버에서는 세션이 닫히고 그 계정의 남은 메일이 해당 회차에서 `Failed` 로 집계됩니다. 다음 동기화 회차에서 새 세션으로 다시 시도합니다.
- POP3·SMTP 경로, MCP·OAuth·API Key 동작은 v0.23.3 과 같습니다. [v0.23.3 릴리즈 내용](v0.23.3.md)을 참고하세요.
