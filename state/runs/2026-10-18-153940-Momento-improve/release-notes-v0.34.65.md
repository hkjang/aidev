# Momento v0.34.65 — 로그인 분당 10회 제한이 리버스 프록시 뒤에서도 IP 별로 셉니다

리버스 프록시 뒤에 Momento 를 두고 `security.trusted_proxy_cidrs` 에 프록시 대역을 등록해 둔 운영자를 위한 **보안 동작 수정**입니다. 로그인 속도 제한이 설치 전체를 한 덩어리로 세던 것을 클라이언트별로 세도록 고치고, `login`·`login.failed` 감사 기록이 프록시 주소가 아니라 실제 접속자를 적도록 맞춥니다. 화면 구성, API 의 요청·응답 모양, 데이터베이스 스키마, 설정 항목은 하나도 달라지지 않습니다.

## 한 사람의 실패 10번이 전 직원을 429 로 막고 있었습니다

`login` 핸들러는 제한 키와 두 감사 기록에 **원시 `RemoteAddr` 판독기**인 패키지 함수 `clientIP(r)` 를 세 번 따로 불렀습니다. 이 제품이 `docs/ADMIN_GUIDE.md` 로 안내하는 배치가 바로 리버스 프록시 뒤(안내의 nginx 블록이 `X-Forwarded-For` 를 붙입니다)인데, 그 배치에서 `RemoteAddr` 은 **언제나 프록시 주소 하나**입니다.

| 항목 | 값 |
|---|---|
| 한도 | `newRateLimiter(10)` — 분당 10회, 분 고정 창 |
| 제한 키 (이전) | `clientIP(r)` = 프록시 주소 하나 |
| 그래서 실제 한도 | IP 별이 아니라 **설치 전체의 분당 10회 합계** |
| 운영자가 보는 것 | 429 `RATE_LIMITED` / `too many login attempts` |

두 방향으로 틀립니다.

- **막아야 할 것을 막지 못합니다.** 개별 출처에 대한 brute-force 제한으로 동작하지 않습니다. 한 공격자가 한도를 쓰는 동안 그 한도는 전원이 나눠 씁니다.
- **막아서는 안 될 것을 막습니다.** 비밀번호를 잘못 기억한 한 사람의 실패 10번이, 같은 프록시를 지나는 **전 직원의 로그인**을 1분간 429 로 막습니다. 아무도 공격하지 않는 평일 아침에 전사 로그인 장애로 나타납니다.

`docs/ADMIN_GUIDE.md` 의 문제 해결 표는 이 429 에 대해 「IP당 분당 10회 … 프록시 뒤에서 모든 사용자가 한 IP로 보이면 `trusted_proxy_cidrs` 를 설정합니다」라고 안내해 왔습니다. 그 안내는 이 릴리스에서 **처음으로 사실이 됩니다** — 지금까지 로그인 경로는 그 설정을 읽지 않았으므로, 지시대로 설정한 운영자에게도 아무 변화가 없었습니다. 안내 문구는 고칠 것이 없어 그대로 둡니다.

## 감사 기록이 사람이 아니라 프록시를 적고 있었습니다

같은 이유로 `login` 과 `login.failed` 감사 행의 `client_ip` 에도 프록시 주소만 남았습니다. 로그인 실패 추적은 「어디서 들어온 시도인가」에 답하기 위해 있는 기록인데, 모든 행이 같은 한 주소를 적고 있으면 그 용도를 잃습니다.

| 감사 활동 | 이전 `client_ip` | 이번 릴리스 |
|---|---|---|
| `login` | 프록시 주소 | 전달된 실제 클라이언트 |
| `login.failed` | 프록시 주소 | 전달된 실제 클라이언트 |

이미 저장된 행은 고치지 않습니다. 그때 기록된 값은 그 시점에 서버가 본 값이고, 사후에 실제 접속자를 되살릴 방법이 없습니다 — 감사 기록을 추정값으로 덮어쓰지 않습니다.

## 왜 로그인만 달랐습니까

`internal/httpapi/server.go` 에는 이름이 거의 같은 판독기가 둘 있고, 서로 다른 질문에 답합니다.

| 판독기 | 무엇을 답하나 |
|---|---|
| 패키지 함수 `clientIP(r)` | `r.RemoteAddr` 에서 호스트만 떼어 낸 **원시** 값. 아래 두 곳이 자신의 첫 단계로 씁니다 |
| 메서드 `s.clientIP(r)` | 그 위의 **신뢰 계약**. `RemoteAddr` 이 운영자가 `trusted_proxy_cidrs` 로 신뢰한 대역에서 왔을 때만 `X-Forwarded-For` 를 오른쪽에서 왼쪽으로 걸어 실제 클라이언트를 찾고, 아니면 헤더를 무시합니다 |

collector 의 속도 제한(`s.Limiter.Allow(req.SiteID + "|" + ip)`)과 세션 쿠키의 `Secure` 판정(`requestSecure`)은 **이미** 메서드 쪽 계약 위에 서 있었습니다. 로그인만 다른 계약을 쓰고 있던 것이 결함입니다. 그래서 collector 와 같은 모양으로 핸들러 첫 줄에서 `ip := s.clientIP(r)` 를 **한 번만** 계산해, 제한 키와 두 감사 기록이 같은 값을 쓰게 했습니다 — 세 자리에서 따로 부르는 동안에는 언제든 두 자리가 다시 어긋날 수 있었습니다.

두 판독기는 역할이 다르므로 **통합하거나 이름을 바꾸지 않았습니다.** 원시 판독기는 `s.clientIP` 와 `requestSecure` 자신이 쓰는 단계입니다.

## 설정에 따라 무엇이 달라지는지

**`trusted_proxy_cidrs` 가 비어 있으면(기본값 `[]`) 동작은 한 비트도 달라지지 않습니다.** 신뢰 대역이 없으면 `s.clientIP` 는 `X-Forwarded-For` 를 무시하고 원시 `RemoteAddr` 을 그대로 돌려주므로, 이전 코드와 같은 값입니다. 프록시를 쓰지 않거나 등록하지 않은 설치에서 이 릴리스는 버전 숫자만 바뀝니다.

달라지는 것은 **신뢰 대역을 등록한 설치**입니다. 거기서는 이제 제한이 전달된 클라이언트별로 세어지고, 감사 기록이 그 클라이언트를 적습니다.

트레이드오프를 숨기지 않고 적습니다. **신뢰 대역을 실제 프록시보다 넓게 적어 둔 설치에서는, 신뢰된 범위에서 오는 요청이 `X-Forwarded-For` 를 바꿔 가며 로그인 제한을 우회할 수 있습니다.** 이는 이 릴리스가 새로 만든 성질이 아니라, 그 설정이 이미 collector 의 속도 제한과 쿠키 `Secure` 판정에 대해 갖고 있던 성질입니다 — 로그인이 그 계약에 합류하면서 영향 범위가 넓어진 것입니다. 지나치게 넓은 `trusted_proxy_cidrs` 에 대한 경고는 아직 없습니다. 운영자가 할 일은 하나입니다: **`security.trusted_proxy_cidrs` 에 실제 프록시의 주소 대역만 적혀 있는지 확인하십시오.** 전체 사설 대역이나 `0.0.0.0/0` 이 적혀 있다면 이 릴리스를 올리기 전에 좁히는 것이 맞습니다.

## 확인

- **프로덕션 배선으로 증명했습니다.** 손으로 만든 핸들러가 아니라 `s.Handler()` 가 등록한 실제 라우트 `POST /api/v1/auth/login` 으로 보냅니다. `internal/httpapi/server_test.go` 의 두 subtest 는 (1) 신뢰 프록시 뒤에서 서로 다른 `X-Forwarded-For` 가 한도를 공유하지 않고, 자기 한도를 쓴 쪽은 여전히 429 를 받는 것, (2) `RemoteAddr` 이 신뢰 대역 밖이면 헤더를 바꿔 가며 보내도 한도를 벗어나지 못하는 것을 확인합니다. 429 거절이 `decodeJSON`·`Auth.Login` 보다 앞이라 이 둘은 데이터베이스 없이 돕니다.
- **감사 IP 는 소스 문자열 검사로 갈음하지 않았습니다.** `internal/httpapi/integration_test.go` 의 DB 게이트 테스트가 실제 PostgreSQL 의 `audit_logs.client_ip` 를 읽어, `login.failed` 행이 프록시 `192.0.2.1` 이 아니라 전달된 클라이언트 `198.51.100.7` 을 적는 것을 확인합니다.
- **고치기 전 실패를 봤고, 고친 줄만 되돌려 실패가 되돌아오는 것까지 확인했습니다.** 제한 쪽은 `server_test.go:253` 「다른 클라이언트가 429 를 받았다 — 로그인 제한이 프록시 주소 하나로 묶여 있다」, 감사 쪽은 `integration_test.go:2680` 「the login.failed audit row recorded "192.0.2.1", want the forwarded client 198.51.100.7」입니다. 대조용 subtest(신뢰 대역 밖)는 변경 전후 모두 통과하는 회귀 가드이므로 red 가 되지 않습니다 — 그대로 적습니다.
- **전체 게이트**: 로컬 `postgres:17-alpine` 을 `MOMENTO_TEST_POSTGRES_DSN` 으로 걸고 `make verify` 를 끝까지 돌려 exit 0. `go test -race ./cmd/... ./internal/...`, `go vet`, `govulncheck`, SDK `npm ci`·`npm audit`·typecheck·테스트·build, 콘솔 `npm ci`·`npm audit`·lint·테스트·build 를 포함합니다. 서비스·콘솔·SDK 버전 및 Compose 이미지 이름 일치 검사, toolchain 일치 검사 통과.
- **프로덕션 Docker 이미지 빌드** 통과. 빌드한 이미지를 PostgreSQL 17 과 함께 기동해 마이그레이션·`/health/ready`(4초)·버전 응답(`{"version":"0.34.65","commit":"29279af27b70"}`)·콘솔 서빙(200)·부트스트랩 로그인(200)을 확인했습니다. 배포용 아카이브 자체의 로드·checksum·기동 검사는 태그 푸시 후 기존 릴리스 워크플로가 수행합니다.
- **고친 동작이 산출물까지 닿는지 추론하지 않고, 그 기동한 이미지에 직접 넣어 측정했습니다.** 컨테이너가 보는 호출자 주소는 도커 브리지 게이트웨이 `172.18.0.1` 이고, 이것이 이 측정에서 「프록시」 역할을 합니다.

| 측정 | 결과 |
|---|---|
| `trusted_proxy_cidrs` 가 비어 있을 때의 `login` 감사 행 | `172.18.0.1` — **이전과 같은 값**(기본 설정에서 동작이 달라지지 않음) |
| 신뢰 등록 후 실패 로그인 (`X-Forwarded-For: 198.51.100.7`) | `login.failed` 행 `198.51.100.7` |
| 신뢰 등록 후 **성공** 로그인 (`X-Forwarded-For: 203.0.113.9`) | `login` 행 `203.0.113.9` |
| 클라이언트 A(`198.51.100.7`)로 12회 연속 시도 | 10회째부터 `429` — 자기 한도를 쓴 쪽은 여전히 막힙니다 |
| A 가 막힌 **직후** 클라이언트 B(`203.0.113.9`) | `401` — 한도를 공유하지 않습니다. 이 릴리스 전에는 여기서 `429` 였습니다 |
| 신뢰 대역을 좁혀 호출자를 신뢰 밖으로 돌린 뒤, 헤더를 12번 바꿔 가며 시도 | 전부 한 버킷으로 세어져 `429` — 헤더로 한도를 벗어나지 못합니다 |

### 이 릴리스가 증명하지 않은 것

- **단위 테스트는 성공 `login` 감사 행을 보지 못합니다.** 테스트 픽스처의 `password_hash` 가 리터럴 `'hash'` 라 성공 로그인을 만들 수 없고, 그 줄이 실패 행과 **같은 지역 변수**를 한 줄 아래에서 쓴다는 것이 테스트 쪽 근거의 전부입니다. 그래서 추론으로 남기지 않고 위 표처럼 **기동한 이미지에서 성공 로그인을 실제로 만들어** `login` 행이 `203.0.113.9` 을 적는 것을 확인했습니다. 이 한 줄은 자동 회귀 테스트로는 덮여 있지 않습니다.
- **로그인 외의 감사 기록은 아직 프록시 주소를 적습니다.** 같은 결함이 남은 감사 호출이 10 파일에 55 곳 있습니다(`admin.go` 16곳이 가장 많습니다). 추상적인 경고가 아닙니다 — 위 측정과 같은 실행에서 설정을 바꾼 `setting.update` 행은 전달된 클라이언트가 아니라 `172.18.0.1` 을 적었습니다. 이 릴리스는 그 곳들을 손대지 않았습니다. 한 번에 묶으면 변경이 12 파일로 번져 되돌릴 수 없는 릴리스가 되므로, 파일 단위로 나누어 뒤 회차에서 옮깁니다.
- **한도에 닿은 뒤의 로그인 시도는 감사에 전혀 남지 않습니다.** 429 분기가 `s.audit` 보다 앞에서 return 합니다. 이 릴리스가 만든 성질이 아니고 바꾸지도 않았습니다 — 다만 그 성질 덕에 위의 429 테스트가 데이터베이스 없이 돕니다.

## 범위와 배포

바뀐 것은 `internal/httpapi/server.go` 의 `login` 핸들러와 테스트 두 파일, 그리고 버전 선언입니다. 콘솔·SDK 코드, API 의 요청·응답 모양, 데이터베이스 마이그레이션, 설정 항목, `.github/workflows/*.yml` 은 바뀌지 않았습니다.

이번 수정은 **Tier 2** 입니다 — 릴리스 노트만으로 끝내지 않습니다. 보안 제어의 동작과 감사 기록의 내용이 달라지므로, **리버스 프록시 뒤에서 `trusted_proxy_cidrs` 를 설정해 둔 설치의 운영자에게는 따로 알립니다.** 그 운영자가 받는 변화는 둘입니다: (1) 지금까지 전사 로그인을 막던 429 가 사라지고, (2) 감사 화면의 로그인 IP 가 오늘부터 다른 값을 적기 시작합니다. 두 번째는 알리지 않으면 「감사 기록이 갑자기 바뀌었다」는 문의가 됩니다. 프록시를 쓰지 않는 설치에는 Tier 3 — 릴리스 노트로 충분합니다.

기존과 같이 태그 푸시 후 GitHub Actions 가 `momento:v0.34.65` 를 빌드하고, 오프라인 아카이브 `momento-v0.34.65.tar.gz` 와 `.sha256` 을 로드·기동 검증한 뒤 Release 에 첨부합니다. 설치 절차는 `docs/OFFLINE.md` 를 따릅니다.

배포 담당자는 확대 적용 전에 다음을 봅니다.

1. 올리기 **전에** 「관리 → 보안」의 「신뢰할 Reverse Proxy CIDR」(`trusted_proxy_cidrs`)에 실제 프록시 대역만 적혀 있는지 확인합니다. 넓게 적혀 있으면 좁히고 나서 올립니다.
2. 프로필 메뉴의 버전이 `0.34.65` 로 보이는지, `/api/v1/version` 이 같은 값을 답하는지 확인합니다.
3. 프록시를 거쳐 한 번 로그인하고, 감사 기록의 `login` 행 IP 가 프록시 주소가 아니라 **자기 PC 의 주소**인지 확인합니다. 이것이 이 릴리스의 동작을 운영 환경에서 확인하는 가장 빠른 방법입니다.
4. 중단 조건: 3번이 프록시 주소를 그대로 보이거나, 정상 사용자가 429 를 받으면 확대 적용을 중단하고 배포 담당자가 이전 `momento:v0.34.64` 이미지로 되돌립니다. 데이터 구조가 같으므로 되돌려도 추가 조치는 필요하지 않습니다.

이 세션에서는 실제 배포와 운영 환경 확인을 수행하지 않습니다.
