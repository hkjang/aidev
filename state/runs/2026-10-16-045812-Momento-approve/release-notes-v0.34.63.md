# Momento v0.34.63 — 「망 대역 추가」가 적은 그대로의 대역을 저장합니다

콘솔 **관리 → 망 대역**에서 사내 대역을 등록하는 관리자를 위한 수정입니다. v0.34.58 이 「CIDR」 칸의 **틀린 표기**를 보내기 전에 걸러 냈다면, 이번에는 그 칸을 통과한 **올바른 표기**가 서버에서 어떻게 되는지를 고칩니다. 화면 구성과 API 계약은 달라지지 않습니다.

## 호스트 비트가 켜진 CIDR 이 500 으로 돌아왔습니다

`10.20.30.1/24` 는 `net.ParseCIDR` 이 통과시키는 값이고, 폼의 `judgeCIDR`(v0.34.58)도 막지 않습니다 — 「그 주소가 속한 /24」라는 뜻이 분명하기 때문입니다. 그런데 `createNetwork` 는 파싱이 계산해 둔 대역을 버리고 사용자가 적은 글자를 그대로 넣었습니다.

| 항목 | 값 |
|---|---|
| 저장 대상 | `network_ranges.cidr` (PostgreSQL `cidr` 타입) |
| 거절 이유 | 넷마스크 오른쪽에 비트가 켜진 값 (SQLSTATE `22P02`) |
| 사용자가 받던 응답 | 500 `NETWORK_CREATE_FAILED` + pgx 원문 |

화면은 「`10.20.30.1/24` 는 `10.20.30.0/24` 로 저장됩니다」라고 안내하고 있었는데, 실제로는 저장이 되지 않았습니다. 새 `normalizeCIDR` 의 결과를 INSERT 와 감사 기록의 `cidr` 값에 넘겨, 안내 문장과 저장값이 처음으로 일치합니다. 판정은 넓히지도 좁히지도 않았습니다 — `net.ParseCIDR` 이 거절하는 값은 여전히 400 `INVALID_CIDR` 이고, 코드와 메시지도 그대로입니다.

## 그 정규화가 IPv4-mapped IPv6 대역을 IPv4 로 접어 넓혔습니다

`(*net.IPNet).String()` 에는 그대로 쓸 수 없는 표기가 하나 있습니다. `::ffff:a.b.c.d` 형태에서는 그 메서드가 주소를 IPv4 점표기로 접으면서 **넷마스크의 96 비트를 같이 지웁니다.**

| 사용자가 적은 값 | 접힌 결과 | 이번 릴리스의 결과 |
|---|---|---|
| `::ffff:0:0/96` | `0.0.0.0/0` | `::ffff:0.0.0.0/96` |
| `::ffff:10.0.0.0/104` | `10.0.0.0/8` | `::ffff:10.0.0.0/104` |
| `::ffff:10.1.2.3/120` | `10.1.2.0/24` | `::ffff:10.1.2.0/120` |

틀리는 것이 저장값만이 아닙니다. collector 는 `$1::inet <<= cidr` 로 방문자의 주소가 어느 망에 속하는지 판정하는데, `203.0.113.9` 는 `::ffff:0.0.0.0/96` 에 걸리지 않고 `0.0.0.0/0` 에는 걸립니다. 즉 **등록한 적 없는 범위로 넓어진 대역 때문에 엉뚱한 IPv4 방문자가 그 망으로 분류됩니다.**

호스트 비트만 깎는 것이 이 함수의 일이므로 주소 체계는 사용자가 적은 쪽을 유지합니다. 넷마스크가 128 비트 폭이면 `net/netip` 으로 직접 글자를 만들고, 호스트 비트는 그 체계 안에서 깎습니다.

정규화는 「망 대역 추가」 경로 하나만 씁니다. 다른 핸들러와 설정 화면의 「신뢰할 Reverse Proxy CIDR」(`trusted_proxy_cidrs`)은 각자의 계약이 있어 이 함수를 그쪽으로 번지게 하지 않았습니다.

## 확인

- Go: 로컬 PostgreSQL 17 을 연결한 `go test -race -count=1 ./cmd/... ./internal/...` 와 `go vet ./cmd/... ./internal/...` 통과. 서비스·콘솔·SDK 버전 및 Compose 이미지 이름 일치 검사, toolchain 일치 검사를 포함합니다. 회귀 테스트는 `internal/httpapi/network_cidr_test.go` 에 있고, 순수 함수의 반환값과 **실제 PostgreSQL `cidr` 컬럼에 저장된 글자**를 함께 확인합니다. 별도 부하 테스트는 `MOMENTO_LOAD_POSTGRES_DSN` 을 지정하지 않아 실행하지 않았습니다.
- `govulncheck`: 코드가 호출하는 취약점 **0건**. 가져오는 패키지 4건·필요 모듈 20건의 비호출 취약점은 별도로 보고되었습니다.
- SDK: `npm ci`·`npm audit`(취약점 0건)·typecheck·테스트 **29건**·build 통과. 이번 릴리스에 SDK 코드 변경은 없습니다.
- 콘솔: `npm ci`·`npm audit`(취약점 0건)·`npm run lint`·테스트 **259건**·프로덕션 빌드 통과. 콘솔 코드 변경이 없어 테스트 수는 그대로입니다(259건). 빌드의 500 kB 초과 청크 경고는 남아 있습니다.
- 프로덕션 이미지 빌드 통과. 빌드한 이미지를 PostgreSQL 17 과 함께 기동해 마이그레이션·`/health/ready`·버전 응답(`0.34.63`)·콘솔 서빙·부트스트랩 로그인을 확인했습니다.
- 수정이 산출물까지 닿는지 추론하지 않고 **그 기동한 이미지에 직접 넣어** 측정했습니다. `10.20.30.1/24`·`::ffff:10.1.2.3/120`·`::ffff:0:0/96` 세 값이 모두 201 로 저장되고, 목록이 각각 `10.20.30.0/24`·`::ffff:10.1.2.0/120`·`::ffff:0.0.0.0/96` 를 답합니다 — 앞의 하나는 이전에 500 이었고, 뒤의 둘은 접혀서 `0.0.0.0/0` 이 될 자리였습니다. 배포용 아카이브 자체의 로드·checksum·기동 검사는 태그 푸시 후 기존 릴리스 워크플로가 수행합니다.

## 범위와 배포

바뀐 것은 `internal/httpapi/admin.go` 와 그 테스트, 그리고 버전 선언입니다. 콘솔·SDK 코드, API 의 요청·응답 모양, 데이터베이스 마이그레이션, 설정 항목, `.github/workflows/*.yml` 은 바뀌지 않았습니다. **관리자가 새로 할 일은 없고, 화면에서 달라지는 것도 없습니다** — 지금까지 500 으로 막혔던 입력이 저장된다는 것이 달라지는 전부입니다.

이미 저장된 행을 고칠 필요는 없습니다. 접힘은 정규화를 도입한 이 릴리스 주기 안에서만 존재했고 배포된 적이 없으며, 정규화 이전의 서버는 원문을 그대로 넣어 PostgreSQL 이 같은 체계로 저장했습니다.

이번 수정은 Tier 3 로 릴리스 노트에만 안내합니다. 기존과 같이 태그 푸시 후 GitHub Actions 가 `momento:v0.34.63` 을 빌드하고, 오프라인 아카이브 `momento-v0.34.63.tar.gz` 와 `.sha256` 을 로드·기동 검증한 뒤 Release 에 첨부합니다. 설치 절차는 `docs/OFFLINE.md` 를 따릅니다.

배포 담당자는 확대 적용 전에 프로필 메뉴의 버전이 `0.34.63` 으로 보이는지, `/api/v1/version` 이 같은 값을 답하는지, 「관리 → 망 대역」의 기존 목록이 그대로 보이는지 확인합니다. 바뀐 경로가 망 분류의 입력을 만드는 곳이므로, 첫 적용 후에는 **새로 추가한 대역이 목록에 적은 그대로 보이는지**와 사내/외부 분류가 평소와 같은지를 한 번 봅니다. 평소와 다르면 확대 적용을 중단하고 배포 담당자가 이전 `momento:v0.34.62` 이미지로 되돌립니다 — 되돌려도 데이터 구조는 같으므로 추가 조치는 필요하지 않습니다. 이 세션에서는 실제 배포와 운영 환경 확인을 수행하지 않습니다.
