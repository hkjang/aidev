# Hunter v1.22.0

**공통 자원 폼**의 JSON 칸을 비웠을 때 그 칸이 선언한 그릇을 제출하도록 고친 릴리즈입니다. 유효한 JSON 입력이 만드는 요청은 한 글자도 달라지지 않으며 서버 API·권한·감사 기록, 일반 PostgreSQL·네 환경변수·서비스 Docker 이미지 하나의 기본 배포를 유지합니다.

## 사용자가 달라지는 점

- **JSON 칸을 비우면 모든 칸이 똑같이 `{}` 를 보냈습니다.** 제출 본문을 만드는 `resourceSubmitBody`(`web/src/resource-form-state.ts`)는 JSON 칸마다 `JSON.parse(values[f.key] || "{}")` 를 썼습니다. 빈 문자열이 `"{}"` 로 바뀌므로, 칸이 선언한 기본값이 무엇이든 비워서 제출한 값은 객체 `{}` 였습니다. 서비스의 **추가 공격 표면**(`targets`)은 `web/src/resources.tsx` 에서 `default: []` 로, 연동의 **연동 세부 설정 (JSON)**(`config`)은 `default: {}` 로 선언합니다. 즉 배열을 선언한 칸만 선언과 다른 그릇을 저장했습니다.
- **잘못된 그릇을 막는 서버 검사가 없습니다.** `targets` 의 자료형을 확인하는 서버 검증은 없으므로 `{}` 는 `400` 이 아니라 그대로 저장됐습니다. 조작자는 저장이 성공했다고 보게 됩니다.
- **서비스의 공격 표면이 말없이 그려지지 않았습니다.** 자산 그래프는 `internal/app/domain.go` 에서 그 값을 `s["targets"].([]any)` 로 읽습니다. 저장된 `{}` 는 이 타입 단정에 실패하고, Go 의 `, ok` 형태 단정은 오류를 내지 않으므로 그 서비스의 추가 공격 표면이 아무 안내 없이 목록에서 사라졌습니다.
- **진단 대상 승인이 말없이 해제됐습니다.** 같은 파일의 재승인 비교는 `url`·`environment`·`network`·`team`·`owner`·`criticality`·`targets`·`repository`·`image` 가 달라졌는지 확인하고, 달라지면 관리자라도 진단 대상을 다시 명시적으로 승인해야 합니다. `[]` 에서 `{}` 로 바뀐 값은 이 비교에 **변경된 값**이므로, JSON 칸을 비운 저장이 그 서비스의 진단 대상 승인까지 함께 해제했습니다.
- **선언한 그릇을 제출하고, 다른 그릇은 칸 이름으로 거절합니다.** 이제 JSON 칸은 `resourceJSONWire` 를 지납니다. 빈 입력(공백만 있는 입력 포함)은 칸이 선언한 그릇의 새 복제본, 즉 `default` 가 배열이면 `[]`, 아니면 `{}` 를 제출합니다. 파싱된 값의 그릇이 선언과 다르거나 숫자·문자열·불리언 같은 맨 스칼라 또는 `null` 이면 요청을 만들지 않고 "<칸 이름>: 대괄호로 감싼 배열([...]) 형태로 입력해 주세요." 또는 "<칸 이름>: 중괄호로 감싼 객체({...}) 형태로 입력해 주세요." 를 표시합니다. JSON 이 아닌 글에는 기존 "<칸 이름>: 올바른 JSON 형식을 입력해 주세요." 문구가 그대로 답으로 남아, 조작자는 두 문제 중 어느 쪽인지 구분할 수 있습니다.

## 운영 조건과 한계

서버 계약은 바꾸지 않았습니다. 두 JSON 필드의 API 형식·권한 검사·감사 기록과 일반 자원 수정의 `expected_updated_at` 비교, 409 입력 보존 규칙도 그대로입니다. 프로덕션 변경은 화면 파일 하나(`web/src/resource-form-state.ts`)이며, 선언한 그릇과 다른 값은 서버에 닿기 전 화면에서 거절합니다. 이번 릴리즈는 화면이 보내는 값만 고치므로, 이전 버전에서 이미 `{}` 로 저장된 `targets` 와 그때 해제된 진단 대상 승인은 자동으로 되돌리지 않습니다. 해당 서비스는 공격 표면을 다시 입력하고 진단 대상 승인을 다시 받아야 합니다. 날짜 칸의 제출 값 검사는 v1.21.0 에서 같은 함수에 들어왔고, 이번에는 같은 함수의 JSON 분기를 같은 방식으로 맞췄습니다.

## 검증과 배포

`web/tests/resource-form-state.test.mjs` 에 시험 두 개를 더했습니다. 하나는 `targets`·`config` 의 실제 선언으로 빈 입력 네 가지(`""`, 공백, 탭·줄바꿈)를 제출해 선언한 그릇이 나오는지 확인하고, 다른 하나는 선언과 다른 그릇과 맨 스칼라·`null` 아홉 가지가 칸 이름이 붙은 한국어 안내로 거절되는지, JSON 아닌 글은 기존 문구로 남는지, 유효한 입력은 그대로 제출되는지 단언합니다. 수정 전 동작(`JSON.parse(values[f.key] || "{}")`)으로 되돌리면 이 두 시험만 실패해 108통과/2실패가 되는 것을 먼저 확인했습니다.

`npm --prefix web ci` 후 `npm --prefix web test` 가 `web/tests` 19개 파일에서 110개 검사를 실행해 모두 통과했고 실패·건너뜀은 0개입니다. 릴리즈 커밋에서 실행한 검사와 건너뛴 검사는 [검증 기록](validation.md)에 적었습니다.

브라우저에서 JsonInput 을 직접 비워 확인하거나, 저장된 `{}` 가 자산 그래프와 재승인 비교에 미치는 영향을 PostgreSQL 이 붙은 서버에서 재현하지는 않았습니다. 서버 쪽 Go 변경은 없습니다.

화면 캡처는 v1.9.0의 검증 장면을 보존했습니다. 가이드·README·llms.txt·openapi.json 의 버전 표기를 갱신하고 가이드 HTML·PDF 를 재생성했습니다.
