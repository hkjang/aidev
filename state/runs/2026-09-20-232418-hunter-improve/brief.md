- 과제: 서버 CSV 보고서의 공백·제어 문자 뒤 수식 접두사 보호를 목록 CSV와 일치시키기 (가치 4 / 위험 1 / 작업량 M)
- 왜: `internal/app/domain.go:csvSafe`는 첫 바이트만 검사하여 ` =1+1`, ` \t=1+1` 같은 문자열을 그대로 내보내지만, `web/src/list-export.ts:csvCell`은 같은 값에 작은따옴표를 붙여 보호한다. 실제 보고서 CSV 다운로드와 목록 CSV의 보호 규칙을 맞추면 내보내기 경로에 따른 보호 누락을 없앨 수 있다.
- 수용 기준: 1) 인증된 `GET /api/reports/export?format=csv`에서 공백·C0 제어 문자 뒤의 =,+,-,@로 시작하는 제목은 원문 전체 앞에 작은따옴표 하나를 추가하고, 기존 첫 글자 수식·탭·CR·LF 보호도 유지한다. 일반 한글, CVE, 빈 문자열, 따옴표·쉼표·여러 줄 본문, 이미 작은따옴표로 보호된 값은 불필요하게 바꾸지 않는다. 2) 서버의 보호된 셀 내용과 프런트 `csvCell`을 CSV 디코딩한 내용이 공유 JSON 사례 전체에서 일치한다. CSV의 BOM·헤더·열 순서·한글·다운로드 헤더·현재 접근 범위와 JSON 내보내기의 원래 값은 유지한다. 3) 실제 PostgreSQL 격리 스키마의 `testApp`→`a.Routes()`를 통과해 서비스·발견 건을 HTTP로 생성하고 보고서 CSV를 다운로드하여 BOM 제거 후 `encoding/csv.Reader`로 파싱한다. 수정 전 공백 접두사 사례가 실패하고 수정 후 통과해야 하며, 동일 발견 건의 JSON 내보내기는 작은따옴표 없이 원문을 유지함을 증명한다. 미인증 CSV 요청도 기존대로 거부되어야 한다.
- 건드릴 파일: `internal/app/domain.go:csvSafe` — 프런트의 기존 보호 판정과 같은 선행 문자 검사로 한정 수정; `exportReport`는 실제 호출 지점이며 권한·조회·감사는 변경하지 않음. `internal/app/report_csv_test.go`(신규) — `TestReportCSVFormulaSafety`, `TestCSVSafeSharedVectors` 제안; 기존 `internal/app/core_test.go:testApp, loginTest, request, mustRequest` 재사용. `internal/app/testdata/csv-safety.json`(신규) — input/expected 셀 내용의 공통 golden 사례. `web/tests/convenience.test.mjs` — 기존 `csvCell`, `listCSV` 테스트에 같은 fixture를 `new URL("../../internal/app/testdata/csv-safety.json", import.meta.url)`로 읽는 회귀 추가. `web/src/list-export.ts:csvCell,listCSV`는 기준 경로로 읽되 기존 정상 동작은 넓히지 않음. `web/src/pages.tsx`의 `/api/reports/export?format=csv` 링크와 `web/src/list-tools.tsx:ListTools`의 `downloadCSV` 호출까지 확인했으며 UI 변경은 필요 없음.
- 검증 명령: `node --experimental-strip-types --test web/tests/convenience.test.mjs`; `npm --prefix web test`; 격리 테스트 DB의 HUNTER_TEST_DSN을 안전하게 주입한 환경에서 `go test -race -count=1 -timeout 5m -run '^(TestReportCSVFormulaSafety|TestCSVSafeSharedVectors)$' ./internal/app`; `go vet ./...`; `git diff --check`. 신규 테스트 이름은 제안이며 구현 시 위 이름에 맞춘다. 이 저장소의 testApp은 DSN이 없으면 skip하므로 반드시 -v 출력 또는 JSON 결과로 HTTP 테스트가 실행됐는지 확인한다. 정찰에서 실제 실행한 것은 `npm --prefix web test`(92 pass, 0 fail/skip; Node v22.23.1)와 실제 TS 함수 호출뿐이며 Go·DB·스프레드시트 앱 검증은 미수행이다. 구현 검증은 저장소 요구 Node 26·Go 1.26.5 이상을 사용한다.
- 위험과 피할 것: auth·migrations·workflows·PentAGI·보고서 조회 범위·일반 자료 저장값·JSON 출력은 건드리지 않는다. CSV 인용만으로 수식 보호를 대체하지 말고 원문 trim/삭제도 하지 않는다. Go unicode.IsSpace와 JS \s는 완전히 같지 않으므로 JS의 기존 `[\s\u0000-\u001f]*` 계약을 명시적으로 맞춘다(특히 U+FEFF, U+00A0, U+0085는 기대값을 구별). 선행 탭/CR/LF는 수식이 없어도 기존처럼 보호한다. PostgreSQL이 저장할 수 없는 NUL은 순수 함수 fixture에서만 검사하고 HTTP 사례에 넣지 않는다. 손으로 복사한 csvSafe 대역이나 소스 문자열 검색을 테스트 증거로 쓰지 않는다. 실제 Excel/LibreOffice 실행은 미확인이므로 임의 명령 실행 재현으로 보고하지 않는다. 기존 웹 보호와의 출력 불일치는 소스 및 TS 실행으로 확인했지만 서버 HTTP 재현은 구현자가 먼저 확정해야 한다. 과거의 handoff 상한·메일·추적 스니펫 과제를 다시 구현하지 않는다. 전체 Go 스위트는 이 좁은 변경을 검증하려고 무조건 돌리지 않는다.
- 차선 후보: 긴 검색어의 목록 주소 복사에서 500자 초과 부분이 조용히 잘리는 문제 — `listSharePath`가 저장 보기용 `savedListQuery`를 재사용해 실제 501자 검색어를 500자로 줄임을 TS 실행으로 확인했다. 저장 보기의 기존 500자 한도는 유지하고, 주소 복사의 별도 판정·오류 안내 또는 보존 정책을 정한 뒤 실제 링크 복원 결과로 검증한다.

구현 순서·예산: 공유 사례와 HTTP 실패 재현 12분 → csvSafe 최소 수정·양쪽 golden 비교 10분 → 좁은 DB race·웹 전체·vet 13분 → 결과 정리 및 환경 문제 예비 10분(합계45분, 추정). DB를 준비하지 못하면 skip을 통과로 적지 말고 미검증을 명시한다. 이번 과제의 핵심은 서버 내보내기 배선 검증이며 순수 함수 테스트만으로 완료하지 않는다.
