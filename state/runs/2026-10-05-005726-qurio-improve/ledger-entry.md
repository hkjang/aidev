## 2026-10-05
- 선택: `postgresCTEColumnList` 의 역방향 WITH 추적 루프를 메모이제이션해 PostgreSQL 게이트의 quadratic 제거 (가치 4 / 위험 2 / 작업량 S)
- 결과: 성공
- 요약: `postgresCTEColumnList`(sqlsafe.go:952)의 역방향 루프가 **함수 호출 후보 사이트마다** 토큰 스트림을 0번까지 다시 훑어, `SELECT upper (x) AS a0, …` 같은 **평범한 별칭 투영**이 바이트 2배마다 4배가 되는 quadratic 이었다 — base 201bf2e 재측정 4000/8000/16000 terms = **112 / 446 / 1759 ms**(325KB), DB 권한 없이 validate 엔드포인트로 도달한다. 같은 파일의 `fromItemContext`(882)는 이미 memo+trail 로 같은 결함을 닫아 두었고 그 주석(821-828)이 "a core pinned for minutes, reachable without any database privilege" 라고 사유를 적어 두었는데, 이 루프만 그 memo 밖에 남아 있었다. 루프를 `cteWithList` 로 떼어내 **걸음은 한 줄도 바꾸지 않고**(같은 순서·같은 조건·같은 종료) lazy memo+trail 로 감쌌다. 메모 키는 **(커서, columnDepth) 두 값** — 이 루프는 다른 깊이의 토큰을 *건너뛰기만* 해서 바깥 그룹을 빠져나가 형제 그룹 안까지 보므로, 커서만으로 키를 잡으면 fail-open 이 된다(아래에서 실측으로 확인). 서로 다른 깊이 8개를 넘으면 메모 없이 기존 걸음으로 폴백해 적대적 중첩 질의의 O(n²) 메모리를 막는다. **프로덕션 파일 1개(+65/-6, 신규 메서드 2개 + 구조체 필드 2개 + 상수 1개)**, 테스트 1개. 허용목록·`callAdjacent`(724)·`fromItemContext`(882)·`postgresAliasColumnList`(752)·Oracle 경로는 한 줄도 건드리지 않았다.
  **수정 후 측정**: 4000/8000/16000 terms = **5.8 / 10.4 / 19.7 ms** (doubling 당 1.79배·1.91배 = 선형). 16000 terms 기준 **89배** 빨라졌다(1.754s → 0.020s).
  **선재 테스트 공백을 함께 메웠다 (정직하게 — 이게 이 회차의 가장 중요한 발견이다)**: 수용 기준 4(메모를 `return true`/`false` 로 고정해 기존 테스트가 깨지는 것을 확인)를 하려고 고정했더니 **아무 테스트도 깨지지 않았다**. 원인을 추적하니 이 루프는 WITH 목록의 **두 번째 이후** 질의 이름에서만 돌고(첫 번째는 967행의 `previous == WITH` 지름길로 빠진다), 기존 스위트의 CTE 케이스는 `WITH totals(…) AS`·`WITH cte(a,b) AS` **단일 CTE 두 건뿐**이라 루프에 커버리지가 **0** 이었다. 그래서 `TestAnalyzeDialectAllowsPostgresLaterCTEColumnLists`(허용 5건)와 `TestAnalyzeDialectLaterCTESearchDoesNotExemptFunctionCalls`(차단 7건)를 추가했고, 이 둘은 **base 201bf2e 의 sqlsafe.go 에서도 통과**함을 확인했다(판정 불변 = 기존 동작을 고정한 것이지 바꾼 것이 아니다).
  **검증**: ① 새 scale 테스트 red(1.754s) → 수정 → green(0.010s). ② 걸음의 답을 `true`/`false` 로 고정하면 새 차단/허용 테스트가 **각 방향으로** 깨짐 → 복원(인과 확인). ③ **깊이 키가 하중을 받는 것을 fail-open 으로 실증**: 메모 키를 `cteMemoFor(0)` 로 깊이 붕괴시키면 `SELECT * FROM (WITH p (x) AS (…), q (y) AS (…) SELECT * FROM p, q) sub, side_effect_fn (3) AS z` 가 **blocked → ro=true/low 로 뒤집힌다**(깊이 1 의 CTE 사이트가 칠한 "true" 를 깊이 0 의 호출 사이트가 훔친다). 이 두 질의를 차단 테스트에 고정했다. ④ **판정 불변 증명**(이 저장소의 확립된 방식): 현실 질의 **91건 × postgres·oracle = 182 판정**(`WITH a (x) AS`, `WITH RECURSIVE t (n) AS`, `WITH a (x) AS (…), b (y) AS (…)`, `SELECT fn (x) AS a, side_effect_fn (y) AS b`, 인용 식별자, 별칭 컬럼 목록, WITH ORDINALITY, 쓰기·DDL·멀티스테이트먼트·깨진 문법 포함)을 base `201bf2e` 의 sqlsafe.go 와 수정본에서 각각 덤프해 비교 — **diff 0, md5 동일(`80d8f2cf416eccfe2bc55ec144f5a17d`)**. ⑤ **차별 퍼즈**: base 사본을 별도 패키지로 올려 같은 프로세스에서 나란히 돌려 무작위 토큰 질의 **40만 × 2방언 = 80만 비교** + 중첩 CTE 생성기 **6만 × 2방언 = 12만 비교(중첩 최대 14 — 깊이 한도 8 폴백 경로 통과)**, **drift 0**. ⑥ 깊이 한도를 0(메모 **완전 off**)·1·1000 으로 바꿔 전체 스위트 재실행 — 한도 0 에서 **스케일 테스트만** 실패하고(1.90s) 정합성 테스트는 **전부 통과**, 1·1000 은 전부 통과 = **순수 성능 변경**임을 코드로 고정. ⑦ `go test ./... -count=1` **28 패키지 ok exit 0**, `go test -race ./internal/domain/sqlsafe/` ok, `go vet ./...`·`go vet -tags=integration ./...`·`make check-go-format`·`go build ./...` 통과. ⑧ 폐기 PostgreSQL 17(도커 127.0.0.1:55601 — 과거 점유 포트 회피) bootstrap(fresh-install → migrations) 후 CI 와 같은 세 env 로 `go test -race -p=1 -tags=integration ./... -count=1` → **30 패키지 전부 ok**. 임시 덤프·퍼즈 파일과 base 사본 패키지는 전부 삭제했고(`git status` 로 확인: 변경 2파일), 컨테이너는 제거했다.
  **통합 2회차에서 실패 1건이 났고 내 변경이 아님을 증명했다(정직하게)**: 같은 DB 에 스위트를 연속으로 한 번 더 돌리자 `TestSSEDiscardsQueuedDeltaAfterProviderCredentialChange/delete` 가 `credential_race_integration_test.go:236: ERROR: new row for relation "qurio_secrets" violates check constraint "qurio_secrets_check" (SQLSTATE 23514)` 로 깨졌다(나머지 29 패키지 ok). 세 가지로 좁혔다 — ① `go list -deps -tags=integration ./internal/intelligenceapi` 에 **sqlsafe 가 0건**이라 이 패키지는 내 코드를 실행조차 하지 않는다 ② 단독 실행 **3/3 통과** ③ **DB 를 DROP/CREATE 하고 bootstrap 후 다시 전체 실행하니 30 패키지 전부 ok**. 즉 1회차가 `qurio_secrets` 에 남긴 행에 의존하는 **선재 픽스처 격리 결함**이며(프로필의 '공유 폐기 DB 잔존 행' 범주), CI 는 매번 새 DB 로 1회만 돌려 녹색이다. 고치지 않고 ideas.json 에 신규 항목으로 올렸다 — 이번 과제 범위 밖이고 증명 없는 수정은 금지다.
