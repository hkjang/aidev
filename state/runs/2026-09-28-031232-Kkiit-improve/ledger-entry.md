- 선택: 웹훅 수정 저장의 DB 실패를 404 "웹훅을 찾을 수 없습니다." 가 아니라 500 으로 알리기 (가치 3 / 위험 1 / 작업량 S)
- 결과: 성공
- 요약: `updateMyWebhook`(webhooks.go:174)이 `UPDATE webhooks ...` 의 모든 오류를 `err != nil || tag.RowsAffected() == 0` 로 묶어 404 `webhook_not_found` 로 돌려주어, 같은 파일 `createMyWebhook` 이 같은 표의 INSERT 오류를 이미 500 `create_failed` 로 보고하는 것과 비대칭이었다 — 목록에서 웹훅을 보고 있는 소유자가 수정만 하면 "없는 웹훅" 이라는 안내를 받았다. 저장 실패를 500 `webhook_save_failed` "웹훅을 저장하지 못했습니다."(createMyWebhook 문구와 동일)로 가르고 `RowsAffected()==0` 만 404 로 남겼으며, 20줄 아래 `deleteMyWebhook` 의 동일 패턴도 함께 갈라 500 `webhook_delete_failed` 로 보고한다. 검증: 실제 라우터 + 버릴 PostgreSQL 16(docker 29.7.2)으로 HTTP→DB 왕복 통합 테스트를 먼저 실패시킨 뒤 수정해 통과시켰고, 임시 프로브로 실패 경로의 오류가 `*pgconn.PgError{Code:"22021", Message:"invalid byte sequence for encoding \"UTF8\": 0x00", Where:"unnamed portal parameter $3"}` 이고 행이 존재함에도 RowsAffected 가 0 이라는 것(= 문장이 아예 실행되지 않음)을 눈으로 확인한 뒤 프로브를 제거했다. 분기를 두 방향으로 변이시켜(항상 500 → `status=500 want=404`, 항상 404 = 원본 → `status=404 want=500`) 각각 다시 실패하는 것을 확인했다. 깨끗한 DB(DROP/CREATE)로 `go test ./cmd/... ./internal/...` 전체 통과(httpapi 82.9초, 통합 실제 실행), `go vet ./cmd/... ./internal/...` 무결, `gofmt -l cmd internal` 무출력, `npm --prefix web test` 10건 통과. 프런트는 `error.message` 를 그대로 띄우므로 `web/`·`internal/ui/dist` 를 건드리지 않았고 `docs/openapi.yaml` 의 PUT `/me/webhooks/{id}` 에 핸들러가 실제로 내보내는 `'400'` 과 새 `'500'` 두 줄만 더했다. 프로덕션 파일 1개(webhooks.go).
