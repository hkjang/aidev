- 선택: UserInfo POST가 form-encoded `access_token`(RFC 6750 §2.2)을 받게 하고, 헤더와 본문에 둘 다 오면 400 `invalid_request`로 거절 (가치 2 / 위험 1 / 작업량 S)
- 결과: 성공 (커밋 76f5974)
- 요약: `POST /realms/{realm}/protocol/openid-connect/userinfo`는 라우트로 등록되어 있었지만 토큰은 `bearerToken(r)`이 `Authorization` 헤더에서만 읽어, RFC 6750 §2.2대로 본문에 `access_token=…`을 싣는 RP·SDK는 **유효한 토큰으로도 401 `invalid_token`** — "토큰을 버리고 다시 받아라"는 답 — 을 받았다. `userInfo` 안에서만 고쳤다(`bearerToken` 시그니처는 그대로 — `mcp.go:117`·`middleware.go:167`도 쓴다): POST일 때만 `r.ParseForm()` 후 `r.PostForm.Get("access_token")`을 헤더 값과 합치고(`r.FormValue`는 쿼리도 읽으므로 쓰지 않음), 둘 다 있으면(값이 같아도) §2 "하나만 써야 한다"대로 `WWW-Authenticate: Bearer error="invalid_request"` + 400 `invalid_request`로 끝낸다 — 토큰이 나쁜 게 아니라 요청이 잘못된 것이라 401로 토큰을 버리게 하지 않는다. GET은 본문을 읽지 않고 쿼리 방식(§2.3)은 일부러 받지 않는다(토큰이 접근 로그에 남는다). `writeUserInfoUnavailable`(500) 분기와 realm 조회 순서는 그대로다. 검증: 새 연동 테스트 `TestIntegrationUserInfoReadsTheTokenFromAPostBody`(헤더 GET 200 기준값 → 본문만 POST 200 + `sub`·`preferred_username` 일치 → 헤더+본문 400 invalid_request + WWW-Authenticate → 본문 garbage 401 invalid_token → GET 쿼리 401 → POST 쿼리 401)가 **수정 전 핸들러에서 첫 단언(본문만 → 200)이 실제로 401 `invalid_token`으로 실패함**을 확인했고, 수정 후 통과. 라우트 워커 테스트(`TestIntegrationSuspendedRealmRefusesEveryProtocolEndpoint` — 빈 본문 POST userinfo는 realm 조회에서 먼저 끊겨 401 그대로)와 CSRF·API 키 라우트 테스트도 통과. `make lint` 통과(golangci-lint 0 issues, govulncheck 0, eslint --max-warnings 0), `make test` 전체 통과(exit 0) — `go test -race ./...` 13개 패키지 ok(httpserver 115s / store 81s), 연동 테스트 SKIP 0건(기존 컨테이너 셋 재사용, CA `/tmp/resso-test-certs-0916`), `go vet`, `npm run test`(29파일/161테스트, 디스크 파일 수와 일치), `npm run build`. `docs/compatibility.md`의 UserInfo 행에 POST 본문·둘 다·쿼리의 답을 한 문장으로 적었다(문장만이라 PDF·캡처 재생성 없음).
