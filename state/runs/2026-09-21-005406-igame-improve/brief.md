- 과제: Migrate의 체크섬 거부·DDL 롤백·재실행 안전성을 실제 PostgreSQL로 검증 (가치 4 / 위험 1 / 작업량 M)
- 왜: `internal/database/database_test.go`의 5개 테스트는 migrationNames의 이름·순서만 확인하여, 기동 때 호출되는 Migrate의 체크섬 거부와 SQL/이력 기록의 원자성을 증명하지 못한다. 실제 PostgreSQL에서 이 경계를 검증하고 `make test-db`에 연결하면 잘못된 마이그레이션 변경이 부분 적용 상태를 남기는 회귀를 배포 전에 발견할 수 있다.
- 수용 기준: 1) 실제 `database.Migrate`와 embedded `migrations.Files`를 실행하여 최초 적용 후 모든 파일의 체크섬이 기록되고, 두 번째 호출에서는 이력의 checksum/applied_at와 대표 seed 행이 바뀌지 않음을 확인한다. 2) 테스트 소유 DB 영역의 이력 체크섬을 변조하면 해당 파일을 식별하는 오류로 중단하며 변조값을 덮어쓰지 않는다; 정상 체크섬으로 복구하면 다시 성공한다. 3) 실제 SQL 오류로 특정 migration의 이력 INSERT를 실패시키면 그 migration의 DDL과 이력 모두 롤백되지만 앞서 완료한 migration은 남는다; 오류 원인을 제거하고 재호출하면 정상 완료한다. 테스트는 mock pool·소스 문자열 검사 없이 PostgreSQL의 실제 상태를 조회해 이 세 계약을 증명하고, `make test-db DSN=...`가 API와 database 패키지 모두 실행해야 한다.
- 건드릴 파일: `internal/database/database_pg_test.go`(신규) — 실제 pool·격리 fixture 및 위 회귀 테스트; `Makefile:test-db` — 기존 DSN 필수 가드를 유지하고 `./internal/api/... ./internal/database/...`를 실행; `README.md:개발과 검증` — DB 테스트 범위와 격리/권한 전제 한 문단. 읽기 참조: `internal/database/database.go:Migrate,migrationNames`, `internal/api/admin_pg_test.go:migratedPool`, `migrations/migrations.go:Files`, `migrations/010_silent_sso.sql`, `cmd/igame/main.go:main`.
- 검증 명령: `go test ./cmd/... ./internal/... ./migrations/...`; `go vet ./cmd/... ./internal/... ./migrations/...`; `bash scripts/check-release-contract.sh`; 일회용 PostgreSQL 준비 후 `IGAME_TEST_DSN="$TEST_DSN" go test ./internal/database/... -run '^TestMigrate' -v -count=1`; `make test-db DSN="$TEST_DSN"`; `IGAME_TEST_DSN="$TEST_DSN" go test -race ./internal/database/... -run '^TestMigrate' -count=3`. TEST_DSN은 구현자가 만든 일회용 DB의 실제 DSN이다. 새 테스트 이름은 TestMigrate 접두사를 사용한다.
- 위험과 피할 것: 운영 DB와 API fixture의 public schema를 변조하지 않는다. `internal/database/database.go`와 `migrations/*.sql`은 수정하지 않고, auth·workflows·환경 변수 계약도 그대로 둔다. 이미 적용된 SQL의 체크섬을 정당화하거나 자동 갱신하는 코드는 금지한다. DSN 미설정만 skip하고, DSN 설정 후 연결/권한/SQL 오류는 반드시 실패로 낸다. .github/workflows에서 IGAME_TEST_DSN을 자동 제공하지 않는 현 상태까지 이번 과제에서 넓히지 않는다. 과거의 근거 없는 릴리즈 실패 진단·감사 게이트 완화·랭킹 정책 변경을 반복하지 않는다.
- 차선 후보: 로컬 릴리즈 감사 `make audit-release` 추가 (가치 3 / 위험 1 / 작업량 S) — 10분 안에 격리 PostgreSQL fixture를 준비하지 못할 때만 선택. 읽어 본 `.github/workflows/release.yml`과 동일한 SDK/web `npm audit --audit-level=low` 및 `govulncheck@v1.6.0 ./...`를 Makefile 타깃에 묶고 docs/release.md에 선행 `make deps`와 네트워크 필요를 명시한다. 워크플로·lockfile·감사 임계값은 변경하지 않고 실제 명령의 실패를 숨기지 않는다. 현재 취약점/릴리즈 실패의 존재는 미확인이며 이 과제의 전제가 아니다.

실행 순서와 45분 예산:
1. 8분: IGAME_TEST_DSN fixture를 구성한다. 테스트마다 UUID 기반 전용 schema와 전용 pool의 search_path를 지정하고, 모든 커넥션에 적용되도록 pgxpool 설정을 사용한다. 공유 public로 폴백하지 않도록 한다. pgcrypto는 DB 전역 extension이므로 일회용 DB에 한 번 준비하고 테스트가 임의로 DROP EXTENSION하지 않는다. 안전한 식별자 인용 및 cleanup 순서(pool close 후 자기 schema만 제거)를 지킨다. API의 migratedPool은 현재 기본 schema에 실제 migration을 적용하므로 그대로 재사용해 이력을 변조하면 안 된다.
2. 10분: 최초/재실행 및 checksum 변조 테스트를 작성한다. checksum은 embedded SQL bytes의 SHA-256과 비교하고 이름·개수는 migrationNames에서 구한다. applied_at 재작성도 잡도록 DB 값을 전후 비교한다.
3. 12분: rollback 테스트를 작성한다. 가능한 구체적 방법은 빈 전용 schema에 schema_migrations와 BEFORE INSERT trigger를 먼저 두고 `NEW.name='010_silent_sso.sql'`일 때만 RAISE EXCEPTION하는 것이다. Migrate를 호출하면 001~009는 commit하고 010의 `oidc_flows.silent` 추가 뒤 이력 INSERT가 실패한다. 호출 후 앞선 이력/seed가 보존되고 010 이력과 silent column은 없는지 확인한 다음 trigger를 제거하고 Migrate를 재호출해 둘 다 생기는지 검증한다. 이는 실제 DB 오류 주입이며 SQL 파일 교체나 가짜 트랜잭션은 필요 없다. 컬럼 조회는 information_schema에서 자기 schema를 명시한다.
4. 5분: Makefile/README 연결, 기본 검사와 전체 test-db 실행.
5. 예비 10분: fixture 정리·race 반복·실패 원인 진단. 격리 권한/extension 문제로 막히면 공유 schema 수정으로 우회하지 말고 위 차선으로 전환한다.
