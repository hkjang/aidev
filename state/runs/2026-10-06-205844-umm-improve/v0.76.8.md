# v0.76.8 — `make test-web` 이 CI 가 묻는 것을 묻습니다

이번 회차에도 **제품은 한 줄도 바뀌지 않았습니다.** umm 을 쓰는 사람이 보는 화면, API, 데이터는
v0.76.7 과 똑같습니다. 바뀐 것은 **저장소에서 `make test-web` 을 친 사람이 받는 답**입니다. 전에는
그 답이 초록색인데도 CI 는 빨갰습니다 — 같은 트리에서, 같은 질문인 줄 알고.

`.github/workflows/ci.yml` 의 `Frontend` 절은 게이트 **아홉 개**를 돌립니다. 저장소가 사람에게
내주는 로컬 타깃 `make test-web` 은 그중 **넷**만 돌렸습니다. 빠진 넷 가운데
`npm audit --audit-level=high` 가 있었고, **하필 그것이 v0.76.7 회차를 빨갛게 만든 게이트**입니다.

```
    같은 트리에서  CI 의 Frontend 절  vs  make test-web

      ci.yml 의 게이트          전: make test-web      후: make test-web
    ━━━━━━━━━━━━━━━━━━━━━━━   ━━━━━━━━━━━━━━━━━   ━━━━━━━━━━━━━━━━━
    npm ci                      ─                   ─   (make web 의 일)
    test:offline-queue          ─                   ✓
    audit --audit-level=high    ─   ← 여기서 빨감    ✓
    typecheck                   ✓                   ✓
    lint                        ✓                   ✓
    check-i18n                  ✓                   ✓
    test                        ✓                   ✓
    build                       ─                   ✓
    verify:pwa                  ─                   ✓
```

도달할 수 없는 게이트는 사람이 통과시킬 수도, 고칠 수도 없습니다. 그래서 PR #167 은 로컬 검증을
전부 통과한 뒤 **CI 에서만** 떨어졌고, 그 빨간색이 PR 의 결함처럼 읽혀 회차 하나를 수리에 더
썼습니다. 그때 main 도 똑같이 빨갰으니 PR 의 결함이 아니었습니다.

## 판정이 커밋에서 오지 않는 게이트가 있습니다

`make test-web` 이 돌리던 넷은 전부 **트리를 보고 답하는** 게이트입니다 — 같은 커밋이면 어제도
오늘도 같은 답입니다. `npm audit` 은 다릅니다. 이것은 **레지스트리에 묻습니다**, 그리고 레지스트리는
새 권고를 매일 공개합니다. 어제 초록이던 트리가 **아무도 손대지 않아도** 오늘 빨갛습니다.

v0.76.7 회차에 일어난 일이 정확히 그것입니다. `source-map-js@1.2.1` 에
GHSA-68fv-2mgg-jv7q(high)가, `dompurify@3.4.14` 에 권고 둘(low)이 붙었고, 저장소의 코드는 한 줄도
바뀌지 않았습니다. 이런 게이트야말로 로컬에 있어야 합니다 — **커밋이 아니라 날짜가 판정을 바꾸는
게이트는, 사람이 밀기 전에 스스로 물어볼 수 있어야 합니다.**

## 순서도 CI 와 같습니다

```make
test-web:
	npm --prefix web run test:offline-queue
	npm --prefix web audit --audit-level=high
	npm --prefix web run typecheck
	npm --prefix web run lint
	node web/scripts/check-i18n.mjs
	npm --prefix web test
	npm --prefix web run build
	npm --prefix web run verify:pwa
```

목록이 아니라 **`ci.yml` 과 같은 순서**입니다. 값싸고 판정이 커밋과 무관한 둘이 앞에 옵니다 —
`ci.yml` 머리말이 버전 검사를 맨 앞에 두는 이유("Before anything slow")와 같습니다. 그래서 취약한
잠금 파일에서는 **두 번째 게이트에서 멈추고**, 뒤의 느린 `build` · `verify:pwa` 를 낭비하지
않습니다.

## 느슨하게 만든 것은 없습니다

이 변경은 로컬에 검사를 **더하기만** 합니다. 이것을 적어 두는 이유는, 빨간 CI 를 초록으로 만드는
가장 쉬운 길이 언제나 임계값을 내리는 것이기 때문입니다.

- **`--audit-level=high` 그대로입니다.** 범위도, `.github/workflows/*` 도, `Dockerfile` 도,
  `engines` 도 손대지 않았습니다.
- **`npm ci` 는 일부러 넣지 않았습니다.** 설치는 `make web` 의 일이고, 시험 타깃이 멀쩡한
  `node_modules` 를 지우는 것은 되돌릴 수 없는 환경 변경입니다. 이 타깃은 설치가 없으면 첫 게이트
  에서 멈춥니다 — v0.76.5 가 그 실패에 이름을 붙여 두었으니, 그 답은 Node 가 아니라 `npm ci` 를
  말합니다.
- **`make test-go` 는 그대로입니다.** CI 는 `-p 1` 로 직렬화하고 race 검출기와 `govulncheck` 를
  더 돌립니다. 그쪽 드리프트는 격리된 PostgreSQL 에서 경합 증거를 먼저 모아야 하는 별 과제이고,
  이 회차에서 추측으로 맞추지 않았습니다.
- 두 목록이 어긋나지 않게 하는 **기계적 검사는 넣지 않았습니다.** `ci.yml` 을 다른 파서로 다시
  읽는 것이 그 자체로 계약을 둘로 만듭니다. 대신 타깃 위의 주석이 `ci.yml` 의 `Frontend` 절과
  맞춰 두라고 적습니다 — **이 변경의 가장 약한 고리이고, 그렇게 적어 둡니다.**

## 결함을 손으로 만든 대역 없이 재현했습니다

주장은 "로컬이 초록인데 CI 가 빨갛다" 이므로, **같은 트리에서 둘을 나란히** 돌려야 증거가 됩니다.
`4f2de72` 가 올린 잠금 파일 6줄만 되돌려(`dompurify 3.4.16→3.4.14` ·
`source-map-js 1.2.2→1.2.1`) **CI 가 실제로 거절한 그 잠금 파일**을 만들고, 그 하나의 트리에서
고치기 전 타깃과 고친 뒤 타깃을 돌렸습니다.

```
    같은 취약 잠금 파일, 같은 트리

    전의 test-web (게이트 4개)        EXIT=0   Tests 230 passed      ← 결함
    후의 test-web (게이트 8개)        EXIT=2   audit 에서 멈춤
                                               GHSA-68fv-2mgg-jv7q (high)
                                               2 vulnerabilities (1 low, 1 high)
    잠금 파일을 되돌리면              EXIT=0   게이트 8개 전부 통과
```

첫 줄이 고친 결함입니다. **CI 는 빨갛고 저장소의 로컬 게이트는 초록** — 그리고 그 초록은 시험이
230개 통과했다는 참말이어서, 보는 사람이 의심할 이유가 없었습니다.
