- 과제: `/v1/jobs/{job_id}/result`에 `HEAD` 메서드 허용 (가치 3 / 위험 1 / 작업량 S)
- 왜: `internal/httpapi/server.go:85`가 `Methods(http.MethodGet)`만 등록해 gorilla/mux가 `HEAD`를 `405`로 거절한다(정찰에서 완료된 PDF job에 `http.Head`를 보내 직접 확인: status=405, `Allow`·`Content-Length`·`Cache-Control` 모두 빈 값 — `documentResponse` 래퍼까지 닿지 않음). 다운로드 관리자·`curl -I`·프록시의 존재/크기 프로브가 실패하는데, 핸들러가 이미 `http.ServeContent`를 쓰므로 HEAD는 라우트만 열면 본문 없이 같은 헤더(`Content-Length`, `Accept-Ranges`, `Content-Disposition`, `Content-Type`, `Last-Modified`)를 돌려준다.
- 수용 기준: 1) 완료된 job의 `/v1/jobs/{id}/result`에 `HEAD`를 보내면 `200`, `Content-Length`가 GET 본문 길이와 같고, 응답 본문은 0바이트, `Accept-Ranges: bytes`·`Cache-Control: no-store`·`X-Content-Type-Options: nosniff`·`Content-Disposition`(GET과 동일 값)·`Content-Type`이 붙는다. 2) 없는 job ID 또는 결과 파일이 아직 없는(`queued`) job에 `HEAD`를 보내면 GET과 같은 `404`(본문은 net/http가 HEAD에서 자동으로 버리므로 상태 코드만 검사). 3) 기존 GET 동작(`TestJobResultServesRangeRequests`, `TestJobResultReturnsNotFoundWhenFileIsGone`, `TestJobResultSanitizesInjectedUploadFilename`)은 수정 없이 그대로 통과. 4) 새 통합 테스트는 라우트를 `Methods(http.MethodGet)`으로 되돌리면 `405`로 실제 실패해야 한다(요약에 적을 것).
- 건드릴 파일:
  - `internal/httpapi/server.go:85` `routes()` — `.Methods(http.MethodGet, http.MethodHead)`로 변경. 한 줄. 이유를 짧은 주석으로(ServeContent가 HEAD를 처리하므로 라우트만 열면 됨). 다른 라우트(`/v1/jobs/{job_id}`, `/v1/history` 등)는 건드리지 말 것 — JSON 핸들러는 `Content-Length`를 직접 계산하지 않아 HEAD 의미가 다르고 이번 과제 범위 밖.
  - `internal/httpapi/integration_test.go` — `TestJobResultServesRangeRequests`(613행) 옆에 `TestJobResultAnswersHeadProbes` 추가. 기존 헬퍼 `startAppServerWithConfig(t, nil)` + `createCompletedPDFJob(t, serverURL)`를 그대로 쓰고, `http.Get`으로 전체 본문 길이를 먼저 잰 뒤 `http.Head`로 위 1)을 검사. `resp.ContentLength`(Go 클라이언트가 HEAD 응답의 `Content-Length` 헤더에서 채움)와 `io.ReadAll(resp.Body)` 길이 0을 함께 확인. 2)는 같은 테스트 안에서 `serverURL + "/v1/jobs/does-not-exist/result"`에 `http.Head` → `404`.
