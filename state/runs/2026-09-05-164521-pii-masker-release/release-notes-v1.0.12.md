Bound how many synchronous masks run at once. Asynchronous jobs were capped by the `PII_MASKER_MAX_CONCURRENT_JOBS` semaphore, but the synchronous path had no limit at all, so simply calling `/v1/mask` concurrently bypassed that ceiling and decoded and re-rendered as many documents in parallel as there were in-flight requests — page rendering costs tens of times the upload size in memory, so a handful of concurrent calls could exhaust the server that the async limit was meant to protect. `Service` now owns a `syncSlots` semaphore sized by `PII_MASKER_MAX_CONCURRENT_SYNC` (default 4), and `ProcessSync` starts work only after it acquires a slot. A request that finds every slot taken waits at most `PII_MASKER_SYNC_QUEUE_WAIT_SECONDS` (default 10 seconds, `0` rejects immediately) — waiters still hold their uploaded bytes in memory, so the wait is deliberately short — and is then turned away through a new `service.ServerBusyError` that the API renders as `503` with a `Retry-After` header and `server_busy` metadata. Cancelling the request context abandons the wait immediately.

Verified by two integration tests (five concurrent requests against a held upstream stay at a peak concurrency of two and then all five finish `200`; with the slots full, a second request never reaches upstream and comes back `503` with `server_busy`) and four `internal/service` unit tests covering immediate rejection, reuse after release, acquisition after waiting, context cancellation, and the rejection metadata. `gofmt -l`, `go vet ./...`, `go build ./...`, `go test -count=1 ./...` and `go test -race -count=1 ./...` all pass, `-race -count=5` showed no flakiness, and temporarily removing the slot acquisition from `ProcessSync` made the new tests fail as expected. The README documents the limit and both environment variables.
