# Postra v0.25.10 — IMAP 이 아닌 첫 응답을 운영자에게 그대로 말합니다

v0.25.9 부터 IMAP `Dial` 은 RFC 3501 §7.1.1 의 환영 메시지가 아닌 첫 줄을 거부합니다. 그런데 **그 거부가 운영자에게는 `서버 환영 메시지 수신 단계: 알 수 없는 오류로 중단되었습니다` 로만 보였습니다** — 멈춘 단계는 알려 주고 원인은 알려 주지 않는 문장입니다. 진단은 저장되고 화면에 보이므로 **서버가 보낸 배너는 한 글자도 싣지 않는다**는 규약이 있어서, 화면에는 "수신 포트가 아직 110 이나 25 다" 를 짐작할 단서가 하나도 남지 않았습니다. 그래서 설정 오류인 실패가 **네트워크 장애처럼** 읽혔습니다. 이번 릴리즈는 그 조합에 다음에 확인할 설정을 적어 줍니다.

**프로덕션 변경은 `internal/application/sync_diagnostics.go` 한 파일입니다** — 상수 1개와 `syncHint` 의 분기 1개. 거부 판정, 재시도 횟수, 단계·분류 레이블은 한 글자도 바뀌지 않습니다. **새 설정 키, 새 환경변수, DB 마이그레이션, 화면 변경, API 응답 모양 변경은 없습니다.**

**정상적인 IMAP 서버에 붙는 설치는 아무 변화가 없습니다.** 달라지는 것은 이 거부가 실제로 일어났을 때 동기화 실패 진단에 적히는 문장 하나뿐입니다.

## 무엇이 어긋나 있었나

- `syncHint` 는 `greeting` 단계에 이미 힌트 두 개를 갖고 있었습니다 — **993/995 포트에 보안 모드가 TLS 가 아닌 경우**와 **서버가 침묵하는 경우**(`timeout`·`closed`·`reset`). v0.25.9 이 새로 만든 거부는 `Class` 가 `other` 라서 두 힌트 어디에도 걸리지 않고 빠져나갔습니다.
- 그래서 최종 Summary 가 `IMAP mail.corp.local:110 (none) · 서버 환영 메시지 수신 단계: 알 수 없는 오류로 중단되었습니다 · 제한 60.0초 · 연결 시도 3회` 로 끝났습니다. **운영자가 가장 먼저 봐야 할 것(수신 포트와 프로토콜)이 화면에 없습니다.**
- 서버 원문을 싣지 않는 규약이 여기서는 불리하게 작용했습니다. 평소에는 그 규약이 비밀값·메일 주소 유출을 막지만, 이 거부에서는 **배너가 유일한 단서**였고 그것이 제거된 자리에 아무 설명도 들어가지 않았습니다.
- v0.25.9 의 릴리즈 노트는 운영자에게 "이 단계로 멈추면 호스트·포트·프로토콜을 먼저 확인하라" 고 적었습니다. **그 안내가 화면에는 없었습니다** — 노트를 찾아 읽은 사람만 알 수 있었습니다.

## 무엇이 바뀌었나

`stage=greeting` + `protocol=imap` + `class=other` 한 조합에 힌트가 붙습니다:

> 서버의 첫 응답이 IMAP 환영 메시지가 아닙니다. 수신 포트와 프로토콜 조합을 확인하세요(POP3 110·995 또는 SMTP 25·587 포트에 IMAP으로 접속했거나, 프록시가 다른 서버로 연결하고 있을 수 있습니다)

- **이 조합에 도달하는 거부는 두 가지이고, 한 문구가 둘 다에 맞습니다** — `Dial` 의 `isGreeting` 가드(태그 없는 `OK`/`PREAUTH`/`BYE` 가 아닌 첫 줄)와, **프로토콜 행 상한을 넘겨 끝나지 않은 첫 줄**(`errUnframed`). 운영자에게는 둘 다 "첫 줄을 IMAP 환영 메시지로 쓸 수 없었다" 는 같은 뜻입니다. 추측으로 두지 않고 어댑터 테스트로 **실제 루프백 연결 위에서** 두 거부가 모두 `greeting`/`other` 를 지고 오는 것을 확인했습니다.
- **기존 두 힌트가 그대로 우선합니다.** 새 분기는 greeting 힌트들 **맨 뒤**에 있습니다. 993/995 + 보안 모드 불일치, 그리고 동시 접속 정황은 잘못된 포트보다 **더 좁은 진단**이므로 먼저 나가야 합니다. 하위 테스트가 그 우선순위를 고정합니다 — 이 힌트를 추가하는 것으로 누구의 더 정확한 진단도 빼앗지 않았습니다.
- **POP3 는 범위 밖입니다.** POP3 어댑터는 자기 어휘(`+OK` 부재)로 거부하고, IMAP 포트를 지목하는 문구는 그 운영자를 엉뚱한 곳으로 보냅니다. `protocol=pop3` 는 전처럼 힌트 없이 지나갑니다.
- **새 `Stage`·`Class` 레이블이 없고 `domain.SyncDiagnostic` 에 필드가 추가되지 않았습니다.** 힌트는 기존 `Hint` 경로로만 흐르므로 생성되는 API 계약, 브라우저 화면, `internal/transport/spa/assets` 는 손대지 않았습니다.
- 힌트는 **읽기 경계(`safeSyncDiagnostic`)를 넘어서도 살아남는지** 함께 단언합니다 — 허용 목록 토큰만으로 Summary 를 다시 조립하는 그 경로를 통과하지 못하면 힌트는 아무 값도 없습니다.

**두 가지 한계를 밝혀 둡니다.** ① 실시간 대기(IDLE) 연결이 떠 있는 동안 포트가 잘못 설정되어 있으면 `AccountSessions > 1` 이므로 **동시 접속 힌트가 먼저 나갑니다** — 덜 정확한 안내입니다. 우선순위를 뒤집으면 반대 방향의 오진이 생기므로 이번에는 바꾸지 않았고, 하위 테스트로 현재 동작을 고정해 두었습니다. ② `class=other` 에 도달하는 **제3의 경로**(어댑터가 분류하지 못한 read 오류)가 생기면 이 힌트가 그 경우에도 나갑니다. 지금 코드에서 확인된 경로는 위 두 가지뿐입니다.

## 검증

- **수정 전 FAIL → 수정 후 PASS 를 눈으로 확인했습니다.** 실패 출력이 이 릴리즈가 고치는 결말입니다:
  - `imap_greeting_test.go`: `summary "IMAP 127.0.0.1:43739 (none) · 서버 환영 메시지 수신 단계: 알 수 없는 오류로 중단되었습니다 · 제한 60.0초 · 연결 시도 3회 · 이 서버에 Postra가 유지 중인 연결 1개(이 계정 1개)" carries no hint about the first response not being an IMAP greeting` — 루프백 서버가 `+OK POP3 ready <1234@maildrop>` 로 인사한 계정 생성 → 동기화 → 작업 조회 경로의 **실제 최종 Summary 원문**입니다.
  - `sync_diagnostics_test.go`: `hint = "", want "서버의 첫 응답이 IMAP 환영 메시지가 아닙니다. …"`
  - 같은 실행에서 **우선순위 하위 테스트 4개**(POP3 범위 밖 / 침묵은 기존 힌트 / implicit TLS 우선 / 동시 접속 우선)는 처음부터 통과했습니다 — 새 분기가 기존 진단을 빼앗지 않는다는 뜻입니다.
- **문구가 양쪽 거부에 맞는지 추측하지 않고 측정했습니다.** 과대 길이 greeting 도 `greeting`/`other` 로 분류되는 것을 어댑터 테스트가 실제 `Dialer{}` 로 확인합니다. 그 과정에서 비자명한 사실 하나를 발견해 적어 둡니다: **정확히 `maxLineBytes+1` 바이트인 행은 상한을 넘기지 못합니다.** 상한은 누적치를 넘기게 될 **읽기**에서 트립하므로 그런 행은 마지막 1바이트에서 멈춰 `class=timeout` 으로 분류됩니다(처음 쓴 픽스처가 15.01초 걸려 timeout 으로 FAIL 하면서 드러났습니다). 픽스처를 리더 버퍼 하나 이상 넘기도록(`maxLineBytes+64KiB`) 고쳐 0.02초에 `other` 로 통과합니다. **이 크기를 줄이면 테스트가 15초 걸려 실패합니다.**
- `go test -race -count=1 -timeout=900s ./...` — 25개 패키지 실패 0건
- **플레이크 확인**: `go test -race -count=3` 로 `./internal/application`·`./internal/adapters/imap` 통과, 플레이크 0건
- `go build ./...`, `go vet ./...`, `make lint-format` 무지적, `go mod tidy` 무변경, canonical API 계약 검사(`postra-contracts -check`) 종료 코드 0
- `make lint-security` — 141개 파일 지적 0건
- `govulncheck ./...`(CI 와 같은 v1.6.0, Go 1.26.9) — 호출되는 취약점 0건
- `make frontend-check` 통과 후 `internal/transport/spa/assets` 변화 없음 — 버전만 올린 이번 태그의 `/app` 번들이 최신입니다(릴리즈 워크플로가 같은 검사를 다시 합니다)
- **외부 PostgreSQL(`POSTRA_TEST_PG`)과 브라우저 e2e 는 이 기계에서 돌리지 않았습니다.** 다만 이 릴리즈가 담는 커밋(`ae1b4d0`)의 CI 검사 **10개가 전부 success** 이고 그 안에 `PostgreSQL · restart · isolation · approval`, `real browser · auth · mail workflows`, `docker build`, `govulncheck`, `Go DTO · JSON Schema · OpenAPI · TypeScript drift` 가 포함됩니다 — 로컬에서 비워 둔 칸을 파이프라인이 덮고 있습니다.

## 업그레이드 및 호환성 주의사항

DB 마이그레이션, 새 설정 키, 새 필수 환경변수가 없습니다. 실행 파일 또는 컨테이너 이미지를 교체한 뒤 재시작하면 끝이고, 되돌릴 때도 v0.25.9 로 그대로 내려갈 수 있습니다.

- **성공/실패 판정은 바뀌지 않습니다.** v0.25.9 에서 실패하던 계정은 그대로 실패하고, 성공하던 계정은 그대로 성공합니다. 달라지는 것은 실패 진단에 **한 문장이 더 붙는다**는 점뿐입니다.
- `서버 환영 메시지 수신` 단계로 멈춘 IMAP 계정이 보이면 이제 화면이 먼저 **수신 포트와 프로토콜**을 가리킵니다. IMAP 은 143(STARTTLS) 또는 993(implicit TLS)이고, 110·995 는 POP3, 25·465·587 은 SMTP 입니다.
- **진단 문장을 대시보드·알림에서 문자열로 잡아 두었다면** 이 힌트가 새로 등장할 수 있습니다. `domain.SyncDiagnostic` 에 필드가 추가되지 않아 API 응답의 모양(JSON 키)은 그대로입니다.
- 실시간 대기(IDLE)가 켜진 계정에서는 **동시 접속 힌트가 이 힌트보다 먼저 나갈 수 있습니다**(위 "한계" 참고). 그 경우에도 단계는 `서버 환영 메시지 수신` 이므로 포트 확인은 여전히 유효한 첫걸음입니다.
- v0.25.9 의 IMAP 환영 메시지 요구와 Go 1.26.9 · `golang.org/x/net` v0.60.0 툴체인 고정, v0.25.8 의 기본값 implicit TLS 인증서 검증 보증, v0.25.7 의 `STARTTLS 전환` 단계 진단, v0.25.5 의 거부된 `LIST` 크기 선별 경고, v0.25.4 의 크기 제한 없는 계정 본문 잘림 수정, v0.25.3 의 POP3 `fetch` 진단 교정, v0.25.2 의 OpenTelemetry v1.45.0, v0.25.1 의 "계정당 인바운드 연결 하나"와 `mail.idle_enabled`, v0.25.0 의 동기화 실패 진단은 바뀌지 않았습니다.
