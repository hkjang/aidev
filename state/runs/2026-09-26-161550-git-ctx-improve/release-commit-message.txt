release: v0.77.18

감싸인 데드라인 오류가 호출 추적에 timeout 이 아니라 error 로 기록되던 것을 고칩니다.
internal/calltrace/calltrace.go:112 의 Span.Fail 은 err == context.DeadlineExceeded 로
값 비교를 했고, 이는 저장소에서 데드라인을 값으로 비교하던 유일한 자리였습니다 — 다른
12곳은 이미 errors.Is 를 씁니다. 원격 소스의 데드라인은 net/http 가 *url.Error 로 감싸고
호출자가 다시 단계 이름을 덧붙여 도착하므로, 값 비교는 실제 타임아웃을 평범한 오류로
분류했고 bare context.DeadlineExceeded 만 timeout 으로 통과했습니다. 같은 sourceErr 를
읽는 두 자리가 어긋나 있던 것이 근거였습니다 — search/service.go:3326(→Fail)은 error 로
기록하고 3415(errors.Is)는 같은 오류를 타임아웃으로 읽어 진단문을 썼습니다. 그래서
사용자에게 보이는 문장은 "tool timeout" 인데 mcp_call_steps.status 에는 error 가 저장돼
운영자가 상태 값으로 타임아웃을 셀 수 없었습니다. 값 비교를 errors.Is 로 바꿔 한 줄
고쳤고 감싸인 데드라인이 도착하는 이유를 주석에 적었습니다. 상태 문자열 상수 값과
호출부(search·mcp)는 한 줄도 건드리지 않았습니다. 실제 Recorder·Span 과 실제
fmt.Errorf("%w")·&url.Error{Err: context.DeadlineExceeded} 를 쓰는 5케이스 표 회귀
시험을 두었고, 수정 전 코드에서 예측한 두 래핑 케이스만 실패함을 먼저 확인했습니다 —
bare 데드라인·일반 오류·nil 세 케이스는 수정 전에도 통과하는 동작 무변경 대조군입니다.
새로 기록되는 행만 달라지며 이미 저장된 행은 바뀌지 않습니다. context.Canceled 를 별도
상태로 나누는 것은 mcp_call_steps.status 계약과 관리 콘솔을 함께 건드리는 변경이라
이번에도 분리해 뒀습니다. 마이그레이션과 재색인은 필요하지 않습니다.
