## 2026-09-17
- 선택: [캠페인 mcp-oauth-2026-09] `/mcp`·`/mcp/gateway` 가 개인 키 옆에 Keycloak SSO 액세스 토큰도 받게 — OAuth 2.1 리소스 서버 절반만 구현 (가치 5 / 위험 2 / 작업량 M)
- 결과: 성공
- 요약: 이 저장소는 사용자별 계정(`auth_users`)·Keycloak OIDC 웹 로그인(`auth_identities` 에 sub 연결)·개인 proxy key 가 모두 있어 표준을 그대로 적용할 수 있었다. 새 파일 `internal/proxy/mcp_oauth.go` 하나에 메타데이터·401 도전·토큰 검증·계정 매핑을 두고, 키와 토큰을 가르는 자리는 기존 `authenticateProxyContext`(키 해시 조회가 빗나간 뒤, passthrough 분기 앞)에 넣되 **MCP 두 경로 + JWT 모양 + 설정 활성** 일 때만 타게 했다 — 꺼져 있으면 분기 자체가 실행되지 않아 새 설치는 아무것도 달라지지 않고(테스트로 고정: 메타데이터 404, 완벽한 토큰도 예전과 같은 `invalid_api_key`), 켜져 있어도 REST 경로는 토큰을 거부하고 `WWW-Authenticate` 를 붙이지 않는다. **고른 것과 이유**: ① 설정 자리는 런타임 설정 레지스트리(`mcp.oauth.enabled/resource/audience/scopes`, 환경변수 `MCP_OAUTH_*`, 카테고리 `mcp.oauth` 는 권한 그룹 security) — 파드 재시작 없이 모든 파드가 보고, 발급자·클라이언트 ID·Redirect URI 는 기존 SSO(Keycloak) 설정을 재사용(이 저장소에 `oidc.*` 키는 없고 SSO 설정 행이 그 역할). ② 리소스 식별자 출처는 `mcp.oauth.resource` → **SSO Redirect URI 의 origin + `/mcp`**(이 저장소에 `server.public_url` 류가 없고, 콜백 URI 가 유일하게 이미 적혀 있는 공개 주소다) → 요청 Host(최후). 식별자 하나가 `/mcp` 와 그 아래 `/mcp/gateway` 를 함께 덮고(python SDK 의 계층 검사와 맞음), 세 well-known 경로 모두 같은 문서를 낸다. ③ 대상은 표준대로 aud 의 리소스 식별자 또는 aud/azp 의 관리자 목록만 — weekly 와 달리 웹 로그인 client_id 를 자동 허용하지 않았다(다른 클라이언트여야 한다는 표준의 Keycloak 절과 맞추기 위해; 필요하면 관리자가 목록에 적는다). ④ 서명은 기존 `keycloakVerifyJWT`(RS256 전용, `HS*`·`none` 은 alg 검사에서 거부) 재사용; nbf·typ=ID·cnf·sub·대상은 위에 층으로 더했다. ⑤ 주체 식별자는 `sso:<user id>`, 범위는 `mcp.oauth.scopes ∩ 계정 역할 범위 ∩ 토큰 scope 의 Clustara 어휘`, 역할은 DB 의 것(토큰 realm role 이 admin 이어도 올라가지 않음을 테스트로 고정), 계정은 sub 연결 신원 → email 순으로 **찾기만** 하고 비활성·비밀번호 변경 강제 계정은 거부. 관리 화면은 SSO(Keycloak) 페이지에 카드(스위치·식별자·허용 대상·범위·MCP URL/메타데이터 URL/매퍼 값 복사), 문서는 ADMIN_GUIDE(설정 표·Keycloak 클라이언트/매퍼 절차·curl 확인·거부 메시지별 조치 표)와 USER_GUIDE §3.13. 검증: 가짜 IdP(실제 RSA 키, discovery·JWKS 서빙)로 서명한 JWT 를 쓰는 신규 테스트 5개(표준의 테스트 목록 전 항목 — 꺼짐 기본값, 401 헤더/REST 미부착, 정식 aud 통과, azp 호환 통과, 다른 앱 토큰 거부 메시지에 본 값과 고칠 값, 만료·다른 issuer·잘못된 키·HS256·typ=ID·cnf·nbf·sub 없음 각각 거부, 미등록/비활성 계정 거부 + 계정 미생성, 유효 토큰의 REST 거부, 키는 그대로), `go build ./...`·`go vet ./...`·`go test ./...` 전부 통과(20 패키지). 문서 참조 테스트가 백틱 `/authorize` 를 라우트로 읽어 한 번 실패해 문구를 고쳤다. **미해결 참고**: 기존 `currentAccessClaims` 가 관리 API 에서 Keycloak 액세스 토큰을 role 매핑으로 이미 받고 있다(이번 일 이전부터의 동작, 캠페인 범위 밖이라 손대지 않음 — 표준의 "MCP 경로 밖에서 토큰을 받지 않는다" 와 어긋나므로 별도 검토 대상). 실제 Keycloak·실제 MCP 클라이언트로의 종단 확인은 이 세션에서 할 수 없었다. 이번 세션 규칙에 따라 버전·changelog 마커는 건드리지 않았다.
