## KCB Cutover Dashboard v1.17.0

이번 판은 **➕(하위 추가)가 "activity.json 데이터 형식이 올바르지 않습니다." 라는 엉뚱한 `400` 으로 막히던 경우** 를 없앱니다. 관리 화면(`/admin`)의 ➕ 는 `PUT /api/activities` 에 `action: 'add'` 를 보내고, 서버는 새 작업의 ID 를 **`부모ID-현재시각(ms)`** 으로 만들어 왔습니다. 이 방식은 **부모 ID 가 길수록 자식 ID 가 더 길어져서**, 저장 직전 검증의 **`id` 120자 제한** 을 넘기면 요청 전체가 거절되었습니다.

**데이터가 잘못 저장된 적은 없고, 조용한 성공도 아니었습니다.** 검증은 파일에 쓰기 전에 하므로 막힌 요청은 **아무것도 저장하지 않고** 끝났습니다. 다만 화면에 뜨는 문구가 **파일 업로드 형식 문제** 로 읽혀, 관리자는 방금 누른 ➕ 가 왜 안 되는지 알 방법이 없었습니다. v1.16.0(없는 부모 → `404`)이 **문구만** 바로잡은 것과 달리, 이번에는 **막히지 않고 실제로 추가되게** 고쳤습니다.

### 버그 수정
- **긴 ID 작업 아래 하위 추가가 "activity.json 데이터 형식이 올바르지 않습니다." `400` 으로 거절되는 것 수정**: 새 작업 ID 를 `부모ID-현재시각` 으로 이어 붙이던 것을 **부모 ID 와 무관한 UUID**(`crypto.randomUUID()`, 36자)로 바꿨습니다. 부모가 아무리 깊거나 ID 가 길어도 자식 ID 는 36자로 고정되므로 120자 제한에 걸리지 않습니다.
  - 두 경로로 걸렸습니다. 하나는 **ID 가 긴 작업이 들어 있는 `activity.json` 을 업로드** 한 뒤 그 작업 아래에서 ➕ 를 누르는 경우입니다 — 업로드 검증은 **120자까지 허용** 하므로, 부모 ID 가 **107자 이상** 이면 자식이 곧바로 120자를 넘겼습니다.
  - 다른 하나는 **➕ 로만 단계를 내려간 경우** 입니다. ID 가 한 단계마다 14자씩 늘어 `13 → 27 → 41 → … → 111 → 125` 가 되므로, **9단계** 에서 125자가 되어 더 이상 하위를 추가할 수 없었습니다. 그 전 단계까지는 멀쩡히 되다가 특정 깊이에서만 막히는 모양새였습니다.
  - 같은 밀리초에 같은 부모 아래로 ➕ 가 두 번 들어오는 경우에도 `부모ID-시각` 이 똑같아져 **ID 중복** 으로 같은 `400` 이 났습니다. UUID 는 같은 시각의 연속 추가에도 서로 다른 ID 를 줍니다.
  - **기존 작업의 ID 는 바꾸지 않습니다.** 이미 저장된 트리는 그대로 열리고, `parentId` 관계로 동작하는 삭제·상태 전파(v1.10.0)도 그대로입니다. 새로 추가되는 작업의 ID 모양만 달라집니다.

### 검증
- `npm run test:unit` — 101개 통과. `addActivity` 에 **120자 부모 아래 자식·손자 추가가 업로드 검증을 통과** 하는지, **같은 시각 연속 추가가 서로 다른 ID** 를 받는지, 입력 배열을 바꾸지 않고 기존 ID·순서를 유지하는지 고정했습니다.
- `npm run test:e2e` — 41개 통과. 120자 ID 부모 아래 추가한 자식이 `200` 으로 저장되고, 이어지는 `GET` 에서도 같은 자식과 부모 관계가 유지되는지 확인합니다.
- `npm run build`, `npm run lint` 통과.

### 배포
폐쇄망 배포는 기존과 같습니다.

```bash
docker load < cutover-v1.17.0.tar.gz
docker run -d -p 3000:3000 \
  -e USER_PASSWORD=1234 \
  -e ADMIN_PASSWORD=admin1234 \
  -e AUTH_SECRET=운영환경용-충분히-긴-임의문자열 \
  -v cutover-data:/app/data \
  --name cutover-app \
  --restart always \
  cutover:v1.17.0
```

데이터 구조는 바뀌지 않았으므로 `cutover-data` 볼륨을 그대로 쓰면 됩니다. 되돌려야 하면 v1.16.0 이미지로 다시 올려도 됩니다 — 이번 판에서 추가한 작업의 UUID ID 도 v1.16.0 이 그대로 읽습니다.
