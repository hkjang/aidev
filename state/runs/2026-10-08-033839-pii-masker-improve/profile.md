# pii-masker 프로필 (2026-10-08)
- 목적: PDF/PNG/JPG의 PII 영역을 Upstage 호환 추론으로 찾아 마스킹 파일을 돌려주는 동기·비동기 HTTP API와 Playground UI.
- 스택: Go 1.25.0(go.mod·Dockerfile 동일). gorilla/mux, pdfcpu, x/image, vendor 고정. DB 없음 — job.json·입력·출력을 디스크에 보관. 단일 HTML UI, Docker/Compose.
- 구조 (총 10.5k줄, 테스트가 절반):
  - cmd/pii-masker — 진입점. internal/app (app.go) — HTTP 서버 배선, graceful drain, 보존 스위퍼.
  - internal/config (config.go 347줄) — `PII_MASKER_*` Load/정규화. `SupportedMIMEs`는 하드코딩(:155).
  - internal/httpapi (server.go 483줄, integration_test.go 2268줄) — mask/jobs/history/config/test-connection + static/index.html.
  - internal/service (service.go 766줄) — 동기 슬롯·비동기 runner, draining, sweeper, 문서 처리. `mapError`(:734~)가 에러→`core.APIError` 분류의 단일 지점이고 `maskingFailedError`(:117)·`*masking.RegionPlacementError`(:759)·`*unrecognizedPayloadError`만 특별 취급, 나머지는 `processing_failed` fallback.
  - internal/jobs (store.go 290줄) — 메모리 맵·job.json 영속/복구, `cloneJob`(:265).
  - internal/upstage (client.go 821줄) — 인증, allow-host, 리다이렉트·HTTPS 강등 검사, `prepareUpstreamAttachment`(:336)가 이미지를 **내용 기준으로** PNG 정규화.
  - internal/document — attachment.go(`detectAttachmentMIMEType`:43), image.go(`DecodeImage`/`DetectImageFormat`/`ValidateImageDimensions`, MaxImagePixels=50M).
  - internal/masking — engine.go 818줄(`placeRegion`:428, `placementError`:418, `RegionPlacementError`:399, `MaskImageFile`:499, `MaskPDFFile`:548/`maskPDFFileInternal`:558), policy.go 431줄(`MaskValue` + `ComputeMaskedRuneSpans`:88).
  - internal/core/types.go — 공용 JSON 계약. internal/mock/upstage.go — 내장 추론(pdf·png만, `isMockSupportedMIMEType`:167).
- 빌드·테스트: `go test -count=1 ./...`(8패키지, 1초 내 — 2026-10-08 ok 확인), `go vet ./...`, `go build ./...`, `gofmt -l ./cmd ./internal`(무출력), `git diff --check`, `go test -race -count=1 ./internal/<pkg>`. 느린 것 없음. 외부 Upstage 불필요.
- 관례: 영어 명령문 커밋 + PR 머지, 한국어 README가 동작 문서. 환경변수 설정, 마이그레이션 없음, CLAUDE.md·docs/·.github CI 없음.
- 위험 구역: upstage 인증/호스트 검사, service draining/WaitGroup, jobs.load의 RemoveAll, 업로드 크기 제한. PDF는 사각형 덧그리기라 원문 텍스트 레이어는 남는다(README:90).
- 자주 깨지는 곳:
  - **에러 분류**: 10/06 회차가 "업로드 탓(`processing_failed`/400/retryable:false)" 대 "업스트림 답 탓(`masking_failed`/502/retryable:true)"의 경계를 그었다. 새 에러를 만들 때 어느 쪽인지 먼저 정하고, `placeRegion`의 `page %d has no usable dimensions`가 **의도적으로** 업로드 쪽임을 기억할 것(engine.go:429~431 주석, engine_test.go:378이 못 박음).
  - 선언 MIME vs 실제 내용: 10/03(출력 인코딩)·10/04(업스트림 전송 바이트) 두 회차가 연속으로 고쳤다. 새 경로를 건드릴 때 "응답이 광고하는 것"·"바이트"·"업스트림이 받는 것"을 각각 확인할 것.
  - config의 곱셈 오버플로: duration 6건(9/29)·MiB(10/02) 해결. `envInt` 자체는 건드리지 않고 호출 지점만 바꾸는 패턴이 세 회차 연속 채택됐다.
  - 룬 정렬: `MaskValue` 결과는 원문과 룬 수가 같아야 한다(policy.go:88). 깨지면 가림 상자가 엉뚱한 글자 위에 그려진다.
- 검증 함정:
  - `startAppServerWithConfig`(integration_test.go:1809)·`startAppServerWithUpstream`(:1812)은 config를 직접 조립한다. `Load` 관련 회귀는 customize 안에서 실제 `config.Load` 결과를 써야 한다.
  - `buildMultipartBody`(:1686)는 `contentType` 인자를 쓰지 않는다(CreateFormFile → octet-stream → 내용 스니핑). PDF·PNG는 스니핑이 맞게 나와 기존 테스트가 통과하지만, 선언 MIME을 실제로 보내야 하면 `buildMultipartBodyWithFilenameParam`(:1713).
  - 내장 mock은 application/pdf·image/png만 받고 페이지 번호·필드를 임의로 돌려주지 않는다. 특정 업스트림 응답이 필요하면 직접 만든 handler를 `startAppServerWithUpstream`에 물릴 것(`offPageBoxUpstream`:1678이 본보기).
  - PDF 픽스처: `createBlankPDF(w,h)`(integration_test.go:1995, `/Count 1`)·`blankPDF(w,h)`(masking/engine_test.go:422). 두 패키지에 중복으로 있다.
  - `t.Setenv` 테스트 병렬화 금지. 기본값 테스트는 값을 명시적으로 비울 것.
  - `GOARCH=386 go test ./internal/document`는 `TestValidateImageDimensionsRejectsPixelBomb`에서 실패한다(10/04 기록 기준 — 10/05·10/06·10/08 세 회차 모두 재실행하지 않아 **미확인**).
  - `app.orDefault`와 `upstage.httpClient`는 비양수 timeout을 보정하지만 retention·syncQueueWait는 보정 없이 쓴다.
  - Docker 빌드·Windows Rename·32비트 실행 경로는 계속 미확인.
