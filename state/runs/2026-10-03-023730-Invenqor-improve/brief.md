- 과제: `POST /api/v1/assets/merge` 가 openapi 가 선언한 정규형이 아닌 UUID 철자를 받아 두 방언이 같은 요청에 다르게 답하고, 병합 기록이 비정규형으로 남아 MCP `merged_into` 조회가 못 찾는 것을 기존 `canonicalUUID` 로 막는다 (가치 3 / 위험 2 / 작업량 S)
- 왜: 2026-10-01 회차가 `splitAsset` 에 넣은 `canonicalUUID`(`server/internal/httpapi/assets.go:661`, 주석 648-660)가 바로 옆 `mergeAssets` 에는 적용되지 않아, `primary_id`·`secondary_ids` 가 `uuid.Parse` 의 느슨한 철자(대문자·`urn:uuid:` 접두·중괄호·하이픈 없는 32자)를 그대로 SQL 로 가져간다. openapi 는 두 필드를 `format: uuid` 로, 오류를 `"400" Primary or secondary assets missing` 하나로만 약속하는데(`openapi.yaml:2229-2235`), `canonicalUUID` 의 주석이 split 쪽에서 실측해 기록한 대로 PostgreSQL 의 UUID 열은 대문자·중괄호·하이픈 없는 철자를 조용히 접어 행을 맞추고 `urn:uuid:` 는 22P02 로 터지는 반면 SQLite 폴백의 TEXT 비교는 모두 못 맞춘다 — 같은 요청에 200/500 과 400 이 갈린다.
- 수용 기준:
  1) 실재하는 자산 id 를 **대문자**로 써서 merge 를 요청하면 두 방언이 같은 코드로 끝난다. 권장 동작은 `splitAsset` 과 같은 **정규화 후 수용**(대문자는 `format: uuid` 의 적법한 철자이고 `canonicalUUID` 가 `parsed.String()` 로 소문자를 돌려준다) — `TestSplitAssetFoldsUpperCaseSourceIDToCanonicalForm`(`asset_split_validation_test.go:274`)의 merge 판이다.
  2) `urn:uuid:<id>`, `{<id>}`, 하이픈 없는 32자 철자는 두 방언 모두 400 `INVALID_MERGE` 로 끝나고 PostgreSQL 에서도 500 이 나지 않는다 — `TestSplitAssetRejectsNonCanonicalAssetID`/`...SourceIDs`(`asset_split_validation_test.go:204`·`235`)의 merge 판. `primary_id` 와 `secondary_ids` 양쪽을 덮을 것.
  3) 1) 의 대문자 요청으로 병합한 뒤 MCP `asset_get` 으로 그 secondary(정규형 id)를 조회하면 `merged_into` 가 primary 를 가리킨다. 지금은 `asset_changes.after_json.secondary_ids` 에 보낸 글자가 그대로 들어가고(`assets.go:770-772` 가 `input.SecondaryIDs` 를 직렬화) `mcp.go:747`(SQLite `json_each ... value = $1`)·`mcp.go:752`(PostgreSQL `@> jsonb_build_array($1::text)`) 조회는 **둘 다 문자 일치**라 대문자로 저장되면 PostgreSQL 에서 병합은 됐는데 안내가 안 나온다.
  4) 테스트는 응답 코드만 보지 말고 `assets.status`/`deleted_at` 과 `asset_changes(change_type='merged')`·`audit_logs(action='asset.merge')` 행 수를 직접 세어, 거절된 요청이 아무것도 쓰지 않았음(`assertMergeWroteNothing`, `asset_merge_validation_test.go:49`)과 수용된 요청이 실제로 병합했음을 확인한다.
- 건드릴 파일 (프로덕션은 `assets.go` 한 개):
  - `server/internal/httpapi/assets.go:702` `mergeAssets` — `decodeJSON` 직후·`BeginTx`(716행) **전**에 `canonicalUUID(input.PrimaryID)` 와 `secondary_ids` 각 원소를 통과시켜 실패하면 400 `INVALID_MERGE` 로 끝낸다. 그 뒤의 쿼리·`asset_changes` metadata(770-772)·응답은 **정규형 값만** 쓴다 — `input.PrimaryID`/`input.SecondaryIDs` 를 아래에서 다시 읽지 말고 지역 변수(`primaryID`, `secondaryIDs`)로 전부 교체할 것. 특히 `secondaryID == input.PrimaryID` 자기 병합 스킵(759행)과 metadata 직렬화가 교체 대상이다. `splitAsset`(`assets.go:806-833`)이 쓴 모양을 그대로 따른다.
  - `server/internal/httpapi/assets.go:681` `missingAssetID` — 안의 `uuid.Parse` 모양 검사는 호출 전에 정규화가 끝나면 중복이다. 지우고 주석을 "호출자가 정규형을 보장한다" 로 바꾸든 그대로 두든 구현자 판단(그대로 둬도 동작은 같다). `uuid` import 는 `uuid.NewString()` 이 계속 쓰므로 남는다.
  - `server/internal/httpapi/asset_merge_validation_test.go` — 기존 3건(`TestMergeAssetsRejectsPrimaryThatIsNotAnAsset`:77, `...MissingSecondary...`:99, `...IdsThatAreNotUUIDs`:127) 옆에 위 수용 기준의 테스트를 더한다. 헬퍼는 이미 있는 것을 쓸 것 — `mergeAssetsResponse`(:19), `countRows`(:39), `assertMergeWroteNothing`(:49), `newRuntime`/`testServer`/`authenticateInitialAdmin`, `performAuthenticatedJSON`(`admin_test_helpers_test.go:84`), `insertSoftwareTestAsset`(`software_inventory_test.go:133`). **같은 이름을 새 파일에 다시 정의하면 컴파일이 깨진다.** 수용 기준 3) 은 `mcp_asset_get_merged_test.go`(:22 의 응답 구조체, :63 의 테스트)의 조회 방식을 참고해 쓸 것.

- 위험과 피할 것:
  - **트랜잭션 안에서 `s.internalError` 를 부르면 SQLite 폴백이 교착한다** — `internalError` → `recordDiagnostic` → `DB().ExecContext` 가 새 커넥션을 요구하는데 열린 tx 가 `SetMaxOpenConns(1)`(`storage/runtime.go`)의 유일한 커넥션을 쥐고 있다. 증상은 500 이 아니라 **응답 없음 → 테스트 타임아웃**. 검증을 반드시 `BeginTx` 전에 두어 이 경로를 비켜갈 것. `mergeAssets` 안의 745행 이후 `internalError` 호출들(`tx.Rollback()` 선행이 없다)은 이번 과제 범위가 **아니다** — 고치려 들지 말 것.
  - 기존 merge 3건·split 7건·`mcp_asset_get_merged_test.go` 2건은 모두 `uuid.NewString()` 의 정규형만 쓰므로 영향이 없어야 한다. 깨지면 정규화 위치가 틀린 것이다.
  - `canonicalUUID` 를 **수정하지 말 것** — `splitAsset` 과 그 테스트 3건이 매여 있다. 그대로 재사용한다.
