- 과제: 사용자 목록에서 동일 created_at 행의 페이지 순서를 고정 (가치 2 / 위험 1 / 작업량 S)
- 왜: `internal/server/users.go:listUsers`는 `GROUP BY u.id ORDER BY u.created_at DESC LIMIT/OFFSET`만 사용하므로 생성 시각이 같은 사용자들의 상대 순서가 정의되지 않아 페이지별 조회에서 중복·누락이 발생할 여지가 있다. 유일한 `u.id DESC`를 보조 정렬로 추가하면 데이터가 변하지 않는 동안 검색 유무와 페이지 크기에 관계없이 일관된 사용자 목록을 제공할 수 있다.
- 수용 기준: 1) `/api/v1/users`가 `created_at DESC, id DESC` 순으로 반환하며 생성 시각이 다른 행은 기존 최신순을 유지한다. 2) 동일 timestamp 사용자 여러 명을 두 페이지 이상 조회했을 때 기대 ID 순서와 정확히 일치하고 합친 ID에 중복·누락이 없으며, q 검색과 page/pageSize/total 계약이 유지된다. 3) 실제 PostgreSQL과 `New(...).Handler()`를 통과하는 회귀 테스트가 위 결과를 증명한다. 같은 timestamp의 고정 UUID 6개 이상을 UUID 순서와 다른 삽입 순서로 넣고 pageSize=2 및 3을 비교하며, 다른 timestamp 행도 추가해 생성 시각이 우선임을 검사한다. 응답 반복 일치만 검사하거나 SQL 문자열 검사로 대신하지 않는다.
- 건드릴 파일: `internal/server/users.go:listUsers` — 목록 SELECT의 ORDER BY에 `,u.id DESC`만 추가. `internal/server/users_query_integration_test.go` — 기존 `TestListUsersRejectsOverlongQuery`는 보존하고 `TestListUsersPaginationHasStableOrder` 추가; 기존 DB 초기화·Migrate·Seed·암호화·signIn 패턴 재사용. `docs/api.md` — 사용자 목록 설명에 생성 시각 내림차순, 동률이면 ID 내림차순이라는 계약 한 문장 추가.
- 검증 명령: 저장소 루트에서 `go test -count=1 ./...`, `make lint`. 전용 폐기 DB를 가리키는 `TEST_POSTGRES_DSN`을 설정한 뒤 `go test -v -count=1 ./internal/server -run '^TestListUsers(RejectsOverlongQuery|PaginationHasStableOrder)$'`로 두 테스트의 PASS(특히 SKIP 아님)를 확인하고, 이어 `go test -race -count=1 ./...` 실행. 정찰에서 앞의 전체 일반 테스트와 lint는 실제 통과했고 기존 검색 테스트는 DSN 미설정으로 SKIP했다. 새 테스트 이름은 구현 예정이며 현재 존재하는 테스트로 표시하지 않는다.
- 위험과 피할 것: `internal/auth`, 사용자 상태·역할 변경 로직, `workflow.go`, migrations, `.github/workflows`, 버전 파일과 `internal/ui/dist`는 수정하지 않는다. 기존 count 쿼리, 검색어 200 rune 검증, 권한에 따른 legacyUserName 노출·감사를 유지한다. 테스트는 두 schema를 DROP하므로 운영·공유 DB에 연결하지 않고 동일 DB에서 병렬 실행하지 않는다. 이 변경은 동시 사용자 추가·삭제 사이의 OFFSET 페이지 안정성이나 snapshot 일관성까지 보장하지 않는다. UUID가 생성 시각을 나타낸다고 설명하지 않는다. 실제 DB 재현과 수정 전 테스트 실패는 정찰에서 미확인이다.
- 차선 후보: 감사 CSV 문서의 성공 다운로드=전체 이벤트 보장 표현을 최대 50,000건 범위로 한정 — 1순위가 이미 해결되어 있거나 전용 테스트 DB를 확보하지 못할 때 선택. `docs/api.md` 감사 절의 “필터에 맞는 이벤트가 모두”를 “최대 50,000건 범위의 조회 결과가 끝까지”로 고치고 `internal/server/audit_events.go:exportAuditEvents`의 LIMIT와 대조한다. 기존 safeCSVCell 개선은 완료되었으므로 재선정하지 않는다.

구현 순서·예산(독립 추정, 스킬 반환 형식 아님): 테스트 셋업·데이터 10분 → SQL·문서 5분 → 전용 DB 회귀 및 전체 검증 15분 → 예비 10분, 총 40분. 기존 `db_error_integration_test.go:signIn/sessionCredentials.do`와 `integration_test.go:decodeResponse`는 읽고 호출만 한다. `legacyHTTPPage`는 total만 선언하므로 page/pageSize까지 검증하려면 새 테스트의 로컬 응답 구조체를 사용한다. 필터 사례는 공통 고유 검색어로 fixture만 선택하고, 무검색 사례는 seed 관리자를 포함한 전체 기대 순서를 명시한다. ID 기대값은 테스트 fixture에서 직접 정해 오류가 있는 운영 쿼리로 기대값을 다시 계산하지 않는다. 가능하면 ORDER BY 보조키를 잠깐 제거해 회귀 검출력을 확인하고 복구하되, 제거 전에도 통과하면 실패했다고 쓰지 말고 fixture/쿼리 계획에 따른 한계를 기록한다.

선정 근거: 스키마 생성 도구는 범위가 넓고, loadGrants·승인 comment는 보호 영역이며, 공급자 모델 JSON과 MIME 검증은 오류·호환성 계약을 추가로 정해야 한다. 페이지 순서 고정은 이미 audit 목록의 `occurred_at DESC,event.id DESC`와 같은 방식이며 새 API 필드나 마이그레이션이 필요 없다.

스킬 확인: 요청한 `pmo:estimating-and-contingency`, `technology:implementation-planning`, `technology:solution-exploration`은 현재 Skill/skills.list 도구가 없고, 제공 도구·리소스 목록과 로컬 SKILL.md 검색에서도 찾지 못했다. 고유 절차·반환 형식은 미확인이고 적용했다고 주장하지 않는다. 사용자 지정 정찰 절차와 산출물 형식을 따른다.
