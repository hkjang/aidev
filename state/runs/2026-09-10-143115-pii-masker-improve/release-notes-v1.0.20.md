Report oversized upstream responses as their own error. `performParseRequest` read the inference response through `io.LimitReader(body, 8MB)`, so a response that ran past 8MB — entirely plausible for a document with many pages, or for a request that turns the `verbose` option on — was silently truncated and then handed to the JSON decoder, which reported it as `decode_failed` ("check the endpoint URL and the response format"). That is a dead-end diagnosis: it points at a perfectly healthy endpoint and says nothing about the size that actually caused the failure. The client now reads `maxUpstreamResponseBytes+1` bytes, which is what distinguishes a body that merely fills the cap from one that was cut short, and returns `response_too_large` when the extra byte arrives — a non-retryable error whose detail names the limit and whose hint suggests splitting the document or turning `verbose` off. The 8MB ceiling moved out of the call site into a named constant that records why the body has to be capped at all (the whole response is held in memory while the document is re-rendered). A 4xx/5xx response is still classified by the existing `classifyHTTPError` path first even when it is oversized, because the status code says more about what went wrong than the size does.

Verified with two new `internal/upstage` tests — a 200 response larger than 8MB now yields `response_too_large` with `Retryable=false` and the reported status still 200, and a 500 response of the same size is still reported as `server_error` — plus `gofmt -l` (no output), `go vet ./...`, `go build ./...`, `go test -count=1 ./...` and `go test -race -count=3 ./...`, all passing. Reverting to the previous implementation (the plain limit, with no oversize check) was used to confirm the new tests genuinely fail as `decode_failed` without the fix.
