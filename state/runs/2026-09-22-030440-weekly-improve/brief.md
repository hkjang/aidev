- 과제: 관리자 메일 발송 기록을 서버에서 상태·종류로 좁혀, 최신 성공 50건 뒤의 실패도 찾는다 (가치 3 / 위험 1 / 작업량 M)
- 왜: 현재 `adminMailDeliveries`는 최근 14일의 세 큐를 합친 뒤 최신 50건만 반환하고 `SettingsTab`은 그 결과만 표시하므로, 더 새로운 성공 메일 50건 뒤에 있는 실패는 현황 숫자에는 잡혀도 표에서 찾을 수 없다. 서버 질의에 상태·종류 필터를 LIMIT 전에 적용하고 관리자 카드에 선택기를 두면 운영자가 큐 테이블을 직접 열지 않고 실패 사유를 찾을 수 있다.
- 수용 기준: 1) 기존 GET `/api/v1/admin/mail/deliveries`에 선택적 `status=QUEUED|SENT|FAILED`, `kind=REPORT|TEAM_REMINDER|SCHEDULE_REMINDER`를 지원한다. 누락·빈 값은 전체, 둘 다 주면 AND, 다른 값은 400으로 처리하며 SQL 매개변수를 사용한다. 필터는 세 큐 UNION 전체에 적용하고 시간 창 14일·최대 50건·기존 응답 형태를 유지한다. 2) 관리자 카드의 이름 붙은 상태·종류 선택기가 서버를 다시 조회한다. 전체로 되돌리기, 일치 기록 없음, 조회 실패를 구별하고 빠른 선택 변경 때 이전 응답이 최신 선택 결과를 덮지 않는다. 현황은 전체 집계임을, 목록은 선택 조건의 최근 최대 50건임을 명시한다. 3) 실제 `newTestServer`와 PostgreSQL, 등록된 HTTP 라우트를 통과하는 회귀 시험으로 새로운 SENT 50건보다 오래된 FAILED 행이 기본 목록에는 없고 `status=FAILED`에는 나타남을 증명한다. 세 종류 각각의 필터, 교집합, 14일 밖 행 제외, 빈 결과 배열, 50건 상한, 잘못된 값 400, 일반 사용자 403을 확인한다. 기존 `TestTheOperatorSeesEveryQueueTheRelayTouches`의 세 큐 집계·본문 비노출 주장도 통과해야 한다. 4) 실제 관리자 화면에서 선택 변경 → 요청 쿼리 → 표시 행을 확인하고 지연 응답 역전·실패·빈 상태를 확인한다. 소스 문자열 검사나 손으로 만든 가짜 핸들러만으로 제품 배선 검증을 대체하지 않는다.
