# Momento v0.34.64 — `make verify` 가 CI 의 게이트를 밀기 전에 그대로 돌립니다

이 저장소에 커밋을 올리는 사람을 위한 빌드 도구 변경입니다. **서비스·콘솔·SDK 의 동작, API 계약, 데이터베이스 스키마, 설정 항목은 하나도 달라지지 않습니다.** 운영자가 이 릴리스로 올리면서 할 일은 없습니다.

## 로컬이 녹색인데 CI 가 빨간불이었습니다

밀기 전에 돌릴 수 있는 검사는 `make test` 하나였는데, 그 타깃에는 CI 가 돌리는 게이트 중 여러 개가 들어 있지 않았습니다.

| 게이트 | `make test` | ci.yml `test` job |
|---|---|---|
| `go test` | 있음 (`-race` 없음) | `-race` 있음 |
| `go vet` | 있음 | 있음 |
| `govulncheck` | **없음** | 있음 |
| `npm ci`·`npm audit` (SDK·콘솔) | **없음** | 있음 |
| SDK `npm run build` | **없음** | 있음 |

가설이 아닙니다. 이 저장소가 겪은 verify-failed 두 건 — v0.34.61 주기의 `golang.org/x/text` 권고와 v0.34.62 의 표준 라이브러리 권고 10건 — 이 **둘 다 `govulncheck` 단계**에서 멈췄고, 그 단계는 `make test` 에 아예 없어 아무도 미리 볼 수 없었습니다.

## `verify:` 타깃이 같은 명령을 같은 순서로 돌립니다

`Makefile` 에 `verify:` 를 새로 두어 `.github/workflows/ci.yml` 의 `test` job 이 돌리는 다섯 명령을 **같은 글자·같은 순서**(Go → SDK → 콘솔)로 실행합니다.

```
make test     # 빠른 루프 — 한 글자도 바뀌지 않았습니다
make verify   # 밀기 전 — CI 가 돌리는 것과 같은 게이트
```

`make test` 를 손대지 않은 것은 의도입니다. 반복 작업 중에 `npm ci` 와 `govulncheck` 를 매번 기다리게 만들면 그 타깃을 아무도 쓰지 않게 되고, 쓰이지 않는 게이트는 없는 게이트와 같습니다. 느려서 우회되는 파이프라인은 검사가 적고 빠른 파이프라인보다 나쁩니다.

## 두 선언이 어긋나면 테스트가 실패합니다

게이트가 두 곳에 적히는 한 둘은 언젠가 어긋납니다. `internal/version/buildgates_test.go` 가 그것을 막습니다. 이 테스트가 보는 것은 「게이트가 최신인가」가 **아니라** 「두 선언이 여전히 일치하는가」입니다 — 기존 `toolchain_test.go` 가 go.mod 의 toolchain 지시자와 Dockerfile 베이스 이미지를 짝지어 보는 것과 같은 방식입니다. 최신인지를 묻는 테스트는 읽히지 않고 숫자만 올려 통과시키게 되지만, 일치하는지를 묻는 테스트는 한쪽만 고쳤을 때만 틀립니다.

확인하는 것은 셋입니다.

| 확인 | 어긋나면 |
|---|---|
| ci.yml 의 `run:` 단계 개수 = 표의 항목 수 | CI 에 게이트를 더하고 Makefile 에 안 더한 경우를 잡고, 로컬 짝이 없는 단계를 이름으로 말합니다 |
| 각 항목의 CI 명령이 ci.yml 에 그대로 있음 | CI 쪽에서 `-race` 를 떼는 변경도 빨간불이 됩니다 |
| 각 항목의 로컬 명령이 `verify` **레시피 안에** 그 순서로 있음 | 순서가 뒤바뀌거나 한 줄이 빠지면 잡습니다 |

레시피 안만 보는 이유가 있습니다. `go vet ./cmd/... ./internal/...` 는 `test:` 에도 있어서 `Makefile` 전체를 검색하면 엉뚱한 타깃을 맞히고 순서를 판정할 수 없습니다. `docker build` 단계는 `--build-arg` 값이 의도적으로 다르므로(CI 는 `ci`·`${GITHUB_SHA::12}`, Makefile 은 `DECLARED_VERSION`·`git rev-parse --short`) 면제로 적고 그 이유를 주석에 남겼습니다. 워크플로 파일을 읽기 위해 YAML 파서를 `go.mod` 에 더하지는 않았습니다 — `toolchain_test.go` 와 같이 정규식으로 읽습니다.

## 이 테스트가 증명하지 않는 것

주석에 그대로 적어 두었습니다. 테스트가 텍스트만 읽기 때문입니다.

- **`make verify` 가 통과한다는 것도, make 가 그 레시피를 집어 든다는 것도 증명하지 않습니다.** 그건 실제로 돌려야만 알 수 있어, 이번에 끝까지 한 번 돌렸습니다(아래 「확인」).
- **SDK·콘솔 게이트가 각자의 디렉터리에서 돌아간다는 것을 증명하지 않습니다.** 각 로컬 문자열이 자기 `cd` 를 품고 있어 두 줄이 한 줄로 뭉개지지는 않지만, 파일에 들어 있다는 것이 그 디렉터리에서 실행된다는 증거는 아닙니다. 소스 문자열 검사를 동작의 증거로 쓰지 않습니다.
- **`make verify` 의 녹색이 CI 의 녹색을 보장하지 않습니다.** 데이터베이스 통합 테스트는 `MOMENTO_TEST_POSTGRES_DSN` 없이 건너뛰어지고, 그 수를 실제로 세어 보니 **120건**이었습니다. CI 는 `postgres:17-alpine` 서비스를 띄워 그 DSN 을 줍니다. 추상적인 경고가 아니라 측정값으로 주석에 적었습니다.
- `govulncheck` 와 `npm audit` 는 네트워크와 살아 있는 권고 데이터베이스를 읽으므로 오프라인에서는 이 타깃이 실패합니다. 건너뛰게 만들지 않고 실패를 드러냅니다 — 돌지 못해서 통과하는 게이트는 멈춰 세우는 게이트보다 나쁩니다.

## 확인

- **`make verify` 를 끝까지 한 번 돌려 exit 0.** `go test -race` 11 패키지 ok, `go vet` 무출력, `govulncheck` 는 `Your code is affected by 0 vulnerabilities.`, SDK 는 `found 0 vulnerabilities` + 테스트 **29건** + build, 콘솔은 `found 0 vulnerabilities` + 테스트 **259건** + `✓ 1704 modules transformed`.
- 회귀 금지 확인으로 `make test` 를 따로 돌려 exit 0(29건·259건)이고, 그 레시피가 diff 에 없다는 것을 `git diff` 로 확인했습니다. `make -n verify` 가 ci.yml 의 다섯 줄과 같은 순서로 전개되는 것도 확인했습니다.
- **가드의 red 경로 세 가지를 전부 실제로 재현**한 뒤 복원했습니다 — (1) ci.yml 에 `run:` 단계를 하나 더하자 개수 불일치(`6` vs `7`)로 실패, (2) `verify` 레시피에서 `govulncheck` 줄만 빼자 누락으로 실패, (3) 콘솔 게이트를 Go 게이트 앞으로 옮기자 순서로 실패. 세 경우 모두 복원 후 녹색이고, ci.yml 은 `git checkout` 후 `cmp` 로 바이트 단위 동일 복원을 확인했습니다.
- `.github/workflows/*.yml` 은 **이 커밋에 들어 있지 않습니다.** 빨간불 증명에 쓴 한 줄은 로컬에서만 더했다가 되돌렸습니다.
- 서비스·콘솔·SDK 버전 및 Compose 이미지 이름 일치 검사, toolchain 일치 검사 통과.

## 범위와 배포

바뀐 것은 `Makefile` 의 새 `verify:` 타깃과 `.PHONY`, 테스트 파일 `internal/version/buildgates_test.go`, 그리고 버전 선언입니다. 서비스·콘솔·SDK 코드, API 의 요청·응답 모양, 데이터베이스 마이그레이션, 설정 항목, 워크플로 파일은 바뀌지 않았습니다. 빌드되는 바이너리의 내용물은 v0.34.63 과 같고, 달라진 것은 그 바이너리를 만들기 전에 사람이 돌릴 수 있는 검사뿐입니다.

이번 변경은 Tier 3 로 릴리스 노트에만 안내합니다. 기존과 같이 태그 푸시 후 GitHub Actions 가 `momento:v0.34.64` 를 빌드하고, 오프라인 아카이브 `momento-v0.34.64.tar.gz` 와 `.sha256` 을 로드·기동 검증한 뒤 Release 에 첨부합니다. 설치 절차는 `docs/OFFLINE.md` 를 따릅니다.

배포 담당자가 추가로 확인할 것은 없습니다. 평소대로 프로필 메뉴의 버전이 `0.34.64` 로 보이는지와 `/api/v1/version` 이 같은 값을 답하는지만 보면 됩니다. 이 세션에서는 실제 배포와 운영 환경 확인을 수행하지 않습니다.
