# v0.321.0 — 보고서를 잠깐 읽지 못한 메일 발송이 영구 실패로 남지 않습니다

이 릴리즈는 주간보고를 메일로 받기로 한 작성자를 위한 **전달 신뢰성** 수정입니다. 큐에서 집은 발송이 보고서를 읽는 데 한 번 실패하면 재시도 예산을 건너뛰고 **첫 시도에 영구 `FAILED` 로 박히던** 결함을 고칩니다. 프로덕션 변경은 `internal/app/mail.go` 한 파일이며, 마이그레이션·새 환경변수·설정·프런트엔드 변경은 없습니다.

## 읽지 못한 보고서와 사라진 보고서가 같았습니다

`sendNextQueuedMail` 은 큐에서 발송 한 건을 claim 한 뒤 보고서를 한 번 읽습니다. 그 읽기의 판정이 `if err != nil || report == nil` 한 줄이었고, 양쪽 다 곧바로 `markMailFailed` 였습니다.

그런데 `loadReport` 가 돌려주는 오류는 성질이 다른 두 가지입니다.

- **행이 없다** (`errNotFound`) — 보고서가 지워졌습니다. 한 시간 뒤에도 없습니다.
- **그 밖의 전달 오류** — 연결이 끊겼거나 질의가 시간을 넘겼거나 failover 가 일어났습니다. **다시 해 보면 성공합니다.**

두 번째 경우가 첫 번째와 같은 자리로 갔습니다. `mail.max_attempts`(기본 5)는 한 번도 쓰이지 않고, 한순간의 DB 불통이 그 주의 보고 메일 하나를 영구히 끝냈습니다.

그리고 **실패한 발송을 다시 큐에 넣을 입구가 없습니다.** 운영자도 작성자도 되살릴 수 없습니다. 작성자의 개인 설정 카드에는 "보고서를 읽을 수 없습니다." 가 붙은 `FAILED` 한 줄만 남고, 그 주의 메일은 오지 않습니다.

같은 함수의 **발송** 실패는 그렇지 않았습니다. 릴레이가 거절하면 `retryDelay` 가 1분 → 4분 → 16분 → 1시간 → 2시간으로 벌려 다섯 번의 예산이 약 세 시간을 버팁니다. 릴레이 재시작이나 인증서 재적재를 기다려 주던 것과, 보고서를 읽는 쪽의 같은 성질의 불통을 한 번에 포기한 것이 같은 함수 안에 나란히 있었습니다.

## 이제 사라진 보고서만 즉시 포기합니다

`errNotFound` 만 그 자리에서 `FAILED` 가 되고, 나머지 오류는 **발송 실패와 똑같은 defer 경로**로 갑니다 — 예산이 남아 있으면 `QUEUED` 로 두고 사유와 다음 시도 시각을 적고, 예산을 다 쓰면 포기합니다.

- 697-712행에 있던 defer 블록을 `deferMailRetry` 헬퍼로 뽑아 적재 실패와 발송 실패가 같은 코드를 씁니다.
- 반환 계약은 그대로입니다: 적재 실패는 `true`(릴레이가 실패한 것이 아니므로 다음 행은 나갈 수 있어 쓸기를 계속합니다), 발송 실패는 예산을 다 썼을 때만 `true`(같은 릴레이를 두드리는 것은 재시도 정책이 아닙니다).
- 상세 오류는 `logger.Error("load report for mail", …)` 에만 남고, 작성자가 읽는 문구는 기존 "보고서를 읽을 수 없습니다." 를 `mailReportUnreadable` 상수로 올려 **그대로** 씁니다.

**오류 판정은 `err` 를 먼저 물어야 합니다.** `loadReport` 는 모든 오류 경로에서 보고서를 `nil` 로 돌려주므로, `report == nil` 을 먼저 보는 조건식은 전달 오류까지 전부 즉시 실패로 빠집니다. 과제서가 제시한 순서가 그것이었고, 그대로 썼다가 시험이 고친 뒤에도 같은 실패를 내서 발견했습니다.

사라진 보고서와 읽지 못한 보고서에 **같은 문구**를 쓰는 것은 의도입니다. 둘의 차이는 "다시 할지" 를 결정하는 워커의 일이고, 그 둘을 가려 주는 저장소 오류 문장은 운영자의 로그에 있을 것이지 누군가의 설정 카드에 있을 것이 아닙니다.

## 검증

구현 단계에서 `internal/app/mailreloadretry_test.go` 의 새 시험 세 개를 실제 PostgreSQL 과 `newTestServer`/`server.submitted` → 큐 → `sendNextQueuedMail` 로 실행했습니다. 손으로 주입한 대역이나 소스 문자열 검사는 쓰지 않았습니다.

적재만 실패하는 모양은 `loadReport` 만 읽고 다른 어떤 코드도 읽지 않는 `report_comments` 를 rename 해 만듭니다(전수 grep 으로 확인했고, `t.Cleanup` 으로 되돌립니다). `newTestServer` 가 시험마다 scratch DB 를 만들므로 공유 DB 오염 위험은 없습니다. `errNotFound` 쪽은 `report_mail_deliveries_report_id_fkey` 가 `ON DELETE CASCADE` 라 보고서만 지우면 발송 행이 같이 사라지므로, FK 를 떼고 보고서를 지워 만들었습니다.

오류 경로 시험 `TestAReportThatCouldNotBeReadForAMomentKeepsItsRetryBudget` 은 수정 전 `status=FAILED attempts=1 reason="보고서를 읽을 수 없습니다." — one unreadable moment spent the whole week's report, and there is no way to queue it again` 로 실패했고, 수정 후 통과했으며, `if err != nil && !errors.Is(err, errNotFound)` 한 줄을 `if false` 로 되돌리면 **같은 실패가 그대로 다시 나는 것**까지 확인하고 원복했습니다. 나머지 두 시험(`TestAMailForAReportThatIsGoneIsGivenUpOnAtOnce`, `TestAReportThatStaysUnreadableRunsOutOfTriesAndStops`)은 수정 전에도 통과했습니다 — 바꾸지 말아야 할 동작을 지키는 자리입니다.

시험이 단정하는 것:

- 적재가 실패한 뒤 행이 `QUEUED`·`attempts=1` 로 남고, 사유가 붙고, `next_attempt_at` 이 미래라 큐가 그 행 위에서 돌지 않습니다.
- 그 사이 릴레이는 아무것도 받지 않고, 작성자의 카드가 "메일이 오지 않는다" 고 말하지 않습니다.
- 저장소가 돌아온 뒤 같은 발송이 **한 번** 나가고, 작성자가 고른 주소로 가며, 행이 `SENT` 가 됩니다.
- 예산을 `1` 로 줄이면 첫 실패에서 포기하고, 두 번째 쓸기가 그 행을 다시 집지 않습니다.
- 보고서가 실제로 없어진 발송은 기다리지 않고 그 자리에서 포기하며, 릴레이는 아무것도 받지 않습니다.

릴리즈 단계에서는 이 릴리즈만을 위해 만든 별도 PostgreSQL 데이터베이스(pg16)에서 `go test ./... -count=1` 전체를 실행해 통과했습니다. `go build ./...`·`go vet ./...`·`gofmt`, 버전 검사 아홉 곳, OpenAPI 119경로, 쪽넘김 10목록, 모달 닫기 검사, 프런트엔드 `npm ci`·lint·시험·타입 검사·프로덕션 빌드가 통과했습니다. 로드맵 HTML·PDF 와 두 안내서 HTML 을 기존 스크립트로 다시 만들었습니다. 정확한 실행 시간과 건수는 릴리즈 커밋 메시지에 적혀 있습니다.

제자리에서 소스를 고치는 `mutation-check`·`authz-check` 는 이전 릴리즈와 같이 실행하지 않았습니다. `gh` 를 쓸 수 없는 세션이라 원격 이력을 읽는 advisory `release-check.sh` 도 실행하지 않았습니다. Docker 오프라인 자산 생성과 GitHub Release 게시는 기존 태그 워크플로가 담당합니다.

UI 클릭, 실제 SMTP 릴레이, rename·FK 제거 이외의 DB 장애 주입은 별도로 검증하지 않았습니다. **이미 `FAILED` 로 박힌 지난 발송은 이 버전이 되살려 주지 않습니다** — 다시 큐에 넣는 입구는 여전히 없고, 그 보강은 이번 범위 밖입니다. 집계·목록 질의가 `rows.Err()` 를 보지 않아 조용히 잘리는 자리들(`keys.go:31`, `handover.go:531`, `admin_analytics.go:245·401·460`, `mail.go:849`), `adminUsers` 가 알 수 없는 역할을 조용히 버려 검토 책임자 picker 에 전체 디렉터리를 올리는 별건, 그 picker 의 `limit=500` 잘림, `imports.go:691` 의 순서 조회 실패도 이번 변경에 포함되지 않습니다. 이 문제들을 해결한 릴리즈로 사용해서는 안 됩니다.

## 업그레이드

기존과 같이 PostgreSQL 과 상태 볼륨을 백업한 뒤 v0.321.0 이미지를 올립니다. 스키마와 설정 변경이 없어 별도 데이터 변환은 필요하지 않고, 되돌릴 때도 데이터 되돌림이 필요하지 않습니다.

이 릴리즈는 작성자가 배워야 할 동작 변화가 없는 조용한 수정입니다. 새 화면도, 새 설정도 없습니다 — 안내할 것은 "저장소가 잠깐 흔들려도 그 주의 보고 메일은 다시 시도된다" 한 문장뿐이라 별도 공지 없이 다음 정기 업그레이드에 함께 올려도 됩니다. `mail.max_attempts` 를 기본값 5 보다 낮게 줄여 둔 배포는 이 수정이 벌어 주는 시간도 그만큼 줄어든다는 점만 확인하십시오.

배포 담당 운영자는 먼저 소규모 대상에서 세 가지를 확인합니다: 정상 발송이 계속 `SENT` 가 되는지, 릴레이 거절이 예전처럼 `QUEUED` 로 기다렸다 예산을 다 쓰고 `FAILED` 가 되는지, 보고서가 지워진 발송이 기다리지 않고 바로 `FAILED` 가 되는지. **중단 기준**은 정상 발송이 `SENT` 에 이르지 못하거나, 같은 발송이 `next_attempt_at` 없이 반복 claim 되어 큐가 한 행 위에서 도는 사례가 확인되는 것입니다. 한 건이라도 나오면 확대 배포를 멈추고 v0.320.0 이미지로 되돌립니다 — 되돌리면 첫 시도 영구 실패도 함께 돌아온다는 것을 염두에 두십시오.

배포 후 첫 24시간에는 `load report for mail` 오류 줄과 `QUEUED` 로 남은 발송의 수를 함께 지켜봅니다. 오류 줄이 나오는데 그 발송이 결국 `SENT` 에 도달하는 것이 이 수정이 일한 모습입니다. 성공 기준은 보고서 적재가 실패한 발송에서 **`attempts=1` 영구 실패 0건**, 그리고 `mail.max_attempts` 를 다 쓰지 않은 `FAILED` 0건입니다. `load report for mail` 이 반복되면 그것은 이 수정이 가려 주는 DB 문제의 신호이니 DB 상태를 확인하십시오 — 이 버전은 적재가 실패하는 원인 자체를 고치지 않습니다. 실제 운영 배포와 이 사후 관찰은 이번 로컬 릴리즈 준비에서 수행하지 않았습니다.
