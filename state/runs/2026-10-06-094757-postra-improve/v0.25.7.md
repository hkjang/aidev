# Postra v0.25.7 — 거부된 STARTTLS 가 자기 단계를 말합니다

STARTTLS/STLS 업그레이드 도중 **서버가 핸드셰이크 전에 평문을 밀어 넣으면 Postra 는 업그레이드를 중단하고 연결을 끊습니다**(v0.23.9 부터의 동작). 그런데 그 거부가 운영자에게는 **"서버 연결(TCP) 단계"에서 실패한 것으로, 경과 시간도 없이** 보고됐습니다. 어댑터에서 보안상 가장 중요한 거부가 하필 엉뚱한 단계를 가리키고 있었습니다. 이번 릴리즈는 그 진단 한 가지를 고칩니다. **거부 판정과 차단 동작은 한 글자도 바뀌지 않습니다.** 설정 키, 환경변수, DB 마이그레이션, 화면 변경도 **없습니다**.

**평범한 서버에 붙는 설치는 아무 변화가 없습니다.** 달라지는 것은 이 거부가 실제로 일어났을 때 동기화 실패 진단에 적히는 문장뿐입니다.

> v0.25.6 은 GitHub Release 로 공개되지 않았습니다. 그 릴리즈의 개발 환경 전용 변경(`make frontend-test` 의 클린 체크아웃 가드, README 의 govulncheck 고정 버전)은 **이번 v0.25.7 에 그대로 포함**되어 있습니다. 자세한 내용은 [v0.25.6 노트](v0.25.6.md)를 보세요 — 운영 동작에는 영향이 없습니다.

## 무엇이 어긋나 있었나

- POP3 `Dial`(`internal/adapters/pop3/client.go`)과 IMAP `Dial`(`internal/adapters/imap/client.go`)의 **핸드셰이크 전 주입 가드**는 거부를 평문 `fmt.Errorf` 로 돌려줬습니다. 같은 함수의 다른 모든 실패 — **바로 다음 줄의 TLS 핸드셰이크를 포함해** — 는 자기 단계를 적은 `*domain.InboundError` 를 돌려주는데, 이 한 줄만 빠져 있었습니다.
- 진단을 세우는 `syncDiagnosticStage`(`internal/application/sync_diagnostics.go`)는 `errors.As` 로 단계를 읽습니다. 못 찾으면 호출자의 추측인 dial fallback `StageTCPConnect` 를 씁니다. 그래서 이 거부는 **`서버 연결(TCP)` 단계**로 떨어졌고, `Elapsed` 가 비어 있어 `syncTiming` 은 경과 시간도 출력하지 않았습니다.
- 운영자가 보는 그림은 "서버에 TCP 로 붙지 못했다" 였습니다. 실제로는 TCP 도 붙었고, 환영 메시지도 받았고, `STLS`/`STARTTLS` 도 보냈고, **그 다음에 서버가 평문을 밀어 넣어 Postra 가 업그레이드를 거부한 것**입니다. 방화벽·DNS·포트를 뒤지게 만드는, 사실과 정반대 방향의 안내였습니다.

## 무엇이 바뀌었나

같은 거부를 저장소의 관용구대로 감쌌습니다:

- `Stage: domain.StageStartTLS` — 진단에 **`STARTTLS 전환` 단계**로 적힙니다(이미 등록된 레이블입니다).
- `Command` — 실제로 보낸 동사, POP3 는 `STLS`, IMAP 은 `STARTTLS`.
- `Elapsed` — 업그레이드 명령 직전부터 잰 실제 경과 시간. 같은 함수의 `tlsStart`/`greetStart`/`dialStart` 와 같은 방식입니다.
- `Timeout` — 그 단계의 명령 제한 시간. 이제 진단에 `제한 N초 중 M초 경과` 가 함께 나옵니다.
- `Class` — `domain.ClassifyInbound` 의 판정(`other`). **재시도 판정은 전과 같습니다**: 이전에도 이 오류는 `other` 로 분류돼 재시도 대상이었고, 지금도 그대로입니다.

**거부 자체는 불변입니다.** `Buffered() > 0` 판정, `conn.Close()`, 업그레이드 중단 모두 그대로이고, 기존 거부·정상 업그레이드 테스트 4개가 수정 없이 통과합니다. 새 단계·분류 레이블도 없습니다(`starttls`·`other` 둘 다 기등록) — 따라서 생성되는 API 계약, 브라우저 화면, `internal/transport/spa/assets` 어디에도 번지지 않습니다.

**진단에는 바이트 수만 들어갑니다.** 서버가 밀어 넣은 평문은 로그에도 진단에도 들어가지 않으며, 양쪽 테스트가 그것을 단언합니다.

## 검증

- **되돌려 실패를 먼저 확인했습니다**: 수정 전 `TestPOP3STLSInjectedPlaintextRefusesUpgrade` 는 `Dial error = *errors.errorString ... want a *domain.InboundError naming the stage` 로, `TestIMAPStartTLSInjectedPlaintextRefusesUpgrade` 는 같은 이유로 각각 FAIL 하고 수정 후 PASS 합니다.
- **변이 검증으로 인과를 고정**했습니다: POP3 쪽만 `fmt.Errorf` 로 되돌리면 POP3 거부 테스트 **하나만** 실패하고 정상 업그레이드 테스트는 통과, IMAP 쪽만 되돌리면 IMAP 거부 테스트 하나만 실패합니다. 원복 후 전부 통과하고 변이 흔적 0건을 확인했습니다.
- 테스트는 손으로 만든 대역 없이 기존 `net.Listen` 루프백 스크립트 서버(pop3 `stlsServer`, imap `starttlsServer`)와 실제 `Dialer{}.Dial`, 실제 `DialOptions` 로 돕니다.
- `go test -race -count=1 -timeout=900s ./...` 25개 패키지 실패 0건 — `./internal/adapters/pop3/`, `./internal/adapters/imap/`, `./internal/application/` 포함
- `go build ./...`, `go vet ./...`, `make lint-format` 무지적, `go mod tidy` 무변경, canonical API 계약 검사(`postra-contracts -check`)
- `make lint-security` — 141개 파일 지적 0건
- `make frontend-check` 통과 후 `internal/transport/spa/assets` 변화 없음 — 태그에 담긴 `/app` 번들이 최신입니다(릴리즈 워크플로가 같은 검사를 다시 합니다)
- 외부 PostgreSQL(`POSTRA_TEST_PG`)과 브라우저 e2e 는 돌리지 않았습니다 — 프런트엔드가 바뀌지 않은 Go 전용 변경이라 범위 밖입니다.

## 업그레이드 및 호환성 주의사항

DB 마이그레이션, 새 설정 키, 새 필수 환경변수가 없습니다. 실행 파일 또는 컨테이너 이미지를 교체한 뒤 재시작하면 끝이고, 되돌릴 때도 v0.25.5 로 그대로 내려갈 수 있습니다.

- 진단 문장만 달라집니다. 이 거부를 **대시보드나 알림에서 `서버 연결(TCP)` 문자열로 잡아 두었다면** 이제 `STARTTLS 전환` 으로 나오므로 규칙을 확인하세요. `domain.SyncDiagnostic` 에 필드가 추가되지 않아 API 응답의 모양은 그대로입니다.
- `STARTTLS 전환` 단계로 중단된 동기화를 보게 되면, 그것은 네트워크 문제가 아니라 **서버가 TLS 핸드셰이크 전에 평문을 보냈고 Postra 가 그 연결을 끊었다**는 뜻입니다. 메일 서버 쪽 STARTTLS 설정과 중간 장비(투명 프록시, 메일 검사 장비)를 먼저 의심하세요.
- v0.25.6 의 `make frontend-test` 클린 체크아웃 가드와 govulncheck 예시 고정이 이번 릴리즈에 함께 들어갑니다(개발 환경 전용).
- v0.25.5 의 거부된 `LIST` 크기 선별 경고, v0.25.4 의 크기 제한 없는 계정 본문 잘림 수정, v0.25.3 의 POP3 `fetch` 진단 교정, v0.25.2 의 OpenTelemetry v1.45.0, v0.25.1 의 "계정당 인바운드 연결 하나"와 `mail.idle_enabled`, v0.25.0 의 동기화 실패 진단은 바뀌지 않았습니다.
