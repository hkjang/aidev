## 기록이 없는 job 디렉터리에 업로드 원본이 영구히 남던 문제 수정

`CreateJob`은 업로드 원본을 job 디렉터리에 먼저 쓰고 그 뒤에 `job.json` 기록을 씁니다. 그 사이에 프로세스가 죽거나 디스크가 가득 차면 **마스킹되지 않은 원본 문서만 남고 기록은 없는 디렉터리**가 생기는데, `Store.load()`는 `job.json`이 없거나 손상된 디렉터리를 건너뛰어 맵에 올리지 않았습니다. 맵에 없으니 조회·이력 목록·보존 기간 정리(`DeleteExpired`는 job ID로 디렉터리를 지움) 어디에도 닿지 않아, 마스킹해 달라고 받은 개인정보 원문이 보존 기간과 무관하게 영원히 남았습니다. `job.json`의 ID가 디렉터리 이름과 다른 경우도 같은 결과였습니다 — 정리 작업이 없는 디렉터리를 지우고 실제 디렉터리는 그대로 두었습니다.

- 기동 시 `load()`가 새 `readJobRecord`로 기록 없음·파싱 불가·ID 불일치를 한데 판정해 해당 디렉터리를 `os.RemoveAll`로 삭제하고 로그를 남깁니다. 기동 시점에는 동시 쓰기 주체가 없고 API로 접근할 ID도 없으므로 안전합니다
- `Create`가 `job.json` 저장에 실패하면 맵 항목과 디렉터리(직전에 쓴 업로드 포함)를 즉시 되돌려, 다음 기동까지 원본이 남지 않습니다 (빈 ID로 저장소 루트를 지우지 않도록 가드)
- 정상 job은 이전과 동일하게 유지됩니다. README 보존 정책 문단에 이 동작을 적었습니다

검증: `internal/jobs` 테스트 2개 추가(고아 3종 — 기록 없음·잘린 JSON·ID 불일치 — 이 재로드 후 디스크와 스토어에서 모두 사라지고 정상 job은 유지 / `job.json` 자리에 디렉터리를 만들어 `Create`를 실패시키면 스토어에 없고 디렉터리도 제거). `gofmt -l`·`go vet ./...`·`go build ./...`·`go test -count=1 ./...`·`go test -race -count=3 ./...` 전부 통과했고, 이전 구현으로 임시 되돌려 새 테스트 2개가 실제로 실패하는 것까지 확인했습니다.
