- 과제: 공유 DSN을 직접 여는 통합 시험 12개를 기존 스크래치 DB 하네스로 격리 (가치 3 / 위험 1 / 작업량 S)
- 왜: 현재 네 시험 파일의 12개 시험이 설정된 공용 DB에 직접 마이그레이션·fixture INSERT/DELETE를 실행하므로, 다른 브랜치의 스키마·설정·동명 시험 데이터가 결과에 영향을 줄 수 있다. 이미 적용된 TestDatabaseMigrationsAndSecretRotation의 createScratchDatabase 방식을 나머지에 적용하면 시험별 시작 상태를 보장하고 회차 간 간섭을 줄인다.
- 수용 기준: 1) 아래 12개 시험은 각각 createScratchDatabase(t, dsn)의 반환 DSN으로 openDatabase를 호출하며 공용 DB를 시험 데이터 저장소로 쓰지 않는다. 2) 기존 제품 동작 주장, DSN 미설정 skip, pgvector 미설치 skip, 실제 pool.Close()로 장애를 재현하는 인증 시험을 유지하고 pool 종료 뒤 스크래치 DB 정리가 실행된다. 3) 실제 PostgreSQL에서 대상 시험을 -count=2로 실행해 통과하고, 시험이 사용하는 실제 pool의 SELECT current_database()가 입력 공용 DSN의 DB와 다름을 검증한다(작은 공용 assertion을 각 대상 시험에서 호출해도 됨). 단순 소스 문자열 검사나 가짜 DB로 격리를 증명하지 않는다.
- 건드릴 파일:

  - internal/app/authfailure_test.go: TestOnlyGenuineSignOutIsMarkedAsNoSession — 1곳 격리. 중간 db.Close() 뒤 authenticate가 errNoSession으로 오인하지 않는 주장을 유지. TestLoginSaysTheStoreIsDownRatherThanBlamingThePassword의 의도적인 접속 불가 pool은 변경하지 않는다.

- 검증 명령:
  - 저장소 루트에서 `go test ./... -count=1` 및 `go vet ./...`.
  - 실제 DB가 설정된 셸에서 `test -n "$WEEKLY_TEST_POSTGRES_DSN"` 후 `go test ./internal/app -run 'Test(EmbeddingStalenessIsDetected|LoginThrottleBlocksAndClears|WorkItemMergeAndSplitSurviveTheNextSave|OrganizationTemplateWalksUpToTheNearestOwner|IssueEpisodeStopsAtTheFirstWeekWithoutOne|IssueOutcomeIsRecordedOncePerWeek|WorkLookupFindsOtherPeoplesWorkAndNothingFromTheirReports|WorkLookupAnswersShortQueries|OnlyGenuineSignOutIsMarkedAsNoSession|DeadlineInstantMatchesTheSQLItGuards|ImportedHistoryStillCountsAgainstAccountsCreatedLater|ATitleMatchOutranksAFloodOfRecentBodies)$' -count=2 -v`.

  - 정찰에서 실제 실행한 `go test ./... -count=1`은 exit 0, internal/app 2.802초. 이 세션에는 WEEKLY_TEST_POSTGRES_DSN이 없어 DB 경로는 skip이며 실제 PostgreSQL 통과는 미확인이다. CI ci.yaml은 pgvector/pgvector:pg16과 DSN을 제공하지만 release.yaml은 제공하지 않는다. 사용할 DSN은 구현 환경의 시험 전용 값을 사용하고 운영 DB를 지정하지 않는다.
- 위험과 피할 것: 프로덕션 auth.go/db.go, migrations/, .github/workflows/, 프런트·API 계약은 수정하지 않는다. fixture 정리 DELETE·ON CONFLICT의 일괄 제거는 별도 리팩터이므로 이번에는 유지해도 된다. createScratchDatabase의 URL DSN 및 DB 생성 권한 요구를 그대로 따른다. _test.go 하네스 함수에는 guards 표시를 새로 달지 않는다(Go coverage 대상이 아니며 harnesssweep_test.go에 이유가 있음). weekly_u_* 청소는 보류: SQL 후보 목록과 harnessNameStamp를 함께 바꿔야 하고 DROP DATABASE WITH (FORCE)의 범위를 넓혀 별도 실제 DB 검증이 필요하다. mutation-check/authz-check는 소스를 제자리에서 바꾸므로 이번 단순 시험 배선 변경의 필수 검증에 넣지 않는다. 공유 DB를 초기화하거나 기존 다른 브랜치 DB를 수동 삭제하지 않는다.
- 차선 후보: authz-check 실행 시간·동시 실행 금지 안내를 README와 docs/CHECKS.md에 맞추기 — 스크립트 claim_the_tree에는 이미 표식·경고가 있으므로 새 잠금 구현은 하지 말고 문서만 보완한다. 첫 과제에 실제 DB 검증 환경을 확보할 수 없으면 이 범위를 택한다.

구현 순서·견적: 접속부 12곳 및 DB 이름 검증 10~15분 → 실제 DB 대상 반복 실행 5분 → 전체 시험·vet·가드 확인 5~10분, 합계 20~30분 + 환경/정리 순서 확인 예비 10분. 45분 안에서 환경 문제가 길어지면 차선으로 전환하되 DB 시험 skip을 성공 증거로 보고하지 않는다.
대안 판단: 기존 createScratchDatabase 재사용을 선택했다. 공용 DB DELETE 확대는 병렬 실행 간섭을 해결하지 않고, 트랜잭션 rollback 격리는 pool을 닫거나 내부 트랜잭션을 여는 시험과 맞지 않으며, 하네스 재설계는 범위를 넘는다.
