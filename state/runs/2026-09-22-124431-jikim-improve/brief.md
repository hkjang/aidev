- 과제: Vite 개발 서버의 OpenAPI 링크 프록시 누락 보완 (가치 2 / 위험 1 / 작업량 S)
- 왜: `ApiExplorerPage`의 OpenAPI 3.1 버튼은 `/api/openapi.json`을 열지만 `web/vite.config.ts`는 `/api/v1`만 관리 API로 프록시하여 개발 서버에서 문서 대신 SPA HTML을 반환한다. 누락된 경로를 기존 Go 백엔드로 전달하면 개발 환경에서도 실제 OpenAPI 문서를 열고 API 계약을 확인할 수 있다.
- 수용 기준: 1) Vite 개발 서버를 경유한 `GET /api/openapi.json`이 Go 백엔드의 JSON 응답을 반환하며 `openapi` 값이 `3.1.0`이다(일반 브라우저 링크의 Accept:text/html과 API 요청의 Accept:application/json 모두). 2) `/api/v1`·`/v1`·`/mcp`·상태 경로의 기존 전달 동작 및 `/api-explorer` SPA 라우팅을 유지하고, API 탐색기 링크와 Go 공개 라우트는 변경하지 않는다. 3) 회귀 검증은 실제 Vite 서버에 native fetch로 요청하여 upstream 도착 여부·원래 경로/쿼리 보존·응답 content-type/body를 관찰한다. config 객체/소스 문자열 비교나 fetch mock만으로 통과시키지 않는다.
- 건드릴 파일: `web/vite.config.ts`: default `defineConfig`의 `server.proxy` — `/api/openapi.json`을 기존 `http://127.0.0.1:8080`으로 전달하는 좁은 항목 추가; `web/src/lib/vite-proxy.test.ts`(신규 제안) — Node 환경에서 실제 운영 Vite 설정을 로드하고 실제 Vite→loopback HTTP upstream→native fetch 왕복을 검증; `CONTRIBUTING.md`: 개발 환경 절 — Go 백엔드 8080과 `npm --prefix web run dev`의 연동 및 OpenAPI 확인 주소를 짧게 안내.
- 검증 명령: Node 24 준비 후 `npm --prefix web ci --no-audit --no-fund`; `npm --prefix web test -- --maxWorkers=1`; `npm --prefix web run lint`; `VITE_APP_VERSION="$(./scripts/version.sh)" npm --prefix web run build`; `go test ./...`; 최종 `./scripts/verify.sh`. 모두 현재 package.json/스크립트에 존재하는 명령이며 Go 전체 테스트만 이번 정찰에서 실행하여 exit 0 확인. 프런트 설치·전체 verify는 이번 미실행. 신규 회귀 테스트 추가 후에는 `npm --prefix web test -- src/lib/vite-proxy.test.ts`로 집중 실행할 수 있다.
- 위험과 피할 것: `/api` 전체로 프록시를 넓히거나 API 경로·인증·OIDC·MCP·migrations/·.github/workflows/를 바꾸지 않는다. 이미 시도한 AI HTTP 오류 통합·SSE 콜백 수정·릴리즈 로그 축소를 재작업하지 않는다. 고정 8080을 테스트에서 점유하거나 기존 서비스를 죽이지 말고 실제 upstream을 임시 포트에 띄운 뒤 테스트용 target만 재지정한다(운영 설정의 경로 매칭은 그대로 사용). 테스트는 네트워크·Vite 객체를 직접 실행하고 종료 시 두 서버·watcher·연결을 닫는다. 캐시/의존성 사전 최적화는 임시 경로에 두어 저장소를 오염시키지 않는다. 브라우저 E2E는 docs/screenshots를 덮어쓰므로 이 작은 개발 프록시 수정의 증거로 기존 캡처 suite를 무작정 실행하지 않는다.
