# v0.320.0 — 참조 수를 읽지 못한 첨부 삭제가 살아 있는 이미지 파일을 지우지 않습니다

이 릴리즈는 보고서에 화면 캡처를 첨부하는 작성자와 그 보고서를 읽는 사람을 위한 **데이터 보존** 수정입니다. 첨부 하나를 지우는 요청에서 참조 수 집계가 실패하면 **아직 다른 첨부가 쓰고 있는 이미지 파일을 지워 버리던** 결함을 고칩니다. 프로덕션 변경은 `internal/app/attachments.go` 한 파일의 한 줄이며, 마이그레이션·새 환경변수·설정·프런트엔드 변경은 없습니다.

## 읽지 못한 참조 수가 "아무도 안 쓴다" 와 같았습니다

`deleteAttachment` 은 행을 지운 뒤, 같은 파일을 가리키는 행이 남아 있는지를 `SELECT count(*) FROM report_attachments WHERE stored_path=$1` 로 셉니다. 그런데 그 `Scan` 오류를 `_ =` 로 버렸습니다.

질의가 실패하면 `remaining` 은 제로값 0 으로 남습니다. 그리고 이 분기에서 0 은 곧 **"아무도 이 파일을 참조하지 않는다"** 라서, 바로 아래 `os.Remove` 가 실행됩니다.

저장 경로는 `reportID/sha256.ext` 내용 주소입니다. 같은 보고서에 같은 이미지를 두 번 올리면 **두 행이 한 파일을 공유**합니다. 그래서 그 중 하나를 지우는 요청에서 집계가 실패하면, 지운 쪽이 아니라 **살아 있는 다른 첨부의 이미지가 사라집니다.**

- 그 첨부의 이미지 GET 이 `404 ATTACHMENT_FILE_MISSING` 이 됩니다.
- 목록에서 `available:false` 로 나와 패널에 깨진 첨부로 보입니다.

시험이 증명한 피해는 이 두 가지와 파일 자체의 소실까지입니다. 내보낸 PPTX 덱에서 그 캡처가 빠지는 것은 코드를 읽어 따라간 추론이며 이번에 측정하지 않았습니다.

응답은 `204` 였고 로그는 한 줄도 없었습니다. 운영자는 이미지가 왜 없어졌는지 알 길이 없었습니다. 앞선 다섯 릴리즈가 고친 같은 계열의 `Scan` 오류 무시와 달리, 이번 것은 표시가 틀리는 문제가 아니라 **되돌릴 수 없는 파일 소실**입니다.

## 이제 읽지 못한 집계는 파일을 건드리지 않습니다

집계가 실패하면 `os.Remove` 를 건너뛰어 파일을 그 자리에 둡니다.

- HTTP 상태: `204` 그대로 — 행 `DELETE` 는 이 지점에서 **이미 커밋됐으므로** 실패를 답하면 거짓말이 됩니다.
- 로그: `count attachment references` 경고 한 줄에 `attachmentId`·`error`·`trace`.
- `stored_path` 원문은 로그에 넘기지 않습니다. 저장 파일 이름은 사용자가 올린 내용의 해시입니다.

대가는 참조가 실제로 0 인데 집계를 읽지 못한 경우 파일 한 개가 볼륨에 남는 것입니다. 쓰이지 않는 파일이 남는 것과 쓰이는 파일이 사라지는 것은 되돌릴 수 있는지에서 다릅니다 — 그래서 이 교환을 택했습니다.

다만 그 파일은 **스스로 정리되지 않습니다.** `cleanupAttachmentFiles` 는 보고서 행이 사라진 디렉터리만 회수하므로, 보고서가 남아 있는 한 그 파일은 영구 고아로 볼륨에 머뭅니다. 지금은 운영자가 경고 줄의 `attachmentId` 를 단서로 직접 치워야 하고, 이 회수 경로의 보강은 이번 변경에 포함되지 않았습니다.

정상 경로는 그대로입니다. 참조가 남아 있으면 파일을 보존하고, 마지막 참조가 사라지면 파일을 지우며, 파일이 이미 없으면 그것을 실패로 적지 않습니다.

## 검증

구현 단계에서 `internal/app/attachmentdeletekeepsfile_test.go` 의 새 시험 세 개를 실제 PostgreSQL 과 `newTestServer`/`app.Handler()` 로 실행했습니다. 집계만 실패하는 모양은 `BEFORE DELETE ... FOR EACH ROW` 트리거가 테이블 이름을 바꿔 만듭니다 — `DELETE ... RETURNING` 은 성공하고 뒤따르는 `count(*)` 만 `relation does not exist` 로 실패합니다. 트리거 안에서 `ALTER TABLE ... RENAME` 이 PG16 에서 허용되는지를 임시 테이블과 `BEGIN/ROLLBACK` 으로 먼저 실측한 뒤 이 방식을 썼습니다. 트리거·함수·테이블 이름은 `t.Cleanup` 과 명시적 복원으로 되돌립니다.

오류 경로 시험 `TestADeletedCaptureDoesNotTakeAStillReferencedFileWithIt` 은 수정 전 `the reference count could not be read and the file the surviving row needs is gone` 와 `the surviving capture's image GET=404, want 200` 으로 실패했고, 수정 후 통과했으며, 그 한 줄을 원본으로 되돌리면 같은 실패가 다시 나는 것을 확인했습니다. 정상 경로 시험 두 개는 수정 전에도 통과했습니다 — 바꾸지 말아야 할 동작을 지키는 자리입니다.

- 집계 실패 뒤에도 살아 있는 첨부의 파일이 디스크에 있고, 이미지 GET 이 `200` 이며 원본 바이트가 보존됩니다.
- 목록이 살아 있는 첨부를 `available:true` 로 보고합니다.
- 경고 한 줄이 해당 `attachmentId` 를 담고, 저장 파일 이름은 로그에 나오지 않습니다.
- 두 참조 중 하나를 지우면 파일이 남고, 마지막을 지우면 파일이 사라집니다.
- 파일이 이미 없는 첨부의 삭제는 `204` 이고 제거 실패 경고를 남기지 않습니다.

릴리즈 단계에서는 이 릴리즈만을 위해 만든 별도 PostgreSQL 데이터베이스에서 `go test ./... -count=1` 전체를 실행해 통과했습니다. `go vet ./...`·`go build ./...`·`gofmt`, 버전 검사 아홉 곳, OpenAPI 119경로, 쪽넘김 10목록, 모달 닫기 검사, 변경 관련 가드, 프런트엔드 시험·타입 검사·프로덕션 빌드, 백업·복구 왕복 검사가 통과했습니다. 로드맵 HTML·PDF 와 두 안내서 HTML 을 기존 스크립트로 다시 만들었습니다. 정확한 실행 시간과 건수는 릴리즈 커밋 메시지에 적혀 있습니다.

제자리에서 소스를 고치는 `mutation-check`·`authz-check` 는 이전 릴리즈와 같이 실행하지 않았습니다. `gh` 를 쓸 수 없는 세션이라 원격 이력을 읽는 advisory `release-check.sh` 도 실행하지 않았습니다. Docker 오프라인 자산 생성과 GitHub Release 게시는 기존 태그 워크플로가 담당합니다.

UI 클릭, 이 오류 상황에서의 PPTX 출력, 트리거 rename 이외의 DB 장애 주입은 별도로 검증하지 않았습니다. **이미 사라진 파일은 이 버전이 되돌려 주지 않습니다.** 질의 오류를 버리는 나머지 `Scan` 의 전수 조사, `serveAttachment` 가 아직 저장 파일 이름을 로그에 쓰는 별건, 집계 실패로 남은 고아 파일의 회수, 동시 업로드 개수 상한, 검토 책임자 선택기의 `limit=500` 잘림은 이번 변경에 포함되지 않습니다. 이 문제들을 해결한 릴리즈로 사용해서는 안 됩니다.

## 업그레이드

기존과 같이 PostgreSQL 과 상태 볼륨을 백업한 뒤 v0.320.0 이미지를 올립니다. 스키마와 설정 변경이 없어 별도 데이터 변환은 필요하지 않고, 되돌릴 때도 데이터 되돌림이 필요하지 않습니다.

이 릴리즈는 운영자가 따로 할 일이 없는 조용한 수정입니다. 새 화면도, 새 설정도, 작성자가 배워야 할 동작 변화도 없습니다 — 안내할 것은 "지운 첨부가 다른 첨부의 이미지를 데려가지 않는다" 한 문장뿐입니다. 별도 공지 없이 다음 정기 업그레이드에 함께 올려도 됩니다.

배포 담당 운영자는 먼저 소규모 대상에서 세 가지를 확인합니다: 같은 이미지를 두 번 올린 보고서에서 하나를 지웠을 때 남은 첨부의 이미지 GET 이 `200` 인지, 마지막 참조를 지웠을 때 파일이 정리되는지, 정상 삭제가 계속 `204` 인지. **중단 기준**은 정상 삭제가 `204` 가 아닌 응답을 내거나, 마지막 참조를 지운 뒤에도 파일이 남는 사례가 확인되는 것입니다. 한 건이라도 나오면 확대 배포를 멈추고 v0.319.0 이미지로 되돌립니다 — 되돌리면 파일 소실 결함도 함께 돌아온다는 것을 염두에 두십시오.

배포 후 첫 24시간에는 `count attachment references` 경고와 `ATTACHMENT_FILE_MISSING` 404 를 함께 지켜봅니다. 경고가 나오는데 404 가 늘지 않는 것이 이 수정이 일한 모습입니다. 성공 기준은 참조 수 집계가 실패한 삭제에서 **파일 소실 0건**, 그리고 새로 생기는 `available:false` 첨부 0건입니다. 경고가 반복되면 그것은 이 수정이 가린 DB 문제의 신호이니 DB 상태를 확인하십시오 — 이 버전은 집계가 실패하는 원인 자체를 고치지 않습니다. 실제 운영 배포와 이 사후 관찰은 이번 로컬 릴리즈 준비에서 수행하지 않았습니다.
