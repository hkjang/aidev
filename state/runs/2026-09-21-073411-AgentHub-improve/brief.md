- 과제: Langflow e2e가 runtime-settings의 실제 응답 구조로 백업하고 원래 프로필을 복원하도록 수정 (가치 5 / 위험 1 / 작업량 M)
- 왜: web/scripts/langflow-e2e.mjs의 runtime-settings 검사(137~156행)는 GET 응답의 최상위 before.profiles를 읽지만 internal/api/runtimesettings.go:runtimeSettings는 {settings: {profiles: [...]}, suggestions, runtimes, targets}를 반환하므로, 정상 조회에도 finally가 {profiles: []}를 PUT하여 기존 전역 프로필을 지운다. 실제 settings.profiles를 검증·복제해 복원하고 조회/복원 오류를 실패로 전달하면 검증 스크립트가 운영 설정을 훼손하거나 복원 실패를 성공으로 숨기는 일을 막는다.
- 수용 기준: 1) GET /api/v1/admin/runtime-settings의 2xx·JSON 파싱 성공·body.settings 객체·settings.profiles 배열을 확인한 뒤에만 이 검사 블록의 첫 PUT을 보낸다(실패·누락·null·배열 아닌 값은 빈 프로필로 대체하지 않고 오류; 앞선 Agent 생성까지 금지하는 범위는 아님). 백업은 깊은 복사하고 PUT 복원 본문은 {profiles: 백업배열}로 하며 응답의 suggestions/runtimes/targets는 보내지 않는다. 정상 API가 반환하는 profiles: []는 유효하다. 2) 성공/검사 예외/일부 PUT 실패 모두 finally에서 전체 원래 프로필(config 중첩값·env·description·enabled:false 포함)을 복원한다. 복원 HTTP 비2xx/네트워크 실패는 실행 실패가 되며 검사와 복원이 함께 실패하면 양쪽 원인을 보존한다. 기존 config 오버레이 및 LANGFLOW_AUTO_LOGIN 거절 검사(기대 HTTP 400)는 유지한다. 3) 실제 Server.Handler()+격리 PostgreSQL+Node subprocess가 스크립트에서 사용하는 동일 모듈을 호출하여 서로 다른 런타임의 비어 있지 않은 원본 프로필이 정상/예외 종료 후 DB와 GET에서 보존됨을 증명한다. 무인증 GET 401은 runtime-settings PUT 0회임을 실제 라우터에서 확인한다. Node 장애 테스트는 잘못된 JSON/형태·조회/복원 통신 실패·이중 오류를 보강하되 대역만으로 API 계약을 증명하지 않는다. 수정 전 before.profiles 방식으로 되돌리면 원본 보존 검사가 실패해야 한다.
- 건드릴 파일: web/scripts/langflow-e2e.mjs: 최상위 try 안 runtime-settings 검사 블록 — 검증된 백업/복원 모듈을 실제 호출하고 기존 기대 상태 검사 유지; web/scripts/runtime-settings-check.mjs (신규 제안): 백업/콜백/finally 복원 담당, 브라우저를 띄우지 않고 기존 call(method,path,body) 전달받기; web/scripts/runtime-settings-check.test.mjs (신규 제안): 오류 경계 회귀 테스트; internal/api/langflowsettings_live_test.go: TestLangflowSettings 옆 TestLangflowRuntimeSettings 추가 — 기존 db/session/CSRF/Node subprocess 구성 패턴 사용. 읽기 근거이며 수정 대상 아님: internal/api/runtimesettings.go:runtimeSettings, putRuntimeSettings; internal/runtimecfg/runtimecfg.go:Settings, Profile, Validate; web/scripts/session-gateway-check.mjs:withSessionGateway; internal/api/catalog.go의 runtime-settings GET/PUT 등록.
- 검증 명령: 저장소 루트에서 `node --check web/scripts/langflow-e2e.mjs`, `node --test web/scripts/session-gateway-check.test.mjs web/scripts/silent-sso.test.mjs`와 `go test ./internal/api ./cmd/runtime-proxy`는 정찰에서 통과(30 Node 테스트). 신규 모듈 작성 후 `node --test web/scripts/runtime-settings-check.test.mjs`; 격리 테스트 DB의 AGENTHUB_TEST_DSN과 base64 32바이트 AGENTHUB_ENCRYPTION_KEY를 환경에 설정한 후 `go test -p 1 ./internal/api -run '^TestLangflow(Runtime)?Settings$' -count=1 -v`(신규 이름은 위 제안대로). 마지막 회귀 `go test -race ./cmd/... ./internal/...`는 DB가 있으면 `-p 1` 추가. DSN 없이 통과한 live 테스트 Skip을 검증 완료로 쓰지 말 것.
- 위험과 피할 것: 서버 API 계약/인증/마이그레이션/.github/workflows와 runtimecfg 프로덕션 소스는 고치지 않는다. sessionGateway는 이전 회차에 해결됐으므로 다시 바꾸거나 범용 설정 프레임워크로 확장하지 않는다. putRuntimeSettings는 syncRuntimeEnvironment를 호출하므로 live 검증은 공유 배포·기존 서비스 DB가 아닌 런타임 없는 격리 DB에서만 한다. 관리자 API는 API 키 대신 실제 관리자 세션+CSRF를 써야 한다(TestLangflowSettings 참고). Settings는 profiles 하나이며 임의 미래 최상위 필드 보존까지 약속하지 않는다. 원본 백업을 콜백에 직접 넘겨 변경시키지 않는다. 일반 설정용 {value: ...} 포맷과 혼동하지 않는다. 기대 400 검사까지 requireSuccess로 감싸지 않는다. DB row 부재를 동일한 부재로 되돌리는 API 신설은 범위 밖이며 이 과제는 GET이 반환한 유효 설정 내용 보존이 계약이다. 감사 details 원문/DLP 재마스킹·정책 actor 수정 및 BASE_VERSION 상향은 불필요하다.
- 차선 후보: guide-shots 전역 설정 백업 실패 시 seed 중단 — guide-shots.mjs 121행의 실패 후 continue와 132행 seed 실행은 여전히 존재한다. 다만 policy/DLP/sessionGateway/tracking 네 API 계약과 값 부재 처리를 함께 다뤄야 해 이번보다 범위가 넓다.

구현 순서와 시간 예산(추정, 총 45분): 기존 live 검증 틀로 비어 있지 않은 runtimeSettings 보존 실패 재현 10분 → 작은 전용 모듈 추출 및 기존 검사 배선 12분 → 오류 경계/DB 정상·예외 검증 13분 → 회귀와 오류 대응 여유 10분. 별도 추상화·CI 편집·가이드/PDF 작업은 넣지 않는다. 격리 DB를 준비하지 못하면 live 미검증으로 명시하고 대역 테스트만으로 release-ready를 주장하지 않는다.

확인 한계: 현재 AGENTHUB_TEST_DSN 미설정으로 DB live와 Ready Langflow 브라우저 검사는 실행하지 않았다. 데이터 손실은 실제 GET/PUT 소스와 호출 코드의 구조 불일치로 확인했으며 이번 정찰에서 배포 데이터를 지워 재현하지 않았다. 요청된 pmo:estimating-and-contingency, technology:implementation-planning, technology:solution-exploration은 Skill/skills.list/skills.read 도구가 노출되지 않았고 로컬 SKILL.md 검색에서도 발견되지 않아 절차·반환 형식은 미확인이다. 사용자 지정 과제서 형식과 후보 평가·대안 비교·시간/여유 추정으로 정찰을 완료했다.
