fix: release jupiq v1.8.5

`/usage`가 같은 `group_by`를 추세와 소비량 두 경로에 넘기면서 소비량만 조용히
`user`로 되돌아가던 것을 응답이 스스로 밝히도록 고쳐 릴리스합니다. 스키마·설정
변경이 없고 기존 응답 필드와 SQL·limit이 모두 그대로이므로 patch를 올립니다.

- `GET /api/v1/usage?group_by=project`는 `trend`·`server_trend`를 project로 묶지만
  (`settings.go`의 `allowedGroup`이 project를 압니다) 같은 핸들러가 같은 값을 넘기는
  `ResourceConsumption`은 시간별 롤업에 project 열이 없어 말없이 user로 되돌리던
  문제 — 한 응답 안에서 추세는 프로젝트별이고 `consumption`은 사용자별인데 응답에
  그 사실이 어디에도 없어, 호출자가 두 목록을 같은 축으로 읽고 프로젝트별 소비량을
  본 것으로 착각합니다
- `resource_usage.go`의 함수 안 집계 표를 패키지 수준 `consumptionColumns`로 올리고,
  그 표만을 근거로 되돌림 결과를 알려주는 `ConsumptionGroupBy(groupBy)`를 더했습니다.
  아는 값은 그대로 돌려주고 모르는 값은 `user`를 돌려줍니다. `ResourceConsumption`이
  같은 맵을 쓰므로 집계와 안내가 갈릴 수 없습니다
- `api/core_handlers.go`의 `usage`가 이미 읽던 `groupBy`로
  `consumption_group_by`를 성공 분기에만 싣습니다. 소비량 조회가 실패하면 종전처럼
  `consumption`과 함께 이 키도 생략합니다
- SQL·인자·`boundedLimit(limit, 100, 500)`·반환 형식은 무변경이고 `/usage/consumption`
  도 무변경입니다. 계약을 좁히지 않으므로 문서 밖 `group_by`는 계속 200에 user 그룹
  으로 답합니다. `/usage` 200이 자유 형식이어서 `openapi.yaml`은 바꾸지 않았고 프런트
  는 `consumption`을 읽지 않아 화면 변경도 없습니다
- 실제 PostgreSQL 16에 project 라벨이 붙은 `metric_samples`와 `resource_usage_hourly`
  행을 넣고 실제 `store.Store`·실제 `usage` 핸들러로 `/api/v1/usage?group_by=project`
  를 부르는 통합 테스트와, 표 기반 `ConsumptionGroupBy` 단위 테스트를 더했습니다
- 롤업에 project 열을 더하는 쪽은 마이그레이션과 수집기까지 번져 범위 밖으로 뒀습니다.
  마이그레이션·설정 변경 없습니다
