MCP-OAUTH-STANDARD.md 와 weekly 참조(mcpoauth.go)를 따라 같은 능력을 이 저장소 구조로 만들었다 — 새 파일 `internal/api/mcpoauth.go` 하나에 메타데이터·401 도전·토큰 검증·계정 매핑을 두었다. **고른 것과 이유**: (1) 설정 자리 — 이 저장소 설정은 키마다 JSON 오브젝트라(tracking·oidc 와 같은 모양) `mcp` 키 아래 `oauth:{enabled,resource,audience,scopes}` 로 두어 경로가 표준 이름 `mcp.oauth.enabled` … 그대로 읽히게 했고, audience·scopes 는 oidc.scopes 처럼 배열로 저장하되 화면은 공백 구분 한 칸이다. 켤 때 OIDC issuer 가 비어 있으면 저장 시점에 400 으로 거부하고(postra 방식), 저장 뒤 issuer 가 비워지면 런타임에 조용히 꺼진 채 `mcp oauth is enabled but inactive` 를 로그에 남긴다. (2) 리소스 식별자 — `mcp.oauth.resource` 가 비면 `requestBaseURL`(서비스 공개 URL, 없으면 관찰된 주소) + `/mcp`, 즉 OIDC redirect URI 와 같은 출처에서 만든다. 메타데이터 주소는 리소스 옆에서 파생한다. (3) 대상 — aud 에 리소스, 또는 aud/azp 가 `mcp.oauth.audience` 나 웹 로그인 `oidc.client_id` 에 있으면 통과(weekly 와 같음; Keycloak 26 은 client id 를 azp 에만 싣는다). 거부 메시지는 본 `aud=[…], azp="…"` 와 적을 값·매퍼 값을 그대로 말한다. (4) 계정 — 웹 로그인이 계정을 `oidc_subject` 로만 매고 같은 username 의 로컬 계정은 별칭으로 분리하므로, 토큰도 `sub` 로만 찾는다(username 폴백 없음). 없거나 비활성이면 "sign in to the web portal once first" 로 거부하고 계정을 만들지 않으며 role claim 은 읽지 않는다. (5) 권한 — `AuthType="oauth"` 주체의 권한은 `mcp.oauth.scopes`(기본 `mcp:access games:read rankings:read profile:read`)를 토큰의 scope 가 이 어휘를 말할 때만 교집합으로 좁힌 뒤 개인 키와 같은 `effectiveKeyPermissions`(전역·역할 정책 교집합)를 탄다. 그 과정에서 `Principal.Can` 의 관리자 우회가 `AuthType != "api_key"` 여서 OAuth 관리자가 전권을 얻을 뻔한 것을 `== "session"` 으로 좁혔고, `callMCPTool` 의 tool 권한 검사도 키에만 걸려 있던 것을 세션 아닌 모든 자격으로 넓혔다(PG 테스트가 이 누락을 잡았다). (6) 검증 — go-oidc 는 `SupportedSigningAlgs` 가 비면 discovery 가 광고하는 알고리즘(HS256 포함)을 받으므로 RS/ES/PS 목록을 명시했고, `SkipClientIDCheck` 로 라이브러리 대상 검사를 끄고 직접 한다. nbf 는 go-oidc v3.20 이 5분 여유로 검사한다. typ=ID·cnf·빈 sub 는 직접 거부. 캐시된 provider 가 요청 컨텍스트로 JWKS 를 재요청하다 실패하지 않도록 `oidcProvider` 가 `context.WithoutCancel` 로 만들게 고쳤다(웹 로그인에도 잠재해 있던 문제). OAuth 토큰은 `requireMCPAuth` 의 `authenticateMCP` 에서만 갈라지므로 REST·관리 API 는 그대로다. 꺼져 있을 때 JWT 는 예전과 똑같은 "authentication required" + 옛 `WWW-Authenticate` 를 받는다(새로운 말을 흘리지 않음). 관리 화면 `/admin/security` 에 "MCP SSO (OAuth)" 카드(스위치·리소스 식별자·복사 가능한 MCP 주소·메타데이터 주소·허용 대상·범위, issuer 없으면 스위치 비활성)를 두고, docs/ADMIN_GUIDE.md 3.4(설정 표·Keycloak 공개 클라이언트·Audience 매퍼 표·curl 확인·거부 메시지별 조치·introspection 없음의 한계), docs/mcp.md "키 없이 SSO로 연결", docs/keycloak.md·docs/api.md 를 갱신하고 공용 `tools/guide/md2pdf.mjs` 로 ADMIN_GUIDE.pdf(23쪽)를 다시 구웠다. 검증: `gofmt -l`, `go vet ./cmd/... ./internal/... ./migrations/...`, `go build ./...`, `go test ./...` 전체, `go test -race ./internal/api/`, docker `postgres:16-alpine` 으로 `internal/api` PG 테스트 전체 통과(새 Go 테스트 9 + PG 6 — 가짜 IdP 가 실제 RSA 키로 JWT 를 서명하고 discovery·JWKS 를 서빙: 꺼짐 상태 불변·issuer 필요·메타데이터 두 경로·401 헤더는 MCP 에서만·다른 앱 토큰/만료/nbf/다른 issuer/위조 issuer/HS256/ID 토큰/cnf/빈 sub 거부·등록 계정으로 tools/list(azp 목록·aud 리소스·웹 client azp 세 경로)·범위 밖 tool 거부·미등록/비활성 거부와 users 불변·키 불변·REST 거부·관리 API 저장 왕복), `npm run lint`, `tsc -b`, web 테스트 246개(새 5개), `make web-build`(오프라인 번들 검사 포함), `scripts/check-release-contract.sh` 통과. 실제 바이너리 smoke 는 이 호스트의 :8080 을 다른 프로젝트의 smoke 프로세스가 쓰고 있고 listen 주소가 고정이라 돌리지 못했다 — PG 테스트가 실제 라우터를 끝에서 끝까지 돌리므로 그것으로 갈음했다. 실제 Keycloak·실제 MCP 클라이언트로의 확인은 배포 뒤 관리자 가이드의 curl 절차로 남긴다. 관리 화면 캡처는 캡처 도구가 파괴적이라 찍지 않았다.
