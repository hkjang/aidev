## 2026-10-04
- 선택: 메일 본문을 8BITMIME 협상 없이 생 8비트로 보내는 것을 quoted-printable 7비트 인코딩으로 바꾼다 (가치 3 / 위험 2 / 작업량 S)
- 결과: 성공
- 요약: `internal/mail/mail.go:compose`가 `Content-Transfer-Encoding: 8bit` 헤더와 함께 `normalizeBody`의 생 UTF-8 본문을 그대로 DATA로 썼지만, `Deliver`도 `startSession`도 `client.Extension("8BITMIME")`을 보지 않는다(`startSession`은 STARTTLS와 AUTH 두 확장만 본다 — 읽어서 확인했다). RFC 6152는 서버가 8BITMIME를 광고했을 때만 8비트 본문을 허용하므로, 패키지 주석이 전제한 7비트 전용 사내 릴레이에서는 한글 본문이 거부되거나 깨져 도착할 수 있었다. 본문을 `mime/quotedprintable.NewWriter`로 인코딩해 **한 경로로 언제나 7비트**를 보내게 했다(프로덕션 파일 1개 + 테스트 1개, 새 의존성 없음). 광고 여부로 분기하지 않았고 `MAIL FROM`에 `BODY=8BITMIME`도 붙이지 않았다 — 8BITMIME 릴레이도 QP를 받으므로 경로를 둘로 만들어 얻는 것이 없다. 이것은 결함 재현이 아니라 규약 위반 제거 + 상호운용성 확보이고(실제 7비트 전용 릴레이가 없어 거부·깨짐은 재현하지 않았다) 그 구분을 커밋 메시지에 그대로 적었다. 검증은 기존 `fakeRelay`(실제 `net.Listen` + 실제 SMTP 대화 + 실제 `smtp.Client`)로만 했다 — 손으로 만든 대역 객체나 소스 문자열 검사는 쓰지 않았다. 릴레이에 `noEightBit` 필드를 더해 EHLO 응답의 광고를 끌 수 있게 했고, 필드가 serve goroutine보다 먼저 확정되도록 `startRelayAs`로 릴레이를 통째로 받게 해 경합을 피했다(`-race` 통과로 확인). 새 테스트는 수신 바이트가 전부 < 0x80인 것, 헤더 두 줄(`quoted-printable` 전환 + `charset=UTF-8` 유지), QP 줄이 76자를 넘지 않고 소프트 줄바꿈(`=` + CRLF)으로 접히는 것, 점을 떼고 `quotedprintable.NewReader`로 되돌리면 `normalizeBody(원문)`과 **바이트 단위로 같은** 것, `MAIL FROM`에 `BODY=`가 없는 것을 단언한다. 기존 254행 단언은 약화시키지 않고 "수신 바이트에 `\r\n..`은 있고 `\r\n...`은 없으며, 점을 떼고 QP를 되돌리면 `.점으로 시작하는 줄`이 그대로 있다"로 강화했다(`Subject: =?utf-8?q?`·`From: =?utf-8?q?` 단언은 손대지 않고 그대로 통과한다). 검증: `gofmt -l .` 무출력, `go vet ./...`, `go build ./...`, `go test -count=1 ./internal/mail`(**8.640s** — 정찰 base 실측과 동일), `go test -count=1 ./...` 전부 ok, `go test -count=1 -race ./...` 전부 ok(mail 9.666s), 임시 `postgres:16-alpine`로 `make test-integration`(store 4.445s / api 1.000s), `./scripts/check-version.sh` 1.8.7, `git diff --check` 무출력. 임시 컨테이너와 프로브 테스트 파일은 제거했다.
