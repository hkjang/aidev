# v0.319.0 — 첨부 순서를 읽지 못한 업로드가 이미지를 저장하지 않습니다

이 릴리즈는 보고서에 화면 캡처를 첨부하는 작성자를 위한 오류 처리 개선입니다. 다음 순서를 조회하지 못해도 **0번 이미지로 저장하고 성공을 답하던** 결함을 고칩니다. 프로덕션 변경은 `internal/app/attachments.go` 한 파일이며, 마이그레이션·새 환경변수·설정 변경은 없습니다.

## 순서를 읽지 못했는데 저장은 성공했습니다

`uploadAttachments` 는 같은 보고서·삽입 위치 안의 `coalesce(max(sort_order),-1)+1` 을 읽습니다. 그런데 그 `Scan` 오류를 버려, 조회가 실패해도 `nextOrder` 의 초기값 0으로 저장을 계속했습니다.

공개 PATCH 로 기존 첨부의 `sortOrder` 를 PostgreSQL 정수 상한인 `2147483647` 로 바꾸면 다음 업로드에서 `max+1` 이 넘칩니다. 고치기 전에는 이때도 `201` 과 `sortOrder: 0` 을 반환하고 새 행과 파일을 남겼습니다. 기존 0번 첨부와 순서가 겹치고, 순서를 복구한 뒤 같은 이미지를 다시 올리면 두 벌이 됐습니다.

이제 순서 조회가 실패하면 트랜잭션을 시작하거나 이미지 파일을 쓰기 전에 중단합니다.

- HTTP 상태: `500`
- 오류 코드: `QUERY_FAILED`
- 안내: `첨부 이미지의 순서를 조회할 수 없습니다.`

거절된 업로드는 기존 첨부와 파일을 보존합니다. 조회가 정상인 업로드는 기존과 같이 `201` 을 반환하고, BEFORE/AFTER 각 그룹의 끝 번호를 받습니다.

## 검증

구현 단계에서 `internal/app/attachmentuploadorder_test.go` 의 새 시험 두 개를 실제 PostgreSQL 과 `newTestServer`/`App.Handler()` 로 실행했습니다. 오류 경로 시험은 수정 전 `answered 201, want 500` 으로 실패했고, 수정 후 통과했으며, 원본 코드를 복원하면 같은 실패가 다시 나는 것을 확인했습니다. 정상 그룹 회귀 시험은 수정 전에도 통과했습니다.

- 거절 전후 목록 ID·순서·건수와 디스크 파일 목록이 같습니다.
- 기존 이미지 GET 은 계속 `200` 이며 응답 바이트가 보존됩니다.
- 공개 PATCH 로 순서를 복구한 뒤 같은 이미지를 재시도하면 한 번만 저장되고 해당 그룹 끝에 배치됩니다.
- BEFORE/AFTER 의 다음 번호를 독립적으로 계산하고 정상 업로드는 `201` 을 반환합니다.

릴리즈 단계에서도 별도 시험용 PostgreSQL DB 에서 `go test ./... -count=1 -json` 을 실행해 전체를 통과했습니다(`internal/app` 178.567초). 참조 파일이 없는 `TestSuppliedReferencePPTXRendering` 한 개는 SKIP 이며, DB 접속 부재로 건너뛴 시험은 없습니다. `go vet ./...`·`go build ./...`·변경 Go 파일의 `gofmt`, 변경 관련 가드 14개, 버전·OpenAPI 119경로·쪽넘김 10목록·모달 검사, 두 시간대의 프런트엔드 시험 각각 173개, 타입 검사·프로덕션 빌드·`scripts/build.sh` 가 통과했습니다. 백업·검증·복구 왕복 검사도 시험 컨테이너에서 통과했습니다. 로드맵 HTML·PDF 와 두 안내서 HTML 을 기존 스크립트로 다시 만들었습니다.

이전 릴리즈와 같이 제자리 소스 변경을 하는 `mutation-check`·`authz-check` 는 실행하지 않았습니다. `gh` 사용이 금지된 세션이므로 원격 이력을 읽는 advisory `release-check.sh` 는 실행하지 않았고, Docker 설치 검사는 이번 로컬 준비 범위에서 실행하지 않았습니다. Docker 오프라인 자산 생성과 GitHub Release 게시는 기존 태그 워크플로가 담당합니다.

UI 클릭과 새 오류 시나리오의 PPTX 출력, 정수 오버플로 이외의 DB 장애 주입은 별도로 검증하지 않았습니다. 기존 중복 순서의 정리, PATCH 상한 제한, 동시 업로드 직렬화·개수 상한은 이번 변경에 포함되지 않습니다. 이 문제들을 해결한 릴리즈로 사용해서는 안 됩니다.

## 업그레이드

기존과 같이 PostgreSQL 과 상태 볼륨을 백업한 뒤 v0.319.0 이미지를 올립니다. 스키마와 설정 변경이 없어 별도 데이터 변환은 필요하지 않습니다. 이 버전은 순서를 읽지 못하는 원인 자체를 고치지 않으므로, `QUERY_FAILED` 가 나타나면 DB 상태와 해당 그룹의 순서값을 확인한 뒤 재시도합니다.

배포 담당 운영자는 먼저 소규모 대상에서 정상 첨부의 `201`, 목록의 그룹 끝 배치, 기존 이미지 GET 을 확인합니다. 정상 입력 업로드가 실패하거나 기존 이미지의 목록·파일·바이트가 바뀌는 사례가 한 건이라도 확인되면 확대 배포를 중단하고 v0.318.0 이미지로 되돌립니다. 스키마가 같아 데이터 되돌림은 필요하지 않지만, 이전의 오류 무시 결함도 돌아옵니다.

배포 후 첫 24시간에는 운영자가 첨부 관련 문의와 `QUERY_FAILED` 응답을 확인합니다. 성공 기준은 확인한 순서 조회 실패에서 새 행·파일 생성 0건, 원인 복구 후 동일 이미지 재시도에서 단일 저장입니다. 실제 운영 배포와 이 사후 관찰은 이번 로컬 릴리즈 준비에서 수행하지 않았습니다.
