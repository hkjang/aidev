- 결과: 성공
- 요약: 두 게이트는 같은 스캐너(`scanOraclePolicy`)가 만든 같은 토큰 스트림을 읽는데, PostgreSQL 쪽만 `postgresCTEColumnList` 면제를 가지고 있어 `WITH recent (id, total) AS (…) SELECT * FROM recent` 가 Oracle 에서만 `Oracle SELECT의 비허용 함수 호출 recent()` 라는 허위 사유로 blocked 됐다 — 같은 질의에서 컬럼 목록만 빼면 통과하므로 게이트가 자기와 어긋난 상태였다(4b29d08 이 `callAdjacent` 로 닫은 것과 같은 뿌리). `oracleReadOnlyViolations` 에 지연 `postgresTokenIndex` 선언 + 허용목록 검사 앞 면제 `continue` 를 **PostgreSQL 호출부와 같은 위치·같은 모양으로** 넣고, 헬퍼 본문은 한 줄도 바꾸지 않은 채 이름만 `cteColumnList` 로 바꿔 두 게이트가 규칙을 공유하는 것을 드러냈다(선례 4b29d08 의 `postgresCallAdjacent` → `callAdjacent`). **프로덕션 파일 1개(+16/-2줄)**, 테스트 2개. 허용목록(`oraclePureFunctions`·`oracleParenthesisKeywords`·`postgresPureFunctions`)·`scanOraclePolicy`·`callAdjacent`·`fromItemContext`·`postgresAliasColumnList` 의 기존 네 분기는 건드리지 않았고, `postgresAliasColumnList` 전체를 Oracle 로 옮기지 않았다(그 `AS` 분기는 FROM 문맥 없이 무조건 면제해 Oracle 에서 fail-open 이 된다).
  검증: ① 새 단위 테스트 2개(허용 6건·차단 7건) red → 수정 → green. ② `cteColumnList` 를 `return true` 로 고정해 다시 red — 내 차단 테스트뿐 아니라 기존 Oracle·PostgreSQL 차단 테스트 9건이 함께 깨져 좁히는 조건들이 양 방언에서 모두 하중을 받는 것을 확인 → 복원. ③ **프로덕션 배선**으로도 red→green: 실제 `dbexec.Connection{Dialect: Oracle, AllowedSchemas: []string{"REPORTING"}}` 로 `analyzeExecutionPolicy`(MCP·runtimeapi·legacyapi 가 모두 지나는 단일 게이트)를 호출해 base 에서 실패·수정본에서 통과, 팩토링 서브쿼리 **안의** 실제 호출(`WITH recent (id) AS (SELECT side_effect_fn(id) …)`)은 계속 `ErrUnsafeStatement` 임을 같은 테스트에 고정. 손으로 만든 대역 없이 실제 타입만 썼다. ④ 차별 스윕: 현실 질의 78건 × postgres·oracle = **156 판정**을 base `814482a` 의 sqlsafe.go 와 수정본에서 각각 덤프해 기계적으로 비교 — **PostgreSQL 78행 전부 바이트 단위 동일(diff 0)**, **내 변경으로 새로 막히는 질의 0건**, Oracle 오탐 12건 제거, 차단 유지 66행; `WITH a (x) AS (SELECT side_effect_fn(1) FROM dual)` 은 허위 `a()` 사유만 사라지고 진짜 `side_effect_fn()` 사유로 계속 blocked. ⑤ `AnalyzeDialect` 임시 fuzz 4,889만 exec(oracle+postgres 동시), 패닉 없음. ⑥ 폐기 PostgreSQL 17(도커 127.0.0.1:55517 — 과거 점유 포트 회피) bootstrap(fresh-install → migrations) 후 `go test -race -p=1 -tags=integration ./... -count=1` **2회 연속 30 패키지 전부 ok**, 컨테이너 제거. ⑦ `go test ./... -count=1` 28 ok exit 0, `go vet ./...`, `go vet -tags=integration ./...`, `make check-go-format`, `gofmt -l cmd internal migrations scripts`(무출력), `go build ./...` 통과. 커밋 3bf8799.
  **과제서와 어긋난 판정 하나(측정으로 교정)**: 수용 기준 3 은 인용 식별자 `"A" (x) AS (…)` 를 "차단 유지" 로 적었으나, base 에서 실측하면 **PostgreSQL 이 이미 이것을 ro=true/low 로 통과시킨다**. `WITH` 는 그 자리에 질의 이름만 허용하므로 인용 여부와 무관하게 호출이 될 수 없고, Oracle 만 차단하면 이 과제가 고치려는 바로 그 비대칭이 남는다. 그래서 PostgreSQL 호출부와 같은 위치(인용 검사 **앞**)에 면제를 두어 두 방언이 같은 입력을 같은 값으로 읽게 하고, 그 근거를 테스트 주석과 커밋 메시지에 남겼다.
  **검증 못 한 것(정직하게)**: 실 Oracle 데이터베이스에 붙이지 못했다 — 이 환경에 Oracle 인스턴스가 없다. Oracle 증명은 전부 게이트 판정 수준(sqlsafe + dbexec 정책)이고, 수정이 질의를 *통과*시키는 방향이므로 Oracle 서버가 최종 문법 심판이다(2026-10-02 회차와 동일한 한계). 릴리즈 워크플로의 Oracle 실서비스 단계도 돌리지 못했다. 또 **내 변경이 Oracle 최악 경로의 상수를 약 8.5배 올린다**: `cteColumnList` 의 역방향 WITH 추적 루프만 메모되지 않아 `SELECT f0 (x) AS a0, f1 (x) AS a1, …` 모양이 quadratic 인데(측정: 330KB 질의가 base postgres 2.07s / base oracle 0.24s / 수정본 oracle 2.07s), 이는 **PostgreSQL 에 선재하며 내 변경으로 PostgreSQL 은 전혀 달라지지 않았다**(timing·판정 모두 동일) — Oracle 이 PostgreSQL 과 같은 비용으로 올라온 것이다. 새 결함 범주가 아니라 선재 결함의 방언 파리티이므로 이번 범위에서 빼고 아래 보류 아이디어로 수치와 함께 올렸다.
