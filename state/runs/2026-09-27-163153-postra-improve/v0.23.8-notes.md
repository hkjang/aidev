# Postra v0.23.8 — 응답을 끝내지 않는 POP3 서버가 수집 작업을 붙잡던 문제 수정

POP3 다중행 응답(`LIST`, `UIDL`)이 한 번에 모을 수 있는 양에 상한을 적용하는 패치 릴리즈입니다. 줄 하나하나는 짧지만 응답을 끝내는 `.` 을 끝내 보내지 않는 서버가 계정 동기화를 영원히 붙잡아 두던 문제를 고쳤습니다. IMAP 쪽의 같은 결함은 v0.23.7에서 닫았고 POP3만 남아 있었습니다. 새 설정 키, DB 마이그레이션, 새 필수 환경변수는 없습니다.

## 줄은 짧은데 응답이 끝나지 않던 문제

- `readList`는 서버가 종결자 `.` 을 보낼 때까지 줄을 모으는데, 몇 **개**까지 모을 수 있는지는 아무것도 제한하지 않았습니다(`internal/adapters/pop3/client.go`). 게다가 `s.deadline()` 이 루프 **안** 에 있어 줄을 읽을 때마다 명령 데드라인을 다시 밀어냅니다. 그래서 짧은 줄만 계속 흘리고 종결자를 보내지 않는 서버에 대해서는 **60초 명령 데드라인조차 루프를 끝내지 못합니다.** 데드라인이 결국 구해 주지 못하는 것이 v0.23.7과 똑같은 이 결함의 핵심입니다.
- 위치는 IMAP보다 나쁩니다. `readList`는 열거 단계에서 불립니다(`internal/application/sync.go`의 `UIDL`, 이어서 크기를 합치는 `List`). 첫 메시지를 만지기도 전이므로, 그런 maildrop 하나가 해당 계정의 동기화를 통째로 멈춰 세우고 수집 워커를 점유합니다.
- 수정 전 코드에서 실제 `net.Listen` 서버로 재현했습니다. 종결자를 보내지 않는 서버에 대해 열거 한 번이 테스트 바이너리 자체의 타임아웃까지 매달렸습니다: `panic: test timed out after 1m30s`. 90초는 60초 명령 데드라인을 넘긴 시간이므로 "데드라인이 끝내 주지 못한다"가 그대로 증명됩니다. 스택은 `poll.setDeadlineImpl → pop3.(*session).deadline → readList → UIDL`, 즉 루프 안에서 데드라인을 계속 새로 미는 그 줄입니다. 빈 줄만 보내는 변종도 같은 모양으로 1분 10초까지 매달렸습니다.
- 계정의 접속 호스트는 계정 소유자가 고르는 값이므로 이 입력은 신뢰할 수 없습니다.

- `readList`가 이제 이번 응답의 비용을 세고, 상한을 넘으면 `s.conn.Close()`로 세션을 폐기한 뒤 `pop3 multi-line response exceeds %d bytes`를 돌려줍니다. 응답의 나머지가 알 수 없는 오프셋으로 소켓에 그대로 남아 있어 다음 명령이 그 바이트를 자기 응답으로 오해할 수 있으므로, 이 명령 하나만 실패시키지 않고 세션을 버립니다.
  - `maxListBytes`(32 MiB): 한 다중행 응답이 모으는 줄의 총량. 한 maildrop 전체가 응답 **하나**로 오기 때문에 상한은 가장 큰 정상 maildrop을 통과시켜야 합니다.
  - `listLineOverhead`(CRLF 2바이트 + 문자열 헤더 16바이트): 줄마다 `len(line)`에 더해 함께 청구합니다. 줄은 CRLF가 이미 벗겨진 채 도착하므로 `"\r\n"` 하나는 `len(line) == 0`으로 측정됩니다. 빈 줄만 보내는 서버에 대해 `len(line)`만 세면 합계가 전혀 늘지 않아 같은 무한 루프가 그대로 남습니다. IMAP 어댑터가 v0.23.7에서 `responseLineOverhead`로 막은 것과 정확히 같은 우회입니다. 보관된 줄이 차지하는 16바이트 문자열 헤더까지 함께 청구하므로 최악의 경우 상주 메모리도 대략 상한 수준으로 묶입니다.
- 32 MiB는 추정이 아니라 실측으로 정했습니다. RFC 1939 §7이 허용하는 최대 길이(70자) unique-id로 5000건짜리 `UIDL` 응답을 만들면 전선 위 383,893바이트, 과금 기준 **463,893바이트 = 메시지당 92바이트**입니다. 따라서 32 MiB는 한 maildrop에 **364,722건**까지 받아들입니다. IMAP의 8 MiB를 그대로 베끼면 9만 1천 건짜리 정상 maildrop이 거부됩니다.
- 본문(`RETR`)을 읽는 `retrBody`는 손대지 않았습니다. 본문은 이 경로로 모이지 않으며 크기 상한은 이전과 같이 `sync.max_message_bytes`가 결정합니다.

## 검증

- 이 패키지의 **첫 테스트 파일**입니다(이전에는 `[no test files]`). 손으로 만든 대역 없이 `net.Listen("tcp", "127.0.0.1:0")` 스크립트 서버를 실제 `pop3.Dialer{}.Dial`로 물려 3건을 추가했습니다: 종결되지 않는 응답이 0.70초에 상한 오류로 실패하고 같은 세션의 `List`·`Retrieve`도 이어서 실패하는 것, 가장 값싼 줄인 **빈 줄**만 무한히 보내는 서버도 1.38초에 같은 상한에 걸리는 것(오버헤드가 없으면 0바이트로 우회됨), 5000건짜리 정상 `UIDL`/`LIST` maildrop이 전수 일치하며 상한에 8배 이상의 여유를 남기는 것.
- 상한값은 정상 경로 테스트가 `t.Logf`로 실측값을 남기고 경계값을 단언합니다: `a 5000-message UIDL response is 383893 bytes on the wire, charged 463893 against the 33554432-byte bound (92 per message, so the bound admits 364722 messages)`. 여유 단언이 실제로 청구되는 값 위에서 측정되므로 오버헤드를 올려 여유를 몰래 잡아먹을 수 없습니다.
- 변이 검증: 상한 검사를 죽이면 새 endless 테스트만 타임아웃으로 실패하고 정상 경로 테스트는 통과(ok 1.079s)함을 확인한 뒤 원복했습니다.
- `go test -race -count=3 ./internal/adapters/pop3/`(ok 7.550s), 전체 `go test -race -count=1 ./...`(실패 0), `go build ./...`, `go vet ./...`
- `make lint`: `gofmt` 빈 출력 + CI와 같은 플래그의 `gosec v2.28.0` Issues 0(Files 138)
- 계약 검사(`postra-contracts -check`, exit 0), `git diff --check`
- 프런트엔드 소스 변경이 없어 포함된 `/app` 번들은 v0.23.7과 동일합니다.

테스트는 로컬 루프백 서버만 사용하며 운영 메일 서버나 운영 데이터에 접근하지 않습니다. 실제 POP3 서버에서의 동작과 외부 PostgreSQL, 32비트 빌드는 이번에 검증하지 않았습니다.

## 업그레이드 및 호환성 주의사항

DB 마이그레이션, 새 설정 키, 새 필수 환경변수는 없습니다. DB·SecretStore·ObjectStore·KEK를 백업하고 유지한 상태에서 실행 파일 또는 컨테이너 이미지를 교체한 뒤 재시작하세요.

- 정상적인 메일 수집 동작과 결과는 달라지지 않습니다. 한 `LIST`/`UIDL` 응답이 32 MiB가 넘는 줄을 모으는 서버에서만 동작이 바뀌며, 그 경우 세션이 닫히고 해당 계정의 그 회차 동기화가 실패로 집계된 뒤 다음 회차에서 새 세션으로 다시 시도합니다.
- 메일함이 아주 큰 계정도 영향받지 않습니다. 최대 길이 unique-id 기준 실측이 메시지당 92바이트이므로 한 maildrop에 36만 건까지 상한 아래입니다.
- 메일 본문 크기와는 무관합니다. 본문은 `RETR`의 별도 경로로 오며 이 상한이 세지 않습니다. 본문 상한은 이전과 같이 `sync.max_message_bytes`가 결정하며, 0 이하로 끈 계정은 크기 제한 없이 본문을 계속 받습니다.
- IMAP 경로의 상한(`maxLineBytes` 1 MiB, `maxResponseBytes` 8 MiB, `maxResponseLiterals` 64)·거부 임계값·드레인 예산·설정 키는 v0.23.7 그대로이며 SMTP 경로, MCP·OAuth·API Key 동작도 같습니다. [v0.23.7 릴리즈 내용](v0.23.7.md)을 참고하세요.
