Invenqor Server·Agent v0.2.8 릴리즈 노트

릴리즈 일자: 2026-07-30 호환 Agent: v0.2.8 (v0.2.7 Agent도 그대로 동작합니다)

이번 릴리즈는 그동안 고도화하지 않았던 콘솔 화면 — 감사 로그, Server 진단 로그, 자산 인벤토리, Query DSL, API·MCP 키, 내 계정 보안, 운영 통계, 시스템 정보 — 의 결함을 찾아 고치고 사용성을 올렸습니다. Agent 동작 변경은 없습니다.

1. 모든 시각이 조용히 틀렸습니다

가장 넓게 퍼져 있던 결함입니다. SQLite 대체 모드에서 Server가 "2026-07-29 19:17:12" — 시간대 표시가 없는 UTC — 를 반환했고, 브라우저는 이를 현지 시각으로 읽었습니다. 한국에서는 감사 로그, 로그인 시각, 키 회전 시각, 사용자 생성 시각이 모두 9시간 밀려 표시되었습니다. 값이 있으니 화면은 정상으로 보이고, PostgreSQL로 확인하면 재현되지 않습니다.

일부 행은 Go의 time.Time.String() 형식("… +0000 UTC")이었습니다. 이 형식은 브라우저가 파싱을 보장하지 않으므로, 어떤 브라우저에서는 값이 그대로 노출되고 어떤 브라우저에서는 Intl.DateTimeFormat이 예외를 던져 화면 전체가 오류 화면으로 떨어질 수 있었습니다. 방어 코드는 세 곳의 날짜 포맷터 중 한 곳에만 있었습니다.

  • 스캔에서 JSON까지 시각을 운반하는 단일 타입(apitime.Time)을 도입해 드라이버가 무엇을 주더라도 UTC 오프셋을 포함한 RFC 3339로 나갑니다. 응답 구조체가 이 타입을 선언하므로 새 엔드포인트가 실수로 되돌릴 수 없습니다.
  • 실제 응답 13종을 순회해 *_at 필드가 모두 RFC 3339인지 확인하는 테스트를 추가했습니다. 손으로 map을 만드는 새 핸들러가 문제를 되살리는 경로까지 막습니다.
  • 콘솔 날짜 포맷터를 한 곳으로 모으고 읽을 수 없는 값에서도 예외를 던지지 않게 했습니다. “3분 전”처럼 최신성을 직접 답하는 표기를 추가했습니다.

2. 감사 로그가 이미 내려받은 행만 검색했습니다

검색과 필터가 브라우저에서 동작해 최근 수백 건만 대상이었습니다. 지난주의 삭제를 검색하면 결과가 없고, 그것이 “그런 기록이 없다” 로 읽혔습니다. 책임성 도구가 낼 수 있는 가장 나쁜 답입니다. 오래된 이벤트로 이동할 방법도 없었습니다(상한 500건, 페이징 없음).

  • 검색어·행위·행위자·자원·결과·기간을 질의에서 처리합니다. 기간은 운영자가 실제로 입력하는 YYYY-MM-DD를 받고 종료일은 그날 전체를 포함합니다.
  • 조건에 일치하는 총 건수와 페이징을 제공합니다.
  • 행위·자원·결과 선택 목록은 이 설치에 실제로 기록된 값에서 만듭니다.
  • CSV 내려받기: 감사 추출은 보통 콘솔 밖에서 증적으로 쓰이고, 화면에서 손으로 옮기는 것이 증적이 잘못 베껴지는 경로입니다. UTF-8 BOM을 포함해 스프레드시트에서 바로 열리며, 추출 자체도 audit.export로 감사 기록됩니다.
  • 감사 항목에서 같은 request ID의 Server 진단 로그로 이동할 수 있습니다.
  • 만족할 수 없는 기간 조건은 빈 페이지가 아니라 400으로 거부합니다.

3. 내 계정 보안

  • 현재 상태를 몰랐습니다. MFA가 켜져 있는지 화면에서 알 수 없어 “TOTP 설정 시작”과 “TOTP 비활성화”를 동시에 제공했습니다. /api/v1/auth/me가 이제 계정의 보호 상태를 보고하고, 화면은 해당하는 동작만 제공합니다.
  • Keycloak 계정에 비밀번호 양식을 보여줬고, 그 시도는 HTTP 500이었습니다. 외부 인증 계정은 password_hash가 NULL이라 스캔이 실패했습니다. 이제 PASSWORD_NOT_LOCAL로 구분하고, 화면은 양식 대신 Keycloak에서 관리한다는 안내를 표시합니다.
  • 틀린 TOTP 코드가 로그인 실패로 계산되지 않았습니다. 잠금 카운터와 IP 속도 제한이 모두 이 시도를 보지 못해, 비밀번호를 아는 공격자가 2차 코드를 무제한 추측할 수 있었습니다(같은 입력에서 복구 코드도 받습니다). 이제 실패로 기록되어 계정 잠금과 IP 제한이 함께 적용됩니다.
  • 복구 코드로 MFA를 활성화할 수 있었습니다. 활성화는 Authenticator가 동작함을 증명해야 하는 단계인데 복구 코드를 받아들여, 앱을 등록하지 않은 채 MFA가 켜지고 사용한 코드도 소비되지 않았습니다. 이제 Authenticator 코드만 인정합니다.
  • QR 코드로 등록합니다. 그동안은 otpauth:// URI를 눈으로 읽어 입력해야 했습니다. 카메라를 쓸 수 없으면 Secret과 URI를 직접 입력할 수 있습니다.
  • 복구 코드를 모두 복사·파일로 저장할 수 있고, 남은 개수를 표시하며 2개 이하면 경고합니다. 재발급은 Authenticator 코드를 요구합니다(복구 코드로는 불가 — 유출된 코드 하나로 계속 새 코드를 만들 수 없어야 합니다).

4. 진단 로그·자산·Query DSL·키

  • 구성요소 필터가 콘솔에 손으로 적혀 있었습니다. Server가 기록하는 agent_preflight와 keycloak을 고를 수 없었습니다. 목록을 Server가 제공하고 조건 일치 건수가 표시 건수보다 많으면 잘렸다는 사실을 알립니다.
  • 자산 인벤토리에 환경·중요도·담당 부서 필터와 정렬을 추가했습니다. 분류가 판정하는 값으로 좁힐 수 없어 “운영 환경의 치명 자산”을 Query DSL로 물어야 했습니다. 총 건수와 표시 구간을 함께 보여주고 CSV로 내려받습니다.
  • Query DSL이 사용 가능한 필드와 연산자를 표시합니다. 그동안은 필드 이름을 추측하고 거부 메시지를 읽어 다시 추측해야 했습니다. 목록은 파서의 허용 목록에서 발행되므로 화면에 있는 필드가 거부되지 않습니다. 자주 쓰는 질의도 제공합니다.
  • API·MCP 키가 7일 내 만료를 경고하고, 한 번도 쓰이지 않은 키를 표시하며, 폐기된 키는 기본으로 숨깁니다. 만료된 키는 연계 시스템에서 401로 나타나므로 경고는 그 전에 이 화면에 있어야 합니다.
  • 실행 정보가 실제 수신 주소를 표시합니다. 설정과 무관하게 7070을 적어 두었습니다.

5. 화면 결함

  • 액션 버튼이 없는 화면의 제목이 한 줄로 누웠습니다. 제목 블록이 첫 번째이면서 마지막 자식이 되어 버튼 정렬 규칙에 걸렸습니다(Query DSL 화면).
  • 차트 색이 색각 검증에 실패했습니다. 두 색이 채도 하한 미달로 회색으로 읽히고, 모든 구성 비중 패널이 시작하는 첫 두 색이 정상 시야에서 ΔE 14.5였습니다. 시각화 화면에서 검증한 8색 팔레트를 콘솔 전체로 올렸습니다.
  • 구성 비중 패널이 상위 7개만 표시하고 나머지를 조용히 버렸습니다. 보이는 비율이 100%가 되지 않는데 이유가 어디에도 없었습니다. 나머지는 기타 N종으로 합칩니다.
  • 다크 모드에서 알림 문구가 배경과 2.2:1이었습니다(측정값). 7.9:1로 교체했습니다.
  • 사용할 수 없는 페이지 이동 버튼이 활성 버튼과 똑같이 보였습니다.
  • 운영 통계가 자산이 없을 때 최신성 100% 를 표시해, 비어 있는 시스템이 건강한 시스템으로 읽혔습니다. 분모가 없으면 —로 표시합니다.
  • 화면 간 이동 링크(#/logs?request_id=…)가 동작하지 않았습니다. 경로 파서가 질의 문자열을 페이지 이름의 일부로 읽었습니다.

호환성

  • 데이터베이스 마이그레이션이 없습니다.
  • API 시각 형식이 바뀝니다. SQLite 대체 모드에서 "2026-07-29 19:17:12" 또는 "… +0000 UTC"를 받던 응답이 이제 RFC 3339("2026-07-29T19:17:12Z")를 반환합니다. PostgreSQL 응답은 그대로입니다. 이 값을 파싱하는 연계 시스템이 있다면 확인하십시오 — 대부분의 파서에서는 오히려 정상화입니다.
  • GET /api/v1/admin/audit이 total·has_more·facets를 추가로 반환하고 필터 파라미터를 받습니다. 기존 limit만 사용하는 호출은 그대로 동작합니다.
  • 추가된 엔드포인트: GET /api/v1/assets.csv, GET /api/v1/admin/audit.csv, GET /api/v1/query/schema, POST /api/v1/auth/totp/recovery-codes.
  • GET /api/v1/system/info에 listen_address가 추가됩니다.
  • 로그인 시 TOTP 코드를 틀리면 이제 계정 잠금 카운터가 올라갑니다. 자동화가 잘못된 코드를 반복 전송하고 있다면 계정이 잠길 수 있습니다.
