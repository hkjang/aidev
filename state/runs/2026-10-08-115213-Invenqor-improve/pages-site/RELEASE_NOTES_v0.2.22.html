Invenqor Server·Agent v0.2.22 릴리즈 노트

릴리즈 일자: 2026-09-03 호환 Agent: v0.2.22 (Linux·Windows)

이번 릴리즈는 결함 하나를 고칩니다. 자리는 v0.2.20·v0.2.21과 같은 자산 질의 DSL이고, 이번에는 틀린 답이 저장 모드마다 달랐습니다 — 같은 질의가 PostgreSQL에서는 HTTP 500으로 끝나고 SQLite fallback에서는 빈 목록으로 돌아왔습니다.

1. id 절이 호출자가 쓴 값을 그대로 데이터베이스에 넘겼습니다

assets 테이블의 id 컬럼은 UUID입니다. 그런데 id를 지목한 절은 값을 쓰인 그대로 파라미터로 실었습니다.

PostgreSQL은 그 파라미터를 uuid로 읽으므로 id = "web-01"은 절 하나가 아니라 문장 전체를 실패시켰고, 운영자에게는 읽지 못한 값이 무엇인지 이름조차 없는 HTTP 500이 돌아왔습니다. SQLite fallback은 같은 값을 텍스트로 비교해 HTTP 200에 빈 목록 — 마치 그런 자산이 없는 것처럼 — 을 돌려줬습니다. 그리고 어느 쪽이든 /query/validate는 그 식을 이미 “유효하다”고 답한 뒤였습니다.

두 모드는 철자만 다른 UUID에 대해서도 서로 다른 답을 했습니다. PostgreSQL은 대문자로 쓰였거나 하이픈이 빠진 UUID를 같은 값으로 읽지만, fallback의 텍스트 비교는 그러지 않습니다. 그래서 식별자를 대문자로 출력하는 보고서에서 복사해 온 운영자는 운영 환경에서는 자산을 찾고 fallback에서는 아무것도 찾지 못했습니다.

id 절은 이제 어느 저장 모드가 보기 전에 해석됩니다. UUID가 아닌 값은 400 INVALID_QUERY로 거절되며, 오류 메시지가 읽지 못한 값과 올바른 형태의 예를 함께 이름합니다. UUID인 값은 모든 자산이 저장돼 있는 표준 표기로 접혀 두 모드가 같은 자산을 가리킵니다. /query/validate도 같은 답을 하므로, 콘솔이 “쓸 수 있는 식”이라고 알린 뒤 실행에서 실패하는 일이 없습니다.

콘솔이 렌더링하는 문법 참조에서 id의 타입은 text가 아니라 uuid로 적히고, 대소문자와 하이픈 표기를 구분하지 않는다는 사실이 함께 적혔습니다. 예시도 0d0f… 같은 생략형이 아니라 완전한 UUID로 바뀌었습니다 — 생략형은 이제 거절되는 값이기 때문입니다.

검증

  • 컴파일 수준. UUID가 아닌 id 값이 SQL로 컴파일되지 않고 값을 이름하는 오류가 되는지, 그리고 대문자·하이픈 없는 표기가 표준 표기로 접혀 실리는지를 두 저장 모드 모두에서 고정했습니다.
  • HTTP 경로까지. /query/execute가 web-01, 0d0f, host:web-01에 대해 값을 담은 INVALID_QUERY 400을 돌려주는 것과, /query/validate가 같은 판정을 내리는 것을 엔드포인트 너머에서 확인합니다. 또 자산 하나를 만든 뒤 원래 표기· 대문자 표기·하이픈 없는 표기 세 가지로 질의해 모두 같은 한 건이 돌아오는 것을 확인합니다. 결함의 증상이 저장 모드마다 달랐으므로 이 테스트는 SQLite fallback과 CI의 PostgreSQL 잡에서 모두 돕니다.

호환성

  • 데이터베이스 마이그레이션이 없습니다.
  • API 응답 형식 변경이 없습니다.
  • id 절에 UUID가 아닌 값을 쓰던 질의의 응답이 달라집니다 — 이전의 PostgreSQL HTTP 500과 fallback의 빈 목록 대신, 이제 값을 이름하는 400 INVALID_QUERY가 돌아옵니다. 어느 쪽도 자산을 돌려준 적은 없으므로 조회 결과가 줄어들지는 않습니다.
  • SQLite fallback에서 대문자로 쓰였거나 하이픈이 빠진 UUID가 이제 자산을 찾습니다. PostgreSQL의 결과는 종전과 같습니다.
