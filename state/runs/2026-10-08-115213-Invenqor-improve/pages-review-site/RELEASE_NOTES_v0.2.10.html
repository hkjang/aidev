Invenqor Server·Agent v0.2.10 릴리즈 노트

릴리즈 일자: 2026-07-30 호환 Agent: v0.2.10 (Linux·Windows)

Windows용 Agent를 추가합니다. Linux판과 같은 수집 스키마·자산 키·등록 절차· 서명 업데이트를 사용하므로, 혼재 환경에서 Server 설정을 나누거나 분류 규칙을 따로 만들 필요가 없습니다.

1. 배포와 설치

invenqor-agent-windows-x86_64.zip — 정적 링크 단일 실행 파일이며 .NET이나 VC++ 재배포 패키지가 필요하지 않습니다. 대상은 Windows 10/11과 Windows Server 2016 이상, x86_64입니다.

# 관리자 PowerShell, 압축을 푼 디렉터리에서
.\scripts\install.ps1
notepad "$env:ProgramData\Invenqor\config.toml"   # [server] url 설정
Restart-Service invenqor-agent
& "$env:ProgramFiles\Invenqor\invenqor-agent.exe" `
  --config "$env:ProgramData\Invenqor\config.toml" --diagnose
경로 내용
%ProgramFiles%\Invenqor\invenqor-agent.exe 서비스 실행 파일
%ProgramData%\Invenqor\config.toml 설정
%ProgramData%\Invenqor\state\ 식별자, 인벤토리 해시, 미전송 큐
  • install.ps1은 멱등입니다. 다시 실행하면 바이너리만 교체하고 설정과 미전송 큐를 유지하며 권한을 복구합니다. 구성 관리 도구에서 반복 실행해도 안전합니다.
  • 두 디렉터리를 icacls로 SYSTEM과 Administrators로 제한합니다. 상태 디렉터리에는 장비 자격 증명이 있고 설정 파일에는 등록 Token이 들어갈 수 있습니다. --diagnose가 이 조건을 점검해, 일반 사용자가 읽을 수 있으면 실패로 보고합니다. Linux에서는 “서비스가 읽을 수 있는가”가 문제이고 Windows에서는 그 반대 — LocalSystem은 언제나 읽을 수 있으므로 위험은 다른 사람도 읽을 수 있다는 것 입니다.
  • 서비스는 LocalSystem으로 지연 자동 시작합니다. 첫 수집이 부팅 임계 경로에서 다른 모든 것과 경쟁하지 않게 합니다. 수신 포트는 열지 않습니다.
  • 골든 이미지를 만들 때는 -NoStart로 설치하고 이미지화 전에 %ProgramData%\Invenqor\state를 삭제하십시오. 남겨 두면 모든 복제 호스트가 같은 agent-id를 사용합니다.

LocalSystem을 쓰는 이유는 권한 확대가 아니라 수집 범위입니다. Service Control Manager 열람, 모든 로드된 사용자 하이브의 설치 소프트웨어, 어댑터 구성은 하위 권한 계정에서 읽을 수 없습니다.

2. 자동 업데이트

Windows는 실행 중인 실행 파일을 덮어쓰거나 삭제할 수 없습니다. 하지만 이름을 바꿀 수는 있고, 이동된 파일에서 실행이 계속됩니다. 이것이 Windows 자동 업데이트가 성립하는 유일한 순서입니다.

  1. 서명·SHA-256·크기·플랫폼을 검증하고 스테이징합니다.
  2. 새 바이너리를 설치 볼륨에 씁니다. 스테이징 디렉터리(%ProgramData%)와 설치 경로(%ProgramFiles%)가 같은 볼륨이라는 보장이 없으므로, 이름 변경이 한 볼륨 안에서 일어나도록 대상 옆에 씁니다.
  3. 새 바이너리를 실행해 --version이 약속한 버전을 보고하는지 확인합니다. 실패하면 폐기하고 실행 중인 바이너리를 그대로 둡니다.
  4. 기존 바이너리를 invenqor-agent.exe.previous로 옮기고 새 파일을 원래 경로에 놓습니다. 바이러스 검사기가 새로 쓴 파일을 잠시 잠그는 일이 흔하므로 몇 초간 재시도합니다.
  5. 서비스는 스스로를 중지하고 시작할 수 없으므로(SCM은 중지 중인 서비스의 시작을 처리하지 않습니다) 전용 종료 코드로 중지하고, install.ps1이 설정한 SCM 복구 동작이 새 바이너리로 되살립니다. 별도 helper 서비스나 예약 작업을 설치하지 않습니다.

콘솔에서 --update-now를 실행한 경우에는 SCM으로 서비스를 직접 재시작합니다.

릴리즈는 버전·OS·아키텍처로 구분되므로 같은 버전의 Windows판과 Linux판이 공존하고, 각 Agent는 자신의 플랫폼 릴리즈만 받습니다. Agent가 요청할 때 자신의 플랫폼을 보내고 응답의 플랫폼도 검증합니다 — 이전에는 요청이 os=linux로 고정되어 있어 Windows Agent가 Linux 바이너리를 받아 자기 점검에서 실패했을 것입니다. 서명은 플랫폼별 실행 파일 각각에 대해 따로 만들어야 합니다.

3. 수집 내용

같은 카테고리를 만들되 원천과 몇몇 필드가 다릅니다. 판단 근거가 되는 세 가지를 특히 확인하십시오.

  • 운영체제 이름: 모든 Windows 11 호스트는 레지스트리 ProductName에 “Windows 10 …”을 보고합니다. Microsoft가 값을 갱신하지 않았기 때문이고, 이 값을 그대로 쓰는 인벤토리는 Windows 11 전체를 Windows 10으로 집계합니다. 빌드 번호 22000 이상에서 이름을 교정합니다. Server 계열은 빌드 번호 체계를 공유하므로 교정 대상이 아닙니다. 패치 수준 판단에 필요한 UBR(빌드의 네 번째 자리)과 표시 버전(23H2)도 함께 보고합니다.
  • 설치 소프트웨어: Uninstall 레지스트리를 세 범위 모두 읽습니다 — 64비트 machine 뷰, WOW6432Node의 32비트 뷰, 로드된 각 사용자 하이브. 첫 번째만 읽는 것이 흔한 실수이며 32비트 제품과 사용자별 설치가 전부 누락됩니다. Windows가 프로그램 목록에서 숨기는 항목(SystemComponent, 업데이트·핫픽스 ReleaseType, 번들 설치 프로그램의 자식 항목)은 제외합니다. 제외하지 않으면 패치된 서버에서 수천 건의 핫픽스가 실제 소프트웨어를 덮습니다. Win32_Product는 사용하지 않습니다 — 조회할 때마다 설치된 모든 패키지에 Windows Installer 정합성 검사를 유발합니다.
  • 서비스: 현재 상태와 시작 유형을 함께 보고합니다. 멈춰 있는 서비스가 멈춰 있어야 하는 것인지는 상태만으로 답할 수 없습니다. 실행 계정(run_as)과 이미지 경로도 함께 보고합니다.

그 외: 로컬 계정은 RID(이름을 바꿔도 유지되는 식별자)와 로컬 그룹 소속을 보고하므로 관리자 권한 계정을 식별할 수 있습니다. 볼륨은 드라이브 종류와 레이블을, 어댑터는 연결 상태와 DNS 접미사를 보고합니다. 도메인 가입 여부와 SMBIOS 펌웨어 UUID도 포함합니다. 프로세스 명령행은 Windows에서도 기본 비수집입니다 — 서비스와 예약 작업의 명령행에 자격 증명이 들어가는 경우가 흔합니다.

WMI는 사용하지 않습니다. 통상적인 방법이지만 COM 아파트먼트와 Winmgmt 서비스 의존이 생기고(“일부 호스트에서 에이전트가 멈춘다”의 흔한 원인), 필요한 값은 모두 레지스트리·Win32·SCM에서 얻을 수 있습니다. 펌웨어 UUID는 원시 SMBIOS 테이블에서 직접 파싱합니다.

4. 함께 수정한 것

  • 업데이트 요청이 os=linux로 고정되어 있었습니다. 이제 실행 플랫폼을 보내고 응답의 플랫폼을 검증합니다.
  • Server가 linux 외의 OS 게시를 거부했습니다. 이제 windows를 받고, 지원하지 않는 조합(Windows on ARM 등)은 이유를 밝혀 거부합니다.

호환성

  • 데이터베이스 마이그레이션이 없습니다. 기존 Linux Agent는 그대로 동작합니다.
  • 게시 API의 os 필드가 windows를 허용합니다. 생략하면 이전과 같이 linux입니다.
  • Windows Agent가 만드는 자산 카테고리는 Linux와 동일하므로 분류 규칙과 관계 추론이 그대로 적용됩니다. 다만 system 레코드의 os_family가 windows이므로, 운영 환경을 이름으로 판정하는 규칙이 Windows 호스트명 규칙과 맞는지 확인하십시오.
  • Windows용 릴리즈는 x86_64만 제공합니다.
