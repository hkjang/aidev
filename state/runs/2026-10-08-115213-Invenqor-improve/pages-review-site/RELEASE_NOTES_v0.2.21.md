# Invenqor Server·Agent v0.2.21 릴리즈 노트

릴리즈 일자: 2026-09-03
호환 Agent: v0.2.21 (Linux·Windows)

이번 릴리즈는 결함 하나를 고칩니다. v0.2.20에서 고친 것과 같은 자리, 같은 종류 —
**오류 없이 틀린 답을 주던 것** — 이고, 이번에는 물어본 키는 맞았는데 그 값을 비교한
방식이 틀렸습니다.

## 1. 속성에 대한 대소 비교가 숫자를 문자열로 비교했습니다

`attributes.` 경로의 값은 저장된 JSON 문서에서 **텍스트로 꺼내집니다.** 그래서
`<`, `<=`, `>`, `>=` 비교가 한 글자씩 문자 순서로 이루어졌습니다.

`"16000000000"`은 `'1' < '2'`이므로 `"2000000000"`보다 앞섭니다. 즉 16 GB를 가진
호스트가 `attributes.memory_bytes >= 2000000000`의 **바깥**에 놓였고,
`attributes.cpu_count > 9`는 코어가 10개인 장비를 빼놓았습니다. 둘 다 HTTP 200에
짧아진 목록을 돌려줬을 뿐, 요청한 것과 다른 비교가 수행됐다는 신호는 어디에도
없었습니다. 그리고 `/query/validate`는 그 식을 이미 "유효하다"고 답한 뒤였습니다.

값이 숫자로 읽히는 대소 비교절은 이제 CASE로 컴파일돼, **JSON에 숫자로 저장된 값은
숫자로** 비교합니다 — PostgreSQL에서는 `::double precision`, SQLite fallback에서는
`json_extract`가 이미 돌려주는 값입니다. 그 밖의 것은 종전대로 텍스트로 비교하므로,
지금 텍스트를 정렬하고 있는 절(`attributes.os_version > "20.04"` 같은)이 행을 잃는
일은 없습니다.

등호는 건드리지 않았습니다. 텍스트 비교가 이미 옳고, 여기서 `"1.10"`을 숫자로 읽으면
버전을 담은 속성이 자기 자신과 매칭되지 않게 되기 때문입니다. 콘솔이 렌더링하는 문법
참조에도 숫자로 저장된 값이 대소 비교에서 숫자로 비교된다고 적혔습니다.

## 검증

- **컴파일 수준.** 숫자 값을 가진 대소 비교절이 두 저장 모드 모두에서 숫자 비교로
  컴파일되는지, 그리고 등호와 텍스트 값은 텍스트 비교로 남는지 고정했습니다.
- **HTTP 경로까지.** 숫자 속성을 가진 자산을 만든 뒤 경계를 넘는 대소 비교로 질의해
  실제로 돌아오는 것을, 그리고 텍스트로 저장된 속성의 대소 비교는 종전 결과를
  유지하는 것을 엔드포인트 너머에서 확인합니다. 결함의 증상이 "오류 없이 짧아진
  목록"이라 컴파일 단언만으로는 회귀를 놓칠 수 있기 때문입니다. 이 테스트는 SQLite
  fallback과 CI의 PostgreSQL 잡에서 모두 돕니다.

## 호환성

- 데이터베이스 마이그레이션이 없습니다.
- API 응답 형식 변경이 없습니다.
- 숫자 속성에 대한 대소 비교의 결과가 달라집니다 — 지금까지 빠져 있던 행이
  돌아옵니다. 저장된 질의나 대시보드가 이 비교의 결과 건수에 기대고 있었다면 값이
  바뀔 수 있습니다.
- 텍스트로 저장된 속성의 대소 비교 결과는 그대로입니다.
