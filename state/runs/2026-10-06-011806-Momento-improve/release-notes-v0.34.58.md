# Momento v0.34.58 — 「망 대역 추가」 의 CIDR 칸이 틀린 표기를 보내기 전에 걸러 냅니다

콘솔 **관리 → 망 구분**의 「망 대역 추가」 카드가 달라집니다. 서버·API·데이터베이스는 그대로입니다.

## 지난 네 릴리스가 한 일의 다음 걸음입니다

v0.34.54~v0.34.57 은 **실패한 뒤에 뜨는 문장**을 고쳤습니다. 사용자 다이얼로그, 사이트 다이얼로그, 이 폼(v0.34.56), Event Schema 카드 — 전부 영문 대신 무엇을 고칠지 한국어로 말하게 했습니다.

이번에는 같은 폼에서 **그 실패 자체를 없앱니다.**

## 왕복을 한 번 돌아야 알 수 있었습니다

「CIDR」 칸은 콘솔에서 CIDR 을 손으로 적는 유일한 칸입니다. 그런데 「추가」 버튼은 `!form.name || !form.cidr` 로 **빈 칸만** 막았습니다. 그래서 이런 값들은 전부 전송되었습니다.

```
10.20.30            비트 수가 없습니다
10.20.30.0/33       IPv4 의 범위를 벗어났습니다
10.20.30.0/abc      비트 수가 숫자가 아닙니다
1.2.3.4.5/24        옥텟이 다섯 칸입니다
```

네 값 모두 서버까지 갔다가 `net.ParseCIDR`(`internal/httpapi/admin.go:812`)에 거절당해 400 `INVALID_CIDR` 로 돌아왔습니다. 네트워크를 한 번 왕복해야 **칸 바로 위 placeholder 에 이미 떠 있던** 올바른 모양을 알게 되는 구조였습니다.

## 이제 칸 아래에서 바로 읽습니다

| 적은 값 | 전에는 | 이제는 |
|---|---|---|
| `10.20.30` | 「추가」 가 눌리고 → 왕복 → 400 | 「추가」 가 닫힌 채 **비트 수가 아직 없습니다** + 규칙 |
| `10.20.30.0/33` | 「추가」 가 눌리고 → 왕복 → 400 | 「추가」 가 닫힌 채 **비트 수가 범위를 벗어났습니다. IPv4 는 0~32 입니다.** |
| `10.20.30.0/abc` | 「추가」 가 눌리고 → 왕복 → 400 | 「추가」 가 닫힌 채 **비트 수를 숫자로 적으세요** + 규칙 |
| `1.2.3.4.5/24` | 「추가」 가 눌리고 → 왕복 → 400 | 「추가」 가 닫힌 채 **0~255 네 칸으로 적으세요** + 규칙 |
| (빈 칸·올바른 값) | 아무 안내 없음 | 규칙을 상시 안내 |

칸 아래에는 **늘** 읽을 거리가 있습니다 — 막혔으면 왜 막혔는지, 아니면 알아 둘 것, 그것도 없으면 규칙 자체입니다. 같은 화면의 비밀번호 칸(`PASSWORD_RULE`)이 이미 쓰던 모양입니다.

## 안내 문장의 정본을 하나로 모았습니다

올바른 CIDR 표기를 설명하는 문장은 지금까지 `adminErrors.ts` 의 `describeNetworkError` **안에만** 있었습니다. 즉 사용자는 **틀린 뒤에만** 올바른 표기법을 읽을 수 있었습니다.

새 순수 모듈 `web/src/pages/cidrRule.ts` 가 그 문장을 `CIDR_RULE` 상수로 내보내고, 폼의 helperText 와 `INVALID_CIDR` 의 Alert 이 **같은 상수**를 읽습니다. 두 곳이 같은 말을 하는 것이 누가 양쪽을 다 고치기로 기억하는 일이 아니라 구조상 참입니다.

## 화면이 서버보다 좁아지지 않게 했습니다

서버가 검증의 정본이고 화면은 거울입니다. 그래서 차단하는 것은 **`net.ParseCIDR` 이 확실히 거절하는 값뿐**입니다. 화면이 더 엄격해지면 서버가 받아 줄 값을 넣을 방법이 사라집니다.

통과시키는 것들:

- **호스트 비트가 켜진 값** — `10.20.30.1/24` 는 ParseCIDR 이 통과시킵니다. 막지 않고, 오류 색도 쓰지 않고, 계산한 시작 주소(`대역의 시작 주소는 10.20.30.0/24 입니다.`)만 중립 안내로 보여 줍니다. Postgres `cidr` 컬럼이 이 값을 어떻게 다루는지는 **이 기계에서 데이터베이스로 재현하지 못했으므로** 아무 주장도 하지 않습니다.
- **IPv6 본문** — 판정하지 않고 통과시킵니다. 판정 못 하는 것은 막지 않습니다.
- **비트 수의 선행 0** — `/024`·`/00000000024` 는 ParseCIDR 이 **통과시킵니다.** 기억이 아니라 Go 로 29개 값을 실제로 넣어 보고 알아낸 사실입니다. 정규식으로 '모양' 을 보고 거절했다면 바로 여기서 화면이 서버보다 좁아졌을 자리라, 서버의 `dtoi` 와 같이 십진수 **값**으로 읽습니다.
- **IPv4 주소의 선행 0** — `010.20.30.0` 은 Go 1.17 이후 ParseCIDR 이 거절하지만 통과시킵니다. 막아도 되는 값이지만, 표기 판정을 넓히다 통과시켜야 할 값을 막는 쪽이 더 비쌉니다.

「추가」 가 닫히는 것과 칸이 **빨갛게** 되는 것도 갈라 두었습니다. `10.20.30` 처럼 아직 적는 중일 수 있는 미완성 입력은 버튼만 닫고 오류 색을 쓰지 않습니다. 폼을 열자마자 빨간 글씨가 보이는 일도 없습니다.

## 확인

`web/test/cidrRule.test.mjs` 가 이 성질을 고정합니다(211 → **223**건).

- **부분집합 증명** — 890개 생성 코퍼스(중복 제거 888개)를 Go `net.ParseCIDR` 과 `judgeCIDR` 양쪽에 돌렸습니다. 화면이 막은 727건 중 **서버가 받아 줄 값은 하나도 없었습니다**(위반 0건).
- **실제 프로덕션 배선** — `npm run build` 의 dist 를 `/api/v1/me`·`/api/v1/sites`·`/api/v1/networks` 를 흉내 낸 임시 서버에 올리고 headless Chrome 으로 `/admin?section=networks` 의 칸을 실제로 채워 「추가」 를 눌렀습니다. 버튼 `disabled`, helperText DOM, `Mui-error` 색, 그리고 **서버에 도달한 POST 건수**를 읽었습니다 — 네 값 모두 disabled + 한국어 안내 + **POST 0건**, `10.20.30.1/24` 는 POST 가 1건 실제로 나가고 전송 본문이 적은 값 그대로였습니다.
- **대조** — 변경을 되돌리고 재빌드해 같은 하네스를 돌리면 20건이 실패하고 서버에 POST 가 5건 도달합니다. 순수 함수 쪽도 '무엇이든 통과시키는' 스텁으로 새 12건 중 8건이 먼저 실패하는 것을 확인한 뒤 구현했습니다.
- `INVALID_CIDR` 의 문장을 글자 그대로 묶고 있던 기존 단언(`web/test/adminErrors.test.mjs:619`)은 **한 글자도 고치지 않고** 통과합니다.

릴리스 검증은 이전과 같습니다 — `go test`·`go vet`, sdk `npm audit`·typecheck·테스트 27건·build, 콘솔 `npm audit`(`found 0 vulnerabilities`)·`eslint`·테스트 223건·`npm run build` 모두 통과합니다.

## 범위

바꾼 것은 프로덕션 3파일(`web/src/pages/cidrRule.ts` 신규, `adminErrors.ts`, `AdminPage.tsx` 의 폼 한 곳)과 테스트 1파일입니다. **서버는 손대지 않았습니다** — `admin.go` 가 검증의 정본으로 남고 화면은 그 부분집합만 거릅니다. 설정 화면의 「신뢰할 Reverse Proxy CIDR」 은 다른 엔드포인트의 다른 검사라 포함하지 않았습니다. Go·API 변경과 데이터베이스 마이그레이션은 없습니다.
