# git-ctx v0.77.21

이번 릴리스는 **MCP 응답이 예산에 걸려 절단될 때 답변 구조가 무너지던 두 문제**를 고칩니다. 하나는 v0.77.20 이 알려진 남은 제약으로 남겨 둔 것으로, 절단 뒤 블록을 닫는 펜스가 그 블록을 연 펜스보다 짧아 블록이 닫히지 않았습니다. 다른 하나는 `search-code` 의 결과 개수를 세고 자르는 자리가 실제 적중(hit)이 아니라 고정된 세 개의 구역 제목이어서, 적중이 몇 건이든 결과를 셋으로 보고하고 예산에 걸리면 적중 전체를 떨어뜨렸습니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

> **재색인도 마이그레이션도 필요하지 않습니다.** 저장되는 내용과 검색 결과는 바뀌지 않으며, 바뀌는 것은 절단된 응답을 닫는 백틱 개수와 절단 자리, 그리고 보고되는 결과 개수뿐입니다.

## 수정

### 절단된 코드 블록을 세 백틱으로만 닫았습니다

- `internal/mcp/budget.go`의 `closeOpenFence` 는 `` ``` `` 의 개수를 세어 짝이 맞는지만 보고, 닫을 때는 언제나 백틱 세 개를 붙였습니다. v0.77.20 이 `contentFence` 로 내용보다 긴 펜스를 열도록 고친 뒤에도 절단 경로는 그대로였으므로, 백틱 네 개로 연 블록은 세 개로 닫히지 않았습니다.
- 개수 세기 자체도 내용과 펜스를 구분하지 못했습니다. 한 줄 안의 인라인 백틱과 내용 속의 짧은 중첩 펜스가 모두 펜스로 집계되어, 짝이 맞는 것처럼 보이면 열린 블록을 닫지 않고 그냥 두었습니다.
- 줄 단위로 펜스 상태를 따라가도록 고쳤습니다 — 앞선 공백 세 개까지 허용하고, 여는 줄은 백틱 세 개 이상이며 그 뒤에 백틱이 없는 줄, 닫는 줄은 같은 길이 이상의 백틱만 있는 줄입니다. 열린 채 남았으면 **그 블록을 연 길이 그대로** 닫습니다.

### 코드 검색의 결과 개수와 절단 자리가 적중을 보지 않았습니다

- `sectionCount` 는 `### ` 제목을 결과 하나로 셉니다. 그런데 `formatCodeSearch`(`internal/mcp/format.go:118`)는 `### Repository Matches`·`### Source Matches`·`### Notes` 아래에 적중 하나당 `#### ` 제목을 씁니다. 그래서 적중이 한 건이든 스무 건이든 결과 개수는 언제나 셋으로 보고되었습니다.
- `cutAtBoundary` 도 같은 제목만 보았으므로, 예산에 걸리면 `### Source Matches` 제목에서 잘라 **적중을 하나도 남기지 않았습니다.** 적중 중간에서 자르면 코드 조각도 `Source:` 인용도 없는 제목만 남았습니다.
- 코드 검색의 적중 구역에서는 `#### ` 를 결과 경계로 세고 자르도록 고쳤습니다.
- 이 규칙은 **적중 구역에만** 적용합니다. `codeSearchHits` 는 답변이 `## Code Search` 로 시작하고 `### Source Matches (` 제목을 가질 때만 그 지점을 돌려주고, 다른 모든 답변에는 `-1` 을 돌려줍니다. 다른 곳의 `#### ` 는 **보여 주는 내용 자신의 제목**입니다 — `read-file`·`query-docs`·`export-context` 는 자체 소제목을 쓰는 마크다운을 돌려주므로, 그것을 결과 경계로 보면 개수도 틀리고 내용도 짧게 잘렸습니다. 창 중간에 `#### ` 소제목이 있고 뒤에 `### ` 제목이 있는 문서 파일은 같은 예산에서 전달 바이트의 5분의 1을 잃었습니다.

## 영향 범위

- 절단되지 않은 응답은 전과 완전히 동일합니다. 두 수정 모두 예산에 걸린 응답의 경로입니다.
- 백틱 세 개로 연 블록이 절단되면 전과 동일하게 세 개로 닫힙니다. 달라지는 것은 네 개 이상으로 연 블록(이제 같은 길이로 닫힘)과, 인라인 백틱·중첩 펜스 때문에 짝이 맞아 보여 닫히지 않던 블록입니다.
- `search-code` 의 결과 개수는 이제 실제 적중 건수입니다. 종전의 고정값 셋에 맞춰 둔 클라이언트 측 가정이 있다면 확인하십시오.
- 도구 이름·인자·응답 필드 구조와 인용 형식, 저장되는 청크와 검색 결과, 접근 판정은 바뀌지 않습니다.

## 검증

- 대역 타입을 쓰지 않고 실제 배선으로 회귀 시험했습니다. 실제 `store.Open("sqlite", …)` fixture 와 실제 `mcp.Server.ServeHTTP` 의 JSON-RPC `tools/call` 로 도구를 호출하고 응답 텍스트를 단언합니다.
- 펜스 시험은 백틱 네 개로 연 블록이 절단된 뒤 같은 길이로 닫히는지, 인라인 백틱과 중첩 펜스를 담은 내용이 짝이 맞아 보여도 열린 블록이 닫히는지를 단언합니다.
- 결과 개수 시험은 적중 건수가 다른 코드 검색 응답들에서 보고되는 개수가 실제 적중 수와 같은지, 예산에 걸린 응답이 적중을 최소 하나 온전히(제목과 코드 조각과 `Source:` 인용을 함께) 남기는지를 단언합니다.
- `#### ` 소제목을 가진 `read-file`·`query-docs`·`export-context` 응답이 종전과 같은 개수와 같은 절단 자리를 유지하는 동작 무변경 대조군을 함께 돕니다.
- 수정 전 코드에서 해당 케이스들이 실패함을 먼저 확인했습니다.
- 일반·FTS5 빌드와 전체 테스트, 전체 race, `vet`·`gofmt` 통과
- 버전 정합성·회귀 시험, Kubernetes Kustomize 렌더링과 콘솔 구문·계약 시험 통과
- `govulncheck ./...`: `No vulnerabilities found` (로컬 스캐너 v1.6.0, 릴리스 워크플로는 v1.7.0 으로 다시 수행)
- 로컬 검증 결과는 `docs/completion-audit.md`에 기록했습니다.
- PostgreSQL·pgvector·Vault 통합, Docker 이미지 빌드·오프라인 아카이브 검증 및 GitHub 공개는 태그 푸시 후 릴리스 워크플로에서 수행합니다.

## 업그레이드 참고

- 마이그레이션과 재색인은 필요하지 않습니다.
- 설정·환경변수·API 스키마 변경은 없습니다.
- 절단된 MCP 응답을 고정된 백틱 세 개로 파싱하는 클라이언트 측 스크립트가 있다면, 여는 줄의 백틱 개수를 읽어 같은 길이 이상으로 닫는 줄을 찾도록 바꾸십시오. 표준 마크다운 파서를 쓰는 클라이언트는 손댈 것이 없습니다.
- `search-code` 응답의 결과 개수를 쓰는 자동화가 있다면, 그 값이 이제 적중 건수라는 점을 반영하십시오.
