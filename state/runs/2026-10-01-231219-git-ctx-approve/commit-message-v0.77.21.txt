release: v0.77.21

MCP 응답이 예산에 걸려 절단될 때 답변 구조가 무너지던 두 문제를 고칩니다. 하나는 v0.77.20 이
알려진 남은 제약으로 남겨 둔 것입니다 — internal/mcp/budget.go 의 closeOpenFence 는 ``` 개수의
짝만 보고 닫을 때는 언제나 백틱 세 개를 붙였으므로, v0.77.20 이 contentFence 로 내용보다 긴
펜스를 열도록 고친 뒤에도 백틱 네 개로 연 블록은 세 개로 닫히지 않았습니다. 개수 세기 자체도
내용과 펜스를 구분하지 못해 한 줄 안의 인라인 백틱과 내용 속 짧은 중첩 펜스까지 집계했고, 그래서
짝이 맞아 보이면 열린 블록을 닫지 않고 그냥 두었습니다. 줄 단위로 펜스 상태를 따라가도록
고쳤습니다 — 앞선 공백 세 개까지 허용하고, 여는 줄은 백틱 세 개 이상이며 그 뒤에 백틱이 없는 줄,
닫는 줄은 같은 길이 이상의 백틱만 있는 줄이며, 열린 채 남았으면 그 블록을 연 길이 그대로
닫습니다. 다른 하나는 같은 절단 경로의 코드 검색입니다 — sectionCount 는 `### ` 제목을 결과
하나로 세는데 formatCodeSearch(format.go:118)는 `### Repository Matches`·`### Source
Matches`·`### Notes` 아래에 적중 하나당 `#### ` 제목을 쓰므로, 적중이 한 건이든 스무 건이든 결과
개수는 언제나 셋으로 보고되었습니다. cutAtBoundary 도 같은 제목만 보았으므로 예산에 걸리면
`### Source Matches` 에서 잘라 적중을 하나도 남기지 않았고, 적중 중간에서 자르면 코드 조각도
Source: 인용도 없는 제목만 남았습니다. 코드 검색의 적중 구역에서는 `#### ` 를 결과 경계로 세고
자르도록 고쳤습니다. 이 규칙은 적중 구역에만 적용합니다 — codeSearchHits 는 답변이 `## Code
Search` 로 시작하고 `### Source Matches (` 제목을 가질 때만 그 지점을 돌려주고 다른 모든 답변에는
-1 을 돌려줍니다. 다른 곳의 `#### ` 는 보여 주는 내용 자신의 제목이기 때문입니다 —
read-file·query-docs·export-context 는 자체 소제목을 쓰는 마크다운을 돌려주므로 그것을 결과
경계로 보면 개수도 틀리고 내용도 짧게 잘렸으며, 창 중간에 `#### ` 소제목이 있고 뒤에 `### `
제목이 있는 문서 파일은 같은 예산에서 전달 바이트의 5분의 1을 잃었습니다. 대역 타입 없이 실제
배선으로 회귀 시험했습니다 — 실제 store.Open("sqlite", …) fixture 와 실제 mcp.Server.ServeHTTP
의 JSON-RPC tools/call 로 도구를 호출하고 응답 텍스트를 단언합니다. 펜스 시험은 백틱 네 개로 연
블록이 절단된 뒤 같은 길이로 닫히는지와 인라인 백틱·중첩 펜스를 담은 내용에서 열린 블록이
닫히는지를, 결과 개수 시험은 보고되는 개수가 실제 적중 수와 같은지와 절단된 응답이 적중 하나를
제목·코드 조각·Source: 인용까지 온전히 남기는지를 단언하며, `#### ` 소제목을 가진
read-file·query-docs·export-context 응답이 종전과 같은 개수와 같은 절단 자리를 유지하는 동작
무변경 대조군을 함께 돕니다. 수정 전 코드에서 세 시험(TestTruncatedToolAnswersKeepNoticesOutside
Code·TestTruncationDoesNotReopenClosedCodeBlocks·TestTruncatedSearchCodeCountsAndKeepsWholeHits)이
모두 실패함을 먼저 확인했습니다. 절단되지 않은 응답과 백틱 세 개로 연 블록의 절단 결과는 전과
완전히 같고, 도구 이름·인자·응답 필드 구조와 인용 형식, 저장되는 청크와 검색 결과, 접근 판정은
바뀌지 않습니다. 마이그레이션과 재색인은 필요하지 않습니다.
