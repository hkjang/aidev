- 과제: 운영 홈 RCA 자원 태그를 클러스터별로 정확히 연결 (가치 3 / 위험 1 / 작업량 S)
- 왜: `internal/analyzer/rca.go:AttachFindingResources`는 주석과 달리 kind/namespace/name만으로 인벤토리를 찾아, 두 클러스터의 동명 Pod가 서로 다른 메모리 제한을 가져도 마지막 인벤토리의 값을 양쪽 finding에 붙인다. 운영 홈 장애 후보의 CPU·메모리 태그를 해당 클러스터의 실제 값으로 표시하면 OOM 원인 판단과 자원 조정 판단의 잘못된 근거를 없앨 수 있다.
- 수용 기준:
  1) 동일 namespace/name인 c1·c2 Pod에 서로 다른 CPU·메모리 request/limit를 주면 각 finding의 `resources`는 자기 클러스터 값만 가진다. items 순서를 뒤집어도 결과가 같다. kind의 기존 대소문자 무시, namespace/name 구분은 유지한다.
  2) 동일 이름이 다른 클러스터에만 있으면 태그를 붙이지 않는다. 빈 ClusterID는 빈 ClusterID끼리만 매칭하고 wildcard/fallback으로 취급하지 않는다. 매칭은 되지만 자원 설정이 없는 새 finding과 인벤토리가 없는 새 finding은 Resources=nil을 유지한다. Deployment template spec 요약도 그대로 동작한다.
  3) analyzer 회귀와 실제 SQLite·Server.Routes()·HTTP를 통과하는 운영 홈 회귀를 추가한다. `/admin/k8s/clusters`로 두 클러스터를 만들고 `/admin/k8s/snapshot`으로 default namespace의 동명 OOMKilled Pod를 각각 다른 자원량으로 저장한 뒤, `GET /admin/k8s/home`의 `failure_candidates`를 cluster_id로 찾아 `resources.req_cpu/lim_cpu/req_mem/lim_mem`을 검증한다. fixture는 TOP10 이하로 작게 만들고 배열 순서에 의존하지 않는다. 신규 핵심 회귀가 수정 전 잘못된 동일 태그 때문에 실패하고 수정 후 통과함을 확인한다.
- 건드릴 파일:
  - `internal/analyzer/rca.go:AttachFindingResources` — 인덱스 생성과 finding 조회 양쪽에 ClusterID를 추가한다. 지역 struct 키 또는 기존 `rcaKey(clusterID, namespace, strings.ToLower(kind), name)`의 양쪽 사용 중 작은 변경을 택한다. `rcaKey` 자체의 계약은 바꾸지 않는다. 주석의 실제로 없는 owner workload fallback 설명을 사실에 맞게 고치되 새 fallback을 구현하지 않는다.
  - `internal/analyzer/resourcesummary_test.go:TestAttachFindingResources` — 기존 inventory fixture에도 ClusterID="c1"을 명시한다. 동명 두 클러스터·입력 순서·빈 ID·다른 namespace/kind·비매칭 및 workload template 회귀를 추가한다.
  - `internal/proxy/admin_k8s_test.go:TestK8sHomeAggregates` 인접 영역 — 위 실제 HTTP 종단 회귀를 추가한다. 기존 `openTestStore`, `testConfig`, `postJSON`, `NewServer`, `server.Routes()` 패턴을 사용하고 HTTP 상태 코드와 JSON decode 오류도 확인한다.
  - 읽기 참조: `internal/proxy/admin_k8s_home.go:handleK8sHome`는 전 클러스터 items를 읽어 AttachFindingResources를 호출하며, `internal/proxy/admin_ui.go`의 failRows는 `k8sResTags(f.resources)`를 렌더한다. 이 두 프로덕션 파일은 현재 배선상 수정할 필요가 없다. `internal/analyzer/resourcesummary.go:SummarizePodResources`와 `regularContainers`는 자원 요약/Deployment template 처리를 이미 제공한다.
- 검증 명령: 저장소 루트에서 `go test ./internal/analyzer ./internal/proxy` → `go build ./...` → `go vet ./...` → 최종 `go test ./...`. 수정한 Go 파일에만 gofmt를 적용한다. 정찰에서는 앞의 세 명령이 통과했고 proxy 테스트는 61.874초였다. 전체 `go test ./...`는 이번 정찰에서 미실행이다.
- 위험과 피할 것: auth/session, migrations(`internal/store/sqlstore.go`), workflows, DW 스키마, 버전/changelog/docs 마커는 건드리지 않는다. 이전 회차가 완료한 이벤트·리비전 조인은 다시 고치지 않는다. NodePressure 집계, 자원 수량 파서/initContainer 합산, owner fallback, UI 개편은 별개 과제다. 빈 cluster를 wildcard로 만들어 기존 잘못된 fixture를 통과시키지 않는다. map 순서나 DB 반환 순서에 기대지 말고 실제 응답 값을 검증한다. 과거 human rejection의 구체 접근은 비공개/미확인이므로 인증·정책 변경을 피한다.
- 차선 후보: NodePressure 영향 Pod 집계를 클러스터별로 격리 (가치 3 / 위험 1 / 작업량 S) — 1순위가 이미 해결되어 성립하지 않을 때만 선택한다. `internal/analyzer/workload.go:analyzeNodeConditions`의 podsByNode 생성·조회 양쪽을 기존 `nodeKey(clusterID,node)` 기준으로 바꾸고, `internal/analyzer/workload_test.go` 및 실제 RCA API 응답으로 동명 노드 c1·c2의 Pod 수/목록 분리를 확인한다. 1순위와 묶지 않는다.
