- 과제: 저장 결과 상세의 늦은 응답과 이전 선택의 작업 단추가 남는 문제 수정 (가치 4 / 위험 1 / 작업량 M)
- 왜: `/saved`에서 A를 연 뒤 B를 선택하면 B를 불러오는 동안과 조회 실패 뒤에도 `current`와 삭제·복사·워크스페이스 열기 단추가 A를 가리키며, 연속 선택의 응답이 역순으로 도착하면 마지막 선택과 다른 상세가 표시된다. 마지막 선택의 응답만 반영하고 로딩·오류 중 이전 상세 작업을 막으면 다른 저장 결과를 실수로 다루는 일을 줄일 수 있다.
- 수용 기준: 1) 새 결과를 선택하는 즉시 이전 SQL·결과·작업 단추를 숨기거나 비활성화하고 작업 가능한 `current`를 비운다. 최신 요청 성공 때만 제목·SQL·표·작업 대상·목록 강조가 같은 결과를 가리키며, 최신 요청 실패 때는 오류를 표시하고 이전 결과의 작업을 실행할 수 없어야 한다. 2) A→B 선택 후 B 성공→A 성공 또는 B 성공→A 실패 순서로 응답해도 B의 상세와 작업 대상을 유지한다. 삭제 요청 진행 중에는 중복 삭제를 막고, 삭제 완료가 이후 선택한 B를 초기화하지 않으며 삭제된 A의 진행 중 조회가 뒤늦게 상세를 복구하지 않아야 한다. 3) 제어 가능한 Promise와 DOM/API 대역을 사용하는 회귀 테스트로 로딩·실패 중 작업 차단, 늦은 성공·실패 무시, 삭제 대상 ID 고정 및 후속 선택 보존을 증명한다. 실제 `saved.js` 이벤트/함수를 실행하고 현행 코드에서 실패하는 테스트를 먼저 확인한다(소스 문자열 검사만으로 대체하지 않는다).
- 건드릴 파일: `internal/webui/js/saved.js:showDetail` — 요청 순번 등으로 최신 응답만 반영하고 로딩·오류 상태를 초기화; `renderList` — 선택 강조가 상세 상태와 일치하도록 조정; `tsvBtn/openBtn/deleteBtn` 클릭 처리 — 유효한 상세만 사용, 삭제 시작 시 대상 ID를 고정하고 완료 시 선택 변경 여부 확인; `test/js/saved.test.mjs`(신규) — 실제 페이지 모듈을 DOM/API 대역으로 실행하는 회귀 테스트. `internal/webui/pages/saved.html`은 기존 단추와 상세 영역 구조 확인용이며 꼭 필요한 상태 표시에만 수정한다. 서버 API·저장 서비스 수정은 불필요하다.
- 검증 명령: 저장소 루트에서 `node test/js/saved.test.mjs`(구현 후 신규 테스트), `go test -race ./...`, `go vet ./...`, `gofmt -l .`. 화면 변경이므로 README의 릴리스 요구대로 `DF_SMOKE_REQUIRE_BROWSER=1 bash test/smoke/run.sh`도 실행한다(Docker·Python playwright·Chromium 필요). 정찰에서는 기존 `go test -race ./...` 1회 통과; Node v22.23.1, Go go1.26.7 확인. 브라우저 스모크와 vet는 정찰에서 미실행이다.
- 위험과 피할 것: `auth`, session, migrations, `.github/workflows` 및 `layout.js:api`의 CSRF/401 계약은 건드리지 않는다. AbortController만 추가하면 이미 끝난 응답/오류 경합을 놓칠 수 있으므로 응답 적용 시 최신 선택인지 검사한다. 삭제 완료 뒤 무조건 `current=null`로 만들면 그 사이 선택한 다른 상세를 지우므로 조건부 처리한다. 공통 상태 프레임워크 도입, 목록 페이지네이션, 로그인 UX 개선은 이번 범위 밖이다. 실제 저장 데이터 삭제 재현은 하지 않았고 Node 대역으로 잘못 남는 작업 대상까지 확인했다. 브라우저에서의 클릭 재현은 미확인이므로 구현자가 확인한다.
- 차선 후보: 로그인 폼 429 Retry-After 카운트다운과 재제출 방지 (가치 2 / 위험 1 / 작업량 S) — 첫 과제가 이미 해결됐거나 성립하지 않을 때만 선택. `internal/webui/js/login.js` submit catch는 429에도 즉시 단추를 다시 켜고 `internal/server/http.go:loginHandler`는 초 단위 Retry-After를 이미 보낸다. 서버 제한 정책을 바꾸지 말고 유효한 헤더의 대기 동안 클릭·Enter 재제출을 막으며 누락/잘못된 헤더·네트워크 실패는 영구 잠금 없이 복구해야 한다.

실행 계획·추정: 재현 테스트 10분 → saved.js의 요청/선택 및 삭제 상태 수정 15분 → 회귀·전체 테스트 10분 → 실제 바이너리 스모크 및 여유 10분, 합계 45분. 대규모 추출 없이 페이지 내부 요청 순번과 작은 초기화 함수 사용을 우선한다. 순수 헬퍼만 시험하는 접근은 실제 이벤트 연결을 놓치므로 피한다.
근거: `saved.js:showDetail`은 제목만 바꾼 뒤 await하고 성공에서 무조건 current를 덮어쓰며 catch는 결과 영역만 바꾼다. Node vm에서 원본 파일의 import만 대역으로 바꿔 실행한 결과, B 로딩/실패 때 current=1·deleteHidden=false, 3→4 선택 후 4→3 응답 때 current=3을 확인했다. 서버 `resultsave.go:getSavedResultHandler/deleteSavedResultHandler`, 서비스 `resultsave/service.go:Get/Delete`, `pages/saved.html`, `layout.js:api`, `test/js/load.mjs`, `jstest_test.go`를 직접 읽었다. 신규 테스트 파일은 기존 Go 러너가 glob으로 자동 실행한다.
