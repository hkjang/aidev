- 결과: 성공
- 요약: **보고된 CI 실패 자체는 재현되지 않았다.** 로그에서 뽑힌 줄은 Azure Blob 의 `BlobNotFound` XML 로, 이는 GitHub Actions 가 *잡 로그 blob* 을 돌려주지 못한 응답 본문이며(선두 BOM, `Time:` 접미사) 단계 이름이 `''` 인 것도 같은 이유다 — 즉 보고서에 실패 내용이 담겨 있지 않다. 그래서 CI 잡의 모든 단계를 로컬에서 그대로 돌려 전부 통과를 확인했다(아래 검증). 대신 **보고된 그 단계(ci.yml 의 이름 없는 `- run:` 통합 단계)에 실재하는 결함** 을 찾아 고쳤다: `actions/setup-go@v7` 의 `cache: true` 는 GOCACHE 를 워크플로 실행 간에 캐시하고 GOCACHE 에는 **테스트 결과 캐시**가 들어 있는데, `ci.yml:63`·`release.yml:99` 의 `go test -race -p=1 -tags=integration ./...` 만 `-count=1` 이 빠져 있어 결과 재사용 대상이었다(같은 잡의 표적 `go test` 3곳은 모두 `-count=1`). 그래서 이 게이트는 DB 를 검증하지 않고 녹색이 될 수 있고, 캐시 적중이 부분적이면 실제로 실행되는 패키지 집합이 실행마다 달라져 red/green 이 재현되지 않는다. 두 워크플로에 `-count=1` 을 붙이고(사유 주석 포함), 회귀 방지로 `scripts/ci_workflow_test.go` 를 추가해 `.github/workflows/*.yml` 의 모든 `go test` 가 결과 캐시를 끄도록 고정했다 — 이 테스트는 `go test ./...` 와 CI 통합 실행에 모두 포함된다. 프로덕션 Go 코드는 한 줄도 바꾸지 않았다(파일 3개: 워크플로 2 + 테스트 1). 검증: 새 테스트 red → 수정 → green → `ci.yml` 의 `-count=1` 만 되돌려 다시 red → 복원; 폐기 PostgreSQL 17(도커 127.0.0.1:55492)에서 CI 의 Go 순서(fresh-install → migrations → 전체 통합)를 **깨끗한 DB 로 2회 연속** 통과(31 패키지 ok, `(cached)` 0건, 회차당 ~1분 40초), 수정 전 `-count=1` 없이도 2회 통과했으나 그때는 전부 캐시였다. 또 `go test ./...` 29 ok exit 0, `go vet ./...`·`go vet -tags=integration ./...`·`make check-go-format`·`make lint`·`go build ./...` 통과. CI 의 나머지 단계도 전부 로컬 실행: `npm ci`, `npm run lint`, `npm run typecheck`, `npm test -- --run`(27파일/134테스트 통과), `npm run build`, `npm audit --omit=dev --audit-level=high`(0 vulnerabilities), `npx playwright install chromium`(chromium-1234·headless_shell-1234·ffmpeg-1011 정상 수신 — Playwright CDN 의 BlobNotFound 가설 반증), `CI=1 npx playwright test`(14 passed), `govulncheck@v1.6.0`(0 vulnerabilities), `gosec@v2.28.0`(exit 0) — 어느 단계도 실패하지 않았다. 커밋 12223b0, 컨테이너 제거.
- 실패 재현: 보고된 CI 실패는 **못 함 — 로그 blob 이 404 라 실패 단계·내용이 보고서에 없고, CI 잡의 모든 단계를 로컬에서 그대로 돌려 전부 통과했다(비공개 저장소라 GitHub API 로 실제 로그 조회도 불가: `/repos/hkjang/qurio/actions/workflows` → 404, `gh` 미인증)**. 대신 내가 고친 결함은 새 테스트로 재현했다: `ci_workflow_test.go:36: ci.yml:63 runs go test without -count=1, so a cached result can satisfy the gate: - run: go test -race -p=1 -tags=integration ./...` / `ci_workflow_test.go:36: release.yml:99 runs go test without -count=1 …` — 그리고 결함의 실질 영향도 실측했다: **`public` 테이블 0개인 빈 DB** 에 CI 의 명령을 그대로 돌리자 `cmd/qurio`·`internal/store`·`internal/platformapi`·`internal/backup`·`internal/agentapi`·`internal/jobs`·`internal/integrations`·`internal/authzread`·`internal/domain/legacy` 등이 전부 `ok (cached)` 로 보고됐다(22초, 캐시 아닌 5개 패키지만 실제로 DB 에 접속).
- 보류 아이디어: `ci.yml` 에 `timeout-minutes` 가 없다 — 멈춘 잡이 기본 6시간을 점유한다(release.yml 은 60분) (2/1/S); legacyapi 통합 테스트 10파일 `defer pool.Close()` → `t.Cleanup(pool.Close)`, main 에 54곳 잔존 (3/2/M); 픽스처 DELETE 미등록 통합 테스트 3파일에 정리 추가 (3/2/S); `internal/store` 통합 테스트 6파일 DSN 을 `QURIO_TEST_POSTGRES_DSN` 전용·연결 오류 Fatal 로 (3/2/M); sqlsafe `postgresAliasColumnList` 의 `AS` 분기가 FROM 문맥 없이 무조건 면제 — 실행 가능한 악용 질의 미확인으로 계속 범위 밖 (2/2/S)
