- 과제: 프로파일 PUT에서 visibility 생략 시 기존 공개 범위를 보존 (가치 4 / 위험 1 / 작업량 S)
- 왜: 메타 DB 모드의 `upsertProfileMeta`는 visibility를 생략하면 private으로 기본화한 뒤 기존 레코드에 덮어써, 공유 프로파일의 연결 설정만 수정해도 다른 사용자의 목록에서 사라지게 한다. 특히 manage 수임자는 명시적 공개 범위 변경은 403으로 거부되지만 생략 시 같은 변경이 저장되므로, 기존 값을 보존하면 공유 중단과 권한 계약 우회를 함께 막을 수 있다.
- 수용 기준: 1) 기존 shared/private 프로파일을 소유자·admin·manage 수임자가 유효한 전체 프로파일 정의로 PUT할 때 visibility가 생략되거나 빈 문자열이면 기존 값을 유지하고, 응답 visibility·저장 레코드·GET 목록이 일치한다(이 작업은 일반적인 PATCH 지원이 아님). 2) 신규 POST에서 생략/빈 값은 기존처럼 private; 소유자/admin의 명시적 shared↔private 변경은 성공; manage 수임자의 같은 값 명시는 성공하고 다른 값 명시는 403, 잘못된 비어 있지 않은 값은 400이며 거절 시 정의와 공개 범위는 모두 불변이다. 3) 실제 Register mux와 로그인 쿠키를 통과하는 회귀 테스트가 shared 생성→manage grant→visibility 없는 PUT→별도 무grant 사용자의 GET /api/db-profiles에서 계속 보임을 증명한다; 수정된 name 등 정의 필드도 실제 저장되어야 하고, use-only 사용자의 수정은 403, 익명은 401을 유지한다.
- 건드릴 파일: `internal/mcp/dbapi.go:upsertProfileMeta` — create일 때만 private 기본값을 정하고 update에서는 기존 레코드 로드 뒤 요청 값이 비면 rec.Visibility를 유효 값으로 사용; 권한 검사·rec.Visibility 저장·응답의 visibility가 동일한 유효 값을 사용하도록 한다. `internal/mcp/authhttp_test.go:newAuthServer, withCookie, TestPerUserProfilePermissions, TestAdminShareProfileGrantAndVisibility` — 기존 HTTP 테스트 패턴을 재사용해 회귀 테스트 추가(예: TestProfileUpdatePreservesVisibility). `CHANGELOG.md:Unreleased` — 사용자 영향 한 줄만 추가.
- 검증 명령: 저장소 루트에서 `go test ./... -count=1`, `go vet ./...` (정찰에서 실제 실행하여 모두 통과). 구현 중 표적 테스트는 `go test ./internal/mcp -run 'TestProfileUpdatePreservesVisibility|TestPerUserProfilePermissions|TestAdminShareProfileGrantAndVisibility|TestDBProfileAPILifecycle' -count=1`; 새 테스트명은 위 이름에 맞춘다. 마지막 `git diff --check`.
- 위험과 피할 것: `auth.go`, `authapi.go`, `internal/meta/pg.go`, migrations, workflows는 수정하지 않는다. `authapi.go`의 전용 PUT /api/db-profiles/{id}/visibility는 소유자/admin만 허용하는 기존 계약을 유지한다. `upsertProfile`의 단독 모드·전체 정의 교체 계약·비밀번호 마스킹·프로파일 ACL 공통 함수는 넓히지 않는다. 누락/빈 값만 이번 범위로 다루며 JSON null은 현재 string 디코더의 기존 처리를 유지한다. 실제 HTTP로 생성·권한 부여·수정·목록 확인하고 손으로 만든 컨텍스트나 소스 문자열 검사를 증거로 쓰지 않는다. 감사 로그에 SQL/자격증명 원문을 추가하지 않는다. 기존 actor·카탈로그 인증·async TTL 성공 변경은 HEAD에 없으나 재구현/cherry-pick하지 않는다. 확인 근거와 구현 순서:
1. `registerDBAPI`가 POST/PUT를 `upsertProfile`→`upsertProfileMeta`로 연결한다. 현재 `visibility := req.Visibility` 뒤 빈 값은 private으로 바뀌며, update의 변경 권한 검사는 `req.Visibility != ""` 조건에 묶여 있다. 이후 `rec.Visibility = visibility`와 응답 모두 기본화된 값을 사용한다.
2. `internal/meta/mem.go:MemStore.UpsertProfile`, `internal/meta/pg.go:PGStore.UpsertProfile` 모두 전달받은 visibility를 저장한다. `internal/meta/types.go:CanUseProfile/CanManageProfile`과 `dbapi.go:listProfilesMeta`도 읽었다. 따라서 저장소 수정 없이 API 경계에서 해결할 수 있다.
3. `internal/mcp/webui/db.html`은 AUTH일 때 visibility를 명시하므로 이번 문제의 주된 트리거는 필드를 생략하는 REST 클라이언트이다. 브라우저에서 항상 발생한다고 주장하지 말 것.
