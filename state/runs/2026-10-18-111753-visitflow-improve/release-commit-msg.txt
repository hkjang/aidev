chore(release): VisitFlow v2.8.20

- Lobby Dashboard 가 로비 현황 조회 실패를 「방문 예정 0 · 현재 방문중 0 · 표시할 방문자가
  없습니다」로 단정하던 것을 고친다. `web/src/pages/LobbyPage.tsx` 의 `data` 가
  `{ counts: {}, items: [] }` 로 시작하고 조회 실패의 catch 가 **닫을 수 있는** error Alert
  하나만 띄워서, `/api/v1/lobby/today` 가 한 번도 성공하지 못한 채 실패하면 화면이 네 카드를
  `방문 예정 0 · 현재 방문중 0 · 퇴실 완료 0 · 미방문 0`, 탭을 `현재 방문자 0`, 목록을
  `표시할 방문자가 없습니다.` 로 렌더링했다 — helper 가 그 값을 스스로 「재난 시 체류 기준
  인원」이라 선언하므로 **대피 판단에 쓰라고 내놓은 숫자가 조회 실패일 때 0 을 말했다**.
  신규 순수 모듈 `web/src/lobbyCounts.ts` 의 `lobbyPanel(load, view)` 이
  `loading / failed(캐시 없음) / failed(캐시 있음) / ready` 를 판별 값 하나로 바꾸고 화면이 그
  한 값만 읽는다 — `useState<LobbyLoad>` 로 `?? 0` 이 타입으로 표현 불가능해져 `tsc` 가 네
  카드·탭 라벨·`truncated`·빈 상태 문장 모든 독자에게 처리를 강제한다(v2.8.19 의
  `adminMetrics.ts`·v2.8.18·v2.8.17 과 같은 판단). 최초 실패는 `<Grid>` 네 카드 전체를 숫자
  없는 `Alert severity="warning"` 하나로 **치환**하고, 재조회 실패는 받아 둔 숫자를 남기면서
  기준 시각 + 「최신이 아닐 수 있습니다」를 **닫을 수 없는** Alert 로 함께 보여 준다. `ready` 가
  `at`·`view` 를 스스로 들고 있으므로 마지막 성공 시각이 별도 state 로 어긋날 수 없고 `failed`
  전이가 `prev` 복사 한 줄로 끝난다. `lobbyPanel` 이 `view`(탭·검색어·로비 필터)를 받아
  **다른 화면의 캐시 목록은 버리고 카운트만 남긴다** — 카운트는 `visits.go lobbyList` 가
  role/siteScope 만으로 따로 집계하므로 탭·검색어와 무관하게 참이지만, 오늘 방문 예정자를
  「현재 방문자」 탭에 남겨 두면 닫으려던 거짓말이 그대로 돌아온다. 경고 문구는 숫자를 말하지
  않는다(「건물에 아무도 없다고 판단하지 마세요」, 단위 테스트가 `not.toMatch(/\d/)` 로
  고정한다). 값이 `0` 이라는 사실은 어디서도 실패의 근거로 쓰지 않았다 — 정상 200 의 진짜 0 은
  그대로 0 이고 실패는 판별 값에서만 나온다. 기존 `error` state 는 직접 체크인·퇴실(행동)
  실패용으로 남겼다. EventSource 수명주기·`loadRef`·`connected` 문구·reference-data 의 조용한
  catch 는 0줄 건드리지 않았다. 프로덕션 2개 파일 + 단위 테스트 11개 + e2e 영구 스펙 2개 +
  가이드 한 문단.

- 검증(릴리스 시점에 다시 실행): `cd web && npm ci`(package.json·lock 일치, 버전 올린 뒤에도
  재확인)·`npm run lint`(tsc -b)·`npm test` **114 passed (6 파일)**·`npm run build`,
  `gofmt -l .` 빈 출력·`go build ./...`·`go vet ./...`·`git diff --check` 빈 출력, 임시
  PostgreSQL 16 컨테이너에 `VISITFLOW_TEST_DSN` 을 주고 `go test ./... -count=1`
  (internal/app **57.813s** — SKIP 아님), 그리고 `bash scripts/local-e2e.sh`
  **30 passed (1.2m) / 종료 코드 0** — 실제 `npm run build` 임베드·새 PostgreSQL·실서버·실제
  Chrome(채널 'chrome', 번들 브라우저 미설치)으로 기준 28개 + 새 스펙 2개가 모두 통과했다.
  구현 회차의 red→green 은 수정 전 `LobbyPage.tsx`(git show HEAD) + `lobbyCounts.ts` 없음 +
  새 스펙 있음 상태로 짝지어 `1 failed / 29 passed` 를 먼저 받았다 —
  `expect(locator).toBeVisible() failed` /
  `getByRole('alert').filter({ hasText: /로비 현황을 불러오지 못했습니다/ })` 이
  `element(s) not found` 였고, 같은 실행의 error-context 가 증상 전체를 담았다
  (`paragraph: 방문 예정` / `heading "0"` / `text: 재난 시 체류 기준 인원` /
  `tab "현재 방문자 0"` / `paragraph: 표시할 방문자가 없습니다.`). 정찰이 코드 근거로만 적어
  두었던 「실패 시 `0` 이 실제 브라우저에 그려지는가」는 수정 전 번들의 실제 Chrome 스냅샷으로
  닫혔다 — 그려지며, 그 스냅샷의 유일한 알림은 `alert: Failed to fetch · button "Close"` 였다.
  정상 경로 스펙(30번)은 수정 **전에도** 통과해 선택자가 제품이 아니라 스펙 탓으로 깨진 것이
  아님을 확인했고, 동시에 "정상 200 의 진짜 0 에는 실패 문구가 뜨지 않는다" 의 영구 가드다.
  남은 한계는 정직하게 적는다 — `docs/USER_GUIDE.md` 는 한 문단만 고치고 `USER_GUIDE.pdf` 는
  재생성하지 않았고, `web/e2e` 는 아직 `tsc -b`(npm lint) 의 타입 검사 대상이 아니라 이번에도
  늘어난 스펙을 별도 `tsc --noEmit` 로만 확인했다. 같은 「실패를 0 으로 단정」 유형이 관리
  Dashboard 상단 네 `MetricCard`·「운영 준비도」 막대, KioskPage 의 「현재 방문중 N명」 칩,
  통계 화면의 일곱 요약 값에 남아 있고 다음 후보다. `LobbyPage` 의 reference-data 조용한
  catch 로 「로비」 필터가 소리 없이 비는 것은 이번 범위에서 일부러 뺐다.
