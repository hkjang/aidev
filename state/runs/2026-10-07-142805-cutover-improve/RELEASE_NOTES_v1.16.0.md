## KCB Cutover Dashboard v1.16.0

이번 판은 **이미 지워진 작업 아래에 ➕(하위 추가)를 눌렀을 때 뜨던 엉뚱한 오류 문구** 를 바로잡습니다. v1.15.0 이 `action: 'delete'`·`action: 'move'`·상태 변경 세 형태에 넣은 **대상 존재 검사(`404` `TARGET_NOT_FOUND`)** 에서 `action: 'add'` 한 분기만 빠져 있었고, 그 분기는 전혀 다른 경로로 **`400` "activity.json 데이터 형식이 올바르지 않습니다."** 를 내고 있었습니다. 이번 변경으로 네 형태가 같은 `404` 로 모였습니다.

**이것은 조용한 성공이 아니었습니다.** 해당 요청은 v1.15.0 에서도 **이미 거절되고 있었고 데이터가 잘못 저장된 적은 없습니다.** 고친 것은 **오류 분류(`400` → `404`)와 관리자가 화면에서 읽는 문구** 입니다.

### 버그 수정
- **이미 지워진 작업 아래 하위 추가가 "activity.json 데이터 형식이 올바르지 않습니다." `400` 으로 거절되는 것 수정**: 관리 화면(`/admin`)의 ➕ 는 `PUT /api/activities` 로 `{ action: 'add', parentId }` 를 보냅니다. 서버는 **`parentId` 로 지정한 행이 저장된 목록에 아직 있는지 검사하지 않았습니다.**
  - 그래서 **다른 관리자가 그 사이 지운 행** 의 ➕ 를 내 화면에서 누르면, 서버는 부모가 없는 활동을 목록에 넣고 → 저장 전 검증(`validateActivityImport`)의 **부모 id 존재 검사** 에 걸려 → 라우트가 `400`(`INVALID_DATA`) 을 돌려주었습니다.
  - 이때 빨간 저장 실패 배너(v1.9.0)에 뜨는 문구가 **`activity.json 데이터 형식이 올바르지 않습니다.`** 였습니다. 이것은 **`activity.json` 업로드 파일이 잘못됐다는 뜻으로 읽히는 문구** 입니다. 관리자는 파일을 업로드한 적도 없는데 파일 형식 오류를 보게 되고, **실제 원인(그 행이 이미 사라졌다)과 해야 할 일(목록을 다시 확인한다 / 새로고침한다)은 배너 어디에도 없었습니다.**
  - 바로 옆에서 같은 상황의 🗑 / ▲▼ / 상태 드롭다운은 v1.15.0 이후 **`404` 와 `대상 작업(...)이 상황판에 없어 변경하지 않았습니다. 다른 곳에서 이미 지웠을 수 있습니다.`** 를 제대로 띄우고 있었습니다. **같은 원인인데 ➕ 만 다른 말을 하고 있었습니다.**
  - 이제 `action: 'add'` 도 **`parentId` 가 저장된 목록에 없으면 아무것도 쓰지 않고 `404`** 를 돌려줍니다(`{ error, code: 'TARGET_NOT_FOUND' }`). 다른 세 형태와 **같은 코드·같은 배너 문구** 이고, 1초 폴링이 곧 그 행을 화면에서 치웁니다.
  - **`parentId: null`(최상위 작업 추가)은 부모가 없는 것이 정상이므로 그대로 통과합니다.**

### 알려진 동작 / 한계
- **데이터 보호 효과는 없습니다.** 위 요청은 v1.15.0 에서도 `400` 으로 거절되어 **부모 없는 활동이 저장된 적이 없습니다.** 이번 변경의 값은 **오류 코드의 일관성(네 형태 모두 `404`)과 배너 문구의 정확성** 뿐입니다. 상황판에 보이는 데이터는 이전 버전과 완전히 같습니다.
- **`404` 는 `action: 'add'` 의 `parentId` 에만 새로 걸립니다.** `activities` 배열을 통째로 보내는 저장(관리 화면의 상태 변경·행 편집)은 `targetId`·`parentId` 를 함께 보내더라도 **영향이 없습니다** — 검사를 배열 분기 위로 올리지 않았습니다. 대시보드 제목 변경도 그대로입니다.
- **`parentId` 가 문자열도 `null` 도 아니면(예: 숫자) 이전과 같이 `400`(`UNSUPPORTED_ACTION`) 입니다**(v1.12.0 의 동작). 분기 자체가 성립하지 않는 요청이라 `404` 로 바뀌지 않습니다.
- **`activity.json` 업로드의 `400` 문구는 그대로입니다.** `POST /api/activities/import` 로 실제로 잘못된 파일을 올렸을 때는 여전히 `activity.json 데이터 형식이 올바르지 않습니다.` 가 맞는 문구이므로 손대지 않았습니다. 이번 변경은 **➕ 요청이 그 문구에 도달하지 않게** 한 것입니다.
- **level 50 한계는 이번에 다루지 않았습니다.** 존재하는 level 50 부모 아래에 ➕ 를 누르면 level 51 자식이 만들어져 **여전히 `400` "데이터 형식이 올바르지 않습니다."** 가 뜹니다. 같은 계열의 혼란스러운 문구지만, UI 에서 ➕ 를 숨길지 서버에서 전용 코드로 막을지는 정책 판단이 필요해 **다음 판으로 남겼습니다.**
- 동시 편집 경합(v1.15.0 의 `409`, 가이드 4.5 절), 상태 전파 규칙(v1.7.0, 가이드 4.3 절), 작업 id 생성 방식은 손대지 않았습니다. 데이터 형식·마이그레이션 변경이 없어 **이전 버전으로 되돌리면 완전히 복구됩니다**(되돌리면 위 `400` 문구가 다시 나타납니다).
- 관리자 가이드(`docs/ADMIN_GUIDE.md`) **5.6 절 API 표의 `PUT /api/activities` 행** 에 `action: "add"` 의 `parentId` 도 같은 `404` 대상이라는 한 줄(`null` 예외 포함)을 더했습니다.

### 검증
- 기존 e2e `e2e/admin-missing-target.spec.ts` 에 **2건** 을 더했습니다(5건 → 7건): 없는 `parentId` 로 보낸 `action: 'add'` 가 `404` `TARGET_NOT_FOUND` 이고 **`activities` 와 `lastUpdated` 가 둘 다 그대로인지** 확인합니다.
- **수정 전 실패 / 수정 후 통과** 를 확인했습니다. 수정 전에는 `404` 대신 `400` 이 나오면서 응답 본문에 관리자가 보던 그 문구가 그대로 보였습니다 — `{"error":"activity.json 데이터 형식이 올바르지 않습니다.","code":"INVALID_DATA","details":[{"path":"activities[2].parentId","message":"부모 id \"...\"가 activities에 존재하지 않습니다."}]}`.
- **기존 `200` 계약 2건**(최상위 추가 `parentId: null`, 존재하는 부모 아래 추가)을 수정 전에 먼저 고정해 두고, 수정 후에도 그대로 `200` 인지 확인했습니다. 숫자 `parentId` → `400` `UNSUPPORTED_ACTION` 은 `e2e/admin-put-contract.spec.ts` 가 이미 지키고 있어 통과를 확인만 했습니다.
- `lib/treeUtils.ts`·`addActivity`·`validateActivityImport` 는 **손대지 않아 단위 테스트 기대값 변경이 0건** 입니다. 프로덕션 변경은 `app/api/activities/route.ts` 한 파일(+7줄)입니다.
- 릴리즈 시점 전체 검사 통과: 타입 검사(`tsc --noEmit`), 린트, 단위 테스트 **95건**, 프로덕션 빌드, e2e **40건**(이전 판 38건 + 신규 2건). 아래 배포 이미지도 같은 소스에서 빌드했으며, 올린 이미지를 실제로 띄워 `GET /api/activities` 가 `200` 으로 상황판 데이터를 돌려주는 것까지 확인했습니다.

### 배포
- 폐쇄망 배포용 Docker 이미지: `cutover-v1.16.0.tar.gz`
  ```bash
  docker load -i cutover-v1.16.0.tar.gz
  docker run -d -p 3000:3000 \
    -e USER_PASSWORD=1234 \
    -e ADMIN_PASSWORD=admin1234 \
    -e AUTH_SECRET=운영환경용-충분히-긴-임의문자열 \
    -v cutover-data:/app/data \
    --name cutover-app \
    --restart always \
    cutover:v1.16.0
  ```
- 올린 뒤 확인할 것: 관리자 두 명이 같은 시간대에 콘솔을 쓰는 중 **한쪽이 지운 행의 ➕ 를 다른 쪽이 눌렀을 때** 빨간 배너에 `대상 작업(...)이 상황판에 없어 변경하지 않았습니다. …` 가 뜨는지(이전에는 파일 형식 오류 문구였습니다). **정상적인 ➕ 추가(최상위·존재하는 부모 아래)가 막히지 않는지** 도 함께 봐 주십시오 — 막히면 목록 갱신 문제가 아니라 이번 검사가 과하게 걸린 것이므로 보고해 주십시오.
