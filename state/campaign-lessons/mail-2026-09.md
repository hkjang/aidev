- **발송 결과 기록(complete/UPDATE)과 다음 수신자 INSERT 에는 발송용 컨텍스트를 재사용하지 않고 별도의 짧은 신선한 컨텍스트를 쓴다. 발송 예산을 정할 때 소스에서 '연결 마감 × 시도 횟수(+대기) × 수신자 수' 를 계산해 최대 timeout 설정값에서도 예산이 먼저 만료되지 않는지 확인하고, TCP 는 받되 응답하지 않는 리스너를 릴레이로 두는 테스트로 기록이 queued/sending 에 영원히 남지 않음을 검증한다. 기록 오류는 버리지 않는다(_ = 금지).** — 멈춘 릴레이에서는 발송이 정확히 컨텍스트 만료 시점에 반환해 기록 UPDATE 가 즉시 실패하고, 진단이 가장 필요한 장애 상황에서 '시도마다 기록' 약속이 깨지며 재청구로 중복 발송까지 생긴다. - **발송 고루틴에 상한(버퍼 채널 세마포어 등)을 두어 동시 발송 수를 제한하고, 상한을 넘는 작업은 대기시키되 기록 INSERT 는 즉시 남긴다. 사용자 재시도·클라이언트 루프로 같은 이벤트가 반복 생성될 수 있는 경로(승인 요청 등)에는 같은 주체·같은 대상을 묶거나 억제하는 규칙을 alert 와 동일하게 넣는다.** — 응답 없는 릴레이에서 고루틴 하나가 수 분씩 살아남으므로 상한이 없으면 고루틴과 TCP 연결이 계속 쌓이고, API 키 하나로 관리자 전원에게 메일을 쏟아낼 수 있다. (근거: ai-admin, dataworks, 2회)
- **메일 본문에 넣는 링크는 쓰기 전에 실제 라우터 소스(프론트 해시 형식·경로 목록, 서버 핸들러)에서 존재하는 경로인지 확인하고, 안내 문구('다시 보내면 처리됩니다', '회전하면 새 키 발급', '<누가> 제출했습니다')는 그 동작의 코드 경로를 따라가 사실인지 확인한다. 테스트가 잘못된 링크·문구를 그대로 단언해 결함을 고정하지 않도록 한다.** — 존재하지 않는 경로로 가는 링크와 실제 동작과 다른 안내가 여러 저장소에서 반복됐고, 잘못된 안내가 스팸 메일·반복 알림 같은 2차 결함을 유발했다. (근거: dataworks, seaton, sqlon, 5회)
- **이벤트 알림 훅을 붙이기 전에 소스에서 세 가지를 확인한다: (1) 트리거 조건이 상태값이 아니라 상태 전이를 보고 실제 이벤트당 한 번만 발화하는지(부분 승인처럼 같은 상태에 머무는 경우 포함), (2) 알림이 의존하는 데이터(작성자 필드 등)를 제품 코드가 실제로 채우는지, (3) 다른 알림이 나간다고 가정하고 억제한다면 그 알림이 요약 모드·사용자 설정·관리자 설정에 의해 안 나갈 수 있는지. 테스트에서 제품이 채우지 않는 값을 직접 주입해 통과시키지 않는다.** — 조건을 잘못 잡아 승인자를 제출자로 적은 중복 메일이 나가거나, 절대 채워지지 않는 필드 때문에 약속한 알림이 한 번도 발송되지 않거나, 억제 조건이 다른 알림을 삼켜 버렸다.
