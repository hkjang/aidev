## 이 캠페인에서 다른 저장소가 이미 걸린 것 — 시작 전에 확인하고, 끝내기 전에 다시 확인하세요
(캠페인 "mail-2026-09" 의 리뷰 거절·심사 거절·회귀 19건에서 정제한 규칙. 러너가 자동으로 붙였습니다.)
- **발송 결과 기록(UPDATE/INSERT)은 발송용 컨텍스트가 아니라 context.Background 기반의 짧은 별도 컨텍스트로 수행하고, 발송 예산은 (재시도 횟수 × 연결 마감 + 대기)보다 크게 잡으며 기록 오류를 버리지 않는다** — TCP는 받되 응답하지 않는 릴레이에서는 발송이 예산을 다 써 버려 기록 UPDATE가 deadline exceeded로 실패하고 행이 영원히 '대기/발송 중'으로 남는다 (근거: ai-admin, hunter, seaton, 4회)
- **TLS 없는 연결에서 자격증명을 보낼지 정책을 먼저 정하고, 'AUTH LOGIN만 광고 + STARTTLS 없음' 가짜 릴레이를 127.0.0.1이 아닌 주소에 띄워 평문 전송/인증 실패를 직접 확인한다** — server.Name != host 비교는 두 값이 같은 설정값이라 항상 거짓이고 표준 PlainAuth는 비-localhost 평문에서 항상 실패하므로 코드만 보면 놓친다 (근거: appstore, madi, vibe-coders, 3회)
- **메일 본문의 링크 경로·안내 문구·행위자 표기를 쓰기 전에 UI 라우터의 실제 경로, 게이트/회전 등 도메인 로직의 실제 동작, 이벤트의 실제 행위자를 소스에서 대조한다** — 존재하지 않는 경로, 사실과 다른 안내(재전송하면 승인 적용·회전하면 만료 해소), 승인자를 제출자로 적는 문구가 그대로 사용자에게 나간다 (근거: dataworks, seaton, sqlon, 4회)
- **발송 고루틴에 세마포어 상한을 두되 기록은 즉시 남기고, 승인 요청 같은 이벤트도 같은 사용자·같은 요청의 재시도를 묶거나 억제하는 규칙을 둔다** — 죽은/침묵 릴레이에서 알림마다 고루틴과 TCP 연결이 상한 없이 쌓이고, API 키 하나로 관리자 전원에게 메일을 쏟아낼 수 있다 (근거: ai-admin, dataworks, 2회)
- **알림 이벤트를 상태 스냅샷(state == X)이 아니라 실제 전이·행위로 판별하고, 부분 승인·헤더 없는 재요청 같은 중간 상태 케이스를 테스트한다** — 부분 승인 뒤에도 같은 상태에 머무는 경우 '제출' 메일이 중복 발송되고 행위자까지 잘못 표기된다 (근거: sqlon, dataworks, 2회)
- **테스트 릴레이는 connection refused·Accept 후 침묵·AUTH만 광고(STARTTLS 없음) 3종을 갖추고, 잘못된 값을 단언하거나 제품에서 채워지지 않는 필드를 주입해 통과시키는 테스트를 만들지 않는다** — connection refused만 있으면 컨텍스트 만료·평문 인증 경로를 타지 않고, 결함을 고정하는 테스트는 회귀 방지가 아니라 리뷰 거절 사유가 된다 (근거: madi, sqlon, dataworks, vibe-coders, seaton, 5회)
- **알림 발송 조건에 쓰는 데이터 필드(작성자 등)가 실제 제품 코드 경로에서 채워지는지 확인하고, 비어 있으면 조용히 반환하지 않는다** — 필드를 채우는 경로가 없으면 문서와 설정 스위치가 약속한 알림이 한 번도 발송되지 않는다 (근거: vibe-coders, 1회)
- **시험 발송 실패 응답의 형식을 프론트 API 클라이언트의 non-2xx 오류 파싱 규약에 맞추고, 실패 시에도 결과 표시와 발송 기록 갱신이 실행되게 한다** — 클라이언트가 다른 오류 스키마만 파싱하면 실제 오류 메시지가 사라지고 발송 기록도 갱신되지 않는다 (근거: vibe-coders, 1회)
