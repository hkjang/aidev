## 이 캠페인에서 다른 저장소가 이미 걸린 것 — 시작 전에 확인하고, 끝내기 전에 다시 확인하세요
(캠페인 "mail-2026-09" 의 리뷰 거절·심사 거절·회귀 38건에서 정제한 규칙. 러너가 자동으로 붙였습니다.)
- **평문 연결 인증 가드(`!server.TLS && server.Name != a.host`)를 참조 구현에서 베끼지 말고, 비교되는 두 값이 소스에서 어디서 오는지 추적해 실제로 달라질 수 있는지 확인한다. TLS 없는 연결에서 자격증명을 보낼지 정책을 먼저 정하고(auto는 STARTTLS 미광고 시 인증 거부+안내, none만 명시적 허용) 문서에 적는다.** — server.Name도 loginAuth.host도 같은 설정 host라 가드가 항상 거짓이고, STARTTLS 없는 릴레이에 비밀번호가 base64 평문으로 나간다. (근거: appstore, dataworks, igame, jupiq, madi, moyro, relio, seaton, visitflow, 13회)
- **인증 경로 테스트는 127.0.0.1이 아니라 비-루프백 주소에 바인드한 가짜 릴레이(STARTTLS 없음, AUTH LOGIN 또는 AUTH PLAIN LOGIN만 광고)로 돌리고, 자격증명이 선로에 나가지 않는 것과 인증이 실제로 되는 것을 둘 다 단언한다.** — stdlib PlainAuth의 localhost 예외 때문에 테스트만 통과하고 실제 릴레이에선 PLAIN이 항상 실패하거나 LOGIN으로 평문 누출된다. (근거: igame, vibe-coders, madi, 4회)
- **발송 결과 기록(UPDATE, 다음 수신자 INSERT)은 발송용 컨텍스트가 아닌 별도의 짧은 컨텍스트로 한다. 침묵 릴레이(accept 후 무응답) 기준 최악 소요(재시도 × 연결 마감 + 대기, timeout 설정 최댓값)를 계산해 발송 예산과 비교하고, 배너를 주지 않는 가짜 릴레이로 기록이 queued/sending에 남지 않는지 시험 발송 경로까지 테스트한다.** — 발송이 예산 만료 시점에 반환하면 같은 ctx로 하는 기록이 deadline exceeded로 실패해 '시도마다 기록' 약속이 진단이 가장 필요한 장애에서 깨진다. (근거: ai-admin, hunter, seaton, 4회)
- **발송 고루틴에 상한(버퍼 채널 세마포어)을 두고 기록 INSERT는 상한과 무관하게 즉시 남긴다. 사용자가 반복 호출할 수 있는 트리거(승인 요청 등)는 같은 사용자·같은 요청을 묶거나 윈도우로 억제한다.** — 상한 없이 띄우면 죽은/침묵 릴레이에서 고루틴과 TCP 연결이 쌓이고, API 키 하나로 관리자 전원에게 요청당 N통을 쏟아낼 수 있다. (근거: ai-admin, dataworks, 2회)
- **메일 트리거·억제 조건을 실제 상태 전이와 재시도 경로에 대조한다: '제출'로 간주한 상태가 부분 승인 뒤에도 유지되는지, 억제 근거로 삼은 다른 알림이 실제로 발송되는지(요약 묶음·사용자/관리자 설정), 헤더 없는 재요청이 새 승인을 만드는지 확인하고 그 경계 케이스를 테스트한다.** — 조건이 상태 기계와 어긋나면 승인자를 제출자로 오표기한 중복 메일이 가거나, 멘션 메일이 나가지도 않을 알림에 묶여 조용히 사라진다. (근거: sqlon, moina, dataworks, 4회)
- **메일 본문의 링크와 안내 문구는 라우터 소스와 실제 동작을 확인한 뒤 쓴다. 링크는 프론트 라우터의 hash 형식·basename·자식 라우트 목록에서 실제 존재하는 경로만 쓰고, '다시 보내면 처리된다', '회전하면 새 키가 발급된다' 같은 문장은 그 동작을 하는 코드를 찾아 사실인지 확인한다. 잘못된 링크를 단언하는 테스트를 만들지 않는다.** — 존재하지 않는 경로와 사실과 다른 안내는 404·중복 메일·스팸 루프로 이어지고, 테스트가 결함을 고정한다. (근거: dataworks, seaton, sqlon, 5회)
- **기능이 의존하는 데이터 필드(예: 작성자)가 실제 제품 경로에서 채워지는지 grep으로 확인하고, 시험 발송 실패 응답은 프론트 apiClient가 non-2xx를 어떻게 파싱하고 onSuccess에서만 상태·기록을 갱신하는지 확인한 뒤 설계한다. 제출 전 저장소의 전체 검증(웹 typecheck 포함)을 돌린다.** — 테스트가 값을 주입해 통과해도 제품에선 한 번도 발송되지 않고, 실패 오류가 화면에 fallback 문구로 바뀌며 기록도 갱신되지 않는다. (근거: vibe-coders, 3회)
- **시작 전에 캠페인의 사람 승인 전용 파일 목록을 확인하고 secret 관련 핸들러·테스트 파일은 건드리지 않는다. 필요하면 그 파일 밖에서 해결하거나 사람에게 넘긴다.** — 보호 파일을 한 줄이라도 건드리면 자동 심사가 needs-human으로 멈춘다. (근거: jikim, umm, 2회)
