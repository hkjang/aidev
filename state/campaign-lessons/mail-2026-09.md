## 이 캠페인에서 다른 저장소가 이미 걸린 것 — 시작 전에 확인하고, 끝내기 전에 다시 확인하세요
(캠페인 "mail-2026-09" 의 리뷰 거절·심사 거절·회귀 20건에서 정제한 규칙. 러너가 자동으로 붙였습니다.)
- **TLS 없는 연결에서 자격증명을 보낼지 정책을 먼저 정하고, 참조 구현의 `!server.TLS && server.Name != host` 가드를 그대로 옮기지 않는다. 'AUTH LOGIN 만 광고 + STARTTLS 없음' 인 비-localhost 가짜 릴레이로 실제 전송 여부를 확인하는 테스트를 둔다.** — 클라이언트 생성 시 넘긴 호스트명과 비교값이 같아 가드가 항상 거짓이 되어 비밀번호가 평문으로 나가거나, 반대로 표준 PLAIN 은 비-localhost 평문에서 항상 실패한다. (근거: appstore, dataworks, madi, vibe-coders, 4회)
- **발송 결과 기록(UPDATE·다음 수신자 INSERT)은 발송용 컨텍스트가 아니라 별도 컨텍스트로 하고, 발송 예산은 소스에서 '연결 마감×시도 횟수+백오프×수신자 수' 를 계산해 그보다 크게 잡는다.** — 응답 없는 릴레이에서 발송 컨텍스트가 먼저 만료되면 기록이 실패해 행이 영원히 'queued/sending' 으로 남아 '시도마다 기록' 약속이 정확히 진단이 필요한 상황에서 깨진다. (근거: ai-admin, hunter, seaton, 3회)
- **배경 발송 고루틴에 세마포어 상한을 두고 상한 초과 시 기록만 즉시 남기고 발송은 대기시키며, 사용자 요청마다 발생하는 알림(승인 요청 등)은 같은 사용자·같은 요청의 재시도를 묶거나 제한한다.** — 응답 없는 릴레이에서는 고루틴 하나가 수십~수백 초 살아 있어 유입이 더 빠르면 고루틴·TCP 연결이 무한히 쌓이고, 억제 없는 이벤트는 API 키 하나로 관리자 전원에게 메일 폭탄이 된다. (근거: ai-admin, dataworks, 2회)
- **메일 본문의 링크 경로와 '이렇게 하면 됩니다' 안내 문구는 쓰기 전에 UI 라우터와 실제 처리 코드에서 확인하고, 테스트 기대값도 라우터 소스에서 가져온다.** — 존재하지 않는 해시 경로를 가리키거나 실제 게이트·회전 로직과 다른 안내를 하면 사용자를 오도하고 같은 메일이 반복 발송되며, 잘못된 링크를 단언한 테스트가 결함을 고정한다. (근거: dataworks, seaton, 3회)
- **알림 트리거는 결과 상태가 아니라 일어난 전이(이벤트)로 판정하고, 상태 머신에 '같은 상태에 머무는 전이' 가 있는지 소스에서 먼저 확인한다.** — 승인 후에도 승인 부족으로 같은 상태에 머무는 경우 상태 기반 조건이 승인 훅을 '제출' 로 오인해 중복 메일을 보내고 승인자를 제출자로 잘못 적는다. (근거: sqlon, 1회)
- **테스트는 제품이 실제로 만드는 데이터와 경로로만 통과해야 한다. 제품이 채우지 않는 필드 주입, localhost 예외, 단일 승인만 다루는 케이스, connection refused 만으로 흉내 낸 죽은 릴레이를 피하고 'TCP 는 받되 응답 없음'·부분 승인·평문 AUTH 케이스를 필수로 넣는다.** — 이런 테스트는 결함을 잡지 못한 채 통과해 커밋 메시지와 가이드가 약속한 동작이 실제 제품에서는 성립하지 않는 상태로 머지된다. (근거: vibe-coders, dataworks, sqlon, madi, seaton, 5회)
- **수신자·작성자 등 메일 대상이 되는 필드는 제품 안에 실제로 그 값을 채우는 쓰기 경로가 있는지 소스에서 확인한 뒤 연결한다.** — 채우는 코드가 없으면 스위치·문서·테스트가 약속한 알림이 실제 제품에서 한 번도 발송되지 않는다. (근거: vibe-coders, 1회)
- **시험 발송 API 의 실패 응답 형식은 프론트 API 클라이언트가 실제로 파싱하는 오류 스키마와 맞추고, 실패 시에도 결과 표시와 발송 기록 목록 갱신이 일어나게 한다.** — 클라이언트가 non-2xx 를 예외로 던지며 다른 스키마만 읽으면 서버 오류 메시지가 fallback 문구로 바뀌고 발송 기록도 갱신되지 않는다. (근거: vibe-coders, 1회)
