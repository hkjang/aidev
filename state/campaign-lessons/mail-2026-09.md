## 이 캠페인에서 다른 저장소가 이미 걸린 것 — 시작 전에 확인하고, 끝내기 전에 다시 확인하세요
(캠페인 "mail-2026-09" 의 리뷰 거절·심사 거절·회귀 36건에서 정제한 규칙. 러너가 자동으로 붙였습니다.)
- **LOGIN 인증의 평문 차단 가드를 참조 구현에서 옮기지 말고, 구현 전에 'TLS 없는 연결에서 자격증명을 보낼지' 정책을 문서에 정한 뒤 server.TLS 만으로 판정한다. 호스트명 비교(server.Name != host)는 NewClient 에 넘긴 값과 같아 항상 거짓이다.** — 8개 저장소가 전부 같은 가드를 복사해 STARTTLS 없는 릴레이에 비밀번호가 base64 평문으로 나갔다. (근거: appstore, dataworks, igame, jupiq, madi, moyro, relio, seaton, 11회)
- **TLS 없는 연결의 AUTH 는 비-루프백 주소에 바인드한 가짜 릴레이(AUTH 광고 + STARTTLS 없음)로 LOGIN 누출과 PLAIN 실패 두 방향을 모두 테스트하고 단언을 남긴다.** — 127.0.0.1 테스트는 stdlib 의 localhost 예외로 통과해 PLAIN 이 항상 실패하는 것과 LOGIN 이 평문으로 새는 것 둘 다 잡지 못한다. (근거: igame, vibe-coders, madi, 3회)
- **발송 결과 기록(UPDATE)과 다음 수신자 INSERT 는 발송용 컨텍스트와 분리된 컨텍스트로 쓰고, 재시도 횟수×연결 마감×수신자 수의 최악 소요를 발송 예산과 소스에서 비교한 뒤 침묵 릴레이(TCP 수락 후 무응답)로 테스트한다.** — 연결 마감 합계가 컨텍스트 예산을 넘으면 기록 UPDATE 가 deadline exceeded 로 실패해 행이 영원히 queued/sending 으로 남아 장애 진단이 불가능해진다. (근거: ai-admin, hunter, seaton, 4회)
- **발송 고루틴에 세마포어 상한을 두되 기록 INSERT 는 즉시 남기고, 재시도로 반복 발생하는 이벤트(승인 요청 등)는 사용자·요청 단위 디바운스/중복 억제 규칙을 명시한다.** — 침묵 릴레이에서 고루틴과 TCP 연결이 상한 없이 쌓이고, 억제 없는 승인 요청은 API 키 하나로 관리자 전원에게 메일 폭탄을 만든다. (근거: ai-admin, dataworks, 2회)
- **이벤트를 알림에 연결하기 전에 트리거 조건의 상태 전이와 조기 반환에 쓰는 필드가 제품 코드 경로에서 실제로 채워지는지 소스에서 추적한다. 테스트가 그 값을 직접 주입해 통과하면 증거가 아니다.** — 부분 승인이 같은 상태에 머물러 중복·오표기 발송, 다른 알림이 실제로 나가는지 확인 없이 억제, 채워지지 않는 필드로 조용히 반환해 한 번도 발송되지 않는 결함이 나왔다. (근거: sqlon, moina, vibe-coders, 3회)
- **메일 본문의 안내 문구(재전송 방법, 키 회전 효과, 행위자 표기)는 그 문구가 설명하는 코드 경로와 대조해 실제 동작과 일치시킨다.** — 문구가 코드와 다르면 사용자를 잘못된 행동으로 유도하고 재알림·스팸 루프를 만든다. (근거: dataworks, seaton, sqlon, 3회)
- **메일 링크 경로는 프론트 라우터 정의(해시 형식, basename, 자식 경로 목록)에서 존재하는 경로인지 확인하고, 테스트는 실제 존재하는 경로를 단언한다.** — 존재하지 않는 경로를 가리키는 링크가 전부 404 로 떨어졌고, 테스트가 잘못된 링크를 단언해 결함을 고정했다. (근거: dataworks, 2회)
- **작업 전에 사람만 승인할 수 있는 파일 목록을 확인하고, 시크릿 처리 핸들러·시크릿 필드 테스트 같은 파일은 수정하지 않고 기존 API 를 호출만 한다.** — 메일 비밀번호 저장을 위해 시크릿 계층 파일을 건드리면 자동 처리가 불가능해져 needs-human 으로 넘어간다. (근거: jikim, umm, 2회)
