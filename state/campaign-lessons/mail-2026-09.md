- **메일 본문에 넣는 링크 경로와 안내 문구('다시 보내면 자동 처리', '회전하면 새 키 발급', '<누가> 제출')는 넣기 전에 UI 라우터·해당 핸들러 소스에서 실제 동작과 일치하는지 확인하고, 이벤트별 실제 행위자를 쓴다** — 링크와 문구가 실제 동작과 달라 존재하지 않는 경로를 가리키거나, 안내대로 하면 스팸·재알림이 발생했고 테스트가 그 잘못된 값을 그대로 고정했다 (근거: dataworks, seaton, sqlon, 4회)
- **정상 경로만이 아니라 실패 경로(평문 인증, 부분 승인, 멈춘 릴레이, 잘못된 링크)를 테스트로 덮고, 기대값은 소스에서 확인한 실제 값으로 단언한다** — 실패 경로 테스트가 없거나 잘못된 값을 단언해 결함이 회귀 방지 없이 남거나 오히려 고정되었다 (근거: dataworks, madi, sqlon, vibe-coders, 4회)
- **발송 결과 기록(DB Update)은 발송용 컨텍스트가 아닌 만료되지 않는 별도 컨텍스트로 하고, 발송 컨텍스트 마감이 연결 마감×시도 횟수+대기 시간보다 큰지 계산해 확인하며, TCP는 받되 응답이 없는 릴레이로 시험 발송해 기록이 '발송 중/대기'에 남지 않는지 본다** — 발송 ctx가 먼저 만료되면 기록 Update가 실패해 진단이 가장 필요한 장애 상황에서 발송 기록이 영원히 대기로 남고, connection refused 테스트만으로는 이 경로를 타지 않는다 (근거: hunter, seaton, 3회)
- **TLS 없는 연결에서 인증을 할지 말지 결정하고, 비-localhost 호스트명·AUTH LOGIN만 광고·STARTTLS 없음인 가짜 릴레이로 자격증명이 평문으로 나가지 않는지(또는 의도한 대체 인증이 동작하는지) 실제로 단언한다** — Go smtp.PlainAuth는 비-localhost 평문에서 거부하고 자체 LOGIN 구현의 평문 차단 조건은 항상 거짓이 되기 쉬우며, 127.0.0.1 테스트는 localhost 예외로 통과해 결함을 숨긴다 (근거: madi, vibe-coders, 3회)
- **알림 트리거는 '상태가 X다'가 아니라 'X로 전이했다'로 정의하고, 같은 사용자·같은 대상의 재시도를 묶는 억제 규칙(중복 키·디바운스)과 발송 고루틴 상한을 둔다** — 헤더 없는 재시도나 부분 승인처럼 상태가 유지되는 경우마다 새 알림이 나가 관리자 전원에게 스팸이 가고 고루틴이 상한 없이 쌓였다 (근거: dataworks, sqlon, 2회)
- **알림 발송 조건에 쓰는 필드(작성자 등)를 실제 제품 코드 경로가 채우는지 확인하고, 테스트에서 값을 직접 주입해 통과시키지 않는다** — 필드를 채우는 경로가 없어 문서가 약속한 알림이 제품에서 한 번도 발송되지 않았고 테스트는 주입값으로 통과했다 (근거: vibe-coders, 1회)
