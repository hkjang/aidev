Actions 분 소진·스펜딩 한도를 확인하고, 깨진 실행을 UI 에서 열어 step 실패가 아닌 프로비저닝 메시지("The job was not started…" 계열)를 읽어 주세요.** 저장소 쪽으로는 **아무 변경도 하지 않았다** — 원인이 단계 실행 전이라 어떤 워크플로 수정도 증상을 가릴 뿐이고(그리고 검증할 수단이 0), 명세의 "검사를 - 실패 재현: **못 함 — 원리적으로 불가능하다.** 실패는 GitHub 이 잡을 러너에 띄우기 전에 일어나므로(실패한 step 0개, 로그 0바이트, 잡 수명 2~3초) 로컬에서 실행할 명령 자체가 존재하지 않고, `gh` 미인증·비공개 저장소라 원본 로그·빌링도 볼 수 없다. 대신 **반대 방향을 측정**했다 — `check.yml:33-54` 과 같은 순서로 main@bd2d84c 를 전부 로컬 실행: `npm ci --no-audit --fund=false` exit 0 → `TZ=UTC npm run check` exit 0 (`Test Files 6 passed (6) / Tests 61 passed (61)`) → `TZ=UTC npm run build` exit 0 → `node scripts/ci-env.mjs` → `.env.dev written for CI` → `migrate: applied 10 migrations` → 서버 기동 `your v0.1.6 (dev) 시작` → `TZ=UTC node scripts/e2e.mjs` → **`163 passed, 0 failed` exit 0**. 저장소 쪽에서 재현되는 실패는 **0건**이다. - 보류 아이디어: PR #5 의 Retry-After 수정과 e2e 포트 환경변수화가 main 에 없다 — CI 가 풀리면 가장 먼저 되찾을 것(4/1/S) / `v.int` 가 `'0x10'`→16·`'1e3'`→1000 을 정수로 받는다 — 다섯 회차 연속 차선(3/1/S) / `ci-env.mjs` 가 `YOUR_DATABASE_URL` 에 55440 을 박아 다른 프로젝트 컨테이너와 충돌하면 로컬 검증이 조용히 남의 DB 를 친다(3/1/S, 이번 회차에 실제로 `irumx_gateway` 인증 실패로 겪었다) / e2e 가 서버 자신의 500 서명을 한 번도 만들지 않아 `alertOperator` 의 서버 경로가 미검증(3/2/S) / `v.instant` 가 ISO-8601 이 아닌 `'2026'`·`'Dec 25'` 도 통과시킨다(2/1/S)
