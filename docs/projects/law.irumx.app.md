- 이번에 새로 배제한 것(앞선 회차들이 못 한 부분): CI 가 빨개진 직전에 들어온 **v0.1.5/v0.1.6 의 DB 차단기·빨리 실패·503**(fd8252a, `db.ts`·`errors.ts`·vendor postgres PATCH 5)이 CI 를 깨뜨렸을 가능성. 앞선 전수 재현은 c62b3a0(차단기 이전)이었다. 특히 acceptance 단계가 **돌고 있는 서버 밑에서 `DROP DATABASE law WITH (FORCE)`** 를 하므로 연결이 강제로 끊겨 차단기가 열리고(10초→최대 120초) 뒤 요청이 503 으로 샐 수 있다고 의심했지만, 같은 서버 프로세스로 재생성된 DB 에 대해 acceptance 26/26 이 통과해 **차단기는 CI 를 깨지 않는다**.
- 보류 아이디어: ① `harness.mjs:342 psqlAll` 이 `spawnSync` 의 `r.error`/`r.status` 를 보지 않아 psql 이 없거나 못 붙으면 문자열 `"nullnull"` 을 돌려준다 — 단언이 전부 존재 검사(`/ERROR/`·`left_over:[]`·개수 3)라 **빈 통과는 아니고 실패 쪽으로 안전**하지만, 실패 사유가 `undefinedundefined` 로 떠서 진단을 가린다. `adminSql` 처럼 던지게(3/1/S, scripts 1파일) ② dev 파생 키의 purpose 분리를 실제로 적용 — `env.ts:212` 루프가 시드 0..31 만 읽어 session/secrets/match 세 키가 바이트까지 동일(3/2/S) ③ `v.oneOf`·`bool`·`json` 경계 테스트 — PR #6 이 미머지로 닫혔으므로 `validate-boundaries.test.ts` 가 main 에 없다, 파일명 충돌 걱정 없이 한 파일로(3/1/S) ④ `Background.run` 실패에 requestId 를 실어 추적 — PR #4 도 미머지라 `pipeline.ts` 의 `redactSecrets` 호출은 여전히 2곳(`:177`·`:519`)뿐이니 그 수정과 함께(3/2/M) ⑤ AT-26 양성 대조를 이 acceptance 실행의 메일로 좁히기 — `check.yml:66` 이 `server.log` 를 서버 기동부터 누적하고 e2e 가 먼저 메일을 보내므로 acceptance 가 한 통도 안 보내도 통과한다(3/3/S)
