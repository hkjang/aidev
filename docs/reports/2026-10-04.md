### [weekly](https://hkjang.github.io/aidev/projects/weekly/)

- 선택: 주소 제한으로 차단된 로그인에 실제 남은 차단 시간을 알려 준다 (가치 3 / 위험 1 / 작업량 S)
- 결과: 성공
- 요약: `loginThrottleFor`(loginthrottle.go:62)는 두 계수기(계정·주소)로 차단을 판정하면서 남은 시간은 `min(created_at) FILTER (WHERE lower(username)=lower($1))` 하나로만 계산했습니다 — 계정 기준입니다. `auth.max_login_attempts_per_ip` 가 켜진 망에서 남의 오타로 주소 계수기가 찬 뒤 들어온 사용자는 **자기 실패 기록이 없으므로 그 min 이 NULL** 이고, `if result.Blocked && oldest != nil` 이 건너뛰어 `RetryAfter` 가 0 으로 남습니다. 그러면 `writeLoginBlocked` 가 `Retry-After: 1` 과 "1분 후에 다시 시도하세요" 를 내보내는데, 주소 차단은 `auth.lockout_minutes`(기본 15분) 동안 유지되므로 **안내를 그대로 따른 사용자는 15분 내내 1분마다 같은 거부를 다시 만납니다** — 올바른 비밀번호로도요. 같은 뿌리에서 감사 기록도 틀렸습니다: `auth.login_blocked` 의 `detail` 이 계정 횟수만 담아 주소 차단은 언제나 `failures: 0` 으로 남고, 운영자는 트레일만 보고 어느 제한이 거부했는지 알 수 없었습니다. 고침은 두 계수기의 `min(created_at)` 을 각각 읽어(`accountOldest`·`addressOldest`) **실제로 차단한 쪽** 의 남은 시간을 쓰고, 둘 다 걸렸으면 늦게 풀리는 쪽을 따르는 것입니다(짧은 쪽을 말하면 같은 벽으로 되돌려 보냅니다). 남은 시간 계산은 `windowRemaining` 한 함수로 모았고, 계정 단독 차단의 동작은 이전과 같습니다. `loginThrottle` 에 `AddressFailures` 를 더해 감사 `detail` 에 `addressFailures` 를 함께 남깁니다(값은 횟수뿐 — 주소나 원문은 넘기지 않습니다). 프로덕션 파일 2개(loginthrottle.go·auth.go) + 시험 1 + 문서 1. 시험은 손으로 만든 대역 없이 프로덕션 `app.Handler()` 와 실제 PostgreSQL 로 `/api/v1/auth/login` 을 두드려, 서로 다른 세 계정으로 실패를 쌓아 주소 계수기만 차게 하고(계정 계수기는 각 1회로 기본 10 에 한참 못 미침) 실패 기록이 없는 계정의 **올바른 비밀번호** 가 429 를 받는 경로를 그대로 지납니다. 검증: `gofmt -l internal/app`(빈 출력)·`go build ./...`·`go vet ./...`, 실제 DB(`weekly-test-pg`, pgvector/pgvector:pg16, 15434 — 이번 회차에 `docker start` 로 올림)로 `go test ./... -count=1` 전체 통과(`ok github.com/hkjang/weekly/internal/app 159.649s`, `EXIT=0`), openapi-check(경로 119개)·paging-check(목록 10곳)·`guard-check.py --changed af45b2c`(14개 도달, 새 시험 2개 `loginThrottleFor` 78%·78%) 통과, `git diff --check` 통과. 고친 뒤 주소 쪽 `RetryAfter` 대입만 되돌려 **같은 실패가 다시 나는 것까지 확인**하고 원복했습니다. 프런트 파일을 한 줄도 바꾸지 않아 `npm` 검증은 돌리지 않았고, OPERATIONS.md 는 렌더 HTML 이 없어 `render-docs.py` 도 돌리지 않았습니다. 커밋 2개(a676c18 수정+시험, f6c96e6 운영 문서) 뒤 트리는 깨끗하고 빌드 산출물은 없습니다.
