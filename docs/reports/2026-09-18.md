(2) 리소스 식별자는 `mcp.oauth.resource` → 기존 `general.base_url` + `/mcp` → 요청 Host(마지막 수단) 순서이며, 채울 때는 `/mcp`로 끝나는 http(s) URL만 받는다. (4) 계정은 웹 로그인과 같은 조회(issuer+subject 바인딩, 또는 아직 바인딩 안 된 `source='oidc'` 계정을 `preferred_username`으로)로 활성 계정만 찾고 아무것도 쓰지 않는다 — 로컬 계정은 이름이 같아도 열리지 않고 토큰의 role/groups는 무시된다. (5) 범위는 `mcp.oauth.scopes`(기본 `read mcp`)를 키 정책 `security.api_key_allowed_scopes`로 자르고, 토큰 `scope`에 read/write/mcp가 실려 오면 교집합만 준다. 캠페인 규칙대로 기존 `/mcp` 핸들러의 `writeAllowed`가 `len(scopes)==0`을 무제한으로 읽는 것을 소스에서 확인했고, 그래서 교집합에 `mcp`가 없으면 빈 슬라이스를 넘기지 않고 403 `insufficient_scope`로 명시적으로 거부한다. (3) 계정 매핑은 웹 로그인과 같은 `digest(issuer|sub)` 만 — Hunter 에는 `oidc.username_claim` 이 없고 웹 로그인도 username 으로 병합하지 않으므로 username 대체 조회는 두지 않았다(로컬 bootstrap 계정이 Keycloak 사용자명으로 열리는 일이 없게). 구현(`internal/app/mcp_oauth.go`): `/.well-known/oauth-protected-resource(/mcp)` 맨 JSON·CORS `*`·꺼지면 404, `/mcp` 401 에 `WWW-Authenticate: Bearer realm="hunter", resource_metadata="…"`(거부 시 `error="invalid_token"`, MCP 경로에서만), `authenticate` 가 같은 Bearer 헤더에서 `hnt_` 접두사 → 키, JWT 모양 → OAuth(요청 컨텍스트의 MCP 표시가 없으면 거부, 즉 REST·GraphQL·관리 API 는 지금처럼 키·세션만), 나머지 → 기존 "로그인이 필요합니다". 검사는 헤더 `typ=ID`·비대칭 알고리즘(RS/ES/PS)을 JWKS 요청 전에 먼저, 그 다음 go-oidc(`SkipClientIDCheck`)로 서명·iss·exp·nbf, 손으로 `cnf`·`sub`·대상(`aud` 에 리소스 식별자, 또는 `aud`/`azp` 가 `mcp.oauth.audience` 또는 웹 client_id) — 거부 메시지에 본 aud/azp 와 적을 값을 넣는다. provider 는 issuer+신뢰 CA 해시로 캐시(`context.WithoutCancel`, Hunter 의 신뢰 CA 클라이언트 재사용)하고 JWKS 재요청은 초당 1회로 묶었다(postra). 범위는 역할 ∩ `mcp.oauth.scopes`(기본 읽기 3개)이고 **교집합이 비면 명시적 거부**. 캠페인 규칙 점검: `KeyID != ""` 를 키/세션 판정에 쓰는 지연 재인가 지점 6곳(agentPrincipal·scheduleOwner·finding_bulk·modelPrincipalCurrent·workflowPrincipal·agents_control)을 모두 나열했는데 어느 것도 MCP 도구 표면에서 닿지 않고(도구가 남기는 scan 행의 credential_key_id 를 다시 읽어 권한을 만드는 소비자 없음), 그래도 `User.Auth="oauth"` 를 두어 감사 기록 `mcp.<도구>` 에 `auth: sso` 로 표시하고 주석에 빈 KeyID 센티널 주의를 적었다;
