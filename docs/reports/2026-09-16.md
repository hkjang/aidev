## 무엇을 왜 바꿨나 (원장 발췌)

### [ReSSO](https://hkjang.github.io/aidev/projects/ReSSO/)

- 선택: Silent SSO 캠페인(silent-sso-2026-09) 제공자 쪽 — RP의 `prompt=none` 루프를 이 서비스에서 볼 수 있게 답변별 카운터와 거절 로그를 두고, RP 구현 규칙과 `auto_login`이 어디 있는지를 문서에 적기 (가치 3 / 위험 1 / 작업량 S)
- 결과: 성공 (커밋 f292349)
- 요약: 09-13 회차의 판단은 그대로다 — ReSSO는 이 캠페인의 **제공자 쪽**이고 상류 issuer·콜백·discovery 조회 같은 RP 코드가 한 줄도 없어(이번에도 `git log`와 grep으로 확인, 그 뒤 세 커밋은 메일·비밀번호 재확인·팔레트) 표준의 `auto_login`·`sessionStorage` 표시·`/login?sso=none`은 여기 둘 곳이 없고, 캠페인 규칙에 따라 identity brokering을 새로 만들지 않았다. 다만 "이 저장소에 OIDC가 없다"는 문장은 ReSSO에 글자 그대로는 맞지 않는다 — ReSSO는 캠페인의 RP 스무 개가 `prompt=none`을 **보내는 상대**이고, 표준이 "이 일의 전부"라고 부르는 무한 루프는 RP 하나가 고장 나면 **제공자에서만 한눈에 보인다**. 그런데 지금까지는 어디에도 보이지 않았다: `prompt=none`의 두 답(코드·`login_required`)이 모두 302라 `resso_http_requests_total`에는 정상 Redirect로, 접근 로그에는 `status=302`로만 남아, 브라우저가 두 호스트 사이를 Redirect 속도로 오가는 루프가 이 서비스가 publish하는 모든 신호에서 바쁘게 잘 도는 Endpoint와 같았다. 그래서 같은 모양의 계열 셋(`resso_token_errors_total`·`resso_introspection_errors_total`·`resso_authorization_errors_total`)이 있는 방식 그대로 `resso_silent_authentications_total{result="code"|"login_required"}`를 더했다(고정 카디널리티 둘, 코드 발급은 `prompt=none`일 때만 센다). 계열에 client 라벨을 두지 않는 대신 거절 한 건에 로그 한 줄(`a silent authentication found no session to reuse`, `client_id`·`remote_ip`·`trace_id`)을 남겨 어느 RP인지 찾게 했다 — 루프는 한 `remote_ip`에서 같은 `client_id`가 초당 여러 번인 모양이다. 세션을 **읽지 못한** 요청은 여전히 `server_error`로 답하고 이 계열이 아니라 `resso_authorization_errors_total{stage="sso_session"}`에 센다 — 거절이 아니고, RP는 `login_required`를 "로그아웃했다"로 읽기 때문이다(표준의 "실패가 아니라 평범한 답"이 성립하려면 진짜 실패는 다른 답이어야 한다). 문서: `docs/compatibility.md`에 «RP가 silent ### [hunter](https://hkjang.github.io/aidev/projects/hunter/)

- 선택: 사내 SMTP 릴레이 메일 알림 (MAIL-STANDARD) — `mail.*` 설정·사람이 기다리는 이벤트 5개·배경 발송·시도 기록·시험 발송·가이드 (가치 5 / 위험 2 / 작업량 M)
- 결과: 성공
- 요약: Hunter 에는 이미 채널·규칙·큐로 된 알림센터(v1.6~1.7)가 있으나 그 큐는 `notification_channels` 표에 JOIN 으로 묶여 있어 설정 기반 가상 채널을 끼우면 검증된 엔진을 여러 곳 건드려야 했다. 그래서 표준 모양 그대로의 작은 `mail` 모듈(`internal/app/mail.go`, `mail_events.go`)을 따로 두고 어려운 부분인 SMTP 전송 함수만 재사용했다(전송에 `auto`=서버가 STARTTLS 를 알리면 암호화, `skip_tls_verify` 추가; 채널 검증은 둘 다 여전히 거절). 설정 그룹 `mail` 은 표준 표의 키 그대로(`enabled` 기본 **꺼짐**, `smtp_port` 25, `security` auto, 인증 선택, `base_url` 비우면 general.public_url, `notify_<이벤트>` true) 이고 비밀번호는 secretFields 로 암호화·`password_configured` 만 반환·감사에 `[REDACTED]`. **고른 이벤트와 이유**: 기준은 "안 오면 손해 보거나 새로고침한다" — (1) `approval_requested` 진단이 검토 대기가 되면 관리자와 해당 팀 팀장에게(요청자 제외; 검토·승인이 켜졌을 때 승인자는 화면을 새로고침하며 기다림), (2) `approval_decided` 승인·반려 결과를 요청자에게(검토자 본인 제외), (3) `scan_failed` 실패·미확정으로 끝난 진단을 요청자에게(에이전트가 만든 진단은 제외해 한 실행이 여러 통이 되지 않게), (4) `agent_waiting` 에이전트가 추가 입력을 기다리며 멈추면 요청자에게(내 차례가 됨), (5) `agent_failed` 에이전트 실행이 실패·미확정으로 멈추면 요청자에게(사용자가 중지한 경우 제외). 발견 건 생성·갱신 같은 "바뀜"은 넣지 않았고 SLA 만료 임박은 알림센터 captureNotificationDue 와 겹쳐 보류. 표준의 다섯 규칙: 이벤트 사이트(insertPreparedScan·approveScan·finishScan·suspendAgent·finishAgent)가 **같은 트랜잭션**에 `mail_deliveries` outbox 행을 남기고 제어 서버의 루프가 보내므로 릴레이가 죽어도 요청은 정상으로 끝난다(워커 전용 프로세스는 행만 남김, 연결 실패는 30초 뒤 1회 재시도 후 실패 기록); 시도마다 시각·이벤트·수신자·제목·상태·횟수·결과를 남기되 본문은 전송 중만 암호화 보관하고 끝나면 지움(90일 보존); 주소는 계정 id → 자동화 관리의 검증된 연락처 메일, 없으면 메일 형식 사용자 이름만 빌려 씀(명부 없음); 자기 행동은 자기에게 안 가고 같은 사람·같은 이벤트 10초 묶음(캠페인 N건 → 한 통, 행마다 "N건 묶음" 기록). 화면: 서비스 설정 새 탭 **메일 알림**(필드·비밀번호 저장됨 배지·삭제·이벤트 스위치) + **시험 발송**(저장된 설정으로 실제 한 통, 결과 즉시 표시, 기록에 남음) + 발송 기록 표.
