### [nexabuilder](https://hkjang.github.io/aidev/projects/nexabuilder/)

- 선택: 수정 과제 — PR #39 의 CI 실패를 증거로 코드 원인에서 배제하고(워크플로 미변경), 그리드가 보내는 알 수 없는 파라미터·죽은 컬럼이 SQL 식별자가 되어 어댑터 URL 이 죽는 실재 결함을 고친다 (가치 4 / 위험 2 / 작업량 S)
- 결과: 성공
- 요약: **CI 판정(코드 아님, 4회차 연속 같은 결론).** `ci-297a248d3235.json` 을 직접 파싱해 재확인했다 — `test + bootJar` 는 `started_at 2026-09-29T15:54:23Z` → `completed_at 15:54:30Z`, **7초** 만에 failure 이고 같은 워크플로의 `analyze (java)` 는 `skipped` 다. 같은 저장소 성공 22건은 470~611초, 앞선 두 실패는 39초·4초였다 — 7초는 `actions/checkout` + Gradle 해석이 끝날 수 없는 시간이라 자바 코드 변경이 죽일 수 있는 구간이 아니다. 더 결정적으로 `git log -1 -- .github/workflows/ build.gradle.kts settings.gradle.kts gradle/` 의 최신이 **2026-09-28 의 버전 범프 `c446d24`** 이고(그 뒤 빌드·CI 설정을 건드린 커밋이 없다), 그 위의 `ee7f786`(같은 `ListExportController` 를 고친 PR #36)은 CI 를 통과해 머지됐다. `git diff --stat master... -- .github/ build.gradle.kts settings.gradle.kts gradle/` 는 이번 브랜치에서도 **빈 출력**이다. 즉 고칠 코드가 없다. CI 로그 본문은 이번에도 **미확인** — `gh auth status` 가 "not logged into any GitHub hosts" 이고 저장소가 비공개다. **워크플로 파일은 한 줄도 바꾸지 않았고 재시도·`continue-on-error` 도 넣지 않았다.** 로컬에서 CI 와 같은 두 명령을 실행해 통과를 확인했다: `sh ./gradlew --no-daemon clean test` → BUILD SUCCESSFUL in 6m, **613건 / 실패0 / 오류0 / skip0**, `sh ./gradlew --no-daemon bootJar -x test` → BUILD SUCCESSFUL in 6s. 그 자리를 채운 실재 결함: `parse:296-304` 가 예약어가 아닌 모든 쿼리 파라미터를 컬럼 필터로 승격시키고 `executeEntityBacked:176-202` 가 그것과 `sortdatafield` 를 `sanitize()` 만 거쳐 `WHERE`/`ORDER BY` 에 문자열로 끼워 넣어, 존재하지 않는 컬럼(`groupscount` 같은 프로토콜 키, `columnsJson` 에 남은 죽은 컬럼)이 `^[a-zA-Z_][a-zA-Z0-9_]*$` 를 통과해 그대로 SQL 식별자가 됐다. `entityDataFields:116-140` 이 이미 쓰던 `SELECT * FROM <t> WHERE 1=0` + `PreparedStatement.getMetaData()` 프로브를 `probeColumns` 헬퍼로 뽑아 재사용하고, 필터·정렬 필드가 그 테이블의 실재 컬럼이 아니면 버린다(비교는 양쪽 `toLowerCase(Locale.ROOT)`). 프로브는 검사할 대상이 있을 때만 돌리고, 프로브가 실패하거나 컬럼을 하나도 못 읽으면 `null` 을 돌려 **기존 동작 그대로** 통과시킨다. `sanitize()`·`RESERVED_PARAMS`·`executeSqlBacked` 는 건드리지 않았다. 프로덕션 파일 1개, 테스트 파일 1개(신규). 커밋 a36eecc.
- 실패 재현: `DataAdapterUnknownColumnIntegrationTest > unknownQueryParameterIsIgnoredInsteadOfFilteringOnIt() FAILED` / `java.lang.AssertionError: Status expected:<200> but was:<500>` — 근본 원인 `BadSqlGrammarException: PreparedStatementCallback; bad SQL grammar [SELECT COUNT(*) FROM t_aucol_8bc80b16 WHERE groupscount = ?]` / `Column "GROUPSCOUNT" not found`. 같은 실행의 `deadSortColumnIsIgnoredInsteadOfReachingOrderBy() FAILED` / 같은 문구, 근본 원인 `bad SQL grammar [SELECT * FROM t_aucol_fbd6b798 ORDER BY dead_col ASC LIMIT ? OFFSET ?]` / `Column "DEAD_COL" not found`. 4건 중 이 2건만 빨갰고 회귀 가드 2건(`existingColumnFilterStillNarrowsTheRows`, `existingColumnSortStillOrdersTheRows`)은 **수정 전에도 초록**이라 "실재하지 않는 컬럼 경로만 깨져 있었다" 가 실행으로 확인됐다. 과제서가 예상한 상태 코드는 400 이었으나 실제는 **500** 이다 — `BadSqlGrammarException` 은 `GlobalExceptionHandler` 의 400 분기에 걸리지 않는다. 결함의 성격(jqxgrid 가 못 읽는 실패 봉투)은 같고 오히려 더 나쁘다.
- 보류 아이디어: CI 실패 로그를 러너가 `gh run view --log-failed` 로 저장해 주지 않으면 이 조사는 4회차째 시간 집계에서 멈춘다 — 러너 쪽 과제(4/1/S) / PR #37·#38·#39 가 전부 `ListExportController` 를 바꾼 채 막혀 있어 사람이 순서를 정리해야 한다, 네 번째 재제출 금지(3/1/S) / README·agent.md·deployment.md 의 낡은 JDK17/Boot3.4.4 표기를 Java21/Boot4.1.1 로 정렬 — 이번 차선 후보였으나 주과제로 회차가 찼다(2/1/S) / 테스트 JVM 종료가 컨텍스트마다 `taskScheduler` 종료 대기로 ~20초씩 지연(이번 `clean test` 로그에도 `Timed out while waiting for executor 'taskScheduler' to terminate` 가 컨텍스트마다 그대로, 3/2/M) / 런타임 차트·피벗의 fetch 실패를 `Nexa.toast` 로 알리기(3/2/M)
- 과제서: 채택 — 지정한 파일 1개·`probeColumns` 헬퍼 재사용·"검사 대상이 있을 때만 프로브"·"프로브 실패 시 기존 동작"·`sanitize()`/`RESERVED_PARAMS`/`executeSqlBacked` 불간섭·`@DirtiesContext` 금지·워크플로 불간섭을 그대로 따랐다. 두 곳만 어긋났다: (1) 실패 상태 코드는 과제서의 400 이 아니라 **500** 이었다, (2) 과제서가 지정한 `DataAdapterIntegrationTest` 에는 `seed()` 픽스처가 없어(시드 USER 엔티티만 쓴다) 엔티티+목록을 시드하는 `DataAdapterListSoftDeleteIntegrationTest` 의 픽스처 형태를 따라 신규 파일 `DataAdapterUnknownColumnIntegrationTest` 로 4건을 넣었다.
